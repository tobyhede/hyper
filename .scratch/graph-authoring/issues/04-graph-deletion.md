# 04 — Graph deletion through both context adapters

Status: resolved
Blocked by: 03

**What to build:** Add `map(mapId).graph(graphId).delete`, an asynchronous capability answering the surviving `{ kind: 'completed', mapId, graphId }`. The last Graph of a Map is unavailable at read and at invocation (ADR 0079); every Space Resource that selects the deleted Graph is repointed in the same Edit (ADR 0076). Survivor preference mirrors `.scratch/command-outcomes/issues/08`: the Active Graph the context shows when it is not the one going, otherwise the Map's `activeGraph ?? graphs[0]` among the survivors. `graph-delete` becomes a reported channel. See `../spec.md`.

**Why:** Deletion carries the largest locality gain — today the Dock passes `preferredGraphId: null` and the rail the Map's `activeGraph`, so the two contexts disagree on where the author lands.

- [x] Both surfaces spend delete through `offered`; the rail's `deleteDisabled` and the Dock's `editsDisabled` for delete are replaced by the capability's `available`.
- [x] The embedded adapter refuses while the containing Space is unsettled; the top level relies on the lifecycle's own recovery refusal.
- [x] Contract tests hold the survivor rule against both contexts, including an author moving the Active Graph while the deletion runs.
- [x] The Dock's `navigation.activateGraph` follow-up is removed if removing it fails no test; if something fails, the ticket records what.
- [x] `pnpm verify`, `pnpm e2e` and `pnpm e2e:ladle` green.

## Comments

**2026-09-26, resolved.** `pnpm verify` green (254 files, 3538 passed, 19 skipped). `pnpm e2e` green (233 passed) and `pnpm e2e:ladle` green (127 passed).

- **The capability.** `graph-authoring-commands.ts` adds `map(mapId).graph(graphId).delete: GraphDelete = Capability<() => Promise<EditOutcome<CompletedGraphEdit>>>`, answering the survivor's `{ mapId, graphId }` as the lifecycle returns it. `GraphAuthoringAvailability` gains `delete`; the Dock answers it with `entityEdits`, the rail with its one `available`. Availability is `available.delete() && addressesGraph && the Map owns more than one Graph`, asked at read and at invocation, and embedded again after `coordination.settled()` — the same prologue as `createGraph` and `deleteMap`. The lifecycle (`spaceResources.deleteGraph`) repoints every Space Resource selecting the Graph in the one Edit; `AuthoredSpace.spaceResources` is now `Pick<SpaceResourceAuthoring, 'deleteMap' | 'deleteGraph'>`. Reports: "Graph not deleted" for an unsettled Space (embedded) and for a lifecycle refusal (`describeSpaceResourceRefusal`); a throw is a break.
- **Survivor rule.** `preferredSurvivor` passes the lifecycle the Active Graph the context's own canvas shows (`context.space.app.navigation`, the target's for embedded, as `deleteMap` reads it) when that canvas is on the Map and not on the Graph going; otherwise the Map's stored `activeGraph` when it survives; otherwise `null`, so the lifecycle takes the first survivor and makes it the Map's `activeGraph`. That keeps the answer, the repointed Resources, the Map's stored Active Graph and `reconcileNavigation`'s landing on one Graph. Both contexts now choose the same way; before, the Dock passed `null` and the rail the Map's `activeGraph`.
- **`navigation.activateGraph` follow-ups removed — nothing failed.** The Dock's follow-up after a completed delete is gone, and so is the rail's (it activated the survivor on the target's canvas when that canvas was on the Map). Reconciliation already moves a canvas whose Active Graph vanished to the Map's Active Graph, which the survivor rule makes the survivor, and a canvas the author moved mid-deletion is no longer yanked back — the contract's "leaves a canvas the author moved while the Graph was being deleted where the author put it" holds that against both contexts. The full `packages/app` and `packages/ui` suites passed with both removed.
- **Command outcomes.** `graph-delete` is a reported channel; its command result is `EditOutcome<CompletedGraphEdit>` through `reportedCommand`, with no Map claim (a Graph deletion never changes the Map). A throw now reaches the reporter and leaves the channel clear rather than saying the failure's message; `command-outcomes.test.ts`'s `graph-delete` block moved onto the reported shape.

The rail's `CanvasSpaceResourceGraphCommands.onDelete` is `(() => Promise<void>) | null` through `offered`, and `deleteDisabled` is deleted; the rail says no local sentence for a Graph deletion. `GraphMenuActions` takes a nullable `onDelete` and drops `deleteDisabled`, matching `MapMenuActions`.
