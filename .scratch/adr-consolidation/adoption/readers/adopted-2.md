## Answers

**Q1.** This is Auto-arrange (R6; ADR 0086): an explicit, author-invoked tool, not part of drawing. Only the positioned strategy runs while the canvas draws, and nothing computes placement at render (R2). It is to live in `graph`, re-siting the render-time `elkjs` lint ban (R6). It is one atomic, destructive Edit that rewrites an existing Map's positions; the result is authored like any other position (R6). A strategy's output only joins an Edit and never honours a drop point (R7; ADR 0086, 0013). It must never become a canvas, a selectable context or a Map (R6, R8); a render-path decision or incremental placement (R6); or a privileged strategy — a change that works for only one strategy means the seam has leaked (R3). Not built: delivery ticket `.scratch/auto-arrange/issues/01-auto-arrange-a-map.md` (not opened), with two open questions — whether the Edit records which strategy produced the positions, and whether it asks for confirmation given that undo doesn't exist. Undo is not built either, so the Edit is reversed only by another Edit (§6). `gridStrategy` is the only automatic strategy; it is pure and test-only (R3).

**Q2.** Decline. R4/R5 and A1 (ADR 0005, 0014, 0041, 0086): the strategy contract carries positions only; a strategy takes a `LayoutStrategyGraph` and returns the same shape with geometry filled in; there is no intermediate "arrangement" type. Why: every consumer wants positions, so a new type adds a translation step at a seam meant to stay thin; React Flow has no layout entity either (A1). "Arrangement" is prose, not a domain term (CONTEXT.md). A Map stores a Resource and its position and nothing else (R4). Cost accepted: the noun names nothing on screen (A1).

**Q3.** Listing must not give them a Map: listing, import completion, export and reference validation read stored state and never initialize (R18); a mapless Space is valid stored state (R15, A5). On first open the server-side boundary initializes it (R16, R18; ADR 0079/0080): before returning, the first complete working-state read persists one atomic Edit — an empty `Map 1`, its empty Active `Graph 1`, and `defaultMap`. The same boundary serves direct opening, Entering, rendering an Open Space Resource and making a link target working (R18). Initialization commits before the Space becomes working; a conflict reloads and accepts a competing initialization if one exists, otherwise the normal retry; any other failure stops the Space opening (R19). Existing Resources are not placed and no strategy seeds them, because nothing authored says where they go (R16, A9, ADR 0080); they stay in the Resources View (CONTEXT.md). Newness is never inferred from Resource count, and no creation marker is stored (R20, A7/A8). A Space with Maps but no default records its first Map and creates nothing (R17).

**Q4.** Add Map creates and selects an empty Map in one Edit, with no Resources and one empty Graph that is its Active Graph (R11; ADR 0079/0040/0041). None of the existing Resources appear; the author adds them, for example from the Resources View (R11). Add Map counts as an Edit through the canvas's Map, so it records the new Map as `defaultMap` and writes the resolved `activeGraph` (R10). (AGENTS.md says Add Map continues into the new Map's name field — an app detail I did not check elsewhere.) The last Map cannot be deleted, because a working Space must keep a durable default (R12): Delete Map is not offered while one Map remains, and the deletion planner answers unchanged when no survivor exists; there is no refusal code. Deleting the default Map moves `defaultMap` to the selected survivor, else the first ("treatment without an ADR"). Deleting a Map or Graph atomically relocates every Space Resource that selects it (R13, ADR 0091).

**Q5.** Add Graph appends an empty Graph and activates it in one Edit (R26). Graph order is authored; new Graphs append; manual reordering is not built (R25). Deleting the Active Graph makes the first survivor active (R27, ADR 0040/0041) — I take "first" as first in authored order, since R25 says survivors keep their order. Deleting the only Graph is refused by design: a Map owns a non-empty ordered collection of Graphs (R22); Delete Graph is not offered while the Map has one Graph and the planner answers unchanged; there is no refusal code (R27). Deleting a Graph relocates any Space Resource that selects it (R13). A second Map cannot reuse a Graph: each Graph belongs to exactly one Map and is authored only through it (R22; CONTEXT.md "Graph"); two Maps telling one narrative hold two Graphs that diverge independently (A10). Reason: with a shared Graph, removing a Resource from one Map would leave a dangling Edge or change every other Map. Graph ids are unique across the Space (`duplicate-graph-id`, R24, ADR 0108); Map-scoped ids were rejected (A11). Activation is navigation, not an Edit (R29).

**Q6.** This is Remove from Map (R34, R35). It changes, in one Edit: because the Resource is Open, it is Closed first in that same Edit, and Close gives back the room it held by reclaiming from the Resources currently clear of it (R35, R41, ADR 0084), so the Edit may move several Resources as one unit (R43); the Map's membership entry and position are removed (R31, R34), and Open Size, a property of the Map, goes with the entry (R32, CONTEXT.md "Map"); every incident Edge in all of that Map's Graphs is removed (R34). It leaves alone: the Resource itself in the Space; its entry, position, Open state and Edges in the second Map, since placement belongs to the Map (R32); the now possibly empty Graphs, which remain, empty being valid (R34, R30); and Resources that are not clear of the subject — removal itself never displaces; only Open, Close and Resize do (R35). Leaving the gap was declined because nothing could reclaim it later: Close is memoryless and the Resource is gone (R35). Deleting from the Space runs the same cascade in every Map (R36).

**Q7.** Growth is Open Size minus the fixed Closed Size, floored at zero per axis (R39). Each Resource moves on at most one axis, decided against S's collapsed rect: at or past the collapsed right edge it takes the width growth only; otherwise at or past the collapsed bottom edge it takes the height growth only; otherwise it does not move; touching counts as clear (R40; ADR 0084, 0093). A (right, 40 lower) is at or past the right edge, so it moves right by the width growth only; the 40-unit offset does not matter — this is the beside-but-lower jump ADR 0093 fixed, and independent per-axis thresholds are rejected (A15). B (directly below) moves down by the height growth only. C (below and right) is at or past the right edge, checked first, so it moves right by the width growth only, not down. D (overlaps the collapsed rect) is neither, so it does not move. Why not C both ways: one axis is enough to stay clear; checking `x` first keeps a Resource beside the subject from moving vertically; the constant collapsed rect makes Open and Close select the same set, so the round trip works (R40). Bands against the Open rect were rejected because the set would change between Edits (A16). Positions are recorded at the Open Edit itself, written into the Map once (R38, ADR 0084); not derived at render, no `move` draft (R38). Undo is not built (§6). Cost: a grid no longer scales uniformly, and a Resource below the subject but not clear on `x` moves down however far left it sits (R40, A15/A16).

**Q8.** Open and Close are memoryless; each reads the Map as it is now (R41, ADR 0084/0093; CONTEXT.md "Placement"). Close reclaims from every Resource currently clear of S, including R, which the author moved there while S was Open, so R is pulled back by the negation of the growth under the same one-axis rule against S's collapsed rect; if R is not clear of the collapsed rect, it stays. The contract calls this deliberate and lists the cost: "Close reclaims from Resources moved into the room" (A14). Do not remember which Resources S's Open pushed (R41, A14): per-open state goes stale, and identical Maps would behave differently depending on history. If S itself was dragged past the neighbours its Open displaced, Close reclaims from none (R41). Open then Close restores every position because growth is nonnegative (R42). A Resource dropped past the collapsed edge inside an Open S was never pushed; Close carries it inside S and a reopen skips it — stated, not clamped (R42).

**Q9.** No, activating a Graph is navigation, not an Edit (R29; ADR 0028/0041/0079; CONTEXT.md "Active Graph", "Authoring"); it touches no Resource or Graph and neither submits nor dirties. On the canvas, emphasis changes, not filtering: every owned Graph is still drawn, each as a coloured line, with the Active Graph emphasised (R29, AGENTS.md). New Edges go into the Active Graph, "the Graph an author's new Edges join" (CONTEXT.md). Nothing is persisted at the moment of switching; the activation becomes durable only when a later Edit in that Map records the Map's resolved `activeGraph` explicitly (R10, R29; CONTEXT.md), a cost the contract labels intended (A18). There is no second "selected Graph" (R29); activation is deliberate, never a side effect of drawing or reading (R29); the fallback to the first Graph when `activeGraph` is unnamed is a read, never a write (R28). In a Map drawn inside an Open Space Resource, an Edit keeps the stored `activeGraph` and does not change the target Space's `defaultMap` (R10, ADR 0116).

**Q10.** No, not as asked. A Map is the only selectable and addressable canvas context, at `/spaces/:spaceId/maps/:mapId` (R8, ADR 0079/0069). Computed, Algorithmic and Space Views no longer exist and there is no dormant compatibility; obsolete identities are invalid input and their URLs are not found (R8; Orientation). Keeping Computed Views dormant was rejected because it "keeps most of the removed complexity"; the cost accepted is that V1 loses the cross-Map flatten (A4). An automatic strategy at render was rejected because it is unauthored, unreachable, and its routed output cannot persist (A3). Automatic strategies are non-addressable capabilities and none draws the canvas (R3, ADR 0086). What the architecture offers instead: the Resources View, a collection of the Space's Resources absent from the selected Map, rendered as a popover on the Dock — not a URL or a canvas (CONTEXT.md); authoring a real Map and using Auto-arrange to produce a grid-like arrangement, a destructive Edit over an existing Map reusing the grid strategy, not built (R6); and (my inference) building the whole-Space glance as an ordinary authored Map, which has its own URL, via Add Map plus Add to Map. I found nothing documented offering a read-only whole-Space listing with its own URL.
