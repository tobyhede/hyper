## Answers

**Q1.** Auto-arrange is an explicit, author-invoked Edit over an existing Map (R6; ADR 0086). Nothing computes placement at render; only the positioned strategy runs while the canvas draws (R2). An automatic strategy returns only attached to an Edit (R7). It is to live in `graph`, re-siting the render-time `elkjs` lint ban in `eslint.config.js` (R6). It rewrites that Map's positions in one atomic Edit; the result is authored like any other position (R6; §6 "Undo is not built"). It must never become a canvas, selectable context, renderer decision, incremental placement, a way to honour a drop point (R6, R7), or something that creates a Map (R6). Reasons: a render-time arrangement is one nobody authored and nothing persists (R2, A3); routed geometry has nowhere to land because a Map stores only a Resource and its position (R4); three spikes that seeded an optimiser reshuffled existing Resources (R7, A12). Not built: delivery ticket `.scratch/auto-arrange/issues/01-auto-arrange-a-map.md` (not opened), with two open questions — whether the Edit records which strategy produced the positions, and whether it asks for confirmation while undo doesn't exist. `gridStrategy` is pure and test-only (R3); nothing says the command must use it, and a change that works for only one strategy means the seam has leaked (R3).

**Q2.** Reject it (R5, A1). A strategy takes a `LayoutStrategyGraph` and returns the same shape with geometry filled in (R5; ADR 0005, kept binding by ADR 0014). Reasons (A1): every consumer wants positions, so the type adds a translation step at a seam meant to stay thin; React Flow has no layout entity either; cost: "the noun names nothing on screen." "Arrangement" is prose, not a domain term (R5; CONTEXT.md). The contract carries positions only (R4), and the canvas reads the authored Map, not computed output (R2).

**Q3.** Listing must not give them a Map. Listing, import completion, export and reference validation read stored state and never initialize (R18; ADR 0079, 0080). A mapless stored Space is valid state (R15). When an author first opens one, one server-side boundary (also used by Entering, rendering an Open Space Resource and making a link target working, R18) persists one atomic Edit: an empty `Map 1`, its empty Active `Graph 1`, and `defaultMap` (R16). It commits before the Space becomes working; on conflict it reloads and accepts a competing initialization, and any other failure stops the Space opening (R19). Existing Resources are not placed and no strategy seeds them, because nothing authored says where they go (R16, A9); they stay in the Resources View, outside the Map. A Space with Maps but no default just records its first Map as `defaultMap` and creates nothing (R17). Newness is never inferred and no creation marker is stored (R20).

**Q4.** Add Map creates and selects an empty Map in one Edit: no Resources, owning one empty Graph that is its Active Graph (R11; ADR 0079, 0040, 0041). Existing Resources are not copied in; authors add them, for example from the Resources View (R11). Every canvas Edit records its Map as `defaultMap`, Add Map included, and writes the Map's resolved `activeGraph` explicitly (R10), so the new Map becomes `defaultMap`. The last Map cannot be deleted, because a working Space must keep a durable default (R12): Delete Map is not offered while one Map remains (`map-authoring-commands.ts`), and `planContextDeletion` answers unchanged when no survivor exists; there is no refusal code. Deleting the default Map moves `defaultMap` to the selected survivor, else the first (treatment without an ADR). Deleting a Map also relocates every Space Resource that selects it (R13; ADR 0091).

**Q5.** Add Graph appends an empty Graph and activates it, in one Edit (R26). Order is authored: creating appends, deleting keeps survivors' order (R25). Deleting the Active Graph activates the first survivor (R27). Deleting the only Graph cannot happen: a Map owns a non-empty ordered collection of Graphs, and the last cannot be deleted (R22, R27); Delete Graph is not offered at one Graph and `planContextDeletion` answers unchanged, with no refusal code. Deleting a Graph relocates every Space Resource selecting it (R13). A second Map cannot reuse a Graph: each Graph belongs to exactly one Map and is authored only through it; Graphs are never shared or filtered from a Space-level collection (R22; ADR 0040, 0041). Reason: a shared Graph would leave a dangling Edge or change every other Map when a Resource is removed from one Map (A10). Two Maps telling one narrative hold two Graphs that diverge independently. Graph ids are unique across the Space (R24; ADR 0108).

**Q6.** In one Edit (R34, R35): the Resource is Closed first in the same Edit, and Close reclaims the room it held from every Resource currently clear of it (R35, R41); then its membership and position are removed from that Map (R31, R34); and every incident Edge is removed from that Map's Graphs, so both Graphs lose them (R34). Left alone: the Resource stays in the Space (R34); its placement in the second Map is untouched, because placement belongs to the Map (R32, R34); emptied Graphs remain (R34); other Resources are not otherwise displaced, because removal itself never displaces and only Open, Close and Resize do (R35). Why Close first: leaving the gap was declined because nothing could reclaim it later (R35). Other Maps are unaffected because Edges are Map-owned (R22, R23). Not covered: whether the remembered Open Size is kept after removal; by R31 a Map stores only Resource and position, so presumably it goes with the entry (my inference).

**Q7.** Each Resource moves on at most one axis, decided against S's collapsed rect (R40; ADR 0093): at or past S's collapsed right edge it takes the width growth only (moves right); otherwise at or past the collapsed bottom edge it takes the height growth only (moves down); otherwise it does not move. Growth is Open Size minus the fixed Closed Size, floored at zero per axis (R39). A (right, top 40 lower) moves right by the width growth only, not down — that was the old beside-but-lower jump (A15). B (directly below) moves down by the height growth only. C (below and right) moves right by the width growth only, because `x` is checked first. D (overlaps the collapsed rect) is clear on neither axis and does not move. The new positions are written into the Map by the Open Edit itself, once, as one unit (R38, R43); nothing is derived at render. Why not move C both ways: one axis is enough to stay clear; `x` first keeps a beside Resource from moving vertically; the constant collapsed rect makes Open and Close select the same set (R40). Independent per-axis moves were rejected (A15, A16); cost: a grid no longer scales uniformly. Assumption: "to its right" means A's left edge is at or past S's collapsed right edge.

**Q8.** R moves back with the others. Close is memoryless: it reads the Map as it is now and reclaims from every Resource currently clear of S, including ones moved there while S was Open (R41; ADR 0084, 0093). R gets the same width or height shift as any other clear Resource. This is deliberate. Do not remember which Resources S's Open pushed (R41, A14): per-open state goes stale, and identical Maps would behave differently; the accepted cost is that Close reclaims from Resources moved into the room. Corner cases (R41, R42): Close reclaims from none if S was dragged past the neighbours its Open displaced; Open then Close restores every position because growth is nonnegative; a Resource dropped past the collapsed edge inside an Open subject was never pushed, so Close carries it inside the subject and a reopen skips it — stated, not clamped.

**Q9.** Not an Edit. Activating a Graph is navigation; it neither submits nor dirties, because it changes nothing authored (R29; ADR 0028; CONTEXT.md "Active Graph", "Authoring"). On the canvas, emphasis changes, not filtering: every owned Graph is still drawn and the Active Graph is emphasised (R29); there is no second "selected Graph". New Edges go into the Active Graph (CONTEXT.md). Nothing is persisted at the moment of switching. The activation becomes durable only when a later Edit in that Map records it, because every canvas Edit writes the Map's resolved `activeGraph` explicitly (R10, R29); the contract accepts this as an intended cost (A18). Do not activate as a side effect of drawing or reading (R29); reading never writes, and the fallback to the first Graph is a read, never a write (R28, R10). An Edit through a Map drawn inside an Open Space Resource keeps that Map's stored `activeGraph` and leaves the target Space's `defaultMap` unchanged (R10; ADR 0116).

**Q10.** Not as asked. A Map is the only canvas context, and the only selectable and addressable one (`/spaces/:spaceId/maps/:mapId`); there are no Computed or Space Views, no flatten across Maps, and no dormant compatibility — obsolete identities are invalid input and their URLs are not found (R8; ADR 0079, 0069). No strategy draws the canvas; automatic strategies are non-addressable capabilities (R3), and the grid is test-only. Why removed: keeping Computed Views dormant keeps most of the removed complexity (A4); a render-time arrangement is one nobody authored and nothing persists (A3, R2); the accepted cost is that V1 loses the cross-Map flatten (A4). What the architecture offers: authored Maps, with Resources not placed on any Map browsable in the Resources View (R16, A9); and Auto-arrange (planned, not built, R6), which would rewrite an existing Map's positions as an explicit Edit — that could produce a tidy grid Map, but it is authored and edit-driven, not an addressable computed view. The contract does not describe a read-only "glance at everything" view; I would raise that as a new decision rather than build it.
