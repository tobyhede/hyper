## Answers

**Q1. Automatic tidy-up command**
The computation is a layout strategy in `@project/graph`. An automatic strategy computes placement from Resources and Graphs alone; `gridStrategy` is the one that exists (AGENTS.md, ADR 0086; CONTEXT.md "Layout strategy"; rendering.md "strategy contract"). Applying it is an Edit over an existing authored Map: it rewrites the positions of the Resources in that Map and nothing else, and the caller (not the strategy) chooses which Resources are arranged (rendering.md; CONTEXT.md). It must never become a render path or a second kind of canvas — automatic strategies are non-addressable capabilities, none draws the canvas; only the positioned strategy reading an authored Map does (ADR 0086, ADR 0079, ADR 0014). It must never be the privileged/primary strategy, and "layout" must not be tied to one strategy in the domain (AGENTS.md, rendering.md); a graph-layout engine is "one member of the set, not what layout means". Its output must not be computed and written back as if it were the authored placement — rendering.md says of the fixture: "don't compute them and write the result back", because that overwrites authored placement with computed placement. And a layout engine must not be re-sited into `core`/`graph`/`persistence`/`ui` as a render-time engine: AGENTS.md says building Auto-arrange means "re-siting the ban rather than obeying the lint message" and puts it in `graph`, attached to an Edit. CONTEXT.md labels Auto-arrange "planned and not yet built". Reason: placement is authored, not computed.

**Q2. New result type for strategies**
Reject it as far as the docs state. The contract is `(graph: LayoutStrategyGraph) => Promise<LayoutStrategyGraph>` with geometry riding as optional `x`/`y` on the elements; positions are the whole output (rendering.md; editing-and-persistence.md citing ADR 0005 and ADR 0086). editing-and-persistence.md says explicitly: "There is no `Arrangement` type and geometry rides as optional fields on the elements (ADR 0005) — don't introduce one." CONTEXT.md repeats: applying a strategy produces no separate entity; the Resources themselves carry the positions. A separate coordinates value would also be a second thing in the position-to-canvas path, whereas the strategy output feeds an Edit that writes positions into the Map, not a separate canvas consumer (ADR 0086). `gridStrategy` being pure keeps the seam honest; if a change works for only one implementation, the contract has leaked. I found no ADR text directly ruling on a "new result value type"; the refusal is inferred from the ADR 0005/0086 statements above.

**Q3. Mapless stored Spaces**
Listing must not initialize them — ADR 0079: "listing, import completion, export and reference checks do not initialize" (editing-and-persistence.md); AGENTS.md: only a first working load initializes, "non-working reads do not initialize". When an author first opens one, the first complete working read atomically and durably persists an empty `Map 1`, its empty `Graph 1`, the Active Graph and `defaultMap`. Its existing Resources are not placed on the new Map — the Map is empty, because Map membership is authored (CONTEXT.md "Map"; AGENTS.md ADR 0079). The Resources stay in the Space, and the Resources View lists those absent from the selected Map so the author can place them (CONTEXT.md "Resources View"; rendering.md on Add Resource and Map membership). Related traps: a mapless ordinary Space cannot appear in a valid aggregate — only a mapless Meta Space is valid (AGENTS.md) — and a mapless ordinary Space can be referenced only by the very Edit that initializes it.

**Q4. Adding another Map**
One Edit creates a new empty Map with its one empty Active Graph and selects it; the Map and Graph ids are minted in that Edit (AGENTS.md ADR 0079; editing-and-persistence.md; CONTEXT.md "Graph": "creating a Map also creates its initial empty Active Graph in the same Edit"). No existing Resources appear on it — membership is explicit and authored; omission means "not in that Map", and the Resources View lists the ones not yet placed (rendering.md "Placement"). Afterwards the Dock's name-continuation focuses the new Map's name field (`'map-name'` continuation, AGENTS.md). The last Map cannot be deleted (ADR 0079, ADR 0040/41), which follows from the rule that a working Space always has at least one Map (CONTEXT.md "Map"). Do not add a "new Space-level canvas" or Space-wide view as a substitute.

**Q5. Managing a Map's Graphs**
The last Graph cannot be deleted through Graph management — a Map owns a non-empty ordered Graph collection (CONTEXT.md "Graph", "Map"; ADR 0041 text). Deletion preserves the relative order of survivors; new Graphs append (CONTEXT.md). Deleting the Active Graph: the Map may name which Graph opens active, failing which it is the first Graph, and a Map "always resolves one Active Graph" (ADR 0041); so after deleting the emphasised Graph, the fallback is the Map's first Graph (or its named one). I found no document stating precisely which Graph becomes active when the active one is deleted; the "always resolves one Active Graph" rule and the first-Graph fallback imply it, but I am inferring. A second Map cannot reuse a Graph: a Graph "belongs to exactly one Map and is authored only through that Map" (CONTEXT.md), and every Edge endpoint must be a Resource in that Map (ADR 0041; editing-and-persistence.md). A Map's `graphs` is ownership, not a filter, so there is no Space-level Graph collection; a Space-level `graphs` key is rejected at intake, and you must not declare the key to work around it (rendering.md). Also: do not clear or filter other Graphs on activation; do not give an author a way to draw no Graph — an empty Graph is valid but cannot be presented until it has an Edge. A new Graph gets a palette colour chosen to stand farthest from the Map's other Graphs, and the arrow head shape.

**Q6. Remove from Map**
Changes: removes the Resource's membership in that Map, its rect there, and its incident Map-local Edges (its Edges in both of that Map's Graphs). If it was Open, it gives back the room it held (CONTEXT.md "Placement/operations") — by ADR 0084, that room comes back via the Close-style negation of displacement, written into the Map in the same Edit. Undo reverses all of it together. Leaves alone: the Resource itself and its content; its membership, position, Open state and Open Size in the second Map, because those are properties of the Map, never of the Resource (CONTEXT.md "Map"); and the Graphs themselves, which remain (a Graph cannot be deleted by this). Remove from Map is not deletion of the Resource (the Space Resource entity menu lists it as a separate item). I could not find a doc spelling out the exact order of "give back room" versus Edge removal.

**Q7. Which neighbours an Open moves**
Rule (AGENTS.md ADR 0093/0084; CONTEXT.md): growth = `openSize - COLLAPSED_RESOURCE_SIZE`, floored at zero per axis. A Resource moves on one axis, decided against S's collapsed rect: at or past its right edge → width growth only; otherwise at or past its bottom edge → height growth only; otherwise it does not move.
- A: moves right by the width growth. The 40-unit-lower top is irrelevant; it is at or past S's collapsed right edge, so width only.
- B: moves down by the height growth (not at or past the right edge, at or past the bottom edge).
- C: moves right by the width growth only — the right-edge test is checked first, so it does not also move down.
- D: does not move — it overlaps the closed rect, so it is at or past neither edge.
The new positions are written into the Map by the Open Edit itself, once; nothing is derived at render time (ADR 0084; "a drawn position is an authored one"). Close applies the negation; Resize applies the difference. C moves on one axis because independent per-axis moves caused a defect: a Resource beside S whose top was a few units lower took the whole height growth on Close, and AGENTS.md says "do not restore independent per-axis moves" (ADR 0093). I did not read the ADR 0093 body; this reason comes from its summaries.

**Q8. Closing after the author moved things**
On Close, R moves back. Close is memoryless: it reads the Map as it is at that moment and reclaims from every Resource currently clear of the closing Resource, including ones the author moved there while it was open (AGENTS.md ADR 0084; CONTEXT.md "Placement/operations"). The docs say this is deliberate; they also note that if S itself has been dragged past the neighbours its Open displaced, Close reclaims from none at all. Do not accept the reviewer's suggestion — AGENTS.md: "do not answer it by recording which Resources a particular Open pushed". Open and Close remember nothing about how the Map got there. The round trip rests on growth being nonnegative, which the floor guarantees; `displace` is not an involution for negative growth, and that asymmetry is "stated and tested rather than clamped". One Edit may change several Resources, and undo reverses all of them.

**Q9. Switching the Graph being worked in**
Not an Edit: "Activating is not itself an edit — it touches no Resource and no Graph" (CONTEXT.md "Active Graph"). It is navigation state, comparable to Map selection, which "is navigation, not an Edit" (editing-and-persistence.md). Canvas: activation is emphasis, not filtering — the Map still draws every Graph it owns, with the newly active Graph emphasised (rendering.md "Multi-Graph overlay"; AGENTS.md); handles take the Active Graph's colour (ADR 0033, rendering.md). New Edges join the Active Graph (CONTEXT.md). An Edge outside the Active Graph cannot remain the Selected Edge (CONTEXT.md). Persistence: nothing at the moment of switching. The Active Graph "may become the authored selection when an Edit records the surrounding Map"; the comparable text for Map selection is "A later successful Edit may record the selection as `defaultMap`". It must be a deliberate act, never a side effect of drawing or reading. I could not find a doc stating the exact field name for a Map's persisted active Graph (AGENTS.md mentions `activeGraph ?? graphs[0]` only in the Space Resource `link` description). Do not model it as "a selection plus an emphasis" — one Active Graph in the current Map (rendering.md).

**Q10. Read-only grid view of a Space with its own URL**
Cannot build as asked. ADR 0079: an authored Map is the only selectable and addressable canvas context (AGENTS.md). Obsolete canvas identities are invalid input and their product URLs are "not found"; automatic strategies, grid included, are non-addressable capabilities, not canvas selections, so a grid view would also need a URL, which they cannot have (rendering.md; editing-and-persistence.md). This repeats ADR 0086: an automatic arrangement is an Edit over an authored Map, never a render path or a second kind of canvas (CONTEXT.md "Layout strategy"). What the architecture offers instead: create or select a Map and use Auto-arrange (planned, not yet built), an Edit rewriting that Map's positions; the Map then has a durable URL `/spaces/:spaceId/maps/:mapId` (ADR 0069/0079); the Resources View lists Resources absent from the selected Map, so a reader can see every Resource not yet placed — it is not a read-only whole-Space grid. Reason for removal: a Map-less view of a Space's Resources gave two ways to draw the canvas, and ADR 0079/0086 settled on authored Maps only. I did not read the deeper ADR 0079 text on why the Space-subject canvas was removed; I rely on its summaries.
