# Hono official agent/LLM resources and behaviour findings

Research date: **2026-08-01**. All probes and fetches done on that date unless noted.

Version scoped to: **`hono` 4.12.33** (`packages/http` declares `"hono": "^4.12.33"`; pnpm resolved `4.12.33`, matching `jsr.io/@hono/hono` latest). Behavioural claims below were checked against the installed source under `node_modules/.pnpm/hono@4.12.33/`, not only against prose — the docs lag the source in several of these areas.

Primary sources only: `hono.dev`, `github.com/honojs/*`, `npmjs.com`.

---

## 1. Verdict up front

**What exists (official):**

- **`/llms.txt`, `/llms-small.txt`, `/llms-full.txt` on `hono.dev`** — all HTTP 200 (5.5 KB / 196 KB / 364 KB). This family is the only agent-facing artefact the Hono org ships.
- Generated by a hand-rolled script, **not** a VitePress plugin: [`honojs/website/scripts/build-llm-docs.ts`](https://github.com/honojs/website/blob/main/scripts/build-llm-docs.ts), wired as `"prebuild": "node ./scripts/build-llm-docs.ts"` before `vitepress build`. So it regenerates from the docs on every site build — never vendor a copy.
- **`jsr.io/@hono/hono`** publishes auto-generated symbol-level API docs, currently 4.12.33. Useful only when an exact type signature is needed; `llms-full.txt` covers the prose.

**What does not exist (checked, negative results):**

- **No official Agent Skill.** The request — [`honojs/hono#4812`](https://github.com/honojs/hono/issues/4812), "Feature Request: Official AI Agent Skill for Hono" — is **open**, filed 2026-03-19. Hono's creator replied that a prototype exists at `yusukebe/hono-skill` and "will be ported soon"; it has not been. That repo is personal, unlicensed, and stale since 2026-03-23. `hono-skill` and `@hono/skill` are both **404 on npm** (verified).
- **No official docs MCP server.** `yusukebe/hono-docs-mcp` is a personal repo (created and last pushed the same day, 2026-03-23) and is not in the official MCP registry.
- **`@hono/mcp` is not this.** Its npm description is "MCP Middleware for Hono" — it is for *building* MCP servers with Hono, and documents nothing about Hono. Don't confuse the two.
- The most recent official signal points away from tooling entirely: in [`honojs/cli#77`](https://github.com/honojs/cli/issues/77) (2026-06-26) the maintainer proposes deleting the CLI's `docs` and `search` commands — "If you want an agent to read the docs, you can use the 'Web Fetch' function in the agent."
- No `AGENTS.md`, `SKILL.md`, `.claude/`, `.cursor/` or `copilot-instructions` anywhere in the `honojs` org, other than `honojs/cli/CLAUDE.md`, which is that repo's own contributor guide.

**Compared to React Flow:** the stories rhyme and end differently. xyflow built a skill, measured it as making results worse, and shelved it deliberately. Hono's creator built a skill *and* a docs MCP, promised to make them official, hasn't in four months, and has since argued the docs path should be removed in favour of WebFetch. Both land on the same rule — fetch `llms-full.txt`, install nothing — but Hono's is unsettled rather than decided, which is the part worth recording so it isn't re-litigated.

## 2. Take `llms-full.txt`, not `llms-small.txt`

The script's only difference is one exclusion list:

```ts
const tinyExclude = ['concepts', 'helpers', 'middleware']
```

The predicate is `filename.startsWith(exclude)`, which also catches `guides/middleware.md` and `guides/helpers.md` by basename. Measured on both files:

```text
hono-llms-full     H1s=98   bodyLimit=2   createMiddleware=29   'hono/factory'=13
hono-llms-small    H1s=46   bodyLimit=0   createMiddleware=6    'hono/factory'=5
```

`llms-small` contains **zero** occurrences of `bodyLimit` — the exact middleware `@project/http` depends on — and no middleware content of any kind, not even the conceptual guide on writing one. For this package it is disqualifying.

## 3. Behaviours that bit this repo

Each of these was found by review against the docs, then reproduced against the real app. All are fixed; the tests named below are the regressions.

### 3.1 `c.notFound()` inside `app.notFound()` recurses until the stack blows

`Context`'s `#notFoundHandler` is seeded from the app's (`hono-base.js:288`), so `context.notFound()` called from within the handler `app.notFound()` installed re-enters that same handler forever.

```js
// hono/dist/context.js:404
notFound = () => {
  this.#notFoundHandler ??= () => createResponseInstance();
  return this.#notFoundHandler(this);
};
```

Every path off the declared contract hit it — `/`, `/api`, `/index.html`, and `/api/spaces/` (the trailing slash a browser address bar produces). Latent only because nothing mounted the app outside its own tests; the first host to wire `app.fetch` as a catch-all would have crashed on every non-API request.

The RPC docs independently say not to use `c.notFound()` when a client infers types: *"the data that the client gets from the server cannot be inferred correctly."* Return an explicit response instead.

Regression: `space-http-app.test.ts`, "answers %s outside the declared contract without recursing".

### 3.2 Rethrowing from `onError` hands the host a rejected promise, not a 500

Hono does not convert a rethrow into a 500. `#handleError` re-invokes the custom handler and lets the throw escape, so `app.fetch()` **rejects**.

```js
// hono/dist/hono-base.js:271
#handleError(err, c) {
  if (err instanceof Error) { return this.errorHandler(err, c); }
  throw err;
}
```

A host without a `.catch` then has an unhandled rejection, which Node 24 answers by killing the process — and this repo already has a scar from exactly that (see the comment in `packages/app/vite-space-http-plugin.ts`). A portable module owes its host a Response on every path, so `onError` must terminate: 400 `HTTPException` keeps its message, any other `HTTPException` returns `getResponse()`, everything else logs and returns 500.

Two related facts: a thrown **non-`Error`** never reaches `onError` at all (both `compose.js:24` and `#handleError` gate on `err instanceof Error`), and an `onError` that *rethrows* is re-entered once per compose frame. Once it returns a Response instead, it is entered once — measured.

Regression: `space-http-app.test.ts`, "answers an unexpected failure with a response rather than a rejection".

### 3.3 Hono's json validator has its own, narrower Content-Type policy

```js
// hono/dist/validator/validator.js:5
var jsonRegex = /^application\/([a-z-\.]+\+)?json(;\s*[a-zA-Z0-9\-]+\=([^;]+))*$/i;
```

When it disagrees with the request's Content-Type it does **not** parse the body and hands the callback `{}` — silently. The docs confirm: *"the request body will not be parsed and you will receive an empty object (`{}`) as value in the callback."*

This module's media policy was more permissive in RFC 9110-legal ways, so those requests passed the 415 gate and then failed as a 400 about the fields of a body that was never read:

| Content-Type | Was | Should be |
|---|---|---|
| `application/json ; charset=utf-8` | 400 "commit request has unexpected fields" | 200 |
| `application/json; charset = utf-8` | 400 (same) | 200 |
| `application/json; x_1=2` | 400 (same) | 200 |
| `application/json; foo="a;b"` | 400 (same) | 200 |

Fixed by letting exactly one policy decide: the media guard rewrites the header it has just validated to canonical `application/json`. Any future divergence would otherwise land in the same silent `{}` hole.

Regression: `space-http-app.test.ts`, "commits a request whose media type carries %s".

### 3.4 `bodyLimit` erases its own status from the RPC contract

`bodyLimit` is declared as a bare `MiddlewareHandler`, whose response type parameter defaults to `Response`. Returning its result from a `createMiddleware` widened the union, and `ExtractTypedResponseOnly` then collapsed the 413 to `never` — while the hand-written 415 in the middleware beside it survived. A client could not compile the oversized-commit branch at all, so the union *under-reported* what the server returns.

Fixed by producing the oversize response in our own code rather than passing Hono's through.

Regression: `space-http-app-types.test.ts`, "declares every status the commit resource answers with".

### 3.5 A json validator's *input* type is its *output* type unless you say otherwise

`in.json` resolves to `unknown extends InputType ? ExtractValidatorOutput<VF> : InputType`. With `InputType` unsupplied it collapses to the callback's return type, so the decoded domain value became the request contract — here a `bigint` revision, which `JSON.stringify` throws on. The contract demanded a value no client could send. (`param` is unaffected: `in.param` stays `{ id: string }` while `out.param` is the branded `UUID`.)

The trap in fixing it: **TypeScript has no partial type argument inference**, so supplying only `InputType` makes every other parameter fall back to its *default* rather than being inferred — and `VF` defaulting to `=> any` drops the route from the schema entirely, silently. `$put` simply stopped existing on the client. The callback has to be named so `VF` can be supplied too.

Regression: `space-http-app-types.test.ts`, "asks the client for the revision in the form the wire carries".

### 3.6 `expectTypeOf` is a runtime no-op here

`vitest.config.ts` configures no `test.typecheck`, and the type test is not `*.test-d.ts`, so `pnpm test` reports it passing regardless of what it asserts. It is enforced only by the root `pnpm typecheck`, whose `include` covers `packages/*/test` — note `pnpm --filter @project/http typecheck` misses it too, since that config's `include` is `["src"]`. `pnpm verify` runs typecheck before tests, so the bar holds; just don't read a green `pnpm test` as evidence about types.

## 4. Confirmed correct — don't "fix" these

- **`c.header()` after `await next()` works by contract.** `Context#header` has an explicit `if (this.finalized)` branch that re-creates the Response so its headers are mutable. The docs' middleware examples prefer `c.res.headers.set()`; both work, and `c.header()` clones rather than mutating in place, so it is the more robust of the two.
- **HEAD interception in middleware is the documented idiom.** Hono auto-converts HEAD to GET in `#dispatch` *before* route matching, so `app.head()` would never fire — the docs say so outright: *"Don't: Try to Create Dedicated HEAD Handlers."* Checking before `next()` rather than after also skips the handler and its repository call.
- **Synthesising 405 in `notFound` is correct, and effectively the only way.** Hono has no built-in 405: a method mismatch on an existing path matches no handler and falls through to the not-found handler.
- **Reassigning `context.req.raw` is supported.** `raw` is a plain writable public field and `header()`/`json()` read it live; Hono's own `bodyLimit` does the identical reassignment. `new Request(existing, { headers })` preserves the body for both string- and stream-source requests, and the `duplex: 'half'` requirement does not fire because the stream rides on the input request rather than the init.
- **The hand-rolled media-parameter scanner is not redundant.** `content-type@2` is a rewrite whose `parse` has **no throw path at all** — `parse('garbage')` returns `{ type: 'garbage' }`, duplicate parameters are first-wins, and an unterminated quoted string is silently dropped. Against `content-type@1`, which threw on malformed parameters, the scanner would have been near-redundant; against v2 it is the only validation present. The `try/catch` that used to wrap `parse` was dead code and has been removed.
