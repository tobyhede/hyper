# 22 — Tracer: one SQL repository reads both databases

**What to build:** The one SQL Space repository exists and serves `listSpaces` and `loadSpace` for PostgreSQL and SQLite, typed without a new assertion, beside the two adapters it will replace. PostgreSQL stores revisions as canonical decimal TEXT, as SQLite already does.

**Blocked by:** 21 — Record the one SQL Space repository.

**Status:** resolved

**Why:** ADR 0095. This is the slice that proves the typing and the `SqlStore` value against both generated contracts before the lifecycle and commit move onto it. A typing experiment (2026-09-17, `tsc` 7.0.2, since deleted) compiled a structural `Tables<…>` slice of `loadSpace` and a guarded revision update against both contracts with no assertion, and caught a misspelled column, a wrong revision type and a missing include field for both databases. Generic typing over Prisma Next's `Collection<C, 'Space', …>` did not compile.

- [x] A `SqlStore` value per database with at most these members: `orm` (the handle for work outside a transaction), `tables(orm)`, `transaction`, `readDocument`, `isDuplicateKey(error, table)`, `serialise`, `close`. `listSpaces`, `loadSpace`, `loadMetaSpaceId`, `markExported` and the conflict re-read after a rollback run outside a transaction today — the re-read must, because the transaction has rolled back — so they take `tables(orm)` over that handle, inside `serialise`. They are not moved into `transaction`, which would add a `BEGIN`/`COMMIT` to every read and change SQLite's contention picture that ticket 18 measured. PostgreSQL's `serialise` runs the operation directly; SQLite's is the in-process queue now in `SqliteSpaceRepository.#serialise`.
- [x] One `serialise` queue per file handle, not per repository object: two repositories over one SQLite handle share it, proven by a test that overlaps their operations. ADR 0095 says the queue orders every repository operation in the process; today `#serialise` is a field of each `SqliteSpaceRepository`, so two over one `SqliteDatabase` (as the HTTP runtime and `test/support/sqlite-harness.ts` each build) do not share it. (Architecture review, 2026-09-18.)
- [x] The shared tables type is declared by the repository over the calls it makes. Property syntax only, no optional row fields, documents `unknown`. Both generated ORMs are assignable to it without a cast, and `eslint-suppressions.json` gains nothing. **Narrowed from the original design — see the Answer.**
- [x] `Order` is the one opaque type parameter each database module derives without assertion — the experiment found `unknown` is not assignable to `OrderByItem` and inference yields `Collection<Contract, never, …>`. **The relation's refined collection (called `Include` in the experiment) could not be kept opaque the same way and is not a type parameter at all in the shipped shape: it stays inside each database module, composed directly inside `loadWithThings`/`loadEvery` rather than crossing the `SqlStore`/`SqlTables` boundary — see the Answer.**
- [x] PostgreSQL's contract stores `revision` and `exported_revision` as TEXT. A planned migration under `migrations/app/` applies it (ADR 0054 keeps relational schema migrations); fixtures, seeds and integration helpers that write raw revisions roll forward in the same change.
- [x] One shared revision codec owns the canonical decimal format and the 2^63−1 ceiling for both databases, on read and on write. Today SQLite's `toDatabaseRevision` checks only the digit format, so a 19-digit value above the ceiling is written; `CONTEXT.md`'s Revision entry already states the ceiling as the rule. PostgreSQL's `toDatabaseRevision` relabel and its `eslint-suppressions.json` entry are deleted. `http-protocol.ts`'s ceiling message stops naming PostgreSQL.
- [x] The existing PostgreSQL adapter reads and writes revisions through that codec until ticket 24 deletes it.
- [x] PostgreSQL's aggregate read wraps the codec's refusal as `AggregateInvariantError`, as it already wraps a document that fails intake. Today its `loadEverySpace` catch narrows to the private `SnapshotValidationError` and rethrows everything else (`src/persistence/postgres-space-repository.ts`, the `catch` under "Every stored Space, parsed"), which is safe only while `document` is `jsonb` and `revision` is `int8` — neither column can hold a value the read step refuses. TEXT revisions end that: a stored revision that is not canonical is the same broken stored state a document that fails intake is, and unwrapped it reaches `src/http/space-host.ts`'s `isAggregateInvariant` as "not an invariant" and is answered 503 `persistence-unavailable`, try again later, for a defect no retry cures — the defect ticket 27 fixed for SQLite, on the database that had no `loadEverySpace` case for it. Admit the codec's error identity alongside `SnapshotValidationError`; do **not** widen the catch to an unconditional one, which would read a connection failure as broken stored state (ticket 27's "The classification default does not flip").
- [x] `repository-contract.ts` carries that case for both databases: an aggregate read of a Space whose stored revision is not canonical raises `AggregateInvariantError`. SQLite proves it today in `test/integration/sqlite-space-repository.test.ts` (`truncates a stored Space whose revision is not canonical`, ticket 27); PostgreSQL has no equivalent case and cannot have one until the column is TEXT, so this ticket is where it becomes reachable and has to be written.
- [x] The contract's existing read cases (`listSpaces`, `loadSpace`, Thing order) run against the one repository on both databases. **Via a new, narrower `sqlReadRepositoryContract` — see the Answer.**
- [x] Because this ticket introduces the codec, it also moves revisions above `Number.MAX_SAFE_INTEGER` into `repository-contract.ts` (today PostgreSQL 1257, SQLite 212 and 305), and adds a case that a revision above 2^63−1 is refused rather than stored.
- [x] `docs/agents/editing-and-persistence.md`'s Prisma Next `int8` workaround bullet is replaced by the TEXT revision rule.

Out of scope: moving the lifecycle (23) or commit (24); changing host composition (26).

## Answer

Built: `src/persistence/sql-store.ts` (`SqlStore<Handle, Order>`, `SqlTables<Order>`, the row shapes), `src/prisma/sql-store.ts` (`postgresSqlStore`), `src/sqlite/sql-store.ts` (`sqliteSqlStore`, a factory since SQLite's store is built per file handle), `src/sqlite/serialise.ts` (`serialiseSqlite`, the per-handle queue `SqliteSpaceRepository` now delegates to instead of owning its own), `src/persistence/sql-space-repository.ts` (`SqlSpaceRepository<Handle, Order>`, `listSpaces`/`loadSpace` only), `packages/persistence/src/revision-codec.ts` (`decodeStoredRevision`/`encodeStoredRevision`/`REVISION_CEILING`/`RevisionCodecError`, plus `CANONICAL_DECIMAL` moved in from `http-protocol.ts` to avoid a circular import), the migration `migrations/app/20260919T1037_revisions_are_text/`, and `test/support/sql-read-repository-contract.ts` (the new, narrower read contract).

**Where this ticket deviated from the checklist's own design, and why.** The checklist describes the shared repository composing `.select('id', 'document').orderBy((thing) => thing.id.asc())` itself, inside a generic `.include('things', build)` call, with the relation's refined collection type (`Include`) opaque and derived per database the same way `Order` is. That does not compile. Every way tried of keeping `Include` opaque across the `SqlStore`/`SqlTables` module boundary — one `asSqlTables`-style identity call solving for `Include` and `Order` together, the same call split in two, a conditional-type `infer` extraction against `Orm['Space']['include']`'s own generic signature, a method-scoped `include<Include>(...)` related directly against the ORM's generic method (TypeScript's own more permissive path for two generic signatures), both unconstrained and constrained to `object` — left `Include` inferred as `Collection<Contract, never, …>` (`ModelName` collapsing to `never`) or refused the covariant return check outright (`'Collection<…>' is not assignable to 'Include'`; `'Include' could be instantiated with an arbitrary type`). `Order` never had this problem — it is a flat, model-agnostic type (Prisma Next's own `OrderByItem`) with one occurrence per accessor, not a generic method's own inferred relation type.

The shipped shape: `SqlTables<Order>.Space` has `orderBy(...).all()` (checked structurally against both ORMs, exactly as the checklist asks) and `loadWithThings(id)`, a single already-composed method. Each database module's own `tables()` implements `loadWithThings` by writing `orm.Space.where({ id }).include('things', (things) => things.select('id', 'document').orderBy((thing) => thing.id.asc())).first()` directly — ordinary forward-typed code, the same shape both existing adapters' `loadStoredSpace` already ran, which compiles today exactly as it always has. Only the *result* — `SqlLoadedSpaceRow`, a concrete row type — crosses the `SqlStore`/`SqlSpaceRepository` boundary; the query composition itself does not. This Answer is where the four dead ends above are recorded, so a later ticket does not re-discover them; `sql-store.ts`'s own doc comment on `SqlTables` states only that `.include`'s relation type cannot be kept opaque across the module boundary and points here for what was tried, rather than repeating the history in source (`docs/agents/workflow.md`'s "a negative result belongs in a ticket, never in source").

**What this means for ticket 23.** `SqlTables<Order>` currently has exactly the two members ticket 22 needs. Extending it for the lifecycle (`loadAggregate`, `initializeAggregate`, `replaceAggregate`, `markExported`) means either (a) adding further already-composed methods in the same style as `loadWithThings` (each database module writes its own real query, only the result crosses the interface), or (b) revisiting whether the deleted experiment's fully-generic approach is recoverable with more time than this ticket had — the four dead ends above are the ones already known not to work, not proof no approach exists. Whichever is chosen, `Order` stays available and working for any further `.orderBy(...)` calls.

**Contract read cases**, per the checklist's "run against the one repository on both databases": rather than threading `SqlSpaceRepository` through the existing giant `spaceRepositoryContract` (which exercises the full `SpaceRepository` interface `SqlSpaceRepository` does not implement yet), a new `test/support/sql-read-repository-contract.ts` takes a harness with a full adapter for seeding (`seed`) and the tracer repository for reading (`read`), and asserts `listSpaces`, `loadSpace` on a missing Space, Thing ordering, revision after a commit, and exported revision. It is wired into both `test/integration/postgres-space-repository.test.ts` and `test/integration/sqlite-space-repository.test.ts` alongside the existing `spaceRepositoryContract` calls. `test:integration:sqlite` (98 tests) and `test:integration:postgres` (83 tests) both pass with it included.

**The big-revision and ceiling cases** landed as three new shared cases in `repository-contract.ts` — "stores and commits a revision above Number.MAX_SAFE_INTEGER as canonical decimal text", "raises an identifiable invariant failure for a stored Space whose revision is not canonical", "refuses to store a revision above the 2^63-1 ceiling" — each needing a raw, codec-bypassing column write no repository method offers, so `RepositoryHarness` gained one new optional member, `writeRawRevision`, implemented by both SQL harnesses and left `undefined` for `MemorySpaceRepository` (which mints every revision in-process and so can never hold a non-canonical or over-ceiling one; the three cases skip their body when it is absent). PostgreSQL's own weaker "does not narrow the expected revision" case and SQLite's "speaks bigint at the repository boundary…" (its ceiling round-trip half only — the raw-column-shape assertion stayed, being SQLite-specific) and "commits and reloads revisions above…" were removed as now-redundant with the shared cases.

**Postgres migration note**: the planner's placeholder for `revision`'s type change needed a `dropDefault` step before the `alterColumnType`, not just after — see the migration file's own doc comment for the mechanism (Postgres recasts an existing `int8` default across a type change, and the recast default text fails the contract verifier's own default-parsing, `'0'` unquoted vs quoted). Verified by hand against a real PostgreSQL 17.5: migrated to the prior migration, seeded rows with `revision` `2^63−1`, `0` and `exported_revision` `42`/`NULL` as `int8`, ran this migration, read every value back unchanged as canonical `text`.

Postgres integration verified locally against a disposable `hyper_hyper-postgres-data` Docker volume (this checkout's own, reset with `docker compose down --volumes` before use — not the tracked `.env`'s credentials, which were not read).

## Comments

**2026-09-20 (second review pass of the one-SQL-repository branch, M3).** This item's closing clause — "do not widen the catch to an unconditional one, which would read a connection failure as broken stored state" — cites ticket 27's "classification default does not flip" bullet, but that bullet is about a different default (the outer retryable-vs-invariant classification across the whole read path) and not about this inner, I/O-free per-row `try`, which ticket 27's own "The per-row catch is unconditional, by position rather than by type" bullet already declined to narrow, on this repository's own PostgreSQL wrap by name ("the one `instanceof`-gated wrap in the tree is `postgres-space-repository.ts:215`, which ticket 22 now has to fix for exactly this reason"). This item did the opposite of what ticket 27 asked of it, and ticket 23/24's unification of both databases onto one `#loadEverySpace` carried the narrowed shape forward rather than resolving the disagreement. Settled on ticket 27 (see its 2026-09-20 comment): the catch is unconditional now. This item's tick and its "do not widen" clause are left as the historical record of what ticket 22 shipped; they no longer state the current rule.
