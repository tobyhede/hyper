# 17 — SQLite CLI import, replace, and export

**What to build:** `hyper <aggregate>` and `hyper export` against SQLite have the same lifecycle outcomes as PostgreSQL. An empty file initializes; `--dangerous-truncate` replaces under the expected Meta identity; a stale replace conflicts; a successful export records `markExported` at the projected revision. The canonical directory format does not change.

**Blocked by:** 16 — SQLite persists authored Edits.

**Status:** resolved

The CLI is a second process. Ticket 14 showed two independent clients **in one process** on one live file can stall for the busy timeout even on disjoint rows; a second *process* was never measured, and because `node:sqlite` busy-waits synchronously, the in-process numbers do not transfer to it without being measured. **Do not require the CLI and a running host to share a live file.** Operator rule: the host is stopped, or CLI points at a file the host does not have open. A CLI that does hit a held file must fail as BUSY/LOCKED (`SqlConnectionError` transient — retryable, whether SQLite returns it immediately or after the 5000ms busy timeout), not as a revision conflict. Proving that classification is 18; this ticket only has to not pretend concurrent CLI+host writers are in scope.

- [x] CLI target composition can construct the SQLite adapter and close it. Command syntax need not change except for the chosen trusted target-selection mechanism. The browser still cannot name the lifecycle doors.
- [x] `initializeAggregate` on an uninitialized SQLite file establishes the supplied complete aggregate, assigns fresh revisions, and returns `initialized`. An identical concurrent proposal returns `existing` (in one process this needs the repository's in-process serialisation; unserialised, ticket 14's review measured the second proposal failing as an immediate `database is locked` instead). A different proposal against an already-initialized file returns `already-initialized` and overwrites nothing.
- [x] `replaceAggregate` on an uninitialized file returns `uninitialized` rather than establishing first state. A matching expected Meta identity atomically replaces every Space and the singleton identity. A stale expected Meta identity returns `conflict` with the current Meta id.
- [x] Spaces without Meta, Meta naming a missing Space, and a stored aggregate that fails complete intake remain invariant failures, not empty states and not values either door repairs. Invalid proposed aggregates return structured intake refusals.
- [x] `hyper export` against SQLite writes the same versioned aggregate directory PostgreSQL does, then `markExported` for each captured Space revision. A `markExported` after a later Edit still records the projected revision rather than the current one. Interruption must not record a revision against bytes that did not land.
- [x] Canonical directory import/export is the only PostgreSQL↔SQLite bridge. There is no live dump, no merge mode, and no Space-scoped export.
- [x] Integration coverage runs the existing CLI lifecycle behaviours against a temp SQLite file the test process owns alone: initialize, refuse a second different initialize, replace with the flag, conflict on a stale Meta id, export then reopen.

## Answer

**Target selection is the script.** `pnpm hyper:sqlite` (`src/cli/sqlite-entry.ts`) runs the same `runCliMain` as `pnpm hyper`, over `SqliteSpaceRepository`, and closes the client. It requires `SQLITE_PATH` to name a file that already exists, and refuses otherwise before opening anything: SQLite creates a missing file on open, so a mistyped path would otherwise leave an empty, unmigrated file behind (found in code review). The file must already be migrated, as PostgreSQL's must. Choosing by script mirrors `pnpm dev:sqlite`: PostgreSQL stays the default, and a `.env` naming both databases cannot silently move `pnpm hyper`. Command syntax is unchanged, and `SpaceResourceRepository` still does not declare either lifecycle door.

**Repository.** `replaceAggregate` and `markExported` join the in-process queue beside the other operations. Replacement answers `uninitialized`, `conflict` with the current Meta id, `aggregate-refused` for an invalid proposal, or `replaced`, atomically. The shared contract runs every case against SQLite again; its `excludes` option had no remaining caller and is gone.

**Invariants, then truncation (ADR 0094).** Spaces stored without Meta, a stored aggregate that parses but fails complete intake, and a stored document that does not parse make `loadAggregate` and `initializeAggregate` throw `AggregateInvariantError` and leave the rows as they were, as this ticket's invariant row asks. A Meta identity naming a missing Space cannot be stored at all: the foreign key refuses both creating it and deleting the Meta Space beneath it.

`--dangerous-truncate` is the exception, decided after this ticket first resolved. As first committed (`f0ffded7`), SQLite's replacement also refused broken stored state, and PostgreSQL's command refused it one step earlier because it authorized replacement from `loadAggregate`, which throws on it. So neither database's flag could truncate the state an operator most needs gone. ADR 0094 refines ADR 0078: replacement truncates whatever is stored, valid or not, in all three repositories. The command now reads the stored Meta identity with `loadMetaSpaceId`, which does not validate, and a different identity by the time replacement writes is still a conflict. A caller that read no identity may truncate Spaces stored without Meta. An empty repository is still `uninitialized` to replacement, and the command then initializes. The PostgreSQL row lock that makes a winning commit conflict now locks raw rows, so an unparseable row is locked and truncated too. Code review found that with no Meta row there was no singleton lock to queue two overlapping truncations on, so the loser could fail with a raw unique-key or deadlock error; the row locks are now taken in id order, which serialises them (`test/integration/postgres-space-repository.test.ts`, overlapping truncations). That test and the other PostgreSQL cases were written without a database to run them on and are first run by CI.

**Export** is the shared `exportAggregate`, so the directory format, the replace-then-record ordering and the interruption rule are the ones PostgreSQL already has (`test/unit/export-aggregate*.test.ts`). The only bridge between the two databases is that directory; there is no dump, merge or Space-scoped export.

**Coverage.** `test/integration/sqlite-hyper-cli.test.ts` runs `pnpm hyper:sqlite` as a separate process against a migrated temp file the test opens only between commands: initialize, identical re-import as unchanged, a different import refused, replacement with the flag, export then reopen with projected revisions surviving a later Edit, and export imported into a second file. A stale Meta identity cannot be interleaved across two processes on cue, so that case runs `runHyper` in process over a real SQLite repository whose `loadAggregate` lets a replacement in straight after answering. An unset `SQLITE_PATH`, and one naming no file (which must create nothing), are covered too. Truncating a broken file runs end to end through the command too. Repository-level invariant and truncation cases are in `test/integration/sqlite-space-repository.test.ts` and `test/integration/postgres-space-repository.test.ts`; the command flow over broken memory state is in `test/unit/import-aggregate.test.ts`.
