# 24 — One SQL repository commits, and the two adapters go

**What to build:** `commit` runs on the one SQL Space repository for both databases, and `PostgresSpaceRepository` and `SqliteSpaceRepository` are deleted with their private copies of `ThingOwnershipError`, `StaleSpaceRevisionError` and the catch that maps them to outcomes.

**Blocked by:** 20 — One commit decision for every implementation; 23 — One SQL repository owns the Meta lifecycle.

**Status:** resolved

**Why:** ADR 0095. Each adapter repeats the same procedure around the shared decision — identity refusal, transaction, fast-path decision, write under the row lock and revision comparison, otherwise Meta lock, complete load, `decideCommit`, write loop, then outside the transaction a stale revision answered as `conflict` from a fresh read and an owned Thing answered as `rejected`. The comments on that procedure place its bugs in the comparison under the lock and in the outcome mapping, which is exactly what each adapter copies.

- [x] One commit procedure in the repository: `commitIdentityRefusal` first, then the fast path for a single structure-preserving update, otherwise the complete-aggregate path through `decideCommit`. `src/persistence/topology-preserving-update.ts` (ticket 20) is absorbed into the repository.
- [x] An update is written by **one helper** used by both paths, not one statement. It keeps today's statement order: write the document to take the row lock and return the revision the row carried when the lock was granted, compare it, then write the new revision, then the Things, then delete Things the snapshot dropped (which removes nothing on the fast path). A single `UPDATE` that sets the revision returns the new value, not the one it replaced, so the two writes stay separate.
- [x] The repository compares that revision and throws its private stale-revision error to roll back; outside the transaction it answers `conflict` from a fresh `loadSpace`, never a read inside the rolled-back transaction.
- [x] Both adapters already answer an owned-Thing collision met by a write as `rejected` / `invalid-commit` rather than letting it escape as 503. The one repository keeps that, from one declaration of the error.
- [x] The whole `spaceRepositoryContract` commit group passes on both databases; `sqlite-contention.test.ts` and PostgreSQL's concurrency tests still pass.
- [x] `aggregate-commit-differential.test.ts` runs against both databases.
- [x] Both adapter modules are deleted and every import site — HTTP runtimes, CLI entries, tests, `test/support` — uses the one repository with its database's `SqlStore`.
- [x] `src/cli/run.ts`'s conflict comment stops explaining itself through one adapter's internals.
- [x] `AGENTS.md` and `docs/agents/editing-and-persistence.md` name the one repository where they named either adapter.

Out of scope: moving per-database tests into the contract (25); host composition (26); naming database contention as its own outcome.

Note (ticket 28): `decideCommit`'s `write` decision now also carries `spaces` — every stored Space the commit produces, ascending by id. The one SQL repository this ticket builds writes rows and deliberately ignores it, the same as both adapters do today.

## Answer

**Built**, in `src/persistence/sql-space-repository.ts`: `SqlSpaceRepository` gains `commit` and now `implements SpaceRepository` explicitly (it was structurally compatible but undeclared before). `commit` -> `#commitUnserialised` (identity refusal via `commitRequestRefusal`, then try `#commitInTransaction`, classifying what escapes) -> `#commitInTransaction` (fast path, then `#lockMetaIdentity` + `decideCommit`, then the per-change write loop). The fast path (`#commitTopologyPreservingUpdate`) and its pure decision (`decideTopologyPreservingUpdate`/`preservesSnapshotBoundary`/`topologyPreservingCandidate`/`UpdateChange`/`TopologyPreservingDecision`) are absorbed verbatim from the deleted `src/persistence/topology-preserving-update.ts` as module-level (non-exported) declarations in the same file. The one shared write helper is `#writeUpdate(tables, snapshot, expectedRevision, newRevision)`, called by both the fast path and the complete-aggregate path's `update`-kind changes, keeping the checklist's exact statement order (write document under lock -> compare returned prior revision -> write new revision -> upsert Things -> delete dropped Things). `ThingOwnershipError`/`StaleSpaceRevisionError` are the same two classes `replaceAggregate`/`initializeAggregate` already declared on this file before this ticket; `commit`'s write paths reuse them rather than declaring new ones, satisfying "one declaration of the error" without adding a second pair.

**`SqlStore`/`SqlTables` grew for `commit`** (`src/persistence/sql-store.ts`, implemented per database in `src/prisma/sql-store.ts`/`src/sqlite/sql-store.ts`): `Space.writeDocumentUnderLock(id, document)` (the row-lock write `#writeUpdate` and the fast path use; distinct from ticket 23's `relock`, which never writes real content), `Space.setRevision(id, revision)`, `Thing.upsert(input)` (answers the row's actual `spaceId`, so `commit`'s update path detects a collision by reading ownership back rather than catching a duplicate-key error the way `create`'s `Thing.create` does), and `Thing.deleteExcept(spaceId, keepIds)`. `Space.deleteById` changed from `Promise<void>` to `Promise<boolean>` so `commit`'s `delete`-kind change can detect the invariant failure "Space disappeared during commit" the same way both former adapters did.

**A real defect surfaced and was fixed, not carried over**: ticket 23's `Space.deleteById`/`Thing.deleteAllForSpace` used `.delete()`/`.deleteAll()`, which return the deleted row(s) — a *decoded* read. On SQLite that decodes `document` through the json codec on the way back, which throws on stored text that isn't JSON. `#truncateHyperContent` (ADR 0094) calls both over stored state it has never validated, so a Thing with a non-JSON document made `replaceAggregate`'s truncation throw instead of truncating — reachable only once ticket 24 moved `test/integration/sqlite-space-repository.test.ts`'s existing `describe('SqliteSpaceRepository', ...)` block from the old adapter onto `SqlSpaceRepository`, since that suite (not ticket 23's own lifecycle-contract wiring) is what already covered "truncates a stored Space whose Thing document is not JSON". Fixed by switching `Space.deleteById`, `Thing.deleteAllForSpace` and the new `Thing.deleteExcept` to `.deleteCount()` (count-only, selects no columns beside the primary key) on both databases — behaviourally identical for every caller, since none used the returned rows, and it also stops PostgreSQL decoding a `jsonb` document it was about to discard. This is a fix, not a workaround: it restores the "truncation never decodes a stored document" invariant the old `SqliteSpaceRepository.truncateHyperContent`'s own doc comment stated and ADR 0094 requires, which ticket 23's rewrite had silently dropped.

**The post-conflict reload** reads through a new private `#loadStoredSpaceRow(tables, id)` (refactored out of the former `loadSpace` body) rather than through the public `loadSpace` method. Both `commit` and `loadSpace` wrap their work in `#store.serialise(...)`; on SQLite that is a per-process promise-chain queue (`serialiseSqlite`), and calling the public, `serialise`-wrapped `loadSpace` from inside `commit`'s own already-running `serialise` callback would queue a second operation behind the first one's own still-pending completion — a self-deadlock. `#loadStoredSpaceRow` takes `tables` directly (built once as `this.#store.tables(this.#store.orm)` at the call site) so it can run inside `commit`'s existing `serialise` scope, and `loadSpace` itself was refactored to call the same helper so there is exactly one place this logic lives.

**Ticket 29 (fast path commits where the commit decision refuses) is untouched**, per this ticket's instruction: `#commitTopologyPreservingUpdate` still never calls `#lockMetaIdentity` and still runs before it in `#commitInTransaction`, carrying the same defect forward unchanged. Its own checklist stays open.

**Race test**: ticket 23's separate `describe('SqlSpaceRepository (PostgreSQL) — Meta-lock retry race', ...)` block (added because `commit` still lived on `PostgresSpaceRepository` at the time) is deleted rather than kept beside the renamed main block — the former `describe('PostgresSpaceRepository', ...)` block, renamed `describe('SqlSpaceRepository (PostgreSQL)', ...)` with its `repository` now built as `new SqlSpaceRepository(postgresSqlStore)`, already contains both halves of the race ("conflicts a replacement authorized against an identity a concurrent replacement retired" and "judges a complete-aggregate commit against an identity a concurrent replacement retired") once its constructor moved onto the one repository. This satisfies "port the commit-racing half of the Meta-lock race test onto the one repository" by construction rather than by a second copy.

**Contract wiring**: both integration files now call `spaceRepositoryContract` exactly once (no more separate `sqlReadRepositoryContract`/`spaceRepositoryLifecycleContract` calls beside it — `spaceRepositoryContract` already runs the lifecycle group first internally). `test/support/sql-read-repository-contract.ts` (ticket 22's tracer, superseded) is deleted. `test/support/sqlite-harness.ts`'s `openSqliteRepository()` now builds `new SqlSpaceRepository(sqliteSqlStore(database))`.

**`aggregate-commit-differential.test.ts`** now runs its generated property twice, against `SqlSpaceRepository(postgresSqlStore)` and `SqlSpaceRepository(sqliteSqlStore(...))` over a fresh temp file per run, through one shared `assertDifferential({repository, clear})` helper so the property body cannot drift between the two.

**Every import site moved**: `src/http/postgres-http-runtime.ts`, `src/http/sqlite-http-runtime.ts`, `src/cli/entry.ts`, `src/cli/sqlite-entry.ts`, `test/integration/postgres-space-repository.test.ts`, `test/integration/sqlite-space-repository.test.ts`, `test/integration/aggregate-commit-differential.test.ts`, `test/integration/hyper-cli.test.ts`, `test/integration/sqlite-hyper-cli.test.ts`, `test/e2e/postgres-persistence.spec.ts`, `test/e2e/sqlite-persistence.spec.ts`, `test/unit/space-resource-repository.test.ts` (now asserts `SqlSpaceRepository<unknown, unknown>` extends `SpaceResourceRepository` — `unknown`/`unknown` because neither type parameter appears in the class's public surface, so this needs no runtime import of either database's store) and `test/support/sqlite-harness.ts`. `src/cli/run.ts`'s conflict comment now names `SqlSpaceRepository.replaceAggregate`. `.oxlintrc.json`'s two per-adapter overrides are deleted; the boundary-code rationale they carried is folded into the surviving `SqlStore` override's comment, which no longer references either deleted file by name.

**`.oxlintrc.json`, `packages/persistence/src/repository.ts`, `test/support/memory-space-repository.ts`, `test/unit/hyper-cli.test.ts`** each had one present-tense comment naming `PostgresSpaceRepository` directly (not a historical "used to" claim), corrected to name `SqlSpaceRepository`/"the SQL repository". Purely historical past-tense mentions elsewhere (`src/aggregate-directory/identify-space.ts`, `test/unit/import-decoding.test.ts`, `src/persistence/sql-store.ts`'s and `src/sqlite/sql-store.ts`'s own ticket-22/23 typing-history doc comments) were left as-is; they are accurate as history regardless of the later deletion.

**`AGENTS.md`**: the ADR 0095 "Decided" entry is rewritten to state what is built (the one repository, `SqlStore`/`SqlTables`, the shared revision codec, `PostgresSpaceRepository`/`SqliteSpaceRepository`/`topology-preserving-update.ts` gone) and what remains (tickets 25 and 26, both `ready-for-agent`; ticket 29 open and deliberately untouched by this ticket). The `sqlite-space-repository.ts` forward-reference remark is gone with the rest of the stale claim. ADR 0096's "three repositories" became "two, SQL and memory" to match what that ADR's own body already anticipated ("Once that lands there are two copies of the decision, SQL and memory").

**Verification.** `pnpm typecheck` and `pnpm -r typecheck` clean throughout (no new type assertion; `eslint-suppressions.json` unchanged, only shrinks are possible and none were needed here). `pnpm test:integration:sqlite`: 93/93 (`SQLITE_PATH` pointed at a scratch temp file, migrated fresh). `pnpm test:integration:postgres`: 81/81, including both `aggregate-commit-differential` cases and the ported/kept race tests, against the disposable local `hyper_agent` PostgreSQL volume. `pnpm verify`: green — 229 test files, 2879 tests. `pnpm e2e`: green, 223 passed. `pnpm e2e:postgres`: green, 1 passed. `pnpm e2e:sqlite`: green, 1 passed (against a freshly migrated scratch `SQLITE_PATH`). `pnpm postgres:down` run afterward.

**Addendum (code review remediation, 2026-09-20).** `SqlStore`/`SqlTables`'s per-database CRUD implementation, grown above, turned out to be liftable after all: `relock`, `create`, `listIds`, `deleteById`, `setExportedRevision`, `writeDocumentUnderLock`, `setRevision`, `loadAllForReplacement`, `Thing.create`, `Thing.upsert`, `Thing.deleteAllForSpace`, and all four `RepositoryState` operations were declared once, in `src/persistence/sql-store.ts`, over a structural slice of the raw generated `Space`/`Thing`/`RepositoryState` collection named for exactly the calls each makes (the same "assignable without a cast" technique `SqlTables` itself already rests on, extended from the row-returning methods `Orderable` already proved to the plain CRUD methods too — `.create`, `.where().update()`, `.where().deleteCount()`, `.upsert()`, `.select().all()` are none of them the `.include()` relation-typing problem ticket 22's Answer records, so none of that ticket's four dead ends applied here). `src/prisma/sql-store.ts` and `src/sqlite/sql-store.ts` each call these with their own generated collection; `pnpm exec tsc --noEmit -p tsconfig.json` compiled clean with no new type assertion at every step. `Thing.deleteExcept` is the one member that stayed duplicated: its second `.where((thing) => thing.id.notIn(keepIds))` call takes a query-builder callback whose filter-expression type is exactly the kind of ORM-client-internal type `.include` cannot be named from either, so generalising it was judged the same "large speculative abstraction" ticket 22 already declined to chase further, and it was left as the one genuine per-database difference beyond `loadWithThings`/`loadEvery`/`isDuplicateKey`/`readDocument`/`serialise`/`close`. `Orderable`/`asOrderable`/`defineSqlStore` (identical in `src/prisma/sql-store.ts` and near-identical in `src/sqlite/sql-store.ts`) also moved into the shared module, exported for both to import.
