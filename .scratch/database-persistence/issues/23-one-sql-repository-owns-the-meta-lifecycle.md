# 23 — One SQL repository owns the Meta lifecycle

**What to build:** `loadAggregate`, `initializeAggregate`, `loadMetaSpaceId`, `replaceAggregate` and `markExported` run on the one SQL Space repository for both databases, with PostgreSQL's complete sequence on both.

**Blocked by:** 22 — Tracer: one SQL repository reads both databases.

**Status:** resolved

**Why:** ADR 0095. The adapters drifted here: PostgreSQL retries `lockMetaIdentity` once after a replacement and re-locks every stored row and re-checks its revision inside `replaceAggregate`; SQLite does neither. The one repository takes PostgreSQL's steps everywhere, but one of them is untested and has to be settled first. When `lockMetaIdentity`'s self-update finds the row gone — a concurrent replacement deleted and rewrote it — it retries, and since `4ec1d1e7` ("Preserve replacement authorization across lock retry") it returns the Meta id it read **before** the replacement, not the one now stored. `replaceAggregate` then compares a stale caller's expected id against that old id, passes, and overwrites the concurrent replacement; a commit on the complete-aggregate path is judged against the old id. That may be intended, but no test fails if it is reversed, and a load-bearing step needs one (`docs/agents/workflow.md`) before it is carried to a second database.

- [x] **First, on the existing PostgreSQL adapter:** a concurrency test races `replaceAggregate` against the Meta lock retry — a replacement landing between `lockMetaIdentity`'s read and its self-update — and asserts the intended answer for both a `replaceAggregate` authorized against the pre-replacement id and a complete-aggregate commit. Record on this ticket whether returning the pre-replacement id is correct. If it is not, fix it in the PostgreSQL adapter with that test before anything moves.
- [x] The five lifecycle members are implemented once, over `SqlStore`, and pass the whole `spaceRepositoryContract` lifecycle group on both databases, including concurrent initialization and ADR 0094's truncation of broken stored state.
- [x] The Meta-lock retry, as the test above settles it, and `replaceAggregate`'s row re-lock and revision re-check run on both databases; the race test runs against the one repository on PostgreSQL.
- [x] Losing an initialization race is recognised through `SqlStore.isDuplicateKey(error, table)`. SQLite's matches the constraint the driver names in its message where 0.16.0 provides one, reaching PostgreSQL's table-and-constraint precision; if the message does not carry it, record that on this ticket and keep any-`23505` for SQLite.
- [x] Every statement inside a transaction is awaited in sequence; no `Promise.all` inside `transaction`. This keeps Prisma Next 0.16.0's shared-connection interleaving defect unreachable (ADR 0095).
- [x] `sqlite-contention.test.ts` still passes unchanged; in particular a second process still surfaces as a transient connection failure, not a conflict.

Out of scope: commit (24).

## Answer

**The race test verdict: returning the pre-replacement id is wrong.** A concurrency test was written first against the existing (two-adapter) `PostgresSpaceRepository`, racing a manually held `repository_state` row lock (standing in for a concurrent replacement mid-flight) against `replaceAggregate` and, separately, against a two-change `commit`. Both failed against `4ec1d1e7`'s behaviour before any fix: the `replaceAggregate` case landed `{ kind: 'replaced' }` — silently overwriting the concurrent replacement — instead of `{ kind: 'conflict', currentMetaSpaceId: <the identity the replacement actually established> }`; the `commit` case landed `{ kind: 'aggregate-refused' }` (`decideCommit` validating the *current* stored Spaces against an identity no longer among them) instead of `{ kind: 'committed' }`. Both tests pass once `lockMetaIdentity`'s retry answers with **the identity the retry itself locks** rather than the one read before the replacement — i.e. `4ec1d1e7` is reverted. That fix landed on `PostgresSpaceRepository` first (`src/persistence/postgres-space-repository.ts`), with the two new tests in `test/integration/postgres-space-repository.test.ts` ("conflicts a replacement authorized against an identity a concurrent replacement retired", "judges a complete-aggregate commit against an identity a concurrent replacement retired"), before anything moved onto the shared repository, per the ticket's own ordering.

One existing test needed correcting once the fix was in: "leaves one whole proposal when two replacements overlap on the Meta row lock" asserted `{kind:'replaced'}` for *both* of two callers racing the same Meta row lock, reasoning (in its own doc comment) that "both replace... the survivor is whichever PostgreSQL grants the Meta row lock to last." That reasoning missed a second race living inside the same window: the *loser* of the row-lock queue doesn't simply wait its turn and write against the row it originally read — the winner's whole `replaceAggregate`, including `truncateHyperContent`'s delete of the very row the loser is blocked on, runs and commits first, so the loser meets exactly this ticket's race and, correctly fixed, conflicts rather than silently overwriting. Renamed to "conflicts the loser when two replacements overlap on the Meta row lock" and rewritten to assert exactly one `replaced`, exactly one `conflict` naming the winner's identity, and that the winner's aggregate is what survives.

The fix (and the whole `#lockMetaIdentity` implementation) then moved onto `SqlSpaceRepository` unchanged in shape, and the `replaceAggregate` race was ported onto it too, run against PostgreSQL only (`describe('SqlSpaceRepository (PostgreSQL) — Meta-lock retry race', ...)`, placed before the `afterAll(() => db.close())` describe block so it doesn't race a closed connection). The `commit`-racing half of the pair was **not** ported onto `SqlSpaceRepository`, because `SqlSpaceRepository` has no `commit` yet (ticket 24); it stays as `PostgresSpaceRepository` coverage only, and ticket 24's implementer should port it onto `SqlSpaceRepository` alongside `commit` itself.

**`isDuplicateKey` finding.** Investigated against a real duplicate-key error on the pinned `@prisma-next/driver-sqlite` 0.16.0 (`node_modules/.pnpm/@prisma-next+driver-sqlite@0.16.0.../src/normalize-error.ts`), triggered directly against a temp SQLite file for both `spaces` and `repository_state`: `SqlQueryError.table` is **always `undefined`** — nothing in that driver version sets it — but `SqlQueryError.constraint` is not; it is parsed from SQLite's own message (`UNIQUE constraint failed: <table>.<column>`) into exactly `<table>.<column>` text (e.g. `spaces.id`, `repository_state.singleton_id`). `SqlStore.isDuplicateKey(error, table)` on SQLite (`src/sqlite/sql-store.ts`) therefore checks `constraint.startsWith(\`${table}.\`)`, which reaches PostgreSQL's table precision through a different field than `table`, rather than falling back to any-`23505`.

**What ticket 24's implementer needs.**
- `SqlTables<Order>` (`src/persistence/sql-store.ts`) grew nine members beyond ticket 22's two: `Space.loadEvery`, `Space.loadAllForReplacement`, `Space.relock`, `Space.create`, `Space.listIds`, `Space.deleteById`, `Space.setExportedRevision`, `Thing.create`, `Thing.deleteAllForSpace`, `RepositoryState.{read,relock,create,delete}`. All but `Space.loadEvery` are plain, already-composed CRUD (no `Order`, no relation) and compile identically forward-typed on both databases with no assertion. `Space.loadEvery` (the aggregate-wide read with Things) needed SQLite's pre-ticket-23 `loadEverySpace` treatment carried over verbatim in technique — the lower-level `sql`/`execute` builder, overriding `document`'s codec to `'sqlite/text@1'` so a document that isn't even JSON reaches this repository's own per-row classification as raw text rather than throwing inside the driver's json codec. That needed SQLite's `Handle` (`src/sqlite/sql-store.ts`) to widen from ticket 22's bare `Orm` to `{ orm, execute }` — the transaction context's own `execute` (`Tx['execute']`), threaded through so `loadEvery` can run its two lower-level statements on the same connection/transaction as everything else. `tables()`'s own `handle` parameter absorbed that widening with no cast: a real `Tx` is structurally a superset of the two-field `Handle` (it also carries `sql`, `enums`, `invalidated`), so passing `tx` where `Handle` is expected needs no conversion, and the one non-transactional `Handle` value (`sqliteSqlStore`'s own `orm` field) is built once from `database.orm` plus `database.runtime().execute`, called fresh per invocation.
- `toJsonValue`/`JsonValue` moved from being duplicated verbatim in each adapter to one shared export in `src/persistence/sql-store.ts`. `commit`'s own write paths (`createStoredSpace`, `upsertThings`, `importThings`, `replaceStoredSpace`, `writeSpaceDocumentUnderLock` in both remaining adapters) can be pointed at the shared one instead of their local copies when ticket 24 moves them, rather than carrying a third copy forward.
- `replaceAggregate`'s per-row relock (`Space.relock`) writes a constant placeholder `document` (`toJsonValue({})`) rather than round-tripping the row's real one, and never reads `document` at all in the replacement row-scan (`Space.loadAllForReplacement` selects only `id`/`revision`). This is safe *because* the relocked row is always either deleted moments later by the same call's `truncateHyperContent` (the normal path) or the whole transaction rolls back on a revision mismatch (the conflict path) — never observed either way. Nothing needs updating in ticket 24 for this; it's noted here because it is a deliberate departure from the old PostgreSQL adapter's literal round-trip, not an oversight.
- **The lifecycle group split off `spaceRepositoryContract`.** `test/support/repository-contract.ts` now exports `spaceRepositoryLifecycleContract` (the ~16 cases that touch only `listSpaces`/`loadSpace`/`loadAggregate`/`initializeAggregate`/`loadMetaSpaceId`/`replaceAggregate`/`markExported`, never `commit`) over a new `LifecycleRepository = Omit<SpaceRepository, 'commit'>` and `LifecycleRepositoryHarness`. `spaceRepositoryContract` now calls `spaceRepositoryLifecycleContract(name, createHarness)` as its first statement (a `RepositoryHarness` is structurally a `LifecycleRepositoryHarness`, so this is a plain delegation, not a second copy) and keeps the remaining `commit`-dependent cases itself — so both full adapters still run the identical 37 cases they always did, in one call each, with no duplication. `SqlSpaceRepository` is wired to `spaceRepositoryLifecycleContract` directly in both integration files (`test/integration/postgres-space-repository.test.ts`, `test/integration/sqlite-space-repository.test.ts`), seeding through itself now that it owns `initializeAggregate`. When ticket 24 gives `SqlSpaceRepository` a `commit`, switch that wiring from `spaceRepositoryLifecycleContract` to `spaceRepositoryContract` and delete the now-redundant `sqlReadRepositoryContract` calls (ticket 22's tracer, superseded once the full contract runs).
- `PostgresSpaceRepository`/`SqliteSpaceRepository` are otherwise untouched (`commit`, `loadStoredSpace`/`loadEverySpace`, `topology-preserving-update.ts` all still theirs) beyond the `lockMetaIdentity` fix on the PostgreSQL one — ticket 24 deletes both wholesale rather than trimming them.
