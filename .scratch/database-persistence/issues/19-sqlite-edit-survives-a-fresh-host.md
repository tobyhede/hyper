# 19 — A SQLite edit survives a fresh host

**What to build:** The browser proof PostgreSQL already has, for SQLite. An author drags a Thing in a Space served by the SQLite host; that host closes; a fresh SQLite host on the same file opens the Space and the Thing is where the author left it. This is the first thing in CI that drives the SQLite Vite wiring (the SQLite Vite config and its HTTP runtime) through a browser — today only the HTTP runtime is exercised, by the integration suite, and nothing starts the Vite host `pnpm dev:sqlite` uses.

**Blocked by:** None (can start immediately). Ticket 18 is resolved and named "browser-restart E2E on SQLite" as out of scope unless a later ticket asked for it; this is that ticket.

**Status:** resolved

CI placement matches PostgreSQL: the proof runs as the last steps of the existing `sqlite` job, after the SQLite integration step has migrated the job's temp file, exactly as the PostgreSQL proof follows `test:integration:postgres` in the `postgres` job. It brings no migration of its own. It is not a separate job and not sharded — it is one test, like its PostgreSQL counterpart.

- [x] A dedicated Playwright config and spec (beside the PostgreSQL ones) open a Space stored in the migrated SQLite file, drag a Thing, close that host, start a second host on the same file, and observe the Thing at its dragged position; the exported aggregate agrees.
- [x] The two hosts run in sequence, never together: a second process on a live file is unsupported (ticket 18), so the first host has released the file before the second opens it.
- [x] The config carries the PostgreSQL project's policy and says why: `forbidOnly` under CI, `retries: 0`, one worker, a long test timeout, trace retained on failure.
- [x] The host uses its own fixed port, clear of the human's dev ports (5173–5177), the PostgreSQL proof's port, and the default suite's worker-scoped range, so it can run beside `pnpm e2e` and `pnpm e2e:postgres`.
- [x] The test reads `SQLITE_PATH` as the job provides it and cleans up the Space and Thing it minted, as the PostgreSQL proof does.
- [x] The drag and read-back steps — including how the Space's name slot is addressed — are shared with the PostgreSQL proof rather than copied, so a change to the Space's chrome breaks both at once.
- [x] A `pnpm e2e:sqlite` script runs it. CI's `sqlite` job gains, after its integration and live-contract steps: Chromium install (no `--with-deps`, for the reason the `postgres` job records), `pnpm e2e:sqlite`, and a failure-only report upload under its own artifact name. The temp-directory removal still runs last.
- [x] `AGENTS.md` documents `e2e:sqlite` next to `e2e:postgres`, including that it is opt-in locally, needs a migrated `SQLITE_PATH`, and is the second proof a chrome change must grep `test/e2e/` for.

Out of scope: the root `dev:sqlite` script's handling of a relative `SQLITE_PATH` (found in review, and since refused at host composition by `6751ae2a`) — this test starts Vite programmatically and does not go through that script. WAL, crash and power-loss claims remain ticket 18's exclusions.

## Answer

Built as `test/e2e/sqlite-persistence.spec.ts` and `playwright.sqlite.config.ts`, mirroring `postgres-persistence.spec.ts`/`playwright.postgres.config.ts` exactly in policy (`forbidOnly` under CI, `retries: 0`, one worker, 120s timeout, `trace: 'retain-on-failure'`, `reporter: 'list'`), and started programmatically against `packages/app/vite.sqlite.config.ts` the same way the PostgreSQL spec starts Vite against `vite.config.ts`.

**Sharing.** The drag/read-back steps, including the Space-name-slot comment and locator, moved to `test/support/restart-proof.ts`: `openStoredSpace`, `dragThingAndCapturePosition` and `expectThingRestoredAt`. `postgres-persistence.spec.ts` now calls these instead of inlining them — its own behaviour is unchanged (same locators, same `dragBy(page, thing, 0, 220)`, same `data-revision` assertions), which `pnpm typecheck`/`pnpm verify` and a local `pnpm e2e:sqlite` run both hold, and which the PostgreSQL proof itself would have held too had Docker/`.env` been available locally to run it (see below).

**One connection at a time.** Ticket 18 found a second live SQLite writer against one file unsupported, so unlike the PostgreSQL spec — which keeps one `PostgresSpaceRepository` open for the whole test, since PostgreSQL tolerates concurrent connections — this spec never holds more than one `SqliteDatabase` connection to `SQLITE_PATH` open at a time. It opens and closes a connection to seed the fixture, closes it before starting the first Vite host, closes the first host before starting the second (the two Vite hosts are what the checklist's "run in sequence, never together" names), and opens fresh connections afterward only to check the post-first-host revision and to export/clean up. This was verified empirically before committing to it: a throwaway probe script (since deleted) started two Vite hosts in sequence against one migrated file with no explicit host-side close hook — none exists in `vite-space-http-plugin.ts` — and found no contention (a ~1.2–1.5s one-time module-load cost per host, then GETs and a POST commit both in single-digit milliseconds). The one-connection-at-a-time design is nonetheless what the spec keeps, being the one the product itself supports (ADR/ticket 18's "one Hyper process per file").

**Cleanup.** `test/support/clear-sqlite-content.ts` is a small SQLite analogue of `clear-hyper-content.ts` (no `.public` schema prefix), used at the end of the SQLite proof so a rerun against the same `SQLITE_PATH` without re-migrating meets an empty file rather than `already-initialized`. Unlike the PostgreSQL proof, this isn't required for CI correctness — the job's temp directory is removed immediately after this test regardless — but it mirrors the PostgreSQL proof's discipline per the checklist and helps local iteration.

**Port.** `SQLITE_E2E_PORT = 5281` added to `packages/app/e2e/projects.ts`, beside `POSTGRES_E2E_PORT = 5280`: distinct from it, clear of 5173–5177, and below `E2E_PORT_BASE` (>= 5300) so no worker index can reach it.

**CI.** The `sqlite` job gained, between "Verify live database contract" and "Remove the SQLite directory": a Chromium install step (no `--with-deps`, comment pointing at the `postgres` job's own note), `pnpm e2e:sqlite`, and a failure-only `actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` (the same pin the `postgres` job uses) under `playwright-report-sqlite`. No new job, no sharding, no change to the `postgres` job. `test/unit/ci-container-image-pin.test.ts` (container jobs and the `node-version-file` consumer count) and `test/unit/current-domain-vocabulary.test.ts` both still pass — no container job or new `.node-version` consumer was added, and none of the new prose uses the retired "workspace" word in a guarded shape.

**`package.json`/`AGENTS.md`.** `"e2e:sqlite": "playwright test --config playwright.sqlite.config.ts"` added beside `e2e:postgres`. `AGENTS.md`'s E2E bullet now describes `pnpm e2e:sqlite` immediately after `pnpm e2e:postgres` — opt-in locally, needs a `SQLITE_PATH`-migrated file, runs as the last step of CI's `sqlite` job for the same reason `e2e:postgres` runs last in `postgres` — and generalises the following sentences ("both proofs", "the two commands", "it now holds both proofs") rather than duplicating them.

**Verification.** Locally: fresh `mktemp -d`, `SQLITE_PATH=<dir>/hyper.db`, `pnpm db:migrate:sqlite`, then `pnpm e2e:sqlite` — 1 passed. `pnpm verify` — green (223 test files, 2737 tests). PostgreSQL: no `.env` in this worktree, so `postgres:up`/`test:integration:postgres`/`e2e:postgres` could not be run; `pnpm typecheck` and `pnpm typecheck:packages` (which cover the refactored `postgres-persistence.spec.ts` and the new shared module) both pass. `pnpm e2e` was judged inapplicable: nothing under `packages/app/src` or in `packages/app/e2e/graph.ts`'s behaviour changed, only a new exported port constant in `packages/app/e2e/projects.ts` alongside the existing one. No component or story changed, so `pnpm e2e:ladle` was likewise not run.

**Deviations from the ticket text.** None in substance. The "one connection at a time" discipline for the seed/reopen/export connections around the SQLite spec's own two hosts is an addition the ticket didn't spell out in that much detail (only the two *hosts* are named); it was added because the alternative — holding the seeding repository's connection open for the whole test, as the PostgreSQL spec does with `PostgresSpaceRepository` — would have left this test, alone among the three durability proofs, resting on an untested assumption about SQLite's tolerance for a lingering idle connection rather than on the one-connection-at-a-time model the rest of the SQLite workstream (tickets 16–18) established.
