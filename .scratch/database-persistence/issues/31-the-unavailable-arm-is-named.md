# 31 — The unavailable arm is named, and start-up stops retrying what no retry cures

**What to build:** "The database is unreachable" is a thing production names, the way broken stored state already is, so neither arm of the classification is merely the absence of the other. One shared predicate answers it for every reader that asks today — six call sites across four readers. Separately and independently: `retryMetaSpaceEstablishment` stops retrying forever on a failure it cannot classify, or says so where an operator will see it.

**Blocked by:** Nothing now. Ticket 24 (one SQL repository commits, and the two adapters go) is resolved, so Part A's premise holds: one `SqlSpaceRepository` implementation raises `AggregateInvariantError` for both databases from `commit` as well as from a read, rather than two adapters that had to agree independently. Part A is unblocked and ready to pick up; Part B was never blocked.

**Status:** resolved

**Tags:** Defect, release/v1

**Why:** `AggregateInvariantError` was given its own type so two unrelated failures reaching a reader the same way could be told apart (`packages/persistence/src/repository.ts`). Only one of the two got a name. The other is `!isAggregateInvariant(error)` — an else-branch — and four readers now re-derive the same assumption from it, one more than when this ticket was filed: `src/http/space-host.ts:85` re-reads once, `src/http/space-host.ts:151` answers 503, `packages/http/src/index.ts`'s `POST SPACE_COLLECTION_PATH` commit route gained an arm of its own since (`:441`) — `SqlSpaceRepository.commit` (ticket 24) now raises `AggregateInvariantError` the same way a read does, and this route classifies it exactly as the read paths below do — its `GET SPACE_AGGREGATE_PATH` handler still does both for `GET /api/aggregate` (`:462` and `:473` as of the 2026-09-21 audit), and `src/startup/database-startup.ts:140` resets its give-up counter and continues.

That the arm is unnamed is load-bearing rather than untidy. Ticket 18 resolved with SQLite BUSY/LOCKED — immediate or exhausted, both `SqlConnectionError{transient:true}` — answering `persistence-unavailable` (503). It reaches that status *by falling through the default*, because nothing in the tree reads `SqlConnectionError`, reads `transient`, or names unavailability as anything but an HTTP response string. So ticket 18's whole contention matrix rides on the default, and ticket 27 declined to flip the default for exactly this reason: with nothing naming the arm, inverting it answers contention as broken stored state.

The consequence is that an error neither arm actually describes — a code defect, a driver failure nobody anticipated — is silently filed as transient. Ticket 27 (PR #239 review, CR1) took the same shape from the other side: SQLite's per-row catch stays unconditional precisely because a narrowed one would let a fourth error class escape into this arm.

**Part B's exposure, measured rather than assumed.** `retryMetaSpaceEstablishment` (`src/startup/database-startup.ts:132`) is `for (;;)`, and only the invariant arm counts toward giving up — `CONFIRMING_INVARIANT_FAILURES` is 2, while the `!isAggregateInvariant` branch resets the counter and continues. A probe against a repository that always rejects with a connection error reached 10,001 attempts in about two seconds, but it passed an immediately-resolving `wait`, so that number measures the loop and not a deployment. Production injects a real timer and `delay` backs off from `META_SPACE_RETRY_INITIAL_DELAY_MS` (5s) to `META_SPACE_RETRY_MAX_DELAY_MS` (60s). The real exposure is therefore one full aggregate read a minute, forever, against a deployment whose defect no retry cures, with no final failure reported for that class. Quiet, not hot — worth fixing, and not an incident.

## Part A — name the arm

- [x] Red first: a failure that is neither broken stored state nor a recognised transient one is classified as *neither*, and each of the four readers is asserted at its own seam for that input. The test names the third case. One input already expresses it: a stored document that fails its schema, read on the single-Space commit fast path, raises a bare `ZodError` and POST answers 503 — see the audit comment below.
- [x] Transience is named once, beside `AggregateInvariantError` in `packages/persistence/src/repository.ts`, so both consumers of the shared seam can ask. Whether it is a `PersistenceUnavailableError` the repository raises or a predicate over the driver's `SqlConnectionError{transient:true}` is the ticket's to decide — record which and why, and do not tell the two BUSY shapes apart by message (ticket 18, correction (b)).
- [x] The four readers ask the one predicate rather than re-deriving the arm from `!isAggregateInvariant`: `space-host.ts:85`'s single re-read, `space-host.ts:151`, `packages/http/src/index.ts`'s `POST SPACE_COLLECTION_PATH` commit catch (`:441`) and its `GET SPACE_AGGREGATE_PATH` handler (`:462`/`:473` as of the 2026-09-21 audit), and `database-startup.ts:140` all keep their current behaviour for the two named arms.
- [x] The unclassified third case gets a decided answer rather than an accidental one. It is not obviously 503 — that is the claim this ticket exists to stop making by default.
- [x] Ticket 18's contention matrix (`test/integration/sqlite-contention.test.ts`) is green unchanged. It currently passes because of the default; if naming the arm changes any row, the naming is wrong, not the row.
- [x] `test/e2e/` is checked: both restart proofs drive the application surface and `verify` cannot observe them (AGENTS.md).

## Part B — bound the retry, or report it

- [x] Red first, at `retryMetaSpaceEstablishment`'s own interface with an injected counting `wait`: a repository that always fails with an unclassifiable error stops, or reports a persistent-failure state, rather than continuing indefinitely.
- [x] Either an attempt cap on the non-invariant arm or a reported stuck state — pick one and say why. A cap that silently gives up on a genuinely transient outage is the failure mode to avoid; reporting may be the better half.
- [x] `wait` and `report` stay the caller's (ADR 0016, ADR 0081). Nothing is thrown: nothing awaits this call, and a rejection nothing listens for ends the process.
- [x] `test/integration/sqlite-http-runtime.test.ts`'s existing `RETRY_WAIT_BOUND` was added by PR #239's review to stop a classification regression spinning inside the suite. If production gains a bound, reconcile the two rather than leaving the test asserting a limit the code now owns.

## Answer

Resolved 2026-09-21. Five decisions, each with its reason.

**1. Transience is a type the repository raises, not a predicate over the driver.** `PersistenceUnavailableError` sits beside `AggregateInvariantError` in `packages/persistence/src/repository.ts`, with `isPersistenceUnavailable` walking the cause chain the same way `isAggregateInvariant` does, and one `classifyStoredFailure(cause)` answering `broken-stored-state`, `unavailable` or `unclassified` for every reader. Broken stored state wins when a chain carries both. A predicate over `SqlConnectionError{transient:true}` was rejected on evidence, not taste: it would have filed PostgreSQL being down as the third case. Probed against a closed loopback port, a PostgreSQL `loadAggregate`, `commit` and `loadSpace` all reject with Node's own `ECONNREFUSED` error (an `AggregateError` when `localhost` resolves to two addresses), never `SqlConnectionError`, because `@prisma-next/driver-postgres` normalises only errors from a statement (`PostgresQueryable.execute`), not from `pool.connect()` when `runtime.connection()` acquires one — which is how both a transaction and the ORM's `include` reads start. And where the driver does normalise, it marks `ECONNREFUSED` `transient: false`: its flag answers "might an immediate retry succeed", which is not the question a 503 asks. So `SqlSpaceRepository` names the arm from two things it can see, neither by message:

- **A transaction the database never opened**, by position: `#transaction` wraps `SqlStore.transaction` and names any failure raised before its callback ran. That covers the refused pool connection above, pg-pool's own connect timeouts (code-less `Error`s), and a SQLite client closed underneath the repository (`SQLite client is closed`, thrown by `getRuntime` before any connection). `test/unit/postgres-unreachable.test.ts` and `sqlite-space-repository.test.ts`'s "names a database that will not open a transaction unavailable" hold both databases. The accepted cost: a defect that fails before the callback — the driver's runtime failing to construct — is named unavailable too, and is retried with a report on every attempt rather than given up on.
- **The driver's `SqlConnectionError` anywhere on the cause chain** (`isDriverConnectionFailure` in `src/persistence/sql-store.ts`, reading the own `kind` field `SqlConnectionError.is` reads, since `@prisma-next/sql-errors` is not this repository's dependency), whatever its `transient` flag. That is SQLite BUSY and LOCKED, immediate and exhausted alike, and a PostgreSQL connection dropped mid-statement. `#naming` applies it on the way out of every public method, leaving an already-named failure alone.

What stays unclassified: a PostgreSQL non-transactional read (`listSpaces`, `loadSpace`) that fails acquiring its connection surfaces the raw `ECONNREFUSED`. No reader asks those two today — both routes answer 503 unconditionally, which this ticket leaves alone because it names four readers and those two are not among them — so recognising Node's errno codes in the PostgreSQL store was left undone rather than built for no caller.

**2. The third case answers 500 `internal-error` at every HTTP reader, logged, under its own detail** ("The request failed unexpectedly.", beside broken stored state's "Stored repository state is not usable."). 503 claims the condition will pass, which nothing says of a failure this code cannot name. `GET /` (`space-host.ts`), `GET /api/aggregate` and `POST /api/spaces` (`packages/http/src/index.ts`'s `storedFailureProblem`) answer by the same three arms; the single re-read happens only for `broken-stored-state`. A 500 is still retryable to the browser client (`commitFailureForProblem`), which is ticket 35's to decide, not this one's.

**3. The fast path's schema-invalid stored document is now broken stored state.** `#loadStoredSpaceRowForCommit` names *every* failure of the row's decode step `AggregateInvariantError`, by position rather than by type, the way `#loadEverySpace` already did for the same row on the complete-aggregate path — so which commit path meets a broken row no longer decides what the route answers. `#loadStoredSpaceRow` is split into its read and a pure `#decodeStoredSpaceRow`, so the catch wraps no I/O and cannot swallow a connection failure. That is also what makes it robust to ticket 32: whether the decode throws `ZodError` today or the private `SnapshotValidationError` once the pre-parse goes, the position is the same. Ticket 32's implementer should now edit `#decodeStoredSpaceRow`. The contract row changed deliberately to "names a broken stored document broken stored state on the single-Space fast path, and leaves loadSpace's answer narrower". `loadSpace` keeps its narrower, unclassified error, for ticket 27's reason: one Space failing intake is that resource's answer to give.

**4. The single re-read's race is still reachable, and the comments now say why.** `#loadAggregateUnserialised` does run in one transaction behind `#lockMetaIdentity`, but the PostgreSQL driver opens it with a plain `BEGIN` (`query("BEGIN")` in `@prisma-next/driver-postgres`), so it runs at READ COMMITTED, where each statement takes its own snapshot. When there is no Meta row there is nothing to lock, so a rival initialization committing between the `RepositoryState` read and `#loadEverySpace` is still reported as Spaces without Meta. The re-read stays. The comments in `index.ts`, `space-host.ts` and `database-startup.ts` now say "inside one transaction, but at READ COMMITTED each statement takes its own snapshot" rather than implying two transactions. On SQLite the race is not reachable in-process, because `serialise` queues every operation on one file handle.

**5. Part B: an outage keeps retrying, anything else no wait cures stops.** `retryMetaSpaceEstablishment` resets its count only on `unavailable`, and counts `unclassified` toward giving up exactly as `broken-stored-state` does, with one counter: two in a row (`CONFIRMING_FAILURES`) and it returns `undefined`, which `database-http-runtime.ts` already reports as the give-up. Two rather than one because a one-off is not a verdict and a defect repeats. An unbounded retry is kept only for the case it was built for. Every attempt was already reported, so the audit's "or says so" half needed nothing. `wait` and `report` stay the caller's and nothing is thrown. `RETRY_WAIT_BOUND` is gone (audit comment), so there was nothing to reconcile.

**Found on the way, not fixed here.** Probed: `listSpaces` against a PostgreSQL server that refuses connections rejects with `CliStructuredError` `3006` ("Database error while reading contract marker", no `cause`, the reason only in `why` prose), because a non-transactional statement verifies the contract marker before it runs. Read in `@prisma-next/sql-runtime`'s `sql-runtime.ts` but not reproduced: that verification is one memoised promise (`verifyMarkerPromise`), assigned only when `null` and never reset on rejection, and every statement — transactional ones included, through `executeAgainstQueryable` — awaits it. So a runtime whose first marker read ran while the server was down, which `GET /api/spaces` during a start-up outage does, would fail every later statement with that `3006` after the database comes back. That is unclassified here, so start-up now gives up on it after two attempts and asks for the restart it needs, where before it retried uselessly once a minute forever. It is worth its own ticket against the driver or against `verifyMarker`.

`test/e2e/` checked: both restart proofs drive a happy-path edit and reload through the application surface, and nothing here changes the chrome or a successful response. `sqlite-contention.test.ts` is unchanged and green.

**Amendment, 2026-09-21 — contention and shutdown are unavailable too.** A code review of this Answer found two failures it had left unclassified that are neither defects nor broken state, so both answered 500 and counted toward start-up giving up, where before this ticket they had answered 503.

- **PostgreSQL SQLSTATE failures that mean "not now".** `@prisma-next/driver-postgres`' `normalizePgError` turns *every* error carrying a SQLSTATE into `SqlQueryError` (`kind: 'sql_query'`, the code on `sqlState`), including the ones that are contention or an outage, so `isDriverConnectionFailure` never sees them. They are now named by that structured field, walking the cause chain the same way, never by message: `isUnavailableStatementFailure` over `UNAVAILABLE_SQLSTATES`, the one place the set is kept (`src/persistence/sql-store.ts`), applied by `#naming` beside the connection predicate. The set:
  - `08000`, `08001`, `08003`, `08004`, `08006` — connection exceptions. `08P01` (protocol violation) is left out as a client or server defect.
  - `40001` serialization failure, `40P01` deadlock detected — the database aborted this transaction so another could proceed; the same request is expected to succeed later.
  - `53300` too many connections.
  - `55P03` lock not available.
  - `57P01` admin shutdown, `57P02` crash shutdown, `57P03` cannot connect now. `57014` (query cancelled) is left out: a cancel can be deliberate, and a statement timeout is a configuration question.

  None collides with SQLite: `@prisma-next/driver-sqlite` maps its failures onto `23xxx` or `HY000` and raises BUSY and LOCKED as `SqlConnectionError`. `test/unit/sql-connection-failure.test.ts` holds the predicate (each code, the COMMIT wrapper, and a `23505`, an `HY000`, a `57014`, an un-normalised error carrying `sqlState`, and prose naming a code all refused); `sqlite-space-repository.test.ts` holds the repository naming a `40P01` unavailable, leaving a `23505` unclassified, and start-up establishing through three `40001`s in a row where it used to give up after two.
- **`#lockMetaIdentity` giving up.** When a concurrent replacement moves the singleton row under both attempts, it threw a plain `Error`. That is a race that has passed by the next attempt, so it now raises `PersistenceUnavailableError` (`sqlite-space-repository.test.ts`, "names a Meta identity that keeps moving while it is locked unavailable").

`PersistenceUnavailableError`'s doc comment said it covered "contention it gave up waiting on", which was true only of SQLite's BUSY as this Answer first stood; it now lists what the repository actually raises it for.

**Sorting `#commitInTransaction`'s updates by id was considered and not done.** The review's concrete trigger was two concurrent commits updating A,B and B,A deadlocking. Read, not reproduced: a complete-aggregate commit takes the singleton row's write lock (`RepositoryState.relock`, an `UPDATE`) in `#lockMetaIdentity` before it writes any Space, so two such commits queue on that row rather than interleaving; with no Meta row there is nothing to lock, but `decideCommit` then rejects the write ("The repository has no Meta Space") before any row is touched; and the fast path writes exactly one Space. So that interleaving cannot form between two commits as the code stands, and reordering the write loop would change the order `ResourceOwnershipError` is met in for no demonstrated cure. A deadlock that does occur is now `unavailable` either way.

The misconfiguration that `#transaction`'s by-position rule also names unavailable is ticket 36; the cached contract-marker failure under "Found on the way" is ticket 37.

## Comments

**Audit, 2026-09-21.** Read against `d456b00c`.

- Part A's premise holds: nothing in `src/` or `packages/*/src` reads `SqlConnectionError` or `transient`.
- **The third case already exists and is pinned.** `#loadStoredSpaceRowForCommit` (`src/persistence/sql-space-repository.ts`) reclassifies only `RevisionCodecError`. A stored Space document that fails `spaceDocumentSchema` therefore reaches the commit route's catch as a `ZodError`, not an `AggregateInvariantError`, and POST answers 503 `persistence-unavailable`. `test/support/repository-contract.ts`'s "leaves a broken stored document unclassified on the single-Space fast path" asserts exactly that (`rejects.not.toBeInstanceOf(AggregateInvariantError)`). Whatever this ticket decides for the third case changes that contract row, and the row should change deliberately. Ticket 32 changes which error that path throws; settle the classification here first.
- **The GET re-read's stated reason needs checking.** `index.ts`'s aggregate handler and `space-host.ts`'s `readAggregate` justify their single re-read with "`loadAggregate` runs at READ COMMITTED in two statements". `#loadAggregateUnserialised` now runs in one transaction behind `#lockMetaIdentity`. Not checked here whether the race the re-read covers is still reachable; Part A touches both readers, so it should settle that rather than carry the re-read forward on an unverified reason.
- **Part B is mostly overtaken.** `retryMetaSpaceEstablishment` reports every failed attempt through `report`, which `src/http/database-http-runtime.ts` defaults to `console.error`, and that runtime reports the give-up too. The "or says so where an operator will see it" half is therefore built. What remains is only that the non-invariant arm never stops — logged about once a minute at the 60s ceiling. Part B reduces to deciding whether an unbounded, logged retry is acceptable.
- **Part B's last bullet names a test that is gone.** `RETRY_WAIT_BOUND` was removed by `7805d876` (database target composition); `test/integration/database-http-runtime.test.ts` now passes a `wait` that never resolves. There is no test-owned bound left to reconcile.

**Audit history (from `main`, 2026-09-20, merged after resolution).** The comments below were written on `main` against `b1ac983d`, before this ticket was built, and proposed a design (a `persistence-failure.ts` module and a `SqlStore.connectionFailure` member) that the Answer above supersedes: what was built is `classifyStoredFailure` and `SqlStore.isUnavailable`. They are kept for the alternatives they record.

**2026-09-20 (design session, after the architecture review of the one-SQL-repository branch).** Part A's open questions were worked through and settled; the section above is the result rather than the original framing. What the review added to this ticket's own account: the count is **six** classifying sites rather than four readers (`index.ts`'s commit catch and its aggregate handler are separate sites of the same shape, and `space-host.ts:85`/`index.ts:462` are a second duplicated pair), **nine further sites read a persistence failure and classify nothing**, and the driver's transience signal is read in exactly one file in the repository — `test/support/sqlite-second-process.ts:106-108`, which is test support. Nothing in `src/` or `packages/` reads `sql_connection` or `transient`, which is what "the arm is reached by falling through the default" means concretely.

Three alternatives were rejected. A second predicate beside `isAggregateInvariant` leaves the same else-branch one layer up — `!isAggregateInvariant && !isUnavailable` is still an unnamed third case. An error-class hierarchy tested with `instanceof` puts the matching back at eight sites and cannot express `unclassified` at all, since an unclassified failure is by definition not an instance of anything anyone thought to name. Keeping the arm-to-code mapping at each reader was weighed on the grounds that a status code is a transport concern; it lost because `@project/persistence` already declares the problem catalogue.

**Correction (same session).** The review first recorded `ResourceOwnershipError` escaping `replaceAggregate` as a live defect: `#replaceAllSpaces` can raise it through `#importThings`, `initializeAggregate` handles it (`sql-space-repository.ts:733`) and `commit` converts it (`:385`), while `replaceAggregate`'s catch narrows to `StaleSpaceRevisionError` (`:785`) and lets it escape into the 503 arm. The code path is real but **unreachable**: `#replaceUnserialised` runs `loadSpaceAggregate` intake before opening its transaction, and that intake already refuses aggregate-wide duplicate Thing ids (`packages/graph/src/space-aggregate.ts:105-115`), so the only input that could collide never reaches the insert. The asymmetry with `initializeAggregate` is correct too — initialize races on first insert with nothing to lock, replace takes the Meta lock and re-locks every row first.

What survives is smaller and real: the two callers of one private method hold different, unwritten beliefs about what it raises, and replace's belief rests on a check in another package with no test binding them. That is **ticket 39**, to be taken as part of this ticket's refactoring rather than before it.

**Staleness found alongside.** `packages/persistence/src/revision-codec.ts:26-29` still says `#loadEverySpace` "admits this alongside its own `SnapshotValidationError` rather than widening its catch to every error". That catch was widened to unconditional in `5de390f3` (ticket 27's 2026-09-20 comment). The codec's own doc comment now states the opposite of the code it describes.
