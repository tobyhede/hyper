# 01: Describe only the commands a Resource offers

Status: ready-for-agent

**What to build:** A Resource's accessible description names only the keyboard commands the canvas offers it at that moment.

**Why:** `SpaceCanvas` passes React Flow one fixed `ARIA_LABEL_CONFIG` (`packages/app/src/components/SpaceCanvas.tsx:106-113`, passed at `:1598`). React Flow 12.11.2 renders one hidden description element per React Flow instance and points every focusable node's `aria-describedby` at it, so every Resource on the canvas, including those of embedded Maps drawn in the same instance, is told it can be opened with Enter or Space, removed with Backspace or Delete, and moved with the arrow keys. The canvas withdraws some of those commands from a Resource that can still be focused:

- **A running embedded Map edit** (an Open Space Resource in Edit; blur ends nothing, ADR 0064): the root canvas loses `authorOnCanvas` (`packages/app/src/authoring-availability.ts:390`), so Open (`SpaceCanvas.tsx:771`) and delete (`SpaceCanvas.tsx:1189`) do nothing on a root Resource, while move is still offered, because `dragNodes` is `editable && !presenting` (`authoring-availability.ts:421`).
- **A running Markdown body edit** (blur ends nothing, ADR 0064): Open (`SpaceCanvas.tsx:758`, `:771`) and delete (`SpaceCanvas.tsx:1189`, `bodyEditing`) do nothing on any other focused Resource, while move is still offered.
- **An Ur Resource**: it is never Open (ADR 0122, `open-requires-content`), yet it is told Enter or Space opens it.

Because the description element is per instance, describing one Resource differently from another needs a per-node `aria-describedby`, which React Flow lets `node.domAttributes` override (it is spread after React Flow's own `aria-describedby` on the node wrapper).

Found by the `/code-review medium` of PR #349; it predates that PR, which removed only the pending-placement variant no node could carry (`fe1f1c54`).

**Acceptance criteria:**

- [ ] While an embedded Map edit is running, a focused root Resource's accessible description names neither Open nor delete, and still names move.
- [ ] While a Markdown body edit is running, another focused Resource's description names neither Open nor delete, and still names move.
- [ ] A focused Ur Resource's description does not name Open; it names delete and move where those are offered.
- [ ] Where every command is offered, the description is unchanged.
- [ ] The description is derived from the same availability the keyboard handlers read (`authorOnCanvas`, the occurrence's `bodyEditing`, `dragNodes`, the Resource's kind), not decided separately, and a component test in the node environment holds each case above.

## Comments

### Triage, 2026-10-09

> *This was generated by AI during triage.*

**Category:** bug. **State:** ready-for-agent.

The defect is real, but the original criteria named states in which no Resource can be focused, so they were dropped. A node under an inert or read-only policy is `focusable: false` (`packages/app/src/map-surface-policy.ts:73`) and the root canvas's policy is always `'authoring'` (`packages/app/src/compose-app.ts:244`). While presenting, `nodesFocusable` is `selectNodes = !presenting` (`authoring-availability.ts:422`) and the Stage covers the canvas (ADR 0123). A chrome rename is also left out: focusing a Resource blurs the rename field, which commits a valid draft (ADR 0065), and a refused draft takes focus back. The Why and acceptance criteria were rewritten around the reachable states: an embedded Map edit, a Markdown body edit, and an Ur Resource. They also record that React Flow's description is one per instance, so per-node variance needs a per-node `aria-describedby` through `node.domAttributes`. The criteria are testable; the description's exact wording is left to the implementer. Whether move should itself be withdrawn during those edits is a separate question and out of scope here.
