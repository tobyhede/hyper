# A multi-Space Edit is judged against what it commits

Status: resolved
Tags: Improvement
Blocked by: None — can start immediately.

Surfaced by: the 17 September 2026 architecture review of the database-persistence branch, candidate 3, then settled by a grilling loop and recorded as ADR 0095 (refining ADR 0076). Candidate 1 of the same review was rejected as ADR 0094.

## The defect

`runSpaceThingCoordination` (`packages/persistence/src/session-registry.ts`) derives and pre-checks a coordinated Space Thing lifecycle Edit against a candidate that overlays **every** open Space's working Space on the stored aggregate (`:468-473`; again at `:944-947` in `deleteContext` and `:1161-1166` in `delete`), and checks it with `loadSpaceAggregate` directly (`:487`). The commit carries only the participants (`:630-655`), and the repository judges it with `decideCommit` against storage. The barrier waits for in-flight commits only: `waitForIdle` is `!inFlight && !coordinating` (`session.ts:416`), and queued work (`waiting`) is untouched.

Reachable in one tab over HTTP:

- **Link to local-only content.** Space T's newest Graph is still queued local work (behind the barrier's pause) or T is `failed`. Linking M→T reads T's working Space for the selection (`workingTargetSelection`, `:811-816`), picks that Graph, passes the pre-check, answers `completed`, and the repository refuses it as `space-thing-graph-missing`; M becomes `rejected`.
- **Delete after a transient failure.** X is referenced from M and N. Deleting M's Space Thing fails transiently, leaving M `failed` with a working Space that no longer references X. Deleting N's Space Thing counts X's inbound references over working Spaces, cascades through X, passes the pre-check, and the repository answers `conflict` because stored M still references X.

Latent (memory backend only): the pre-check lacks `decideCommit`'s `baselineUnreferenced` forgiveness. A real repository refuses to load such a baseline, so the browser answers `persistence-read-failed` first.

`delete` and `deleteContext` also read `backend.loadAggregate()` inside `derive` (`:934`, `:1145`) and the coordination reads it again (`:459`) — two aggregate reads per turn with a gap between them.

## Decided

**Simplified after a second review (18 September 2026) — see the section by that name below.** The barrier no longer waits for queued work at all: it raises immediately (`persistenceBarrier = true`, `pausePersistence` on every session) and then waits only for commits already in flight, exactly as ADR 0076 had it before this ticket. Local work still queued when the barrier raises stays queued for after the turn. The rest stands:

- One `backend.loadAggregate()` per turn. `derive` and the pre-check use the same view: stored Spaces, with participants read as their working Spaces. Spaces the Edit does not change are read as stored, including the link target's selection and every reference count a deletion cascade takes.
- The pre-check is `decideCommit` over that view, and it acts only on `aggregate-refused` — a `conflict` verdict is not shortcut; `backend.commit` still runs, and the repository's own answer carries the current state.
- A link whose target is `failed` or `conflicted` refuses as `persistence-recovery-required` for the target, like the containing Space. One rule covers a Space Thing deletion and a Diagram/Graph deletion alike: a non-participant Space that needs recovery refuses the Edit as `persistence-recovery-required`, naming itself, when — in either its stored snapshot or its working Space — it references a Space the deletion would remove, or selects the Diagram or Graph being deleted. Neither reading alone is enough: a `failed` edit that added the reference or selection has not reached storage, and one that removed it has not left storage either. A `rejected` Space does not refuse it — its work is already permanently refused.
- Unchanged from ADR 0076: `rejected` Spaces may participate, the persistence outcome is shared by all participants, and the operation answers `completed` once installed.

Rejected, and recorded in ADR 0095: committing every divergent open Space as a participant; refusing whenever any open Space needs recovery; waiting only for the Spaces the Edit touches; waiting for queued local work to commit before deriving the Edit (tried, then undone — see below).

### Review findings (18 September 2026)

A code review of the above found three defects, resolved as follows. Two of them changed what ADR 0097 had already decided — the barrier's wait, and the one recovery rule for both cascades — so they are recorded in **ADR 0099**, refining 0097, rather than edited into an accepted ADR's body (`docs/agents/workflow.md`: an accepted ADR takes no edit but its status line):

- [x] **Fix 1 (high, data loss).** `delete`'s cascade counted inbound references over stored Spaces only, so a non-participant Space that needs recovery and whose *working* Space still references a Space the cascade would delete was not protected — the cascade deleted the Space out from under that Space's own eventual retry. Now refuses as `persistence-recovery-required`, naming the Space that needs recovery, before anything is installed. — `refuses a cascading deletion that would delete a target a failed sibling still references in its working Space` (`packages/persistence/test/space-thing-lifecycle.test.ts`), replacing `does not let an uncommitted sibling reference save a target from a cascading deletion`, which had asserted the cascade running through in exactly this case.
- [x] **Fix 2 (medium).** Same defect in `deleteContext`: the `affected` scan reading stored Spaces only missed a non-participant Space that needs recovery whose *working* Space selects the Diagram or Graph being deleted. Now refuses the same way. — `refuses to delete a Graph a failed sibling still selects only in its working Space` (`packages/persistence/test/session-registry.test.ts`).
- [x] **Fix 3 (medium, starvation).** The barrier's drain loop required every open session to be *simultaneously* idle with nothing queued, rechecked from scratch whenever any single session missed that instant — continuous editing on any open Space, even ordinarily paced, could keep missing it forever, blocking every Space Thing operation. Replaced with: wait for queued work to drain once, raise the barrier (`pausePersistence` on every session), then wait for whatever is still in flight — bounded, since pausing stops a completed commit from chaining into a further one; work submitted after the barrier is up stays queued for after the turn (ADR 0076). — `completes a coordinated operation while an unrelated Space keeps submitting new Edits` (`packages/persistence/test/space-thing-lifecycle.test.ts`), driven deterministically through `MemorySpaceBackendTestControl.deferNextCommit`.

Also corrected: the `isRetry` parameter's doc comment claimed a retry skips both the aggregate read and the pre-check; it skips only `decideCommit` — `loadAggregate` still runs and a read failure still answers `persistence-read-failed` on a retry.

### Simplified further, after a second review (18 September 2026)

A second code review found the shape above — Fix 3's two-phase drain, and Fix 1/Fix 2 as two separate directional scans — over-built. Resolved as follows:

- [x] **The drain (Fix 3) is removed entirely, not bounded.** `runSpaceThingCoordination` goes back to raising the barrier first (`persistenceBarrier = true`, `pausePersistence` on every session) and then waiting only for commits already in flight, exactly as it did before this ticket (ADR 0076). Reason: the drain never made the pre-check *correct* — the pre-check reads stored state either way, drain or not — and it was still unbounded in the general case: a session that keeps chaining queued commits, however ordinarily paced, never reports idle, which hangs every Space Thing operation. Local work queued when the barrier goes up now stays queued for after the turn, plainly. The starvation test written for the bounded drain (`completes a coordinated operation while an unrelated Space keeps submitting new Edits`) is deleted along with it, and so is the regression test the *original* "wait for queued work" decision needed (`accepts a link once a target Space commits its newest queued local Graph`) — its scenario is no longer correct behaviour. Its replacement, `links against a target Space's stored selection, not a Graph still queued behind an in-flight commit`, asserts the reverted behaviour: a link takes the target's *stored* selection, so a Graph added moments earlier becomes selectable only once its own commit lands, on a later turn.
- [x] **Fix 1 and Fix 2 are replaced by one rule.** Both were the same defect checked twice, in one direction each (`delete`'s cascade checked only a non-participant's *working* Space; `deleteContext`'s parallel scan did the same). The new `recoveryBlockedBy` helper checks both directions uniformly for either operation: a non-participant session that needs recovery blocks the deletion when — in either its stored snapshot or its working Space — it references a Space the deletion would remove, or selects the Diagram or Graph being deleted. No direction comparison, no counting the cascade twice; `recoveryRefusal`'s existing refusal shape and code are reused, and no new refusal code is added. Tests: the "add" direction (working has it, storage doesn't) is `delete`'s existing `refuses a cascading deletion that would delete a target a failed sibling still references in its working Space` and `deleteContext`'s existing `refuses to delete a Graph a failed sibling selects only in its working Space`; the "remove" direction (storage has it, a failed local edit moved working away) is newly tested by `refuses to delete a Graph a failed sibling still selects in storage`; and `does not refuse an ordinary deletion because an unrelated Space needs recovery` keeps proving a `failed` Space with no bearing on the deletion never blocks it.
- [x] **`deleteContext`'s recovery check now runs to completion before anything is opened.** The old single loop checked one participant's recovery and opened its session in the same pass, so a refusal reached partway through the set could still leave an earlier participant's session freshly opened in the registry. The check over the whole participant set — including the new shared rule — now completes first; only then are sessions opened for whichever participants still need one. Proven by `opens no session for an earlier stored participant when a later one needs recovery`.
- [x] **The pre-check's `conflict` shortcut is removed.** `decideCommit`'s pre-check now acts only on `aggregate-refused` (the unreachable `rejected` throw is unchanged); a `conflict` verdict no longer substitutes for the real `backend.commit()` call — the repository is always asked, and its own answer carries the current state a conflict names. `keeps a colliding created Space by retrying it as an update` reverts to asserting two backend requests, not one.
- [x] **`SpaceThingLifecycleChange`'s `update.edit` is documented as repeatable.** `backendChange` (building the pre-check's request) and `prepareCoordinatedCommit` (applying it to the session) each call `edit` once per turn, so it must be pure and must mint no identity of its own — two calls would otherwise mint two different ids for what has to be the same logical change. This was already true of every `edit` closure in this module; only the doc comment changed.

## Answer

Implemented in `packages/persistence/src/session-registry.ts`; tests in `packages/persistence/test/space-thing-lifecycle.test.ts`. `session.ts` and `commit-decision.ts` needed no changes — `decideCommit` is reused as-is, and the existing `waitForIdle`/`hasQueuedWork`/`pausePersistence`/`resumePersistence` primitives on `ManagedSpaceSession` were already sufficient once `runSpaceThingCoordination` called them in the right order.

**The barrier (item 1).** `pausePersistence` moved from before the wait to after it: a session that is idle the instant it is paused never gets the `resumePersistence` call that would start its queued commit, so pausing before waiting strands exactly the queued work item 1 exists to drain. Left unpaused, a session's own `submit`/`startCommit` chaining (`session.ts`) already drains a whole queue on its own — an in-flight commit whose completion finds further queued work starts it immediately, without an idle gap in between — so a single `Promise.all(sessions.map(waitForIdle))` waits out a whole chain, however many rounds that takes, and needs no recheck: each session's own promise resolves independently of every other session's, so the wait does not also require them to land on the same instant.

**Revised by the review (Fix 3).** The first shape of this answer re-checked, after that wait resolved, that every session was *simultaneously* idle with nothing queued in one synchronous instant, and restarted the whole wait for every session whenever a single one missed it. Continuous editing on any open Space, even ordinarily paced and spread across more than one Space, can keep missing that instant indefinitely — there is always some tiny gap in which the next edit lands before the recheck runs — starving every Space Thing operation. Fixed by dropping the recheck entirely: wait once, raise the barrier immediately afterward (`persistenceBarrier = true` and `pausePersistence` on every session), then wait once more for whatever is still in flight. That second wait is bounded to at most one more commit per session, because pausing already took effect before it started: a commit that completes with further queued work now settles to idle instead of chaining into the next one, so an edit submitted from here on simply waits for the next turn (ADR 0076) rather than extending this one. Proven by `completes a coordinated operation while an unrelated Space keeps submitting new Edits`, which drives a second, unrelated Space through several rounds of local editing — via `MemorySpaceBackendTestControl.deferNextCommit`, entirely under test control, no real timers — while a genuinely slow Space is what the coordination is actually waiting on, and asserts the coordinated commit lands before that unrelated Space's still-queued edit does.

**Undone by a second review.** Bounding the drain fixed the starvation defect without answering the reviewer's more basic question: what does draining queued work buy, given the pre-check already reads stored state regardless of whether that work has landed? Nothing — the pre-check was never judging the drained work either way, only whatever had *already committed* by the time the barrier's wait resolved, so the drain's only effect was to make more local work commit sooner, at the cost of the whole two-phase mechanism this section describes. `runSpaceThingCoordination` now raises the barrier first and waits only for what is already in flight, as ADR 0076 had it, and the starvation test above is deleted with it — there is no drain left to starve.

**One aggregate read (item 2).** `runSpaceThingCoordination` loads the aggregate once, before calling `derive`, and passes it in as `derive`'s first parameter. `delete` and `deleteContext` no longer call `backend.loadAggregate()` themselves.

**One deviation this surfaced, not asked for by the ticket: a second write mid-`derive`.** `link`'s target initialization (`workingTargetSelection` → `loadWorkingSpace`) commits to the backend *after* the turn's one aggregate read, whenever the target is diagramless. Judging the pre-check against the stale (pre-initialization) view refused the very Diagram that commit had just minted, with `space-thing-diagram-missing` — a real, deterministic failure on the two existing tests exercising target initialization, not a residual race. Fixed by threading a second `derive` parameter, `patchStored(loaded: LoadedSpace): void`, that records a Space's freshly committed content against the turn's one read; `workingTargetSelection` calls it once, after `loadWorkingSpace` returns, and the pre-check reads from the patched map rather than the raw `aggregate.spaces`. `create` and `delete`/`deleteContext` ignore the parameter — only `link` causes a write of this kind.

**The view (item 3).** The containing Space is read as its edited working Space; the link target's selection and every Space a deletion cascade counts references in are read as stored (this turn's one aggregate), never from a live session's working Space, `failed`/`conflicted`/`rejected` or not.

**A second deviation, found via an existing test rather than invented: reference counting cannot use a live session's working Space at all, in either direction.** The existing test `keeps a target referenced by an uncommitted sibling session` relied on exactly the pattern this ticket removes — a sibling's *uncommitted* local addition of a reference protecting a target from a sibling delete's cascade. Once reference counting reads stored only, `decideCommit`'s own `ordinary-space-unreferenced` check refuses committing a candidate that would leave the target unreferenced *regardless* of what this registry's own cascade decided — an uncommitted reference cannot rescue a target from that check any more than an uncommitted removal (the ticket's own delete-after-transient-failure scenario) can protect one from it. There is no reading of "reference count" that satisfies both an uncommitted-removal case and an uncommitted-addition case without reintroducing the working-candidate pattern ADR 0095 rejects. I renamed and reversed that test to `does not let an uncommitted sibling reference save a target from a cascading deletion`, asserting the target was cascaded away.

**Superseded by Fix 1.** That reversed test named a real defect after all, just not one reference counting can fix: the sibling in it is `failed`, and cascading Target away destroys the very Space that sibling's own retry still points at. Reading stored state settles what the *cascade* counts; it does not settle whether the *whole deletion* should be allowed to proceed past a sibling that needs recovery and still depends on what it is about to delete. Fixed at that separate point instead — a check, after the cascade's closure is known, over every non-participant session that needs recovery — and the test renamed again and reversed a second time: `refuses a cascading deletion that would delete a target a failed sibling still references in its working Space`, asserting the deletion refused rather than either saving Target or sinking it.

**Fix 2 is the same rule for `deleteContext`.** Its `affected` scan reads stored Spaces only, for the same reason `delete`'s reference counting does (this same "cannot use a live session's working Space" argument), so a `failed`/`conflicted` sibling whose *working* Space still selects the Diagram or Graph being deleted is invisible to it, is not relocated, and its own eventual retry is refused with `space-thing-diagram-missing`/`space-thing-graph-missing` forever. The same check, generalized: after `participantIds` is known, every non-participant session that needs recovery is checked against its own working Space's selections, not `affected`'s stored ones. — `refuses to delete a Graph a failed sibling still selects only in its working Space` (`packages/persistence/test/session-registry.test.ts`).

**Unified by a second review.** Fix 1 and Fix 2 were the same rule written twice, and each checked only one direction — a non-participant's *working* Space. A `failed` sibling can equally leave the reference or selection sitting only in *storage*, if the local edit that would have moved it away is what failed to commit; neither `delete`'s cascade nor `deleteContext`'s `affected` scan can see that either, for the identical "cannot use a live session's working Space to decide what storage holds" reason. Both scans are replaced by one `recoveryBlockedBy` helper, checked against both a non-participant's stored snapshot and its working Space, called once from `delete` and once from `deleteContext`. `refuses to delete a Graph a failed sibling still selects only in its working Space` and `refuses a cascading deletion that would delete a target a failed sibling still references in its working Space` keep proving the direction Fix 1/2 found; `refuses to delete a Graph a failed sibling still selects in storage` is the new test for the direction this review added.

**Also moved: `deleteContext`'s recovery check now completes before any participant is opened.** The single loop that used to check one participant's recovery and open its session in the same pass could leave an earlier, cleared participant's session open behind a later participant's refusal. The full check — structural (`participantIds`) and the shared rule together — now runs first; opening happens in a separate pass afterward, only for whichever participants still need a session. `opens no session for an earlier stored participant when a later one needs recovery` proves it.

**The pre-check (item 4).** `decideCommit({ changes: backendChanges }, aggregate.metaSpaceId, stored)` runs once `backendChanges` — the exact `SpaceCommit` this turn will send — is built, sorted the way `MemorySpaceBackend.commit` itself sorts `stored` before calling `decideCommit`. Its three `answer` outcomes map as:
  - `aggregate-refused` → `SpaceThingRefusal.aggregate-refused`, unchanged from before (ticket-mandated).
  - `conflict` → reused as the actual `CommitResult` for this turn, skipping the real `backend.commit()` call entirely: local install (`prepareCoordinatedCommit`/`publishCoordinatedCommit`/`installed()`) still runs as normal — the operation still answers `completed` once installed, per ADR 0076 — and the pre-check's own `conflicts` then flow through the *existing*, unmodified post-commit `result.kind === 'conflict'` handling. This reuses 100% of the existing conflict/recovery machinery and adds no new state or refusal code; it only avoids a network round trip for a conflict the pre-check has already, definitively decided. Verified indirectly: `keeps a colliding created Space by retrying it as an update` (a real, unmocked 'create' id collision) now completes in one backend request instead of two, because the pre-check catches the collision before the wasted first attempt — I updated that test's request-count assertions accordingly, with a comment explaining why.
  - `rejected` (a malformed commit request, or no Meta) → this registry's own duplicate-naming check and `backendChange`'s construction already guarantee a well-formed, self-consistent request, and `aggregate.metaSpaceId` is always defined once `loadAggregate` answers `loaded`, so this arm is unreachable through this registry. It throws (an internal invariant violation, the same pattern already used a few lines above for a repeated Space id) rather than inventing a `SpaceThingRefusal` code for a case that cannot fire from a request this module builds.

**The `conflict` shortcut is removed, by the second review.** Skipping `backend.commit()` for a pre-checked `conflict` saved one network round trip, at the cost of trusting the pre-check's verdict to stand in for the repository's own — an assumption this simplification pass chose not to keep. `decideCommit`'s pre-check now acts only on `aggregate-refused`; every `conflict` and every `write` verdict reaches `backend.commit()` as normal, and the repository's answer, not the pre-check's guess at it, is what the existing conflict handling below resolves. `keeps a colliding created Space by retrying it as an update` reverts to asserting two backend requests.

**Retries skip the pre-check — not the read.** `recovery.retry`/`keepLocal` re-invoke `runSpaceThingCoordination` with a new `isRetry` flag, which skips only `decideCommit`; `loadAggregate` still runs on a retry, the barrier still waits, and a read failure still answers `persistence-read-failed`, exactly as a fresh turn does. (The doc comment on `isRetry` originally claimed the read was skipped too — corrected during the review, since it was never true of the code.) A retry's `derive` returns `identityChange`d copies of an already-derived, already-pre-checked change set — nothing the pre-check exists to catch — and running it anyway broke three existing conflict-recovery tests: `MemorySpaceBackendTestControl.queueResult` lets a test inject a `conflict`/failure answer without writing it into the backend's own stored copy, so a fresh `loadAggregate` on retry read the original (never-actually-changed) revision back and manufactured a conflict of its own, purely a test-double artifact. The real backend already re-validates every commit, retry or not (ADR 0093), so skipping this turn's redundant pre-check on a retry loses no safety the ticket adds, and reopens none of the two named bug scenarios (neither re-derives a target selection or a reference count — a retry only resubmits).

**Item 5** is folded into `link`: after the diagram-not-found check and before `workingTargetSelection`, `recoveryRefusal(input.targetSpaceId)` is checked and reused verbatim (it already carries the right `spaceId`), refusing as `persistence-recovery-required` naming the target and initializing nothing, before the existing "must not initialize a Space an already-refused Edit pointed at" ordering.
