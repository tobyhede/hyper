# 08 — Settle the problem-details decode boundary

**What to build:** Decide whether the five assertions in `packages/persistence/src/http-protocol.ts` are defects to remove or an honest parse boundary to except, and act on the answer.

**Status:** ready-for-agent

**Why:** Under ADR 0062 these sites are in the suppressions baseline and are not blocking anything. What keeps this ticket alive is not the lint rule but a specific smell in the code, which the rule happened to point at.

The sites, measured at `46a0b147` (`eslint-suppressions.json` still records 5 for this file):

- `code as HyperProblemCode` (line 124) — `Object.entries` widening `problemCatalogue`'s own keys while building `problemCodeByType`
- `value as Record<string, unknown>` (line 158) — in `decodeProblemDetails`, after the non-null, non-array object check
- `record['type'] as HyperProblemType` (lines 168, 174)
- `value as Record<string, unknown>` (line 210) — in `exactRecord`, after the same object check

Only lines 168 and 174 are the smell this ticket is about: they assert a domain literal type in order to run the lookup that would prove it. A lookup typed `ReadonlyMap<string, HyperProblemCode>` (returning `HyperProblemCode | undefined` for any string) removes both with no exception. Lines 124, 158 and 210 are a different kind — a key-widening by `Object.entries` and two object-to-record narrowings already justified by the check above them — and are out of scope unless the same change removes them for free.

ADR 0057 makes this module the one place an RFC 9457 envelope is decoded into `CommitResult`. That is by definition the boundary where an untrusted representation becomes a domain value — the place where `unknown` is *supposed* to appear and where a checked narrowing is the honest operation, not a lie.

**The question:** is the current code actually doing the checking it asserts? Line 168 checks membership in `problemCodeByType` — but it asserts the type *before* the check that would justify it, which is `no-widen-then-assert` territory in spirit. A decoder that asserts its way to a domain value has the same hole as any other assertion; a decoder that validates and then returns the narrowed value has none.

- [ ] Read the module against ADR 0057 and `docs/agents/http.md` before choosing.
- [ ] Preferred outcome: a real parse — the module already owns the closed sets (`problemCodeByType`), so a lookup typed `ReadonlyMap<string, HyperProblemCode>` returning `HyperProblemCode | undefined` proves what the assertions at lines 168 and 174 currently claim, with no exception needed. `eslint-suppressions.json`'s count for `packages/persistence/src/http-protocol.ts` falls from 5 to at most 3, regenerated by `--prune-suppressions`, never hand-edited.
- [ ] If the parse is not an improvement, leave the sites as they are — they are already recorded and commented. An exception argued in a config file is worse than a documented assertion in the code, which is one of the reasons ADR 0062 rejected the full cleanup.
- [ ] Whichever way it goes, the decoder's contract tests must still assert problem types and decoding, per ADR 0057.
- [ ] Check locally, aimed at the change (`pnpm typecheck`, `pnpm typecheck:packages`, `pnpm exec eslint packages/persistence/src/http-protocol.ts`, `pnpm exec vitest run packages/persistence/test/http-protocol.test.ts`), then open a draft PR and report the `CI passed` result with each job behind it, per AGENTS.md "Before claiming done".
