# 06 — Diagram and Graph deletion decide their successor after their last wait

Status: done
Blocked by: 04

**What to build:** Move the registry's `deleteDiagram` and `deleteGraph` onto the coordination's `prepare`/`plan` shape, so the successor Diagram or Graph and every Space Thing reference rewrite are chosen from the Spaces as they stand after the last wait. Their rules stay in the registry. See `../spec.md`, "Coordinated operations decide after their last wait".

**Why:** Both choose a replacement in `derive` and apply it blindly later. If the replacement is removed during the wait, the edits point `activeGraph`, `defaultDiagram` and referencing Space Things at an id that no longer exists, and the author is told only `aggregate-refused`.

## Red first

- [x] **Graph deletion re-chooses a replacement Graph when its preferred one goes during the wait**, rather than refusing or committing a dangling `activeGraph`. Removing the preferred replacement Graph is possible from outside the lifecycle turn — an ordinary `session.submit()` on the *target*'s own live session, the same shape ticket 05 used for a deleted Diagram — so the test is not struck. See Comments for why the domain answer is "re-chooses", not "refuses" as this line originally assumed, and for how red was proven despite that.
- [x] **Diagram deletion re-chooses the same way**, under the same caveat.

## Build

- [x] Both operations compute successor, keep-last and reference rewrites inside `plan`, against the Spaces the coordination's own aggregate read produced; `prepare` holds only the recovery early-exit and (as an optimisation only, re-asked in `plan`) the target's own live-session "is this even a deletion candidate" check.
- [x] No new refusal code was needed — see Comments.
- [x] Successor and keep-last rules are not moved out of the registry (spec, Out of scope).

## Done when

- [x] The red tests pass; existing context-deletion tests stay green.
- [x] `pnpm verify` is green. `pnpm e2e` is deferred to run once after tickets 04–07 land together, per the coordinator's standing instruction for this series (see tickets 04/05).

## Comments

- **The domain answer is "re-chooses", not "refuses" — and for `deleteContext` no state exists that isn't one of "another candidate is still available" or "none is" (already `unchanged`, keep-last).** `plan` now recomputes `replacementDiagram`/`replacementGraph` from the Spaces the coordination's one aggregate read produced, exactly the same way it computes them the first time: preferred-if-still-present, else the first remaining candidate other than the one being deleted. If the previously-preferred one vanished during the wait, that computation simply lands on a different (still-valid) candidate — a genuine re-choice, not a refusal — and if *no* other candidate remains either, the pre-existing keep-last guard (`(target.document.diagrams?.length ?? 0) <= 1`, or the equivalent Graph check) already answers `unchanged` before a successor is even sought. There is no third state a freshly-read snapshot can present that isn't one of those two, so `SpaceThingRefusal` gained no new arm and `describeSpaceThingRefusal`/`space-thing-context-commands.ts` needed no new wording.
- **Established first, per the ticket's own caveat: yes, something outside the lifecycle turn can remove the chosen replacement during the wait.** Same mechanism ticket 05 documented for a deleted containing Diagram: an ordinary `session.submit()` on the *target*'s own live session — the coordination pauses persistence but not a session's local `submit`, which installs the working snapshot synchronously (ADR 0030), and `plan` reads `managed.session.getState().working` (via the coordination's merged candidate map) fresh, after the coordination's one `backend.loadAggregate()` await. Both red tests inject exactly this, on the mocked `backend.loadAggregate`'s first (and, post-refactor, only) call, matching tickets 04/05's shape.
- **Proving red — domain assertion, not read-count, established by a deliberate second injection point beyond the one the shipped tests use.** At the *natural* injection point (`reads === 1`, the coordination's one real wait for both old and new code), the domain assertion (`deleteGraph`/`deleteDiagram` resolving to `{completed, diagramId, graphId: <the re-chosen id>}`) **already passes against the pre-ticket-06 `derive`-shaped code**, confirmed by reverting only `session-registry.ts` to `62a95b09` (ticket 05's commit) and running both new tests: only `expect(reads).toBe(1)` failed (`expected 2 to be 1`), because old `deleteContext`'s own `derive` does its own internal aggregate read and, at this exact point, its in-`derive` merge of `aggregate.spaces` with every live session's `working` state already sees the injected removal too — so old code's *decision* is coincidentally already correct here, and only the redundant second read (`loadCoordinationCandidate`, called after `derive` returns) distinguishes it. This is the same limitation ticket 04's Comments recorded for its own read-count-discriminated test, and it recurs here for the same structural reason (a `derive`-shaped body's own first read already reflects a live-session mutation injected at that read). To find a genuine domain-level split, I additionally (temporarily, not committed — see below) gated the same injection on `reads === 2` instead of `reads === 1`: old code's `derive` then makes its decision (baking in the still-present preferred Graph's id) **before** the removal happens, and the removal lands only during `loadCoordinationCandidate`'s later, redundant second read — so the stale id is applied at commit time against a snapshot that no longer contains it, and intake refuses it: `{kind:'refused', refusal:{code:'aggregate-refused', errors:[{kind:'invalid-space-snapshot', errors:[{kind:'diagram-active-graph-missing', ref:<the removed id>, ...}]}]}}`, reads=2 — reproduced by running the gated scenario against the reverted `62a95b09` source. Against the ticket-06 `plan`-shaped code, the same `reads === 2` gate never fires at all (new code makes exactly one read), so the coordination sees the *original*, unmodified target and simply completes with the originally-preferred id, reads=1 — a genuine `refused`/`aggregate-refused` vs. `completed` split, proving the underlying defect (a decision baked in before a since-eliminated second read) is real and is what ticket 06 removes. This confirmatory scenario was not kept as a committed test: for the fixed code it does not exercise "re-choice" at all (nothing is ever removed from its point of view, since there is no second read left to land a change in) — it would only pin a historical bug shape that can no longer occur by construction. The two committed tests (gated on `reads === 1`, the shape both old and new code actually reach) are the ones that exercise `plan`'s live re-choice logic today, and are the ones the "Done when" red-then-green requirement is proven against; their old-vs-new discrimination is the read-count, exactly as ticket 04 already established and documented for this same coordination pattern, re-verified independently for this ticket rather than assumed.
- **The eventual settled/stored value is not what the two committed tests assert on, and that is deliberate, not a gap.** Because the injected removal and the coordinated successor-choice edit both land on the *same* session (the target's — a Diagram/Graph's own document, unlike ticket 04/05's cross-Space cascades), the target session ends up with a plain queued Edit (`waiting`, `packages/persistence/src/session.ts`) *and* a coordinated commit. `session.ts`'s `acknowledgeCoordinatedCommit`/`resumePersistence` replay that queued `waiting` snapshot — captured *before* the coordinated edit ran — over the coordinated commit once the barrier lifts, silently reverting the coordinated portion (confirmed by reproducing it: `backend.loadSpace` after settling showed the deleted Graph back, only the independently-injected removal surviving). This is a genuine, pre-existing interaction between a plain queued Edit and a coordinated commit sharing one session, in `session.ts`, unrelated to and out of scope for this ticket (which only touches `session-registry.ts`'s `deleteContext`). The two committed tests instead assert on `targetSession.getState().working` read synchronously the moment `deleteGraph`/`deleteDiagram`'s own promise resolves — which `prepareCoordinatedCommit`'s `observable.install` sets before the async backend round trip begins (ADR 0030) — so they prove `plan`'s decision without depending on that separate, later interaction. Worth flagging for whoever eventually looks at `session.ts`'s coordinated-commit/`waiting` interaction, but not fixed here.
- **`deleteContext`'s `prepare` deliberately does not require the target to already be a live session**, unlike `create`/`link`'s `prepare` (which legitimately need `working(containingSpaceId)` to avoid minting ids/initializing a target for a doomed Edit). `deleteContext` mints nothing and initializes nothing, so there is no wasted work to save by requiring liveness early; `prepare` holds only `recoveryRefusal(targetSpaceId)`, matching `delete`'s (ticket 04) shape, and the "is this even a deletion candidate" check happens once, for real, in `plan`, against the coordination's merged candidate map (aggregate ∪ live sessions) exactly as the pre-ticket-06 code read it — so a target present only in the aggregate (never opened) is handled exactly as before. This is a deliberate difference from `create`/`link`'s `prepare`, not an oversight.
