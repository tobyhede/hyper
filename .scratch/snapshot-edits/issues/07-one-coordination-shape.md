# 07 — The coordination has one shape

Status: done
Blocked by: 05, 06

**What to build:** Delete the coordination's old `derive` shape, the `update` rebase closure and `completedSnapshot`, leaving `prepare`/`plan` as the only way a coordinated lifecycle operation runs. No behaviour changes. See `../spec.md`, "Coordinated operations decide after their last wait".

**Why:** After 04–06 no operation uses the old shape. Leaving it keeps a second way to write an operation that decides before its last wait, which is the defect 04–06 removed.

## Build

- [x] No `derive` path, no `update` change carrying an `edit` closure, and no `completedSnapshot` remain in the registry. Recovery retries (`retry`, `keepLocal`) re-run through the same shape.
- [x] The contract comment on the lifecycle change no longer describes a rebase.

## Comments

- **`SpaceThingCoordinationSource` is gone; `runSpaceThingCoordination` now takes a `SpaceThingCoordinatedOperation` (`{prepare, plan}`) directly** — no discriminant, no `derive` branch. `SpaceThingLifecycleChange`'s `update` arm now carries `snapshot: SpaceSnapshot` (the participant's whole next value) instead of `edit: (current) => SpaceSnapshot`. Every `plan` that used to build an `edit` closure now computes the resulting snapshot once, right there (reusing the `SnapshotEdit.createInDiagram`/`deleteFromSpace` result it already had, instead of calling the operation a second time inside the closure at commit time) — `completedSnapshot` is deleted and its narrow-and-extract check (`if (outcome.kind !== 'completed') throw ...`) is inlined once per call site, immediately after each `SnapshotEdit` call. The generic per-change loop that builds `candidate` (and the `prepareCoordinatedCommit` call) now just reads `change.snapshot` for `update` instead of calling `change.edit(current)`.
- **Recovery now runs entirely through `prepare`/`plan` too.** `startRecovery` still decides synchronously, at the moment `retry`/`keepLocal` fires, exactly which participants become which kind of retried change — that decision logic (`conflictCurrents`, `participants`, `uncommittedCreates`) is unchanged. What changed is the shape it hands to the (single) coordination function: instead of building `SpaceThingLifecycleChange[]` directly (with `update`'s `edit: (current) => current` identity closure, or `edit: (working) => working` for a create-converted-to-update), it now builds `SpaceThingRetryItem[]` — a small local type where `create`/`delete` already carry everything needed (unchanged from before) and `update` names only the `spaceId`. The retried coordination's own `plan(spaces)` resolves each `update` item by reading `spaces.get(spaceId)` — i.e. "commit this Space's current working snapshot" as read by the *retried* coordination's own fresh aggregate read, which is exactly the timing the old `edit: identity` closure ran at (that closure fired inside the retried `runSpaceThingCoordination`'s own per-change loop, itself right after that same aggregate read, with nothing suspending in between). `prepare` for the retry operation does nothing (`Promise.resolve({kind:'proceed'})`) since every decision was already made when `startRecovery` built the retry items.
- **Behavioural equivalence checked, not assumed, for the one place the read source changed.** The old identity-edit closure read `participants.get(spaceId)?.session.getState().working` (the *failed* coordination's own participants map, itself built from `sessions.get`); the new `plan` reads `spaces.get(spaceId)`, where `spaces` is `loadCoordinationCandidate()`'s output for the *retried* coordination, built by iterating the same `sessions` map. Since nothing suspends between the retried coordination's aggregate read and its `plan` call (asserted elsewhere in this file's comments and unchanged by this ticket), and since retry doesn't touch `sessions` in between, the two reads observe the same value. This is exactly what `packages/persistence/test/space-thing-lifecycle.test.ts`'s `retries every participant together with later local work` test exercises and pins: a `meta.submit(...)` made *after* the first (failed) attempt but *before* `target?.retry()` shows up in the retried commit's `update` change (`{document: {title: 'Later local title'}}`), which only holds if the retry reads the participant's *current* working state fresh rather than a value captured earlier.
- Two stale comments (predating this ticket, from tickets 04/05) that said "Inside `derive`" / "after `derive` returns" / "after `derive` has returned" on `workingTargetSelection`'s doc comment were also fixed to say `prepare`, since `link`'s `prepare` is what actually calls it now — ticket 07 asked for "any other comment in the file that mentions the derive shape," and these did. Likewise one stale line in `docs/agents/editing-and-persistence.md` ("Initialization runs inside `derive`...") was updated to `prepare`.
