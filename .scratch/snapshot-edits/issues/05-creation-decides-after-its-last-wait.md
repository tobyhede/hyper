# 05 — Space Thing creation and linking refuse when their Diagram goes during the wait

Status: done
Blocked by: 04

**What to build:** Move Space Thing create and link onto the coordination's `prepare`/`plan` shape, with `SnapshotEdit.createInDiagram` refusing `diagram-not-found` itself. See `../spec.md`, "Coordinated operations decide after their last wait".

**Why:** Both check that the containing Diagram exists in `derive` and never again. `createInDiagram` does not refuse a missing Diagram, so if it is gone when the closure runs, the Thing is added to the Space on no Diagram and the operation reports `completed`.

## Red first

- [x] **Create refuses a Diagram deleted during the wait.** Delete the containing Diagram while the coordination reads the aggregate; creation answers `diagram-not-found` and adds no Thing. First establish whether anything can delete that Diagram outside the lifecycle turn — if nothing can, the test cannot fail: strike it here and record why in Comments. The `createInDiagram` refusal lands either way.
- [x] **Link refuses the same way**, under the same caveat.

## Build

- [x] `SnapshotEdit.createInDiagram` refuses `diagram-not-found`, added to `graph`'s refusal union with a property test: creation into a Diagram the snapshot lacks is always refused and changes nothing.
- [x] Create and link run `createInDiagram` inside `plan`, and map its refusal into `SpaceThingRefusal`. The `derive`-time Diagram checks become early exits in `prepare`.
- [x] Link still refuses a missing Diagram before initializing its target Space or minting any id (ADR 0079); `refuses %s when its containing Diagram is absent` stays green with an empty id source.

## Done when

- [x] The red tests pass or are struck with a reason.
- [x] `pnpm verify` is green. `pnpm e2e` is run because Space Thing creation is canvas-visible. `pnpm e2e:ladle` is not applicable unless a story changes.

## Comments

- **Something outside the lifecycle turn can delete the containing Diagram during the wait: an ordinary `session.submit()` on the containing Space's live session, exactly the shape ticket 04 used for its late Alias.** The coordination pauses persistence (`managed.pausePersistence()`) but does not block a session's local `submit`, which installs the working snapshot synchronously (ADR 0030); the coordination's own `loadCoordinationCandidate` and the later `edit` closures both re-read `managed.session.getState().working` fresh, so a Diagram removed this way during the coordination's one `backend.loadAggregate()` await is what both `plan` and the commit-time `edit` closure see. Both red tests inject exactly this — a `containingSession.submit(...)` filtering the target Diagram out of `document.diagrams` — from inside a mocked `backend.loadAggregate`, on its first (and, post-refactor, only) call.
- **Unlike ticket 04's delete tests, both red tests here are discriminated by the domain outcome itself, not by a read-count assertion.** For `create`, `derive()` is fully synchronous (no `await` in its body), so the old code already made exactly one `backend.loadAggregate()` call before this ticket — the same count the new `prepare`/`plan` shape makes. What differs is what happens once the injected deletion is visible: old `createInDiagram` had no diagram-existence check, so the commit-time `edit` closure (`SnapshotEdit.createInDiagram(current, ...)` where `current` is the live session's post-deletion working state) silently added the new Thing to `things` with no position in any Diagram, and `completedSnapshot` would have accepted that (`outcome.kind === 'completed'`) — except this ticket's graph-level change (`createInDiagram` now refusing `diagram-not-found`) means the SAME old registry code instead hits `completedSnapshot`'s throw: `deletion.kind !== 'completed'` fires with `Error: Space Thing creation through SnapshotEdit answered 'refused'`, thrown from inside the synchronous section between `plan`/`derive` and `backend.commit`, which nothing in `coordinateSpaceThingLifecycle` catches — so the returned Promise **rejects** instead of resolving with a refusal. Confirmed by running both new tests against pre-refactor `session-registry.ts` (only the graph-package change applied, registry unchanged): both failed with `AssertionError: promise rejected "Error: Space Thing creation through SnapshotEdit answered 'refused'" instead of resolving`, at `completedSnapshot` → `Object.edit` → `runSpaceThingCoordination`. Post-refactor, `plan` calls `SnapshotEdit.createInDiagram` against the post-wait Spaces map *before* building the `edit` closure, sees the missing Diagram, and answers `{ kind: 'refused', ... }` directly — no throw, no Thing added, and the injected Diagram-deletion Edit itself still lands once the coordination's barrier lifts (asserted via the same `waitFor`-on-settled pattern ticket 04 used).
- **`SnapshotEditRefusal`'s new `diagram-not-found` arm carries no `diagramId`** (unlike `SpaceThingRefusal`'s and `AuthoringRefusal`'s own `diagram-not-found`, which do), because the caller already has `input.diagramId` in scope and nothing downstream needs the graph package to echo it back — matching `thing-not-found`'s existing shape (no context) rather than inventing a field only ever read at its own call site.
- **`create`/`link`'s `prepare` and `plan` share data through a closure-captured `let`, not a generic `SpaceThingCoordinatedOperation<T>`.** Ticket 04's `delete` never needed `prepare` to hand `plan` anything (its only `prepare` job was the recovery early-exit), so `SpaceThingPreparationOutcome`'s `proceed` arm carries no payload. Generalizing it purely for `create`/`link` would touch `delete`'s shape too for no reason internal to this ticket; instead `prepare` closes over a local `let prepared: {...} | undefined` that `plan` reads back — the same pattern the pre-existing `derive`-shaped bodies already used for `refusal`/`completion`. Inside `plan`, `prepared` is copied to a local `const data` before use so TypeScript's control-flow narrowing survives into the nested `edit` closure (a `let` does not narrow across a closure boundary; a `const` does) — the same reason `delete`'s own `plan` reads `thing`/`source` off `const`s rather than the outer `let`s.
- **`createInDiagram`'s refusal check runs before the `avoidingOverlap` placement step**, so a caller cannot reach `freeAnchor` against an undefined target; `mode === 'avoidingOverlap' ? freeAnchor(...) : position` no longer needs the `target !== undefined` guard the old (silent) version carried, since `target` is proven defined by the earlier `if (target === undefined) return refused` — one line shorter and no behaviour change for the found-Diagram path (verified by the unchanged "never lands avoidingOverlap on a point another Thing already occupies" and "steps a created Space Thing off a point another Thing already occupies" tests, both still green).
- `test/unit/graph-package-surface.test.ts` needed no change: `SnapshotEditRefusal` and `SnapshotEdit` were already listed, and adding a discriminant to an existing exported union type does not add a new exported name.
- `describeSpaceThingRefusal` in `packages/app/src/authoring-refusal.ts` needed no change either: it already has a `diagram-not-found` case (the code already existed on `SpaceThingRefusal` from the old `derive`-time check), and `pnpm --filter @project/app typecheck` passing confirms the switch is still exhaustive.
- `pnpm e2e` deferred: per the coordinator's instruction, it runs once after tickets 04–07 land together, not after each one.
