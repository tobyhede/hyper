# 03 — Rename the Card model to Thing

Status: ready-for-agent
Blocked by: 02

**What to build:** One authored forward migration taking the PostgreSQL model
`Card` to `Thing` and `@@map("cards")` to `things`, with the runtime SQL
identifiers that travel with it and the generated contract artifacts
regenerated rather than swept.

**Why:** ADR 0085: "The PostgreSQL model `Card` becomes `Thing` and
`@@map("cards")` becomes `things`. This is one forward migration; the existing
migration snapshots are history and are not rewritten." This is the half of
change two that change one had no analogue for — Layout was never a table.

- [ ] `src/prisma/contract.prisma` declares `model Thing` with `@@map("things")`
      and `Space.things Thing[]`.
- [ ] One new migration under `migrations/app/`, generated by `pnpm db:migrate`
      from the contract diff, not hand-written and not back-dated into an
      existing directory.
- [ ] `src/prisma/contract.json` and `contract.d.ts` are regenerated with
      `pnpm contract:emit`; `pnpm contract:check` is clean.
- [ ] The 40 existing files under `migrations/app/` are byte-identical to what
      they were before this issue.
- [ ] `src/persistence/postgres-space-repository.ts` speaks the new identifiers,
      including the primary-key-conflict check that names `cards`/`cards_pkey`
      as literal strings.
- [ ] `pnpm test:integration:postgres` and `pnpm e2e:postgres` both pass against
      a **freshly migrated** database, not one that already carries the old
      table.

## Hazards

- **`prisma-next` 0.16.0 has no `renameTable`.** The operation factory exposes
  `createTable`, `dropTable`, `createIndex`, `addForeignKey`, `addColumn`,
  `dropColumn`, `alterColumnType` and friends — the only rename in the whole set
  is `renameRlsPolicy`. So the generated forward migration is a **drop and
  create**, with the index and the foreign key recreated under the new names,
  and it destroys every row in `cards`.

  That is acceptable here and the reason is recorded rather than assumed:
  AGENTS.md states the repo is the only source of state, that development and CI
  are the only environments, and that every database is derived from tracked
  seeds, fixtures and migrations. There is no byte in that table this repository
  cannot mint again. **Confirm the generated operations before committing them**
  — if the diff produces anything other than drop/create for the table, index and
  FK, read why before accepting it.
- **This is the invisible-locally, fatal-on-CI shape.** A local database that has
  already run the old migrations passes whatever the new one does; only a fresh
  one proves it. Neither `pnpm verify`, `pnpm e2e` nor `pnpm e2e:ladle` observes
  any of this — the only two commands that can are the PostgreSQL suites, and
  both are opt-in locally.
- **Running them needs a database**: `.env` from `.env.example` with a password
  and matching `DATABASE_URL`, then `pnpm postgres:up`, then
  `pnpm test:integration:postgres`, then `pnpm e2e:postgres` (it applies no
  migration of its own and needs the database the integration suite has already
  migrated), and always `pnpm postgres:down` afterwards. `docker compose down
  --volumes` is the destructive reset that proves a fresh database.
- **`e2e:postgres` lives in `test/e2e/`, drives the application surface, and is
  broken by chrome changes that nothing else catches.** 02 renames test ids and
  labels; grep `test/e2e/` for them.
- The snapshot files under `migrations/app/*/` contain `end-contract.json` and
  `end-contract.d.ts` that name the old model. Those are history. The new
  migration's own `start-contract` will name `Card` and its `end-contract` will
  name `Thing` — that is correct and is what makes the pair a record of the
  rename.
