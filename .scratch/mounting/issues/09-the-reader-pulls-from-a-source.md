# 09 — The aggregate reader pulls from a source

Status: resolved

ADR 0134 has since replaced the link behaviour this ticket kept: a source lists a link as a link, and the reader refuses one at any path Hyper owns. The link sentences below describe what this ticket built, not what holds now.

**What to build:** the directory reader takes an `AggregateSource` and decides everything a read involves, instead of taking bytes a caller has already chosen and fetched (ADR 0133, refining ADR 0130).

Today each caller lists, asks `scannedAggregatePaths` what to read, reads with its own pool and its own failure policy, and hands `readAggregateFiles` a map, which scans the paths again. The two callers already refuse the same directory differently.

- **`AggregateSource`** in `@project/aggregate`: its name (used in diagnostics as `<name>/<path>`), a listing of one directory (its files and child directories; a missing directory lists empty), a read of one file answering its bytes or the reason it could not be read (never throwing), and the number of reads it allows at once.
- **The reader** reads an aggregate from a source. It lists the root, and refuses a missing `hyper.json` with today's discovery sentence. It then reads and parses `hyper.json` before anything else, so a malformed one stops the read with nothing else read. Next it lists each child directory, the `resources/` of each one holding `space.json`, and `images/`, and reads what today's scan reads, through one pool bounded by the source. Every file that could not be read is collected, and each Space's are reported together as today. A listing that fails stops the read as a discovery failure naming the directory. Id minting, Space ordering, image admission and every existing diagnostic are unchanged.
- **The listing-only scan** is one reader operation over a source, answering the files Import reads, in read order, and the Space directories among them. Export's ownership scan (`scannedAggregateFiles`) and `assertExportableDestination` use it, so `scannedAggregatePaths` and `spaceDirectoryNames` go.
- **Three adapters:**
  - `directorySource` in `src/aggregate-directory/`, the disk at 32 reads at once. It keeps today's link behaviour exactly: a link to a regular file is a file except in `images/`, and `images/` and a `resources/` are listed through a link.
  - `mapSource` in `@project/aggregate`, over bytes already in memory, for Export's read-back and the tests.
  - The mount's interim adapter: `mountAggregate` takes a source, and in this ticket the mounted startup still fetches every blob through today's GitHub source and wraps the result in a `mapSource`. Mount behaviour does not change here; ticket 10 changes it.
- `readAggregateFiles` and `scannedAggregatePaths` leave the package's surface, as do `parseSingleSpace` and `refuseSpaceDocument` if nothing outside it still needs them. `readAggregate(path, newId)` stays as the shell's entry point, if keeping it reads better than inlining `directorySource`.
- Docs that describe today's shape move with the code: `AGENTS.md` and `CLAUDE.md` (the `aggregate` package entry), and `docs/agents/editing-and-persistence.md` (the "pure core" bullet and the Export bullet's `readAggregateFiles` and `scannedAggregateFiles`).

**Out of scope:** the link rule itself (Import vs Export vs Mounting), a shared "establish a fresh store" step for Run and Mount, and the single-Space reader. Each is a separate architecture review candidate.

**Depends on:** nothing.

**Acceptance:**

- `test/unit/read-aggregate.test.ts`'s `READERS` runs every shared case through `directorySource` and `mapSource` over the same files, expecting the same contents or the same diagnostics. Link cases stay disk-only.
- The ordering of reads is pinned by a test: a malformed `hyper.json` reads no other file, and a `mapSource` that records reads shows it.
- A source's bound is honoured: a recording source never sees more reads in flight than it allows.
- Export's read-back, ownership scan and refusal of a misnamed Space directory pass unchanged.
- `pnpm e2e:mount` and the mount unit tests pass unchanged.

## Answer

- **The source.** `AggregateSource` (`packages/aggregate/src/aggregate-source.ts`) is `{ name, concurrency, list(directory), read(path) }`. Paths are relative with `/` between segments, and `''` is the root. `list` answers `{ ok: true, listing: { files, directories } }`, the names directly in the directory, a missing one listing empty, or `{ ok: false, reason }`; `read` answers `{ ok: true, bytes }` or `{ ok: false, reason }`. Neither throws. The answers are tagged rather than `Uint8Array | string` because `anti-slop/no-runtime-typeof` refuses the narrowing a bare union needs.
- **The reader.** `readAggregateFrom(source, newId)` lists the root, refuses one with no `hyper.json` in today's sentence, reads and parses `hyper.json`, and only then lists each child directory but `images/`, the `resources/` of each one holding a `space.json`, and `images/`, whether or not the root lists `images/` as a directory, so a source reaching it through a link still lists it. It reads what it found, in read order, through one pool of `min(concurrency, files)` readers; a concurrency that is not a positive integer is a `RangeError`. A listing that fails is a discovery failure `<name>/<directory>: <reason>`, a failed read of `hyper.json` is the discovery failure it was, and every other unreadable file is reported as before, after its Space's document refusal and beside every other Space's diagnostics. Id minting, ordering, image admission and the diagnostics are the code they were.
- **The scan.** `scanAggregateFrom(source)` answers `{ files, spaceDirectories }` by listing alone, through the private discovery the reader uses. `scannedAggregateFiles` and `assertExportableDestination` are it over a `directorySource`, so `scannedAggregatePaths`, `spaceDirectoryNames`, `listAggregateDirectory` and `directoryExists` are gone: a destination that does not exist lists empty. The GitHub source asks it which blobs to fetch, over a `mapSource` of the tree's paths with empty bytes, and nothing else in that source changed.
- **The adapters.** `directorySource(directory)` (`src/aggregate-directory/directory-source.ts`) reads the disk 32 at once and keeps `isListedFile`'s link rule: a link to a regular file is a file except in `images/`, a child directory is a directory and not a link to one, and `readdir` follows a link when the reader lists `images/` or a `resources/`. `mapSource(name, files)` indexes the paths once, lists a directory by the paths beneath it, and allows every read at once. `readAggregate(path, newId)` stays as the shell's entry point, `readAggregateFrom(directorySource(resolve(path)), newId)`. Export's read-back is `readAggregateFrom(mapSource(destination, files), mintsNothing)`. `mountAggregate` takes `{ source, newId, createObjectUrl }`, and `createMountedStartup` hands it `mapSource(pinned, read.aggregate.files)`.
- **The surface.** `@project/aggregate` adds `readAggregateFrom`, `scanAggregateFrom`, `mapSource` and the types `AggregateScan`, `AggregateSource`, `DirectoryListing`, `SourceListing` and `SourceRead`, and drops `readAggregateFiles`, `scannedAggregatePaths` and `UnreadableFiles`. `AggregateFiles` stays as `mapSource`'s input. `parseSingleSpace` and `refuseSpaceDocument` stay, because `readSingleSpace` calls both.
- **The decision record.** ADR 0130 is merged and accepted, so it is not edited: ADR 0133 refines it, and 0130 carries `Refined by: 0133`.
- **Listing failures are collected.** Every Space directory and `images/` is listed before a failure is raised, and each one that could not be listed is reported together, Space directories in ordinal order and `images/` last. A source allowing no read at once is refused before anything is listed or read.
- **A dangling directory link is unlistable, not absent.** `directorySource` lists a missing directory empty only when nothing is at its path; a `resources/` or `images/` that is a link to nothing is answered as a listing that failed, as the listing it replaces refused it.
- **One difference on disk.** A `hyper.json` that is a directory is now refused as missing, since the root's listing names no such file, rather than as a discovery failure carrying `EISDIR`. Both are discovery failures, and no test held the old sentence.
- **Tests.** `test/unit/read-aggregate.test.ts`'s `READERS` runs every shared case through `readAggregateFrom` over a `directorySource` and over a `mapSource` of every file under the same directory; link cases stay disk-only. The unreadable-file cases wrap a `mapSource` in a source answering a reason for one path. The scan cases run over a `mapSource` of paths, and one holds a `directorySource` scan, a `mapSource` scan and `scannedAggregateFiles` equal over a mixed directory. New cases: a malformed `hyper.json` is the only read a recording source sees; a valid aggregate's reads begin in the scan's order; a source allowing 3 reads never has more in flight, and does have 3; a directory that cannot be listed stops the read, naming it. `packages/app/test/mount.test.tsx` passes a `mapSource`. AGENTS.md's `aggregate` entry (CLAUDE.md is a link to it) and `editing-and-persistence.md`'s reader and Export bullets describe the new shape.
