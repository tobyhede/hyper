# 07 — Map creation through both context adapters

Status: resolved
Blocked by: 06

**What to build:** Move top-level and embedded Map creation behind `MapAuthoringCommands.create`. The asynchronous capability owns creation coordination, live availability rechecking, recovery of the created Map and Active Graph identities, and the embedded context's persistence ordering and durable Space Resource selection. A successful outcome carries those identities; each surface uses them for its own rename continuation.

**Why:** Creation is one Map Edit with two context-specific sequences. Keeping those sequences behind private adapters gives both callers one interface while preserving the rule that caret and focus treatment belong to the surface.

- [x] Top-level creation creates and selects the empty Map and returns its Map and Active Graph identities through the shared interface.
- [x] Embedded creation waits for the required Spaces, durably updates the Space Resource's Map and Graph selection, and returns the same completed outcome shape.
- [x] General availability and current Space state are rechecked at invocation; unavailable is distinct from unchanged and refused.
- [x] Refusals and coordination failures return complete structured Map reports whose lifetime remains with command outcomes.
- [x] The Command Dock and embedded rail request their correctly scoped rename continuations only after a completed outcome; the module imports no continuation, React or DOM treatment.
- [x] The contract suite proves both adapters, and application and Ladle behavior continue to prove the visible command, unavailable treatment and caret continuation.


## Comments

**2026-09-23, resolved.** `pnpm verify` is green: 237 files, 3090 tests passed and 13 skipped. This ticket's agent did not run `pnpm e2e`; the coordinator runs it for the branch. `pnpm e2e:ladle` does not apply, because no `@project/ui` component or story changed.

- **The interface.** `MapAuthoringCommands` gains `create: MapCreate`, where `MapCreate = MapCapability<() => Promise<MapEditOutcome<CreatedMap>>>` and `CreatedMap = { kind: 'completed'; mapId; graphId }`. `create` is a getter, so its `available` is the answer when it is read, as `map(mapId)`'s are. `topLevelMapAuthoringCommands(app, available)` now takes `MapAuthoringAvailability { rename; create }`, because at the top level the two differ: `availability.createMap` is `addResource && chromeTitleEdit`. `embeddedMapAuthoringCommands` takes one `EmbeddedMapAuthoring` object `{ target, spaces, containingSpaceId, select(mapId, graphId), available }`, because creation needs the containing Space and the Space Resource selection write.
- **One sequence, two adapters.** The private `createMap` checks availability, runs the context's `before`, **checks again after that wait**, completes `created-map`, recovers the identities, then runs the context's `after`. The top level has neither hook, so its Edit still lands synchronously on the press. The embedded `before` waits for both Spaces to settle. Its `after` waits for the target to save, writes the Space Resource's selection, and then waits for the containing Space. `space-resource-context-commands.test.ts`'s "persists a new map before the Resource refers to it" still holds the ordering, and the contract suite holds it too.
- **Recovery** reads what `created-map` leaves selected in the composition it ran in, right after the synchronous Edit returns. That is the Map's `activeGraph ?? graphs[0]`, as `createdMapContext` did. `createdMapContext` had no caller left, so it and its three tests are deleted. `coordinatedContextCreate` stays for Graph creation. If recovery finds no Map, or if Space Authoring answers `queued`, the creation throws instead of answering: a queued creation has made nothing yet, so there are no identities to continue at. Through `commandOutcomes.run` that throw reaches the reporter.
- **Reports (concern 2 from 06).** Coordination failures now come back as complete `refused` reports on `map-create`, and each title says what actually happened:
  - "Map not created": an authoring refusal, or Spaces that had not settled before the Edit.
  - "Map not saved": the target did not save the Map it now holds.
  - "Map not selected": the Space Resource refused the selection write, or the containing Space did not save it.
  A **throw** is still a break. It reaches the reporter and draws no sentence, as 06 decided (`broke: null`). Dressing a defect as a refusal is what `CONTEXT.md` forbids, and the Map module has no reporter to tell.
- **Liveness (concern 1 from 06): not made live, and here is why.** Both availability answers are React state computed during App's render (`authoringAvailability` over `editingChromeTitle`, `presenting`, placement and so on). Nothing outside the render holds a later answer. Copying the answer into a ref would only give the same last render under another name. The rail's `!disabled` is a prop in the same way. What *is* live at invocation is the Space state: for the embedded context, whether its target is still the open entry, checked before the wait and again after it (the contract test "creates nothing in an embedded target exited while its Spaces were saving" fails if the second check is removed). For rename, whether the Map still exists and is still selected.
- **Surfaces.** The Dock runs `commandOutcomes.run('map-create', () => mapAuthoring.create.invoke())`, draws `createDisabled` from `mapAuthoring.create.available`, and requests its `map-name` continuation only on `completed`. The rail does the same with its scoped continuation (`subject: outcome.mapId`). **The continuation is now requested one promise later than the press.** The Edit still lands synchronously, so three `SpaceApp` tests that read the new name editor synchronously after the click now `findByRole` it and wait for its focus. All pass, and the focus-restore rule (`didCreateMoveCaret`) is unchanged.
- **`createMapRefusal` is deleted from App**, along with its `ShellNotice` and its line in `refusedUnder`, which now resets `mapDeleteMessage` alone. "Map not created" is drawn from command outcomes. **Draw order:** it used to be drawn after every command-outcomes channel. It now takes `map-create`'s place in `COMMAND_CHANNELS`, after `resource-remove` and before `map-manage`, which is the order ticket 01 laid out for the Map channels. `mapDeleteMessage` is still drawn after all of them until 08.
- **Concern 3: the parameter list is tidied.** `spaceResourceContextCommands(context, document, select, available)` now takes four parameters instead of nine. `SpaceResourceRailContext` moved into `space-resource-context-commands.ts`, and the function builds its own embedded `MapAuthoringCommands` from that context.
- **The rail's refusal is said twice**, as rename's is. The rail's `onCreate` still returns the report's message, because `SpaceResourceSelectors` uses that string both to report locally and to decide that the caret did not move (`movedCaret`). A `null` for an unavailable, unchanged or broken creation leaves `movedCaret` set, so the menu does not return focus. That was already true of `unchanged`, and a broken creation used to reach the `.catch` that cleared it. Ticket 09 should separate "the caret moved" from "a sentence to report" in `CanvasSpaceResourceCommands.onCreate`, and decide whether the rail's local sentence earns its place beside the notice.
- **Tests.** `map-authoring-commands.test.ts` runs a creation contract against both adapters:
  - Completed: the new Map is empty, has one Graph, and that Graph is Active.
  - Withdrawn: answers `unavailable`, publishes nothing and leaves no notice.
  - Refused: carries the complete report, which command outcomes hold and dismiss.
  - `unchanged` answers `unchanged`, and `queued` throws.

  Context tests: the top level selects the new Map, and creation withdrawn while rename stays available creates nothing. The embedded context points the Resource at the new Map only after the target's held commit is released. It also covers "not created" when the containing Space is unsettled, "not saved", "not selected", and a target exited during the wait. A source-scan test holds the claim that the module imports no continuation, React or DOM. `SpaceApp.test.tsx` adds a refused Dock New Map: the "Map not created" notice appears, no name editor opens, and dismissal clears it.
