# 08 — Map deletion through both context adapters

Status: resolved
Blocked by: 06

**What to build:** Move top-level and embedded Map deletion behind `MapAuthoringCommands.map(mapId).delete`. The asynchronous capability owns the last-Map rule, live availability and existence checks, cross-Space coordination, persistence gates, and navigation to the surviving Map and Active Graph. Completed outcomes carry the surviving identities and refused outcomes carry complete structured reports.

**Why:** Deletion contains the most important locality gain: the current callers each know how Space Resources constrain a Map deletion and how Navigation recovers afterwards. One module should make that decision once for both contexts.

- [x] A Space's last Map is unavailable for deletion, and the capability rechecks that rule and Map existence when invoked.
- [x] Top-level and embedded deletion use the same external interface while their persistence and preferred-selection differences remain behind private adapters.
- [x] Every affected Space Resource is coordinated before completion, and the live target Space continues on the surviving Map and Active Graph when required.
- [x] Unavailable, unchanged, refused and completed outcomes remain distinct; only refused outcomes carry a report.
- [x] The shared contract suite proves both adapters, including stale invocation, last-Map, missing-Map, persistence failure and surviving-selection behavior.
- [x] Ticket 05 and the workstream spec are reconciled so ticket 05 retains Graph deletion and no longer claims Map deletion.



## Comments

**2026-09-23, resolved.** `pnpm verify` result is recorded in the commit report. This ticket's agent did not run `pnpm e2e`; the coordinator runs it for the branch. `pnpm e2e:ladle` does not apply: no `@project/ui` component or story changed.

- **The interface.** `MapCommands` gains `delete: MapDelete`, where `MapDelete = MapCapability<() => Promise<MapEditOutcome<SurvivingMap>>>` and `SurvivingMap = { kind: 'completed'; mapId; graphId }` is the Map and Active Graph every repointed Space Resource now selects. `MapAuthoringAvailability` gains `delete` (App answers it from `availability.entityEdits`, as the old `onDeleteMap` was gated). `topLevelMapAuthoringCommands` now takes an `AuthoredSpace` — `{ app, spaceResources }`, which an `OpenSpace` satisfies — because deletion is the cross-Space lifecycle's Edit, not the composition's.
- **One sequence, two adapters.** The private `deleteMap` checks availability, runs the context's `before`, **checks again after the wait**, then calls `spaceResources.deleteMap` once. Availability is general availability, `addresses(mapId)` (the top level: the selected Map; embedded: any Map of a target that is still the open entry) and **more than one Map** (ADR 0079) — so the last Map and a vanished Map are `unavailable` both at read and at invocation, and never reach the lifecycle. The embedded `before` waits for both Spaces and refuses as "Map not deleted" with `PERSISTENCE_UNSETTLED`; the top level has no gate, because the lifecycle refuses a Space whose session needs recovery itself (`persistence-recovery-required`), which the contract proves as its persistence-failure case. Lifecycle refusals are said through `describeSpaceResourceRefusal` under "Map not deleted"; `unchanged` stays `unchanged`; a throw is a break.
- **Dock target (concern 1).** The Dock only ever deletes the Map its cluster shows (`CommandDock.tsx`: `onDelete={() => canvas.onDelete(canvas.selected.id)}`), so the top-level adapter keeps rename's rule: it addresses the selected Map only, and any other id is `unavailable`. `spaceEntityActions`' `onDeleteMap` accepted any id; App now passes `onDeleteMap: null`, because the Map entity group is rendered by nothing but `runEntityCommand`, and the Dock's Delete now invokes the capability directly. `deleteDisabled` on the Dock row and on the rail now read the capability's `available`, last Map included.
- **Surviving navigation (concern 3) — a deliberate rule, held by a preference rather than a follow-up.** Investigating showed that Space Authoring's `reconcileNavigation` already moves a canvas whose Map vanished to the Space's opening Map, synchronously, before `deleteMap` resolves. The old top-level code then *overrode* that with the lifecycle's first-other Map (so the canvas visibly jumped twice when the opening Map was a different survivor), and the old embedded code checked `selectedMapId === mapId` after the await, which reconciliation had already made false — so it never ran. The module now passes `preferredMapId` = the Map the canvas shows when that is not the one going, otherwise the Space's opening Map (or `null` when the opening Map is the one going, in which case the lifecycle moves the opening Map to its own choice). The lifecycle and reconciliation therefore land on one survivor, and the module needs no navigation write of its own: a follow-up `selectMap` was written and then removed because deleting it failed no test. The consequence is the rule the ticket asked for: a canvas showing the deleted Map continues on the survivor and its Active Graph; a canvas the author moved while the deletion ran is left where the author put it, because reconciliation moves only a selection that has gone. Both are contract tests, and replacing the preference with `null` fails four of them. **Behaviour change:** a top-level delete whose Space opens on a different Map than the first remaining one now lands on the opening Map (the old code's first-other choice disagreed with reconciliation). `mobile-dock.spec.ts`'s Delete is unaffected: `created-map` makes the new Map the opening Map, so deleting it falls back to the first other Map as before.
- **Staleness of the report (concern 2).** A refused deletion moves nothing — the gate, the lifecycle refusal and `unchanged` all return before any Edit — so a Map-scoped `map-delete` refusal is never dropped as stale; a completed top-level deletion moves the selection and its settlement is dropped, which is harmless because a completion clears. The contract holds "A refusal moves nothing, so the settlement is not dropped as stale".
- **Surfaces.** The Dock runs `commandOutcomes.run('map-delete', () => mapAuthoring.map(mapId).delete.invoke())`. The rail runs the same against the containing canvas's command outcomes and returns the report's message for `SpaceResourceSelectors`' local sentence, as creation does — so an embedded refusal is now said twice (before, only the rail's sentence), which ticket 09 can weigh with 07's matching note.
- **Removed.** `mapDeleteMessage`, its `ShellNotice` and `refusedUnder` (which reset nothing else) are gone from App; "Map not deleted" is drawn from command outcomes, so ticket 05's "every shell notice" box now holds. `coordinatedMapDelete` and `coordinatedDeleteOk` had no caller left and are deleted with their tests; `coordinatedGraphDelete` stays for Graph deletion. `coordinated-context-delete.test.ts`'s source scan now holds that App deletes Maps through Map authoring and never calls `spaceResources.deleteMap`. `authoring-placement-copy.test.ts` drives its Map deletion through the top-level capability.
- **Tests.** `map-authoring-commands.test.ts` runs a deletion contract against both adapters: completed (Map gone, the referring Space Resource repointed, the canvas on the survivor and its Active Graph), survivor = the opening Map, the author moving mid-flight (lifecycle held by a wrapped spy), stale invocation, last Map rechecked at invocation, a vanished Map never reaching the lifecycle, persistence failure, a refused lifecycle's complete report held and dismissed by command outcomes, and `unchanged`. Context tests: the top level does not delete a Map it has moved off and withholds deletion alone when only deletion is withdrawn; the embedded context deletes a Map its target is not showing without moving either canvas, refuses while the containing Space is unsaved, and deletes nothing in a target exited during the wait. `SpaceApp.test.tsx` adds a refused Dock Delete Map drawn and dismissed as "Map not deleted".
