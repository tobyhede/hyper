# 06 — Map rename through one authoring command interface

Status: resolved
Blocked by: 01

**What to build:** Introduce `MapAuthoringCommands` as the one interface for Map Edits, with Space-scoped creation and Map-addressed rename and deletion capabilities. Complete the rename slice through both the top-level Space and an embedded Space Resource: each capability pairs availability with synchronous invocation, rechecks live availability when invoked, and returns a complete structured report when Space Authoring refuses the rename. Command outcomes owns the report's lifetime and dismissal; the Map authoring module owns its title and message.

**Why:** Top-level and embedded Map rename currently repeat availability, completion and refusal conversion at different call sites. This first slice establishes the deep module and proves that its two private adapters share one test surface before asynchronous coordination joins it.

- [x] `MapAuthoringCommands` exposes Space-scoped creation and `map(mapId)` for Map-addressed rename and deletion; unavailable capabilities cannot be confused with refused Edits.
- [x] Top-level and embedded Map rename use the same synchronous capability, while Map selection, Copy link, focus and notice markup remain outside the module.
- [x] Invocation rechecks live general availability and Map existence; a stale invocation answers `unavailable` without publishing a refusal report.
- [x] A refused rename returns the complete Map report, and command outcomes publishes, dismisses and clears it without interpreting an `AuthoringRefusal`.
- [x] A shared contract suite runs the rename behavior against both private adapters; application coverage proves the existing inline rename treatment still holds a refused draft open.
- [x] Ticket 02 and the workstream spec are reconciled so ticket 02 retains Graph and Reference Resource refusals and no longer claims Map outcomes.


## Comments

**2026-09-23, resolved.** `pnpm verify` green (237 files, 3074 tests). `pnpm e2e` was not run by this ticket's agent — the coordinator runs it for the branch. `pnpm e2e:ladle` is not applicable: no `@project/ui` component or story changed.

- **The interface.** `packages/app/src/map-authoring-commands.ts`: `MapAuthoringCommands { map(mapId): MapCommands }`, `MapCommands { rename: MapRename }`, and `MapCapability<Invocation> { available: boolean; invoke: Invocation }`, with `MapRename = MapCapability<(title) => MapEditOutcome>`. `MapEditOutcome<Completed>` is `Completed | unchanged | unavailable | { refused; report: CommandNotice }`, generic in its completed arm so 07 can declare `MapCapability<() => Promise<MapEditOutcome<{ kind: 'completed'; mapId; graphId }>>>` without a second vocabulary. It stays assignable to command outcomes' `MapCommandResult`, which did not change.
- **Creation and deletion are declared in the interface's doc comment, not as members.** Adding `create`/`delete` members now would have meant both adapters implementing them over the old paths — 07's and 08's work — or stubbing them with an answer that lies. 07 adds `readonly create` beside `map`, and 08 adds `readonly delete` to `MapCommands`, each as a `MapCapability` whose invocation answers a promise.
- **Two private adapters over one private core.** `mapAuthoringCommands(context)` holds availability, the invocation-time recheck and the outcome translation; a context is `{ available, addresses(mapId), complete(mapId, completion) }`. `topLevelMapAuthoringCommands(app, available)` addresses only the *selected* Map — Space Authoring's top-level `renamed-map` refuses any other id as `map-not-found`, so a Map not selected at the press is a stale press (`unavailable`), not a refusal — and completes through `authoring.complete`. `embeddedMapAuthoringCommands(target, spaces, available)` addresses any Map of the target while `spaces.entry(target.id) === target` (an exited target is unavailable), and completes through `completeInMap`, as the rail's old `completeEmbeddedAuthoring` path did for this kind.
- **`available` is a reader, and only as live as its caller.** App builds the top-level commands in a `useMemo` over `availability.chromeTitleEdit`; the rail builds the embedded ones over its own `!disabled`. Both are the last render's answer — nothing outside React holds the top-level availability — so the live part of the recheck is Map existence, selection and entry identity. 07/08 inherit this; a truly live answer would need App's availability outside React state.
- **`queued` translates to `completed`.** A rename accepted behind a running completion lands when it drains, and the editor closed on it before, as for a completion.
- **A refused Map rename is now said twice**: inline, where `InlineTitleEditor` holds the draft open on `report.message` (`renameDraftAnswer`), and as a "Map unchanged" notice on `map-manage`, as this ticket asks. Ticket 09 should decide whether the notice earns its place beside the inline sentence for rename specifically. `unavailable` and a broken invocation close the editor, the latter having reached the reporter; before, a throw escaped into the editor's event handler.
- **The embedded report goes to the containing canvas's command outcomes**, threaded as a required `commandOutcomes` prop beside `continuation` through `SpaceCanvas` and `EmbeddedMapAuthoring`, and as an optional input (like `continuation`) through `useCanvasResourceAuthoring`, the decoration context and `SpaceResourceRailContext`. `spaceResourceContextCommands` takes the `MapAuthoringCommands` and `CommandOutcomes` as two trailing parameters; 07/08 can spend both without further plumbing.
- **`mapManagementRefusal` is deleted from App.** Nothing ever set it non-null — every write was a clear — so the shared "Map unchanged"/"Map not created" slot reduces to `createMapRefusal` under "Map not created" until 07, and `refusedUnder` resets `createMapRefusal` and `mapDeleteMessage` only.
- **Tests.** `map-authoring-commands.test.ts` runs one contract suite against both adapters — completed, unchanged, refused with the complete report, a withdrawn capability and a vanished Map each answering `unavailable` with no Space Authoring publication, and the refused report held and dismissed by command outcomes while `unavailable` leaves `map-manage` clear — plus what each context addresses (top-level: not a Map it has moved off; embedded: any Map of the target without moving its canvas, and nothing through an exited entry). Application coverage: `SpaceApp.test.tsx` refuses a Dock Map rename through a spy on `authoring.complete` (the Dock answers a blank name itself) and `space-resource-embedded-map.test.tsx` refuses a blank rail rename; both prove the draft stays open with its sentence and the "Map unchanged" notice dismisses without closing it.
- **Ticket 02 and the spec.** 01824ef1 had already moved Map outcomes out of ticket 02. The spec's out-of-scope "Inline refusals" bullet still named chrome rename as wholly local; it now names Map rename as the exception.
