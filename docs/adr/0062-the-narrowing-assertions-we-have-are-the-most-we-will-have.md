# The narrowing assertions we have are the most we will have

Status: accepted
Related: 0010, 0057, 0061
Build status: not built

A type assertion that tells TypeScript a value is *more specific* than TypeScript can prove is a claim the compiler cannot check. `@typescript-eslint/no-unsafe-type-assertion` runs as an error, and the assertions already in the tree are recorded once in a committed ESLint suppressions baseline. Nothing new joins that list. A new narrowing assertion fails lint, and the only way past it is to narrow, to parse at the boundary that owns the representation, to change the signature to ask for what the function needs, to prove the fact by construction — or to add an explicit, argued exception that a reviewer sees.

The baseline is a ratchet, not a backlog. `--prune-suppressions` runs in `verify`, so an assertion removed for any reason drops out of the file permanently and the ceiling lowers. Adding an assertion to a file that already has suppressed ones surfaces every assertion in that file, not only the new one, because a count-based baseline cannot tell them apart — so the cost of adding one is reading the ones already there. That is the intended pressure. It is not a schedule.

This deliberately does not call the existing assertions defects, because the evidence does not support it. Every production site was examined in a reviewed pass under `.scratch/anti-slop/` issue 07, which set exactly this test — *"if a site here turns out to have a real missing type boundary rather than a truly safe narrowing, route it back"* — and flagged none. The comments those sites carry state real invariants: a union already narrowed on one side of an equality check, a value the module is the sole producer of, an erasure a library's own type imposes, a genuine external contract. One of them argues correctly against the alternative this decision would otherwise impose, observing that parsing at that site "would put a throw on the per-pointer-frame path for a failure the other readings agree cannot happen." No defect in this repository has been traced to a narrowing assertion.

What has changed is not the verdict on those sites but who writes the next one. `anti-slop/require-safety-comment-for-type-assertion` is satisfied by prose, and prose is the cheapest thing an agent produces; a convincing `SAFETY:` comment costs an agent no more than the assertion it excuses. The existing comments survived human-directed review, delegation and spot-checking against source. Nothing guarantees the next one gets that. A comment also does not survive refactoring — *"the same erasure `placementFromNodes` repairs below"* is true until someone moves that function, and nothing checks it afterwards.

`anti-slop/no-chained-type-assertions` already blocks `as unknown as T` and needs no change. `require-safety-comment-for-type-assertion` stays exactly as it is: every surviving assertion still states its invariant, and the two rules now do different jobs — one demands a reason, the other caps the count. `as const` is untouched, and `as const satisfies Contract` remains the preferred spelling where literals and structure both matter. Broadening to `unknown` to contain a defective external declaration stays legal, local and justified.

We rejected the full cleanup. It contradicts a reviewed outcome without new evidence, it lands on the hard tail by construction — the anti-slop sweep already deleted every assertion with an easy fix — and it moves judgment out of the code and into a config file, trading inline invariants a reviewer reads in context for exception entries further away that can go stale unnoticed. We rejected leaving the rule off, which puts no gate at all on what gets written next and leaves the standard resting entirely on a comment requirement prose satisfies. We rejected file-scoped grandfathering through ordinary config overrides, which would hand a permanent pass to exactly the files most likely to grow new assertions.

The accepted costs are two. A committed suppressions file is a second place violations live, and it is only honest while `--prune-suppressions` runs, so the pruning is part of `verify` rather than a habit. And the baseline counts per file and rule rather than per site, so removing one assertion and adding another in the same file passes silently until the next prune — a swap is invisible where an addition is not.

## The negative to remember

Do not schedule the baseline as debt to be paid down. It drains as files are edited for other reasons, and a project to empty it is the cleanup this decision rejected, arriving under a different name. Do not read a committed suppression list as evidence the rule is decorative — it is the record of what review already accepted, and it only ever shrinks. Do not answer a new finding by widening a type until the assertion becomes legal, by moving it into a helper, or by adding it to the suppressions file by hand.
