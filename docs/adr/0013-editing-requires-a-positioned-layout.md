# Editing requires a positioned layout

Status: accepted
Refines: 0002, 0005
Refined by: 0014

A **positioned layout** is a named, authored card-to-position map — the "hand-placed" kind `CONTEXT.md` has always listed. An **automatic** layout (the route-driven ELK graph, a grid, a tree) computes placement from the graph alone and needs nothing from the space. Editing writes placement, and only a positioned layout has anywhere to write it. So the layout kind alone decides whether a view can be edited: there is no edit mode, no flag, and no state to keep in sync — a positioned layout is draggable and an automatic one is not. Because creating a card *is* placing it (the drop point is the position), this makes automatic views read-only outright, not merely undraggable.

What this reverses is the assumption underneath ADR 0002 and 0005, that placement is *derived* — a layout computes where cards go, a view renders them, geometry is an output. In a spatial presentation tool, position is authored meaning: when someone drags a card next to another, the adjacency is the point. A global optimiser cannot represent that. Three spike increments were the honest attempt — append, then branch, then seeded and interactive ELK — and every one reshuffled the existing cards and placed the new one by global optimisation, so it felt random. The failure is structural, not a matter of tuning, and the spike is kept under `.scratch/` as the evidence rather than deleted, because seeded ELK is what a future review will otherwise re-suggest.

The `Layout` contract survives unchanged. `positionedLayout(map)` sits in the same seam as `elkLayout()` and `gridLayout()`, reading positions where those compute them, so geometry still lands as optional fields on the elements and there is still no arranged-result type. ADR 0005 anticipated this layout in as many words — "a card→position map for a hand-placed one" — and what changes is not the contract but which layout is *operative*. That is the part a reader of 0005 would otherwise take as current intent, since its reasoning is ELK-heavy throughout.

Only authored data persists. A space carries zero or more positioned layouts and, optionally, a pointer naming which view opens it. The pointer records intent — *open me like this* — and never carries an algorithm's parameters, because the moment it does, computed geometry is back in authored content through a side door. Automatic layouts appear in the file nowhere. Layouts are **optional**, so a space can still be written by hand without coordinates for every card; a space with none opens in an automatic view, and a file-first prototype keeps the property that its content can be authored in a text editor.

Auto-arrange is the bridge between the two, and the only crossing point. It runs an automatic layout once and writes the result into a positioned layout's map. At that moment the geometry stops being the algorithm's output and becomes authored, because the author accepted it — an edit, not a cache. It is also the on-ramp: opening a hand-authored space for editing runs the current view once and writes the space's first positioned layout, an explicit act with a visible result, rather than a stray drag silently materialising one.

Edits then split by blast radius. A **structural** edit changes the space and shows up in every layout and view; a **placement** edit changes only the active positioned layout. This is why a layout's positions are allowed to be sparse: a card created while one layout is active genuinely has no position in another, and that is correct rather than a hole to backfill. The asymmetric rule is that positions may omit cards but may not name cards that do not exist — a dangling position keyed by a deleted card is a reference error of the kind `loadSpace` already rejects.

Rejected alongside seeded ELK: putting positions on the **card**, which cannot express the same card sitting at different coordinates in different layouts; requiring **every** space to carry a layout, which reads as consistent until it means no space can be hand-authored without coordinates; **declaring** automatic layouts in the space file for uniformity, which puts algorithm parameters into authored content; and an explicit **edit mode**, which duplicates in a flag what the layout kind already says.

The costs accepted: an automatic view cannot be edited, so arranging a hand-authored space is a deliberate Auto-arrange first; the space file gains a layouts concept and `loadSpace` gains a position-reference check; cards a layout omits need a documented placement (a deterministic grid past the bounding box of the positioned ones, so they read as unplaced rather than stacked at the origin); and two documents stop being true on the day this lands — AGENTS.md's opening claim that elkjs lays the graph out automatically, and `commands.md`'s reasoning that card-drag is free to mean "duplicate" because ELK owns placement.
