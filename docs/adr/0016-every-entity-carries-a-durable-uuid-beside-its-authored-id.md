# Every entity carries a durable uuid beside its authored id

Status: rejected
Refines: 0010

**Rejected, 2026-07-24.** An entity has one id — which is what the model already had; this proposed adding a second, and it is not worth it. The body below is unchanged, because it is the argument a future review will make again.

The reason it fails is internal. Its third paragraph derives an unsaved space's identity from the file path; its sixth says an unsaved space has no durable identity at all; and the first contradicts this same document's rejection of file-name-as-identity. Since a card's namespace was to be its space's uuid, a `git mv` would have moved every card's uuid with it, and the stated defence — that saving freezes the derivation — never reaches a file authored by hand and never saved through the UI.

Every space, card and route carries a `uuid` in addition to the short `id` its author wrote. The two are not redundant, because they do different jobs: the authored id is **scoped to the document** and is what in-file references use, while the uuid is **globally stable** and is what addresses, bookmarks and cross-document references use. `uuid` is optional in a space file, filled in when the file is loaded, minted fresh when the UI creates something, and written out on save.

Collapsing them into one field fails in whichever direction you collapse. If the uuid becomes the id, a route step reads `{ "target": "9f3c8a2e-…" }`, a layout's position map is keyed by hex, and hand-authoring a space file — the property that makes this file-first at all — becomes miserable. If the authored id is the only id, then it is simultaneously a human's choice of name and a permanent address, so renaming a card breaks every link to it, and two spaces cannot both call a card `intro` without colliding the moment they reference each other. Two fields is the cost of letting a name be a name.

Ids are filled in **deterministically** rather than randomly, which is what makes the load path pure. A uuid generated at load and not persisted differs on every load, so it cannot do the one thing ids exist for — a bookmark saved on Monday would point at nothing on Tuesday. UUIDv5 is precisely the tool: a hash of a namespace and a name, so the same file yields the same uuids forever. A card's namespace is its space's uuid and its name is its authored id; a hand-authored space file with no uuid of its own derives one from where it lives, which is a location rather than an identity but works as a bootstrap. Once anything is saved, its uuid is written out literally and never derived again — so the derivation's dependence on the authored id and the file path is a property of the unsaved state only, and saving freezes it.

Genuinely new entities get UUIDv7 instead, because a card the UI creates has no prior name to hash. v7 is time-ordered, which costs nothing today and indexes far better than v4 when the database-backed world arrives; choosing it now avoids choosing it later under a migration. That randomness lives in the store — which is already impure and already takes its dependencies as parameters, since `createPresentationStore(space)` was written in that shape to be testable — and never in `graph`, which stays pure and property-tested.

We rejected mocking `crypto.randomUUID` to let `loadSpace` be impure but testable. It does not avoid writing a deterministic generator, because a mock returning a constant collides every card across the hundreds of cases a property test runs, so it needs a counter — and then a generator exists anyway, wired in a `beforeEach` where nothing at the call site admits it. Seeding is not an alternative: `crypto.randomUUID` is a CSPRNG and unseedable by design, so controlling it means owning it, which is injection under another name. Global mocking also stops working silently the day the code moves to v7, which reads the clock as well as the entropy pool.

We also rejected using the file name as a space's identity. A file name is a location, and the two diverge the moment ADR 0001's nested spaces let one space reference another — at which point the identifier sits inside authored content, and renaming a file stops being a broken bookmark and becomes a data migration. And we rejected putting slugs in the file: the `{name}-{uuid}` form, where resolution reads the trailing uuid and ignores the name, is right for a URI and wrong for a document, where it would be neither readable nor diffable.

The costs accepted: every entity now has two identifiers, and everyone reading the model has to know which one a given position wants. `core` gains a uuid dependency, its first beyond zod. A space that has never been saved has no durable identity, so it is not addressable — which makes Save the act that mints an address, and is the same rule as an unsaved document having no path. Renaming a card's authored id before its first save moves its uuid, so the ids only become trustworthy at the save boundary. And a uuid in a URI is unreadable without a slug in front of it, which this decision leaves unsolved rather than solving prematurely.
