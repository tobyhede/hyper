# SQL databases share one Space repository

Status: accepted
Refines: 0078
Related: 0030, 0054, 0062, 0092

PostgreSQL and SQLite are served by one Space repository implementation. It owns row mapping, the Meta lifecycle, the commit procedure and the mapping of a stale revision or a Thing owned by another Space to a commit outcome. Each database supplies only a small `SqlStore` value: access to its generated tables, a handle for reads and writes outside a transaction, how it runs a transaction, how it reads a stored document, how it recognises a duplicate key, whether it serialises operations, and how it closes. A member added to that value is a place the two databases have begun to differ again, and needs a reason.

ADR 0078 said adapters share "one behavioral contract, not a storage-mechanics port or one lifecycle implementation", and that a future SQLite adapter "may use its own native mechanisms". That was written when the second implementation was memory. `.scratch/database-persistence/sqlite-target-research.md` deferred any shared SQL abstraction "before duplication is measured", and tickets 15–18 built a second adapter directly against the SQLite ORM. The measurement came in: about 350 of each adapter's roughly 443 code lines were the same once the ORM namespace was read past, and the copies had already drifted — PostgreSQL retried the Meta lock after a replacement and re-checked every row's revision inside `replaceAggregate`, SQLite did neither, and the two recognised a duplicate key differently. The deferral's own condition had fired. Memory keeps its candidate-state replacement; this refines 0078 for SQL databases only.

The commit decision is shared more widely still. `decideCommit` in `@project/persistence` is pure and is the one place a change set is validated, for the SQL repository, `MemorySpaceRepository` and `MemorySpaceBackend` alike. The SQL repository keeps a private fast path for a single structure-preserving update, which still answers a revision conflict itself. That path runs only after the same identity refusal `decideCommit` begins with, and it hands a snapshot failing intake to the complete-aggregate decision, so no implementation answers a refusal differently.

Where the two adapters had drifted, the one repository runs PostgreSQL's complete sequence on both databases, and a step is carried to the second only once a test fails when it is reversed. Those steps are correct on SQLite and merely uncontended there, because SQLite's `serialise` queues every repository operation in the process, reads included, and the file has one writer. That queue is the one concurrency behaviour the repository's code varies by database. It is not a claim the databases behave alike under contention: a second process on a SQLite file meets SQLite's file lock and busy timeout and surfaces as a transient connection failure (ticket 18), which is the engine's behaviour rather than the repository's. Statements inside a transaction stay sequential on both databases, which is also what keeps Prisma Next 0.16.0's shared-connection interleaving defect unreachable while PostgreSQL is bound through a pool.

A Revision is stored as canonical non-negative decimal TEXT on both databases, with one shared codec owning its format and its 2^63−1 ceiling. SQLite could not store it any other way on the pinned driver (ticket 14), the HTTP protocol already carries it in that form, and nothing orders or computes over it in SQL. Storing PostgreSQL's as `int8` would have kept the one narrowing assertion that relabels a `bigint` as `number`, and moving that assertion into a new module would add to the ceiling ADR 0062 forbids growing.

The shared tables are typed through a structural type the repository declares over the calls it makes, which each generated ORM must be assignable to without a cast. It is written with property rather than method syntax, declares no optional row field, and types documents as `unknown`, because each of those loosens what assignability proves.

Rejected: two adapters over one shared commit procedure, which leaves the row mapping and lifecycle duplicated and is the arrangement that drifted. Typing the repository generically over Prisma Next's own contract types, which does not compile — the ORM's conditional row types do not resolve inside a generic body — and would need the assertions ADR 0062 forbids. Checking one source file twice under two tsconfigs, which gives each database its full inferred types but needs a second typecheck run and leaves typed lint and Vitest seeing only one database. Waiting for Prisma ORM v8, which as of 8.0.0-rc.11 still types each database's client separately, still cannot read a SQLite integer beyond 2^53, and marks SQLite experimental; moving to it is a separate decision.
