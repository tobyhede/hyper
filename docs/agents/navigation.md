# Navigation & Browser History

Product addresses, the browser's location and history, and how Navigation's position reaches them. Read before touching `packages/app/src/browser-location.ts`, `browser-history.ts`, `destination-coordination.ts`, `addressed-resource.ts`, the address `navigation.ts` answers, `space.ts`'s `browserHistory`, `main.tsx`, or `packages/http/src/product-destination.ts`; before adding a router; or before writing to `window.history` or reading `window.location` anywhere.

## Product addresses (ADR 0069, ADR 0079)

- **Every Space, Resource, Graph and Map has a product URL built from its Id**, spelled as an unpadded 22-character base64url value (`encodeCompactUuid` and `decodeCompactUuid` in `packages/core/src/compact-uuid.ts`; `packages/core/test/compact-uuid.property.test.ts`). The domain, stored documents and HTTP resources keep the canonical UUID spelling. What draws the canvas is a Map, identified by its own UUID, and `/spaces/:spaceId/maps/:mapId` is the durable Map URL shape. The accepted ADR bodies carry their refinement history ([`workflow.md`](workflow.md)), so read their status blocks before their bodies.
- **There is no router library, and adding one is a decision rather than a convenience.** The destination contract is declared once, in `@project/http` (`ProductDestination`, `productDestinationPath`, `resolveProductDestination`; `packages/http/test/product-destination.test.ts`), and the Node host (`src/http/space-host.ts`) resolves the same table the browser does. A browser router would be a second copy of that table, in the browser only, disagreeing with the host the day either moved.

## One module knows the browser exists (ADR 0081)

- **`browser-location.ts` is the one module that knows a browser exists, and no call site decides what the browser does.** It takes the five-member `HistoryApi`, required with no default, the way `newId` is (ADR 0109). **`createBrowserHistory` in `browser-history.ts` is the one adapter that implements it**: it takes a `NativeBrowser` (the part of `window` it reads and writes) rather than reaching for `window`. The application's `window.history` writes — `pushState`, `replaceState` and the return that undoes a held traversal — and its `window.location` reads all go through it, beside `main.tsx`'s one `window.location.pathname` read.
- **`browserHistory()` in `space.ts` is where `window` is named**, by handing it to that adapter. `createSpaceStartup` does not reach the browser itself: it selects that adapter as the default of its third argument, which makes the composition root the place the ambient browser is named. `test/unit/app-http-startup.test.ts` supplies a recording adapter in its place. No test scans for a second reader; `git grep -n 'window\.' packages/app/src` should answer `main.tsx` and `space.ts` alone.
- **There is one history stack, so the location is composed once per session.** `createOpenSpaces` composes it and calls `follow(app)` with whichever composition is on the canvas (`sends a later operation to the composition it followed last` in `packages/app/test/browser-location.test.ts`). `useAddressedResource` (`addressed-resource.ts`) reads the two fields it publishes, `addressedResourceId` and `destinationNotFound`, through one `useSyncExternalStore` (`reads the addressed Resource off the location of the Space it follows`). `useSpaceAddresses` keeps only the clipboard half of Copy link.

## A Navigation operation is never paired with a history write

- **Navigation answers a `NavigationAddress`** — the selected Map, the Active Graph and the presenting Resource, derived from its state and never stored on it. The location hands that address, plus the Resource the location addresses, to `destinationSync` (`destination-coordination.ts`), a pure function that compares the position against what the current pathname resolves to and answers `push`, `replace` or `none` (`packages/app/test/destination-coordination.test.ts`).
- **`none` is what lets `popstate` move Navigation without pushing an entry** over the one the browser just navigated to, and what makes a redundant notification — StrictMode's second invocation included — decide nothing (`writes nothing when the same position is decided a second time`). So a Navigation operation is called for its own sake. Do not put a `moves = getState().x !== y` comparison beside a call site to decide whether to write history: `destinationSync` already decides it, and a second decision at the call site is a second copy that drifts.
- **The `popstate` listener reopens whatever `resolveProductDestinationInSnapshot` answers for the current pathname.** A location it cannot resolve is *reported*, not corrected, and only for the arrival: the first move away from it is written and clears the report (`reports a Back onto a dead address rather than correcting it`, `clears the report and takes one entry when presenting moves off an unresolved location`). Every rule in this section is proved in the node environment against a recording adapter, in `packages/app/test/browser-location.test.ts`.

## Held traversals and entry numbering

- **The `onPopState` listener answers a `PopStateAnswer`.** `undefined` keeps the traversal. `false` holds it: the adapter returns the browser to the entry the traversal left and keeps both entries. Where the browser has the Navigation API it returns by that entry's key through `navigation.traverseTo`, so the return lands there wherever the traversals queued ahead of it have taken the browser. Otherwise it returns by a relative `history.go`, which such a traversal can push past either end; the browser then drops it and the address stays on another entry until the next traversal. A Back or Forward the reader queues while the adapter is returning is asked about like any other traversal, and the return continues while the listener holds.
- **A promise answers either later.** That is how a Back refused by an image replacement that began while its destination was opening is still held. A late `false` holds while no later traversal has been kept and no entry written since. A later traversal the listener held does not count, so a refusal that arrives while that one is still returning sends the browser back to the entry the earlier traversal left (`holds a Back refused by a replacement while a later held Back is still returning` in `packages/app/test/browser-location.test.ts`).
- **The adapter numbers the entries it writes** (`hyperHistoryIndex` in `history.state`) to know how far to rewind, and numbers a fragment link's entry as it arrives, because the browser writes that entry after the current one and fires `popstate` for it. Only a same-document entry written with no `popstate`, such as another script's `pushState`, goes uncounted, and a rewind across it misses by one entry. The index arithmetic is proved against a stand-in browser in `packages/app/test/browser-history.test.ts`; a real browser holding Back and Forward during a replacement in `packages/app/e2e/image-resource.spec.ts`; and a return by key landing on the held entry while the reader jumps on from each arrival in `packages/app/e2e/held-traversal.spec.ts`.
