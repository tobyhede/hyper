# Canvas & Rendering

React Flow, handle geometry, the camera, presenting's Stage, and Edge Authoring. Read before touching `packages/react-flow-adapter`, the canvas/camera modules in `packages/app`, or `edge-authoring.ts`.

## Edge Authoring and drafts

- **ADR 0033 — authoring is drag-to-connect through four spatial handles coloured as the Active Graph; ADR 0090 — seeking-end handles reveal by proximity and eligibility.** Built: source handles appear on the hovered or selected Resource, and are withheld again for as long as that Resource is the one being moved — a drag is hover and Selection both, so `data-dragging` on `.rf-resource-node__inner` gates the two idle reveals beside `data-resizing`, and the resize control's one reveal, Selection, with them — the control is mounted only on a selected Resource, Open or Closed (ADR 0122), and a selected Shape other than the rectangle draws a thin frame at its rect for it to sit on; during a connection drag, seeking-end handles appear only on Resources that are both within **80 canvas units** of the pointer (distance to the Resource's axis-aligned bounds) and eligible for the release under `edgeEligibility` — refused targets (e.g. an exact duplicate) stay invisible. Self-edges remain legal, so the source Resource is eligible when the pointer is near it. They are Graph-independent and the chosen side is not authored. Edge creation is spatial and handle-driven, and has one keyboard form: Connect to Resource, in a Resource's Actions menu, opens the Resources list over the Map's placed Resources bar that one, each asked the same `edgeEligibility` (`connectChoices` in `edge-authoring.ts`), and `EdgeAuthoring.connectTo` completes the choice — to a placed Resource, or to a new Markdown Resource beside the source (`create-and-connect` with `position: 'beside-source'`) — and continues at the new Edge, selected and focused (`.scratch/edge-toolbar/issues/07`). Every Edge gesture writes to the Active Graph and nothing mints one for it: a Map owns at least one Graph (`graphs` is `min(1)` in the schema), and a connection with no Active Graph refuses `map-active-graph-required` (`connectRefusal` in `space-authoring.ts`). Option/Alt empty-drop create-and-connect is built, alongside Active-Graph Edge focusability, each Active Graph Edge's Title and toolbar (`AuthorableEdge` composing `EdgeTitle` and `EdgeToolbar`; see the bullet below) and selection-based deletion. **There is no reconnection**: moving an Edge's end is Delete and draw again (`.scratch/edge-toolbar/spec.md`), so React Flow is handed `edgesReconnectable={false}` and draws no endpoint anchors, and nothing in Edge Authoring or Space Authoring moves an end. Detached Resource creation has its controls too — the toolbar's Add Resource and the graph-focused `C` — and a Resource can be removed from its Map with Backspace or Delete, which acts on the Resource the key was aimed at and falls back to the selection. *Structural* deletion, meaning deletion of a Resource from the Space, is Delete from Space in the Resource's Actions menu (`resource-rail-actions.tsx`), asked through the delete confirmation (`resource-deletion.ts`; `packages/app/ladle-e2e/delete-confirmation.spec.ts`). **ADR 0087 gave those same four handles a second job**: an Edge attaches to whichever of them faces its neighbour, so they are anchors on every Resource and affordances only where the canvas is authorable. The per-Graph attachment machinery that used to serve overview rendering is gone with it.
- **Edge Authoring is one module for the whole Edge lifecycle, and it owns no copy of anything (`.scratch/card-route-editing/edge-authoring-design.md`).** `packages/app/src/edge-authoring.ts` holds the one interaction draft, the refusal that draft ran into and the focus continuation a completed projection owes; `edge-authoring-react.tsx` is its React interface, answering `{ edges, edgeTypes, reactFlowProps, layer, provide }` plus the Edge operation used by the canvas's app-owned delete command. The **render adapter** stays authoritative for the projection, Resource movement and the discriminated `none | resource | edge` selection; **Space Authoring** stays authoritative for eligibility and every semantic Edit. Three consequences are load-bearing. *Selection is folded additively*: one React Flow selection action produces two callback batches — the new subject selected, then the other kind deselected — so reading the resulting arrays answers `none` for a click that plainly selected something, and the second batch must clear the union only when it still names the subject stored. *The Edge subject is the domain `{ graphId, edge }`, never the React Flow id*, which is `<graphId>::<from>::<to>`. That id is minted from the same triple the subject is compared by (`buildGraphRenderEdges`, `sameEdgeSubject`), and ADR 0032 makes the triple unique; a Title is the Edge's content and never enters the id, so titling an Edge redraws the same element. The id never depends on an Edge's index in its Graph: an index-keyed id passes to the next Edge when one is removed, carrying the element React Flow already drew for it, so a focus continuation lands on that stale element, whose `onFocus` bridge writes the other Edge over the selection just installed. **A canvas continuation is therefore spent a commit after the projection that carries it**: React Flow syncs the `edges` prop into a store of its own from an effect and draws from that, so an Edge it has never drawn is still absent when `CanvasContinuation`'s effect first looks. That component subscribes to React Flow's own synced `nodes` and `edges` (`useStore`) for the re-render, because nothing else gives it one — the projection publish is the render that is too early — and resolves an Edge subject against the subscribed list rather than a prop, so the id it mints comes from what the DOM is keyed off. **Both arms are load-bearing**: `syncProjection` copies the Edge list on every publication, which made the Edge arm look like it covered resource targets too, but `mergeProjected` replaces only the nodes — the create-and-connect path — and nothing in the Edge arm fires there. `state.edges` is what React Flow has *taken*, not what it has painted: `EdgeWrapper` still returns `null` while an endpoint's position is unresolved, and that recovery commit is driven by node measurement. Not reachable today, because nothing requests an Edge continuation for a gesture that also creates a Resource — but `staysOwed` is unconditionally true for an edge target, so such a continuation would wait with no timeout and no diagnostic. Don't remove either subscription and don't answer the gap by re-resolving on a timer. *The commands context wraps `<ReactFlow>` rather than sitting in `layer`* — React Flow renders Edges itself, as a sibling of the children it is given, so a provider inside the layer reaches no Edge at all. Backspace and Delete are disabled in React Flow and handled once by the canvas; the selected Resource goes through its completed Edit (Remove from Map, which asks nothing), the selected Edge through `EdgeAuthoring.askToDelete` — the delete confirmation, one question for the selection, as the toolbar's Delete asks — and nothing mutates the controlled projection locally. `queued` at the React Flow seam is an invariant violation rather than an outcome — a pointer release arrives from the event loop with no Edit on the stack — so `connection-completion.ts` reports it and draws nothing.
- **An Active Graph Edge's chrome is `EdgeTitle` and `EdgeToolbar` in `@project/ui`, placed by `AuthorableEdge` in `app`; the HUD's Graph key is `GraphHud`'s own markup (`.scratch/edge-toolbar/spec.md`, tickets 05 and 06).** `AuthorableEdge` stays the React Flow adapter and owns exactly the framework's half: the routed Edge, `EdgeLabelRenderer`, the midpoint and the drawn span (`useRoutedEdgeGeometry` answers `{ path, labelX, labelY, span }`, the span being the straight distance between the drawn line's two ends — so nothing parses the SVG path), the selection translation, the portal placement in `.edge-control-layer` and the `nodrag`/`nopan`/`nokey` containment — `.nokey` there is read by React Flow's still-live Space-key pan activation subscription and by the canvas's delete guard. It draws chrome for the **Active Graph's Edges only**, which are the only Edges that carry a Title; another Graph's Edge is its line. **Revealed** means hovered, selected or having its Title written, and only for an Edge that is selectable (Active Graph, authoring available): hover is the line read through React Flow's own `onEdgeMouseEnter`/`onEdgeMouseLeave` plus the chrome's own pointer events, one canvas-wide `hovered` id in `useEdgeAuthoring` released `HOVER_RELEASE_MS` after the pointer leaves so it can cross from line to toolbar. React Flow draws the label layer beneath the nodes, so a revealed Edge's layer is raised (`.edge-control-layer[data-revealed='true']`). **The Title** is the `wire` treatment: at rest fitted by `edgeTitleRoom(span)` in `@project/ui` (span less `EDGE_TITLE_CLEARANCE`, capped at `EDGE_TITLE_CEILING`, nothing below about three characters and the ellipsis — canvas units, no zoom rule; property-tested in `edge-title-room.test.ts`), whole up to the ceiling while revealed, dimmed when hidden, and the one-activation `Edit Title <name>` control; writing it swaps in `InlineTitleEditor`'s `edge` variant, which reports a refusal through `errorShownBy` rather than drawing its own. **The toolbar** is `[Edit][Show/Hide Title][Delete]` in one `Edge commands` group, named `Edge <Title>` or `Edge <From> → <To>`, built on `CanvasCommandToolbar` (`test/unit/command-surface-sharing.test.ts` lists it). **Keyboard**: the Edge is the tab stop and focusing it selects it; `enterToolbar` in `edge-authoring-react.tsx` (a captured `onKeyDownCapture` in `domAttributes`, so React Flow keeps its own Escape) moves focus on Enter to the toolbar's first command; Escape in the chrome returns to the Edge; the toolbar is not tabbed through on the way to the next Edge. After a Title edit ended by Enter or Escape, focus returns to the Title — waiting for the projection that draws a newly written one — or to the Edge when there is none; a draft completed by blur leaves the caret alone. **To focus and select an Edge programmatically**, request an Edge continuation (`continuation.request({ target: { kind: 'edge', graphId, edge }, select: true, then: 'focus' })`), which `CanvasContinuation` spends once React Flow has drawn it; focusing the element also selects it through the `onFocus` bridge. On the HUD side, the published `GraphLegend` component in `@project/ui` is **deleted** — one production caller, so folding its markup into `GraphHud` concentrated rather than spread complexity — while `graphColor` and `FALLBACK_GRAPH_COLOR` stay a shared seam in `packages/ui/src/graph-color.ts` because the Command Dock's Graph cluster and the HUD's key are two real consumers that must not disagree. The key is kept deliberately: it is the on-canvas colour reference beside the Edges being read, and the only one of the two on screen without a menu being opened for it (`overview.spec.ts` holds them to the same titles, colours and emphasis). `GraphHud` uses Tailwind utilities, which is why `packages/app/src/tailwind.css` `@source`s `packages/react-flow-adapter/src` — without it those classes are purged.
- **Edge Authoring carries a structured refusal across its seam, never prose (ADR 0057).** `EdgeAuthoringState.refusal` is an `EdgeRefusal`: the domain's `AuthoringRefusal` plus the least context a surface needs to recognise its own — `command` with the Edge it names (any of the Edge toolbar's three commands, drawn in that Edge's one alert region under its toolbar) and `gesture` (a completed pointer drag whose surface has gone, so the canvas announcement is all that is left). `connection-completion.ts` answers the same structured value. The draft is `pointer-connect` or `title`; a `title` draft stands only while the selection names its Edge, and a refused Title keeps it standing so the field stays open with its reason. Every toolbar command selects its Edge first — the Selected Edge is the one an authoring gesture acts on — so a retained `command` refusal is dropped when the canvas selection moves. The prose comes from `describeAuthoringRefusal`, derived per render and never stored.
- **ADR 0042 — interaction drafts stay local, and Space replacement invalidates them. Built.** The **result vocabulary** is described in full in `docs/agents/editing-and-persistence.md`, under "Space Authoring's completed-edit lifecycle". The **invalidation half** landed with package 7, and it is the Edge draft that carries it, because that draft is the only one there is: `edge-authoring.ts` holds the epoch it last saw and cancels the draft when `replacementEpoch` moves, when the selected Map changes, when the Active Graph changes, or when the draft's own subject leaves the projection — and by nothing else, so an unrelated completed Edit leaves a drag standing. A cancelled draft also asks for focus, since the element it was about may have been holding it. `replacementEpoch` still gates the completion drain (`space-authoring.ts`) and `SpaceCanvas` is still remounted on `key={replacementEpoch}` in `App.tsx`; those are the other two readers, and they answer different questions. See `.scratch/interaction-draft-invalidation/issues/01`.
- **A Resource's controls reach `CanvasResource` only with the operation that performs them, and presence of that operation is the whole capability (architecture-review/21).** `ResourceNodeData` carries no `titleEditingEnabled` or `resourceEditingEnabled` flag beside `onBeginTitleEditing` and `onOpenChange`, because a boolean beside an operation can disagree with it. `ResourceNode` checks only `data.onOpenChange !== undefined` and `data.onBeginTitleEditing !== undefined`; ordinary availability is decided once, in `canvas-resource-decoration.ts`, by whether the composition assigns the callback at all. The inline title editor is the sharper case and it is a **type** fact rather than a guard: `titleEditor?: ResourceTitleEditor` holds `onComplete` and `onCancel` together, so a composition cannot ask for the editing state without saying what ends it. The Markdown body follows the same rule with the display's `editing` arm, which carries the editor with the Markdown it edits and is made only by `beginEditing` in `@project/ui` (an Image Resource's replacement likewise with `replacing` and `beginReplacing`), so only an Open Resource's own content can be given one; a retained Save keeps that editor and its caret, while an accepted Save or Cancel ends it. `readOnly` is the surviving suppression for a dormant embedded Resource, forwarded from `ResourceNode` to `CanvasResource`, which withholds Open/Close and begin-title-edit regardless of a supplied operation. Don't add a boolean beside an operation, and don't paper over a missing one with `?.`: `projection-types.test.ts` pins the absence of both flags and the title-editor pairing.
- **A Resource's content resolves once, in `graph` (ADR 0070, ADR 0123).** `resolveResourceContent` (`packages/graph/src/lookup.ts`) owns single-hop resolution for every kind: it answers one `ResourceContent` value (`markdown`, `image`, `space`, or `unresolved` for the states intake refuses), and its `via: 'self' | 'reference'` is the whole of read-only-by-reference. The projection puts it on the node's `display` — `closed` or `open`, then `editing` or `replacing`, which `beginEditing` and `beginReplacing` (`packages/ui/src/resource-display.ts`) make only for Open own content — and `CanvasResource` and the embedded Map draw from that alone. A Closed display carries no content. Presenting draws `PresentedResource` on the Stage from the same `ResourceContent`. An Open Space Resource draws the Map and Graph it selects, and in Edit authors the Space it points at. **A drawn Resource names nothing outside itself (ADR 0083)**: neither a Reference Resource's Target nor a Space Resource's target Space is drawn by name on it, so the kind glyph and the Reference Resource's dotted border tell those Resources apart from the ones they point at. The kind glyph sits in the Resource's header rail above the Title, on every kind but the Ur Resource, whose Shape says what it is.
- **The drag lean is a rigid motion in two halves, not one transform.** A dragged Resource leans by `CANVAS_RESOURCE_DRAG_TILT_DEGREES` — `.canvas-resource[data-state='dragging']` in `canvas-resource.css` — and that reaches its own descendants only. An Open Space Resource's embedded Resources are React Flow sub-flow children, drawn as DOM siblings of its wrapper. `discoverEmbeddedOpenSpaceResources` carries the dragged Resource's centre down as `tiltCenter` (a nested embedding takes its dragged *ancestor's*, never its own parent's; `untiltedPosition` walks a leaned publication back before `embedBounds`). `embeddedMap`'s `tiltedPosition` rotates each child's **position** about that centre, and `styles.css` turns each one in place by the same angle off `data-drag-tilted`. `embedded-map.test.ts` holds the motion as a rigid one — distance from the centre preserved, bearing turned by exactly the angle.
- **Edges follow the moved positions; overflowing cuts and the window clip take the same turn.** Nothing in the embedding transforms an Edge (`leaves the Edges to React Flow, which draws them from the positions that moved` in `embedded-map.test.ts`). `leanedClipPath` turns the overflowing cut in place; `turns an overflowing cut about the Resource so it leans with the window` pins the unleaned inset, so clip runs before tilt. The window's SVG `<clipPath>` rect in `SpaceCanvas` is written as `rotate(angle cx cy)` about the same centre.
- **Which Resource is being dragged comes from React Flow's `nodeLookup`** (`useStore` in `SpaceCanvas`), not a projection node's `dragging` flag and not the adapter's `dragOrigins`. **Lean the Resource, never `.rf-resource-node__inner`.** The embedded canvas leans one frame after the frame does, because the embedding is republished through an effect rather than in the render that starts the drag; `expectEmbeddedResourceToFollowDrag` exempts that first frame by name and holds every later one, the release and the settled state to the motion exactly. **The angle is `CANVAS_RESOURCE_DRAG_TILT_DEGREES` in `@project/ui` and is written nowhere else**; `canvas-resource.css` reads it as `--canvas-resource-drag-tilt`, published by `CanvasResource` onto its own element, which is both what lets a Ladle story outside any canvas lean and what the e2e helper reads the angle back from rather than importing it.

- **Resizing is one canvas draft (ADR 0122, ADR 0084).** The render adapter layers one proposed size over the authored Placement and republishes from it; React Flow's node-only dimensions frame is refused. What the draft previews is the **resizing Resource's own rect and nothing else**. Its neighbours are drawn from the authored placement the draft was built on and do not move until the Edit lands, because displacement is applied by the Edit that causes it (ADR 0084) — there is no derived layer over the Map's positions to preview. **`Placement` has no drawn layer and no authored-point conversion**; do not add a draft that republishes a Resource's neighbours, and do not add a `move` draft — a dragged Resource displaces nobody, so drag is React Flow's default and a settled drag authors the drop point exactly. A proposal is floored at the Closed Size on each axis, the one floor for every kind, and there is no snap: a Resize back to the Closed Size is an ordinary Resize and changes no Open/Closed state. General grid snapping is out of scope (ADR 0122). `SpaceAuthoring` receives only the final size; cancellation, focus loss, unmount and replacement discard the complete draft without an Edit.

## The strategy contract and Placement

The rules — authored Maps, which strategy runs at render, positions-only output, Auto-arrange as an Edit, membership and displacement — are owned by [`maps-and-graphs.md`](maps-and-graphs.md) §1, §5 and §6. What follows is how the code keeps them.

- **The strategy contract lives in `graph`, not the adapter.** `gridStrategy` (pure) exists partly to keep the seam honest; if a change only works for one implementation, the contract has leaked. Which Resources get arranged is the caller's choice. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **A `Placement` is built through its module, never by hand; a Map projects only its authored Resource membership.** The resource→position map is one branded `ReadonlyMap<ResourceId, MapPosition>` in `graph/src/placement.ts`, over `core`'s schema-derived point, and `graph` declares no point of its own. Reads are ordinary map reads; **construction is closed** — `new Map()` will not typecheck as one — because a map built by hand and installed whole is the specific bug this exists to prevent. A Map's position keys **are** its Resource membership ([`maps-and-graphs.md`](maps-and-graphs.md) R31), so the canvas projection uses `mapResources` — the Space's own Resource objects for that Map's members, in `space.resources` order — and never manufactures a position for an omitted Resource; the Resources list on the Dock — `ResourcesPopover`, a Popover anchored to the Dock's own trigger — is the surface that reveals one addressed canonically. `Placement.next` promotes only the Resources a completed gesture placed. A Resource a reprojection catches mid-drag keeps the place the author last left it. Nothing in the module mutates an argument or hands two callers the same map, which is why `empty` is a function and the points are copied on the way in. A completed Edit does **not** need a forced identity to re-render: it replaces the working snapshot, and the `LayoutStrategyGraph` derived from it re-fires the same effect (pinned in `placement-rendering.test.tsx`).

- **`canvasProjection` is what the render adapter publishes.** `canvasProjection(space, resolved)` (`packages/app/src/canvas-projection.ts`) takes `@project/graph`'s `ResolvedMap` and answers a `PendingCanvasProjection`: the `strategyGraph` it builds, the `colors` it derives from the Space, the `visibleGraphs` it reads off the Map's own `graphs`, and a `project(laidOut, interaction)` returning the React Flow nodes and edges. None of those is state anything carries. It is a pure module and deliberately not a hook — no store, no React, no DOM — so the whole derivation is tested in the node environment (`canvas-projection.test.ts`, and `canvas-projection.property.test.ts` for the handle-resolution invariant React Flow warns about as #008). The `LayoutStrategyGraph` it takes is **not nullable on purpose**: there is nothing worth projecting before a strategy resolves, and requiring one stops a caller publishing a projection whose every Resource sits at the origin. The Map it projects comes from `map-resolution.ts` ([`editing-and-persistence.md`](editing-and-persistence.md), "Map resolution answers one authored Map"). The word *projection* names this bridging construct in `app` and the adapter and is deliberately absent from `CONTEXT.md`, whose render-layer section forbids inventing a domain term between React Flow's vocabulary and ours.

## Handle geometry

- **A Resource has four Edge anchors, one on each side, and they are the same four handles the authoring gesture uses (ADR 0087).** An Edge attaches to the anchor on the side that faces the other Resource. Nothing about it is stored, authored or carried in the document. There is no per-Graph `<graphId>::in`/`::out` handle family: four anchors named for their sides satisfy React Flow's rule that handles of one kind on a node be distinguishable (warning #008). Don't add one, and don't read an older record that describes such a family as current.
- **The side is chosen in the Edge component, not in the projection — and that siting is the decision, not an implementation detail.** `canvasProjection` is pure, tested in Node and the tempting home; it is the wrong one, because **the projection does not run again during a drag**. The render adapter splices React Flow's live node positions into the published projection and leaves the Edges as they were, and the Edit lands only at settle. A side chosen in the projection is therefore correct only after release, and the Edge stays attached to the far side, crossing its own Resource, until the author lets go. `useEdgeAttachment` in `RoutedEdge.tsx` reads both Resources from React Flow's store; the rule itself is pure (`edge-attachment.ts`, one function from two rects to a side) and tested in the node environment.
- **The axis is chosen by the gap between the rects, not by the vector between their centres; the direction along it is the centre vector's (ADR 0110).** `facingSides` in `edge-attachment.ts` takes the axis whose gap is larger — positive when the rects are clear on it, negative by the overlap depth when not, so two overlapping rects take the axis they overlap on least — and then only the sign of the centres' difference on that axis picks which of the two sides (`edge-attachment.test.ts`). Two Resources are side by side when they are clear of each other on one axis and overlapping on the other, whatever their sizes — and a tall Open Resource with a small one by its lower edge is a pair the centre vector calls vertical. A Resource is 260×146 until resized and any size at or above that after, so large beside small is the normal state of a Map someone is reading rather than an edge case. React Flow's own floating-edge example computes both centres from the *intersection* node's half-size, which is correct only while every node is the same size; don't copy it.
- **A self-Edge is taken first and never enters the rule.** ADR 0032 makes cycles legal, and the facing rule would answer a plausible wrong pair for one: a rect against itself overlaps on both axes and its coincident centres fall to the `>=`, so it leaves Bottom and enters Top, drawing the curve straight through its own Resource. `selfEdgeAttachment` answers a fixed loop over two adjacent sides.
- **An Edge names no handle, and a Resource declares all four anchors of each role.** React Flow resolves an Edge that names no handle to the first bound of that kind, and `getEdgePosition` returns null — drawing **no Edge at all**, not a misplaced one — for a Resource whose handles it cannot resolve. That is why the anchors render on *every* Resource, including a read-only one and a Resource inside a Space Resource's embedded Map. Both states still draw Edges, and an Edge attaches to an anchor: a Read embedding keeps the anchors and withholds the gesture; Edit publishes the same handle affordance the host canvas does. An embedded Resource's `clip-path` leaves `AUTHORING_HANDLE_DIAMETER / 2` of slack on every side that does not overflow the window — `inset(0)` clips the handle centres that sit on the rim, and `embedded-map.test.ts` holds the inset.
- **An anchor is not an affordance.** The four render always; `data-connection-authoring` on `.rf-resource-node__inner` says whether an author may take hold of one, and every reveal rule in `styles.css` is conditioned on it. A Resource that is not authorable carries four unlabelled `aria-hidden` anchors with `isConnectable` false.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `ResourceNode` and `styles.css` dim handles via `opacity` and it looks like a styling choice; it isn't.
- **Handle geometry is declared, never re-measured — do not add `useUpdateNodeInternals`.** React Flow measures handles once and caches, which is its named cause of warning #008, and the documented remedy is `useUpdateNodeInternals`. Here that remedy is **wrong**. `projectResourceNodes` declares `node.handles` from the rect the strategy placed (`declaredHandles` in `projection.ts`), and `parseHandles` in `@xyflow/system` builds `handleBounds` from those declarations without consulting the DOM at all; React Flow's own resize observer re-reads them when a node changes size. Unit tests cannot see what a forced remeasure breaks — jsdom reports `offsetWidth` 0 — so `ResourceNode.test.tsx` pins only that no call is made. The browser suites are the evidence: with the call in place on mount and on Opening, `pnpm e2e` fails 26 tests, among them `editing.spec.ts` "a second connection drawn in the same session resolves its handles" and "opening a Resource displaces its neighbours once…", and `pnpm e2e:ladle` fails three, among them `edge-toolbar.spec.ts` "hovering an Edge's line reveals its toolbar…". Method and the full list are in `.scratch/code-quality/issues/27-decide-whether-resource-node-abstains-from-remeasuring.md`. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **`anchorPoint` and `declaredHandles` both read `AUTHORING_HANDLE_DIAMETER`, and that is load-bearing.** React Flow puts an Edge's end on the *outer rim* of the handle it resolves — `(x + w + 12, y + h/2)` on the right at 24 units — so the Edge component's own arithmetic has to be the same arithmetic, or an Edge lands near its anchor rather than on it.
- **Neither React Flow's `toNode` nor the DOM alone answers "is this empty canvas".** `getClosestHandle` resolves `toNode` by distance from the pointer to a *handle* within `connectionRadius` — 20 at the pinned 12.11.2 — so it is non-null over blank canvas near a handle and **null over the middle of a Resource**, whose centre is some 73px from the nearest handle at 260x146. An Alt/Option empty-drop therefore needs both answers, with a connection target in range outranking the element underneath: drop the DOM half and a release onto a Resource's body authors a Resource on top of it, drop React Flow's half and a release just outside a Resource authors one where the author was aiming at a handle. Both pure rules live in `packages/app/src/edge-authoring.ts`: `dropTarget({ connectionTarget, element })` composes the two answers and `newResourceDrop` decides the Resource. **Two sites ask `dropTarget`** — the preview and the connection release. The DOM half is typed `ElementDropTarget`, three values wide, so a hit-test cannot hand on the `connection-target` only React Flow can resolve. Preview and release ask the same rule but deliberately supply different DOM facts once the pointer leaves the canvas: preview keeps the last container `onMouseMove` classification, while release performs the authoritative `elementFromPoint`. Closing that gap would add a document-level pointer listener and a DOM hit-test on every frame, defeating the narrowed non-positional state write that avoids per-frame flow rerenders. The accepted argument is `.scratch/card-route-editing/edge-authoring-design.md`; don't re-inline either rule into `SpaceCanvas`, don't recompose the precedence at a third site, and don't make the preview hit-test live without measuring that cost.
- **Which anchors exist changes where an Alt/Option empty-drop authors a Resource.** `getClosestHandle` measures distance to a handle, so the anchor set and the drop classification are one question read twice. `pnpm e2e` is what catches a regression.

## Camera

- **A camera command is issued, never awaited, and never contained (ADR 0043).** `setCenter`, `fitView`, `fitBounds` and `zoomTo` return a Promise that is **not a completion signal**. At the pinned release it resolves only when the animation reaches its end: a *superseded* transition fires d3's `interrupt`, which `getD3Transition` does not listen for, so that Promise stays pending forever — and any second camera command while the first is running produces exactly that. `fitView` before `panZoom` exists hangs too (`resolveFitView` begins `if (!panZoom) return`, abandoning the `withResolvers()` resolver). So **never chain required work on one** — a superseded two-phase presentation move did, with `.then`, and stranded the camera at the overview zoom whenever the author traversed inside the pan's own 400ms. Nothing chains: `CanvasContinuation`'s reveal issues its `fitView` and focuses the Resource in the same pass rather than on the Promise (`canvas-continuation.test.tsx` holds it against a real `ReactFlowProvider` whose `fitView` never settles, having no pan-zoom and no measured node). If required follow-up work ever appears, it goes on a timer the issuing effect cancels. `fitView` is worse than the rest here — it *reuses* one resolver across calls, so a second call before the first settles cannot be told apart from it. Equally, **never add a blanket `.catch`**: neither bundle calls `reject`, so the only reachable rejection is a synchronous d3 throw inside a Promise executor — a genuine fault, and the one signal worth hearing — while both real failures are hangs a `.catch` cannot observe. Plain `void` is deliberate. The camera that places an entered Space at its stored framing lives in `packages/app/src/components/cameras.tsx` (`packages/app/test/cameras.test.tsx`, where every stubbed call never settles); the other imperative camera commands are the reveal in `components/CanvasContinuation.tsx` (`canvas-continuation.test.tsx`) and the zoom controls in `react-flow-adapter`'s `ZoomSlider.tsx`, plus the `fitView` prop `SpaceCanvas` hands React Flow. Checking the rule means reading those, not one module; `grep -rnE 'fitView|setCenter|fitBounds|zoomTo|zoomIn|zoomOut|setViewport' packages/*/src` finds them.
- **`maxZoom` is raised so an author can read one Resource at screen size — don't drop it back to the default.** A Resource is 260x146 at the Closed Size, so filling a 1280x720 viewport with one needs a zoom of about 4.9 and a 3840x2160 one about 14.8, against React Flow's default ceiling of 2. `SpaceCanvas` passes `maxZoom={MAX_ZOOM}` (`packages/app/src/camera.ts`, 16) for that reason. Presenting no longer zooms the canvas at all (ADR 0123).
- **Presenting draws on its own Stage, never on the canvas (ADR 0123).** `PresentingStage` composes `Stage` and `PresentedResource` from `@project/ui` with `PresentingChrome`: one 16:9 frame, the largest that fits above the chrome strip, letterboxed, with type sized in container units in `packages/ui/src/stage.css`. The canvas stays mounted behind it, `inert`, and nothing on it knows about presenting — the projection draws every Resource Closed or Open as its Map authors it, and no camera moves, so leaving presenting finds the viewport exactly as it was. **Don't put a presented display, an active-Resource flag or a presenting camera on the canvas.** **Present takes the whole document fullscreen** (`presenting-fullscreen.ts`, over the one Fullscreen API adapter `browser-fullscreen.ts`, which `main.tsx` names `document` for and hands to `createSpaceStartup`, required with no default from there through `createOpenSpaces` to each `createApp`): the request is made synchronously inside the Present gesture, on `document.documentElement` so a dialog portalled to the end of the page stays visible over the Stage. A refusal is tolerated, a presentation opened from a link never asks, and only a presentation that entered fullscreen ends with it — leaving fullscreen leaves presenting, and leaving presenting exits fullscreen. The chrome (`PresentingChrome`) sits in the Stage's strip below the frame and enumerates the active Resource's outgoing Edges, because the Stage shows no neighbour. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a store selector** — `Navigation.moves()` is called at render time in `App` for exactly this reason; as a selector it would hand the store a new array identity every render and re-render until React gives up. It is deliberately **not** `useMemo`'d either: `moves()` takes no arguments and reads the session's current working Space through Navigation, so a memo keyed on the values in scope would go stale when an authored Edge changed the Space and `PresentingChrome` would stop offering the move that had just been drawn. A render-time call is safe here because nothing subscribes to the array's identity: a fresh array cannot feed a re-render. **It can feed an effect too often, though, and that is a real hazard rather than a theoretical one.** `moves` is a new array on every App render, so an effect keyed on it runs on every App render. The scroll-into-view effect is keyed on the selected Resource's id for that reason: keyed on `moves`, it would re-scroll the choices row on every unrelated publish and snap a presenter's sideways scroll back under them. The focus effect still takes `moves` and is safe only because a ref guards its body — key anything new here on the value that changed, never on the array. **The chrome is composed from `@project/ui` and owns its own interaction (design-system baseline Issue 07).** It draws the moves, Back, the applicable keyboard guidance (shadcn's `Kbd`) and Overview from shared primitives, with all of its styling in the module — nothing named `presenting` is in `styles.css`. Four facts about it are decisions rather than details. It **owns the indexed list it renders**, so it computes the selected-index delta and calls `selectBranch(delta)`; `App` does none of that arithmetic. A move **names the action it performs** — `Choose <Title>` unselected, `Go to <Title>` selected — and is never a radio, a toggle or a disabled destination, because selection alone is not the completed action. The moves and the End-of-Graph text **share one polite `role="status"`**, so a changed choice set is announced without focus moving. That region also carries the selection as `sr-only` text: Up and Down rewrite an `aria-label` and a variant class, and neither is a text change, so under `aria-atomic="false"` the region would otherwise have nothing to read and a screen-reader presenter would arrow across a fork in silence. Each control that performs a globally bound key also announces it with `aria-keyshortcuts` — the selected move `ArrowRight`, Back `ArrowLeft`, Overview `Escape` — because the visible `Kbd` guidance is presentation only. And it carries a **focus debt that only its own controls set**: advancing or retreating from inside the chrome restores focus to the newly selected move, else Back, else Overview, while a traversal run from the global arrow keys leaves focus exactly where the presenter left it. The debt **begins owed**, because entering presentation strands focus the same way — presenting removes the whole command surface (ADR 0082), so the Present control focus was on goes with it and there is nothing left for a Space aimed at advancing to defer to. The chrome claiming focus as it mounts is what makes the first Space advance. **The global Traversal keys live in `presenting-keys.ts`**, not in an effect written out in `App`, because a Ladle story proving their one load-bearing rule has to bind the same listener the application binds: the handler **defers to native activation**, so Space on any interactive control activates that control once instead of also advancing. That rule is written over interactive controls generally — chrome and Dock alike — and never as a special case for one button; Arrow and Escape stay global.

## React Flow itself

- **React Flow is pinned to 12.11.2.** The declarative `node.handles` path above intentionally depends on behavior verified against that release. Upgrade both consuming manifests together and run the complete Playwright suite; do not widen the range or accept an automated upgrade without revalidating handle resolution, consecutive connections and warning #008 in a real browser. The camera-Promise facts above are pinned to it too — re-read `setTransform`, `scaleTo`, `scaleBy`, `resolveFitView` and `getD3Transition` when it moves.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. **It is incomplete, though** — a read of it for nesting reported sub flows as absent while `/learn/layouting/sub-flows` exists and is quoted in our own findings, so use it for breadth and fetch the page for a specific mechanism. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`, whose §8 covers multiple canvases and nesting.
- **Every drawn Map uses `createMapSurface` and `useMapSurface` (ADR 0112).** The drawing names its Space composition, Map, Graph, occurrence and policy. The render adapter, Edge interaction draft and continuation belong to that occurrence; authoring, command outcomes, delete confirmation and image replacement belong to its Space. `EmbeddedMapAuthoring` places the shared drawing into the containing React Flow instance. Its Edge ids and endpoint ids name the occurrence, while `data.subject` keeps the domain Edge identity. The Active Graph's Edges use the shared `AuthorableEdge` controls in authoring policy; inert and read-only drawings withhold them. Selection and keyboard commands follow the selected occurrence. **Drawing holds keep an unlisted target composed**: a Space is composed while anything holds it — its listing in Open Spaces, or a drawing of one of its Maps — so a drawn target needs no listing to stay composed. Root presentation and one camera remain the recorded differences. **The root canvas reads its surface the same way.** `SpaceCanvas` takes a required `surface`, the `reading` `useMapSurface` answers for it, and `placement` as one value, and draws under exactly the policy that surface holds: its view, next Resource Title, render-adapter reading, editing reports and availability come from the reading, Space Authoring and Edge Authoring from the surface, and the Map, Active Graph and presenting from `surface.context()`. The Dock and the presenting Stage read that same reading: `App` takes the Space, the selected Map, its projection, the Resources outside it and their memberships from `reading.view`, and a `MapView` carries the Space it was built from, so the Dock and the canvas — the canvas's Space title included — draw from one Map view per drawing. The address, the Resources disclosure and the Stage's Copy link read the Map id from Navigation instead, because Navigation owns the address and the root surface follows its selected Map. Its other props are the Space-level collaborators no surface holds — `commandOutcomes`, `deleteConfirmation`, `imageReplacement`, `nameOnCreation`, `spaceSession`, `spaceResourceTargets`, `resourceEntityActions` — and the two callbacks through which its drawn Maps report their Spaces and clipboard failures to `App`, `onDrawnSpacesChange` and `onDrawnClipboardFailuresChange`. `SpaceCanvas-types.test.tsx` holds that exact set, so a capability the surface can answer is added to the surface rather than threaded through `App` as a prop. `App` keeps its one `useMapSurface` call, because the Dock reads the same availability, and keeps the `key={replacementEpoch}` on the element. An embedded Space Resource can Open, Close and move, but only a root Space Resource offers Edit, so deeper drawings stay inert. References inherit read-only policy. `OpenSpaces.hold` composes a drawn target without listing it; the drawing releases its hold when it leaves, and a composition survives Exit while another holder remains. Keep the canvas mounted through placement pending so a transient empty projection does not release a still-drawn target's composition or outcomes. Undo/Redo dispatch remains deferred until V1 has history, as agreed in ticket 07.

- **An invariant reached from a canvas gesture is reported, not thrown.** `AuthoringResult` says a broken invariant "throws, or is reported through the non-throwing reporter" (`space-authoring.ts`) without saying which a caller picks; at this seam it is always reported. A pointer release or a key press arrives from the browser's event loop mid-gesture, so throwing there unmounts the tree and costs the author their Space for a defect they did not commit. The gesture instead authors nothing and answers the outcome that owes the author no prose — never a refusal, which would put a wiring defect in front of them as their own mistake. `connection-completion.ts` reports a `queued` completion through the reporter supplied by the Space composition (ADR 0109).
- **React Flow's interaction model is the default.** Start from the pinned release's documented keyboard, focus, selection, pointer and accessibility behavior. Prefer shaping Hyper's feature around those expectations over reshaping React Flow around a locally convenient interaction. Every deviation needs an explicit product requirement and an interrogated, recorded reason; do not customize merely because a different gesture seems preferable.
- **A Graph's head markers live once per canvas, not on each Edge (ADR 0105).** `GraphHeadMarkers` is mounted as a child of every `<ReactFlow>` — `SpaceCanvas` and the stories' `StoryCanvas` — and draws one marker per Graph into one hidden `<defs>`, read from the flow's own Edges, so an embedded Map's Edges are covered by the host canvas's. `projectGraphEdges` sets each Edge object's `markerEnd` to its Graph's marker id (`graphHeadMarkerId`, `graph-head-<graphId>`), and `RoutedEdgePath` only forwards the `markerEnd` React Flow hands it. The ids carry no flow prefix, which holds because a page draws Graph Edges in one `<ReactFlow>` — the only page mounting several, the Resource specimens in `resource.stories.tsx`, passes them no Edges. A page drawing Graph Edges in a second flow would need the ids namespaced per flow, as React Flow prefixes its own with the flow's `id`. A new canvas that draws Graph Edges without mounting `GraphHeadMarkers` draws them headless. The glyphs themselves stay `@project/ui`'s `GraphHeadMarker`; the connection preview (`GraphConnectionLine`) is a separate SVG and draws its own.

## Multi-Graph overlay and the fixture

On multi-Graph rendering (`.scratch/multi-route/` retains its historical path): a Map overview draws every Graph that Map owns, and activation is emphasis, not filtering, at all times and not only while presenting ([`maps-and-graphs.md`](maps-and-graphs.md) R22, R29). The dimming surface uses Graph names (`projectGraphEdges`, `GraphHud`'s Graph key and related helpers); do not add Route-named aliases. `graphResourceIds` is right for a view that wants one Graph; no handle filter stands beside it, because an Edge attaches to one of a Resource's four anchors whatever its Graph (ADR 0087). A Map's `graphs` is the full Graph values it owns, and what a selected Map draws is exactly them. There is no Space-level Graph collection and no Map-level list of Graph ids filtering one: `space.graphs` is a derived flatten across Maps, and a document declaring a Space-level one is **rejected at intake** — by the private `retiredSpaceGraphs` in `graph/src/space.ts`, composed into `documentRefusal` and reached only through it, which `loadSpace`, `loadSpaceSnapshot` and `readSingleSpace` each ask once, so neither a file, a commit nor an import can carry one. It is deliberately *not* declared in the schema: `spaceFileSchema` is strict, so an undeclared key is already refused rather than stripped, and this check survives that to *name* the one that matters — a Space-level `graphs` carried the whole topology, and a reader told only that some key is unrecognized has to work out why that one mattered. Don't answer it by declaring the key, which puts it in the inferred document type Hono's RPC contract is checked against. Which Resources a View chooses from its subject is passed into the strategy (ADR 0005, ADR 0040) — don't let the strategy decide it.
The overlay limit: only an acyclic union of the visible Graph Edges lays out on a clean left-to-right axis, as parallel forward paths. A backward Edge can come from a cycle inside one Graph or from two Graphs disagreeing on the order of shared Resources. Nothing routes an Edge: the strategy contract has no routed sections to emit and `RoutedEdge` draws only a bezier (ADR 0086), so a back-edge reads as a self-curling stub. Here “routed” is qualified graph-layout geometry, not the retired Route entity. Read `.scratch/multiple-routes/findings.md` before extending any of this.
The app loads the **tracked fixture aggregate** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev:fixture` serves and what Playwright drives, so e2e asserts *behaviour* against purpose-shaped Graphs rather than demo prose. `hyper.json` names the Map fixture as Meta; ordinary Spaces hang off Linked Spaces, a third Map of Space Resources, so Collection 1 still opens first. Meta is **two disconnected collections** sharing no Resources, which are its first two Maps, `Collection 1` and `Collection 2`: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several Graphs over one spine — plus `T`, a sixth member of that Map no Edge reaches, whose Title is the fixture's one three-line Title (ADR 0083), so the Title ladder and the Map membership Add Resource leaves behind are both drawn by the Space the app and Playwright actually load; (2) `Echo E→F→G→H→E′` — a plain linear collection. Collection 1 and Collection 2 rather than one Map is deliberate — it is still the place in the tree where the Space-subject flatten crosses a Map boundary. Linked Spaces is a third Map of Space Resources and does not share that flatten. Both position maps are **authored**, as placement always is (ADR 0014): a hand-set grid in the space file, so selecting a Map draws its Resources where the file put them and first paint moves nothing. Nothing recomputes the fixture's positions: they are hand-set test data, so don't regenerate them from a strategy. This is about the fixture only; an author-invoked Auto-arrange writing positions back is a different thing ([`maps-and-graphs.md`](maps-and-graphs.md) R6). Each returns to its start via a Reference Resource (`A′`/`E′`, told apart from their Targets by the kind glyph, the dotted border and the Titles the author gave them), never an Edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture Graph is a **line** — one Edge out per Resource — which is the degenerate Graph shape, not a second kind; forks and merges are covered by unit and property tests, not here. The demo stays in `packages/app/example/`, dormant — it is a Space directory nothing loads, kept as narrative content rather than as a pending capability, since the CLI importer loads real Space directories. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a Space file would be scanned as a Resource). If legible multi-Graph overlay becomes real product work, design it deliberately.
