# Canvas & Rendering

React Flow, handle geometry, the camera, and Edge Authoring. Read before touching `packages/react-flow-adapter`, the canvas/camera modules in `packages/app`, or `edge-authoring.ts`.

## Edge Authoring and drafts

- **ADR 0033 — authoring is drag-to-connect through four spatial handles coloured as the Active Graph.** Built: source handles appear on the hovered or selected Thing; target handles appear during the drag. They are Graph-independent and the chosen side is not authored. Edge creation is spatial and handle-driven for now; there is no keyboard Connect control or target-picker workflow. Initial-Graph minting and Option/Alt empty-drop create-and-connect are built, alongside Active-Graph Edge focusability, the selected Edge's controls and endpoint editor (`SelectedEdgeControls`), pointer reconnection and selection-based deletion. Detached Thing creation has its controls too — the toolbar's Add Thing and the graph-focused `C` — and a Thing can be removed from its Diagram with Backspace or Delete, which acts on the Thing the key was aimed at and falls back to the selection. *Structural* deletion, meaning deletion of a Thing from the Space, is still built **as an operation and not as a control**; see the ADR 0040 entry in `docs/agents/editing-and-persistence.md`, which is the one place that list is kept. **ADR 0087 gave those same four handles a second job**: an Edge attaches to whichever of them faces its neighbour, so they are anchors on every Thing and affordances only where the canvas is authorable. The per-Graph attachment machinery that used to serve overview rendering is gone with it.
- **Edge Authoring is one module for the whole Edge lifecycle, and it owns no copy of anything (`.scratch/card-route-editing/edge-authoring-design.md`).** `packages/app/src/edge-authoring.ts` holds the one interaction draft, the refusal that draft ran into and the focus continuation a completed projection owes; `edge-authoring-react.tsx` is its React interface, answering `{ edges, edgeTypes, reactFlowProps, layer, provide }` plus the Edge operation used by the canvas's app-owned delete command. The **render adapter** stays authoritative for the projection, Thing movement and the discriminated `none | thing | edge` selection; **Space Authoring** stays authoritative for eligibility and every semantic Edit. Three consequences are load-bearing. *Selection is folded additively*: one React Flow selection action produces two callback batches — the new subject selected, then the other kind deselected — so reading the resulting arrays answers `none` for a click that plainly selected something, and the second batch must clear the union only when it still names the subject stored. *The Edge subject is the domain `{ graphId, edge }`, never the React Flow id*, which is `<graphId>::<from>::<to>`. That id is minted from the same triple the subject is compared by (`buildGraphRenderEdges`, `sameEdgeSubject`), and ADR 0032 makes the triple unique. It used to be `<graphId>::<index>` and re-index whenever a Graph lost an Edge, which meant a replaced Edge inherited its predecessor's id and, with it, the element React Flow had already drawn — so a completed reconnection landed its focus continuation on the stale element, whose `onFocus` bridge wrote the replaced Edge back over the selection just installed and left the Edge focused with no controls. **A canvas continuation is therefore spent a commit after the projection that carries it**: React Flow syncs the `edges` prop into a store of its own from an effect and draws from that, so an Edge it has never drawn is still absent when `CanvasContinuation`'s effect first looks. That component subscribes to React Flow's own synced `nodes` and `edges` (`useStore`) for the re-render, because nothing else gives it one — the projection publish is the render that is too early — and resolves an Edge subject against the subscribed list rather than a prop, so the id it mints comes from what the DOM is keyed off. **Both arms are load-bearing**: `syncProjection` copies the Edge list on every publication, which made the Edge arm look like it covered thing targets too, but `mergeProjected` replaces only the nodes — the create-and-connect path — and nothing in the Edge arm fires there. `state.edges` is what React Flow has *taken*, not what it has painted: `EdgeWrapper` still returns `null` while an endpoint's position is unresolved, and that recovery commit is driven by node measurement. Not reachable today, because `reconnectOutcome` refuses an endpoint that is not already a Diagram member — but `staysOwed` is unconditionally true for an edge target, so a continuation for a gesture that also created a Thing would wait with no timeout and no diagnostic. Don't remove either subscription and don't answer the gap by re-resolving on a timer. *The commands context wraps `<ReactFlow>` rather than sitting in `layer`* — React Flow renders Edges itself, as a sibling of the children it is given, so a provider inside the layer reaches no Edge at all. Backspace and Delete are disabled in React Flow and handled once by the canvas; the selected Thing or Edge goes through its completed Edit, and nothing mutates the controlled projection locally. **Reconnection runs through the connection callbacks as well as its own, and that is the trap.** `EdgeUpdateAnchors` calls `onReconnectStart` and *then* the store's `onConnectStart`; on release it calls the store's `onConnectEnd` before `onReconnectEnd`. So a reconnect drag arrives as a connection starting from the endpoint that stays put — which silently replaced the reconnect draft, leaving `reconnect()` with nothing drafted and the gesture authoring nothing, and let an Alt-held release author a Thing *and* delete the Edge. A `reconnecting` ref stands both connection handlers down for the drag's duration; don't remove it, and don't reach for a per-gesture flag in state, since both reads happen inside React Flow's own event. Two more facts in the same seam: `onReconnectStart`'s `handleType` names the endpoint that **stays** (the source anchor reports `'target'`), so the endpoint being moved is its inverse; and a source-endpoint drag looks for a new **source** handle, which is why `ThingNode` reads `connection.fromHandle.type` rather than assuming a drag always seeks a target. All of it is invisible to a unit test that calls `beginPointerReconnect` directly — `editing.spec.ts` is what pins it. Hyper never calls `reconnectEdge`; only the *selected* Active-Graph Edge is `reconnectable`, so two transparent endpoint anchors are not permanently live over every Thing's authoring handles. An endpoint released on empty canvas deletes the Edge, and that is safe to distinguish from a cancellation because `onReconnectEnd` is the *only* way a drag can end: **React Flow has no Escape path for a drag at all** — the key is consumed by the focusable node and edge wrappers, and a reconnect anchor is a bare `<circle>` that takes no focus — and `XYHandle` removes its document listeners only from its own `onPointerUp`. Those listeners have no React cleanup, so even an Edge that leaves the projection mid-drag still ends through that handler, which is what makes the `reconnecting` guard safe to clear there and nowhere else. `queued` at the React Flow seam is an invariant violation rather than an outcome — a pointer release arrives from the event loop with no Edit on the stack — so `connection-completion.ts` reports it and draws nothing.
- **The selected Edge's controls are `SelectedEdgeControls` in `app`, and the HUD's Graph key is `GraphHud`'s own markup.** Two vertical production modules that share a design language and no state. `AuthorableEdge` stays the React Flow adapter and owns exactly the framework's half: the routed Edge, `EdgeLabelRenderer`, the label coordinates, the selection translation, the portal placement and the `nodrag`/`nopan`/`nokey` containment — `.nokey` there is read by React Flow's still-live Space-key pan activation subscription, while Backspace/Delete belongs to `SpaceCanvas` and its application guard — plus, now, resolving Edge Authoring's one module-wide refusal to the two channels a selected Edge owns. `SelectedEdgeControls` takes domain facts and callbacks and **no `EdgeProps`, coordinates, `EdgeSubject` or commands context**, which is what lets `packages/app/test/SelectedEdgeControls.test.tsx` and the Ladle catalogue mount every state with no canvas under them. Its endpoint choices are snapshotted when the editor opens, so rows do not move under a pointer already on its way to one; the completion's own re-validation is what keeps the pick safe. Popover open state is controlled from Edge Authoring, which owns the draft. On the HUD side, the published `GraphLegend` component in `@project/ui` is **deleted** — one production caller, so folding its markup into `GraphHud` concentrated rather than spread complexity — while `graphColor` and `FALLBACK_GRAPH_COLOR` stay a shared seam in `packages/ui/src/graph-color.ts` because the Command Dock's Graph cluster and the HUD's key are two real consumers that must not disagree. The key is kept deliberately: it is the on-canvas colour reference beside the Edges being read, and the only one of the two on screen without a menu being opened for it (`overview.spec.ts` holds them to the same titles, colours and emphasis). `GraphHud` uses Tailwind utilities, which is why `packages/app/src/tailwind.css` now `@source`s `packages/react-flow-adapter/src` — without it those classes are purged.
- **Edge Authoring carries a structured refusal across its seam, never prose (ADR 0057).** `EdgeAuthoringState.refusal` is an `EdgeRefusal`: the domain's `AuthoringRefusal` plus the least context a surface needs to recognise its own — `connection`, `reconnection` with the attempted `endpoint` (the editor's From/To and form), `deletion` (the selected Edge's controls, no field), and `gesture` (a completed pointer drag whose surface has gone, so the canvas announcement is all that is left). `connection-completion.ts` answers the same structured value. Which channel a refusal lands on is decided where the interaction is known — a pointer reconnect is a `gesture`, while the selected Edge's endpoint editor uses `reconnection` — so no surface has to infer it from an absent draft. The prose and the Field come from the exhaustive adapters in `authoring-refusal.ts`, derived per render and never stored. A retained `deletion` refusal is dropped when the canvas selection moves, because it names the Edge that was selected when it was made.
- **ADR 0042 — interaction drafts stay local, and Space replacement invalidates them. Built.** The **result vocabulary** is described in full in `docs/agents/editing-and-persistence.md`, under "Space Authoring's completed-edit lifecycle". The **invalidation half** landed with package 7, and it is the Edge draft that carries it, because that draft is the only one there is: `edge-authoring.ts` holds the epoch it last saw and cancels the draft when `replacementEpoch` moves, when the selected Diagram changes, when the Active Graph changes, or when the draft's own subject leaves the projection — and by nothing else, so an unrelated completed Edit leaves a drag standing. A cancelled draft also asks for focus, since the element it was about may have been holding it. `replacementEpoch` still gates the completion drain (`space-authoring.ts`) and `SpaceCanvas` is still remounted on `key={replacementEpoch}` in `App.tsx`; those are the other two readers, and they answer different questions. See `.scratch/interaction-draft-invalidation/issues/01`.
- **A Thing's controls reach `CanvasThing` only with the operation that performs them, and an editor's presence *is* its editing state.** `ThingNodeData` carries `titleEditingEnabled` and `thingEditingEnabled` beside `onBeginTitleEditing` and `onEditThing`; `ThingNode` assigns a `CanvasThing` operation only when both halves are there. A flag raised over a missing operation used to draw a live control that ran nothing, so both layers withhold it. The inline title editor is the sharper case and it is a **type** fact rather than a guard: `titleEditor?: ThingTitleEditor` holds `onComplete` and `onCancel` together, so a composition cannot ask for the editing state without saying what ends it. The Markdown body follows the same rule with `bodyEditor`; a retained Save keeps that editor and its caret, while an accepted Save or Cancel ends it. Don't reintroduce booleans beside the operations, and don't paper over a missing one with `?.`: `projection-types.test.ts` pins the pairings.
- **Open Thing resizing is one canvas draft, with an application-owned Close snap (ADR 0066, ADR 0084).** The render adapter layers one proposed Open Size over the authored Placement and republishes from it; React Flow's node-only dimensions frame is refused. What the draft previews is the **resizing Thing's own rect and nothing else**. Its neighbours are drawn from the authored placement the draft was built on and do not move until the Edit lands, because displacement is applied by the Edit that causes it (ADR 0084) — there is no derived layer over the Diagram's positions to preview. **`Placement.drawn` and `Placement.authoredPoint` are gone**; do not reintroduce a draft that republishes a Thing's neighbours, and do not add a `move` draft — a dragged Thing displaces nobody, so drag is React Flow's default and a settled drag authors the drop point exactly. `THING_CLOSE_SNAP_DISTANCE` is 24 canvas units, independent of viewport zoom. Only a proposal inside that range on **both** axes becomes the exact Closed rect; a one-axis match stays an ordinary Open resize. The preview keeps the Thing Open for the gesture, so its resize control remains available until release. `SpaceAuthoring` receives only the final exact size and decides Resize versus Close; cancellation, focus loss, unmount and replacement discard the complete draft without an Edit.

## The strategy contract and Placement

- **The strategy contract lives in `graph`, not the adapter, and it carries positions only (ADR 0086).** A position lands as optional `x`/`y` on each Thing, and that is the whole of the output: a `LayoutStrategyThing` has no port collection and a `LayoutStrategyEdge` no routed sections, because a Diagram stores a Thing and its position and has nowhere to put either — so neither direction of the contract could ever have used them. `gridStrategy` (pure) exists partly to keep the seam honest; if a change only works for one implementation, the contract has leaked. Which Things get arranged is the caller's choice. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored, and no engine owns it (ADR 0025, refined by ADR 0079).** A strategy is *automatic* (computes placement from Things and Graphs alone — grid, name-sort) or *positioned* (reads a Diagram the author wrote). Automatic strategies are non-addressable capabilities; V1's selectable canvas contexts are authored Diagrams rendered by the positioned strategy. **No strategy is privileged and none may become the focus**; if a change only makes sense for one implementation, the seam has leaked. An automatic arrangement returns as a destructive Edit over an authored Diagram rather than as a render path, which is what took elkjs out of the tree (ADR 0086).
- **A `Placement` is built through its module, never by hand; a Diagram projects only its authored Thing membership.** The thing→position map is one branded `ReadonlyMap<ThingId, DiagramPosition>` in `graph/src/placement.ts`, over `core`'s schema-derived point, and `graph` declares no point of its own: the bare `Point` ADR 0085 split out typed the routed Edge geometry alone, and both left with ADR 0086 (`test/unit/point-type-identity.test.ts` holds the absence). Reads are ordinary map reads; **construction is closed** — `new Map()` will not typecheck as one — because the map built by hand and installed whole is the specific bug this exists to prevent, and it was fixed twice under two names before the type stopped it. Under ADR 0040 a Diagram's position keys **are** its Thing membership, so omission means the Thing is not in that Diagram. The canvas projection therefore uses `diagramThings` — the Space's own Thing objects for that Diagram's members, in `space.things` order — and never manufactures a position for an omitted Thing; the Things list on the Dock — `ThingsPopover`, a Popover anchored to the Dock's own trigger rather than the screen-edge drawer it replaced — is the surface that reveals one addressed canonically. `Placement.next` still promotes only the Things a completed gesture placed, and the render adapter's `syncProjection` reports rendered geometry rather than installing it. A Thing a reprojection catches mid-drag keeps the place the author last left it. Nothing in the module mutates an argument or hands two callers the same map — `SpaceAuthoring.install` retains what it is given rather than copying it, which is why `empty` is a function and the points are copied on the way in. A completed Edit does **not** need a forced identity to re-render: it replaces the working snapshot, and the `LayoutStrategyGraph` derived from it re-fires the same effect (pinned in `placement-rendering.test.tsx` and `space-authoring.test.ts`).

## Handle geometry

- **A Thing has four Edge anchors, one on each side, and they are the same four handles the authoring gesture uses (ADR 0087).** An Edge attaches to the anchor on the side that faces the other Thing. Nothing about it is stored, authored or carried in the document. The per-Graph `<graphId>::in`/`::out` family that Edges used to attach to is **gone** — it existed because elkjs needed ports to route through, ADR 0045 justified its *ids* separately on React Flow's distinguishability rule, and four anchors named for their sides satisfy that ground just as well. Don't reintroduce it, and don't read the five rules the old family had in older records as current.
- **The side is chosen in the Edge component, not in the projection — and that siting is the decision, not an implementation detail.** `canvasProjection` is pure, tested in Node and the tempting home; it is the wrong one, because **the projection does not run again during a drag**. The render adapter splices React Flow's live node positions into the published projection and leaves the Edges as they were, and the Edit lands only at settle. A side chosen in the projection is therefore correct only after release, and the Edge stays attached to the far side, crossing its own Thing, until the author lets go. `useEdgeAttachment` in `RoutedEdge.tsx` reads both Things from React Flow's store; the rule itself is pure (`edge-attachment.ts`, one function from two rects to a side) and tested in the node environment.
- **The rule reads the gap between the rects, not the vector between their centres.** Two Things are side by side when they are clear of each other on one axis and overlapping on the other, whatever their sizes — and a tall Open Thing with a small one by its lower edge is a pair the centre vector calls vertical. A Thing is 260×146 collapsed, 560×420 open and 960×720 as an open Space Thing, so large beside small is the normal state of a Diagram someone is reading rather than an edge case. React Flow's own floating-edge example computes both centres from the *intersection* node's half-size, which is correct only while every node is the same size; don't copy it.
- **A self-Edge is taken first and never enters the rule.** ADR 0032 makes cycles legal, the facing rule divides by a vector that is zero for one Thing, and React Flow draws a `NaN` path as nothing at all. `selfEdgeAttachment` answers a fixed loop over two adjacent sides.
- **An Edge names no handle, and a Thing declares all four anchors of each role.** React Flow resolves an Edge that names no handle to the first bound of that kind, and `getEdgePosition` returns null — drawing **no Edge at all**, not a misplaced one — for a Thing whose handles it cannot resolve. That is why the anchors render on *every* Thing, including a read-only one and a Thing inside a Space Thing's embedded Diagram, which draws Edges while withholding every authoring control.
- **An anchor is not an affordance.** The four render always; `data-connection-authoring` on `.rf-thing-node__inner` says whether an author may take hold of one, and every reveal rule in `styles.css` is conditioned on it. A Thing that is not authorable carries four unlabelled `aria-hidden` anchors with `isConnectable` false.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `ThingNode` and `styles.css` dim handles via `opacity` and it looks like a styling choice; it isn't.
- **Handle geometry is declared, never re-measured — do not add `useUpdateNodeInternals`.** React Flow measures handles once and caches, which is its named cause of warning #008, and the documented remedy is `useUpdateNodeInternals`. Here that remedy is **wrong**. `projectThingNodes` declares `node.handles` from the rect the strategy placed (`declaredHandles` in `projection.ts`), and `parseHandles` in `@xyflow/system` builds `handleBounds` from those declarations without consulting the DOM at all. `useUpdateNodeInternals` passes `force: true`, and the forced path *replaces* `handleBounds` via `getHandleBounds`, which reads whatever the DOM reports at that instant. Unit tests cannot catch a regression here — jsdom reports `offsetWidth` 0, so the forced path silently no-ops. The E2E that can is `editing.spec.ts`, "a second connection drawn in the same session resolves its handles". See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **`anchorPoint` and `declaredHandles` both read `AUTHORING_HANDLE_DIAMETER`, and that is load-bearing.** React Flow puts an Edge's end on the *outer rim* of the handle it resolves — `(x + w + 12, y + h/2)` on the right at 24 units — so the Edge component's own arithmetic has to be the same arithmetic, or an Edge lands near its anchor rather than on it.
- **Neither React Flow's `toNode` nor the DOM alone answers "is this empty canvas".** `getClosestHandle` resolves `toNode` by distance from the pointer to a *handle* within `connectionRadius` — 20 at the pinned 12.11.2 — so it is non-null over blank canvas near a handle and **null over the middle of a Thing**, whose centre is some 73px from the nearest handle at 260x146. An Alt/Option empty-drop therefore needs both answers, with a connection target in range outranking the element underneath: drop the DOM half and a release onto a Thing's body authors a Thing on top of it, drop React Flow's half and a release just outside a Thing authors one where the author was aiming at a handle. Both pure rules live in `packages/app/src/edge-authoring.ts`: `dropTarget({ connectionTarget, element })` composes the two answers and `newThingDrop` decides the Thing. **Three sites ask `dropTarget`** — the preview, the connection release, and the reconnect release, which asks a *different* question of the answer (delete this Edge, not author a Thing) and is therefore the one nobody greps when changing how drops are classified. The DOM half is typed `ElementDropTarget`, three values wide, so a hit-test cannot hand on the `connection-target` only React Flow can resolve. Preview and release ask the same rule but deliberately supply different DOM facts once the pointer leaves the canvas: preview keeps the last container `onMouseMove` classification, while release performs the authoritative `elementFromPoint`. Closing that gap would add a document-level pointer listener and a DOM hit-test on every frame, defeating the narrowed non-positional state write that avoids per-frame flow rerenders. The accepted argument is `.scratch/card-route-editing/edge-authoring-design.md`; don't re-inline either rule into `SpaceCanvas`, don't recompose the precedence at a fourth site, and don't make the preview hit-test live without measuring that cost.
- **Which anchors exist changes where an Alt/Option empty-drop authors a Thing.** `getClosestHandle` measures distance to a handle, so the anchor set and the drop classification are one question read twice. `pnpm e2e` is what catches a regression.

## Camera

- **A camera command is issued, never awaited, and never contained (ADR 0043).** `setCenter`, `fitView`, `fitBounds` and `zoomTo` return a Promise that is **not a completion signal**. At the pinned release it resolves only when the animation reaches its end: a *superseded* transition fires d3's `interrupt`, which `getD3Transition` does not listen for, so that Promise stays pending forever — and any second camera command while the first is running produces exactly that. `fitView` before `panZoom` exists hangs too (`resolveFitView` begins `if (!panZoom) return`, abandoning the `withResolvers()` resolver). So **never chain required work on one** — the superseded two-phase presentation move did, with `.then`, and stranded the camera at the overview zoom whenever the author traversed inside the pan's own 400ms. Nothing chains today, because ADR 0044 left the seam with one command and no follow-up work; if any ever appears, it goes on a timer the issuing effect cancels. `fitView` is worse than the rest here — it *reuses* one resolver across calls, so a second call before the first settles cannot be told apart from it. Equally, **never add a blanket `.catch`**: neither bundle calls `reject`, so the only reachable rejection is a synchronous d3 throw inside a Promise executor — a genuine fault, and the one signal worth hearing — while both real failures are hangs a `.catch` cannot observe. Plain `void` is deliberate. Every camera call in the app lives in `packages/app/src/components/cameras.tsx`, which is what makes that checkable by reading one module; coverage is `packages/app/test/cameras.test.tsx`, where every stubbed call never settles.
- **`maxZoom` must cover the presenting zoom — don't drop it back to the default.** A thing is 260x146, so filling a 1280x720 viewport with one needs ~3.97 and a 4K one ~12.8, against React Flow's default ceiling of 2. `SpaceCanvas` passes `maxZoom={MAX_ZOOM}` (`packages/app/src/camera.ts`) for that reason and nothing else. Removing it does not fail a test, because d3-zoom is asymmetric: `setCenter` ends in `zoom.transform`, which never consults `scaleExtent`, while the wheel, pinch and `scaleBy` paths all clamp into it — so the camera still reaches the presenting zoom and the *first wheel tick* yanks it down to 2 mid-presentation, recovering only at the next traversal step. Measured against the fixture at 1280x720: 0.55 overview, 3.97 presenting, 2 after one wheel tick before the fix and 4.68 after it. This mirrors React Flow's own presentation tutorial, which raises `minZoom` for the opposite reason.
- **Presenting is this canvas, closer in (ADR 0027).** There is no second surface and nothing a Thing is turned into. `PresentingCamera` in `components/cameras.tsx` is the whole mechanism, and it is one `fitView({ nodes: [{ id }], padding, duration })` (ADR 0044). **Don't reinstate the two-phase move** — pan at the wider scale then close in, which ADR 0027 recommends copying from impress.js. impress needs it because it animates with CSS transitions; React Flow animates through d3-zoom, whose default interpolator is already `interpolateZoom` (Van Wijk zoom-out-pan-zoom-in). Both were built behind a toggle and watched on the fixture: indistinguishable. The version it would restore is also the one whose chained second half stranded the camera at the overview zoom (ADR 0043). The chrome (`PresentingChrome`) is screen-fixed and enumerates the active thing's outgoing edges, because at a zoom where the thing is legible its neighbours are provably off frame. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a store selector** — `Navigation.moves()` is called at render time in `App` for exactly this reason; as a selector it handed the store a new array identity every render and re-rendered until React gave up. It is deliberately **not** `useMemo`'d either: `moves()` takes no arguments and reads the session's current working Space through Navigation, so a memo keyed on the values in scope would go stale when an authored Edge changed the Space and `PresentingChrome` would stop offering the move that had just been drawn — which is exactly what makes an Edge drawn from the presented Thing immediately traversable. A render-time call is safe here because nothing subscribes to the array's identity: a fresh array cannot feed a re-render. **It can feed an effect too often, though, and that is a real hazard rather than a theoretical one.** `moves` is a new array on every App render, so an effect keyed on it runs on every App render. The scroll-into-view effect was keyed that way and re-scrolled the choices row on every unrelated publish, snapping a presenter's sideways scroll back under them; it is keyed on the selected Thing's id now. The focus effect still takes `moves` and is safe only because a ref guards its body — key anything new here on the value that changed, never on the array. **The chrome is composed from `@project/ui` and owns its own interaction (design-system baseline Issue 07).** It draws the moves, Back, the applicable keyboard guidance (shadcn's `Kbd`) and Overview from shared primitives, with all of its styling in the module — nothing named `presenting` survives in `styles.css`. Four things about it are decisions rather than details. It **owns the indexed list it renders**, so it computes the selected-index delta and calls `selectBranch(delta)`; `App` no longer does that arithmetic. A move **names the action it performs** — `Choose <Title>` unselected, `Go to <Title>` selected — and is never a radio, a toggle or a disabled destination, because selection alone is not the completed action. The moves and the End-of-Graph text **share one polite `role="status"`**, so a changed choice set is announced without focus moving. That region also carries the selection as `sr-only` text: Up and Down rewrite an `aria-label` and a variant class, and neither is a text change, so under `aria-atomic="false"` there was nothing for the region to read and a screen-reader presenter arrowed across a fork in silence. Each control that performs a globally bound key also announces it with `aria-keyshortcuts` — the selected move `ArrowRight`, Back `ArrowLeft`, Overview `Escape` — because the visible `Kbd` guidance is presentation only. And it carries a **focus debt that only its own controls set**: advancing or retreating from inside the chrome restores focus to the newly selected move, else Back, else Overview, while a traversal run from the global arrow keys leaves focus exactly where the presenter left it. The debt **begins owed**, because entering presentation strands focus the same way — presenting removes the whole command surface (ADR 0082), so the Present control focus was on goes with it and there is nothing left for a Space aimed at advancing to defer to. The chrome claiming focus as it mounts is what makes the first Space advance. **The global Traversal keys live in `presenting-keys.ts`**, not in an effect written out in `App`, because a Ladle story proving their one load-bearing rule has to bind the same listener the application binds: the handler **defers to native activation**, so Space on any interactive control activates that control once instead of also advancing. That rule is written over interactive controls generally — chrome and Dock alike — and never as a special case for one button; Arrow and Escape stay global.

## React Flow itself

- **React Flow is pinned to 12.11.2.** The declarative `node.handles` path above intentionally depends on behavior verified against that release. Upgrade both consuming manifests together and run the complete Playwright suite; do not widen the range or accept an automated upgrade without revalidating handle resolution, consecutive connections and warning #008 in a real browser. The camera-Promise facts above are pinned to it too — re-read `setTransform`, `scaleTo`, `scaleBy`, `resolveFitView` and `getD3Transition` when it moves.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. **It is incomplete, though** — a read of it for nesting reported sub flows as absent while `/learn/layouting/sub-flows` exists and is quoted in our own findings, so use it for breadth and fetch the page for a specific mechanism. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`, whose §8 covers multiple canvases and nesting.
- **An invariant reached from a canvas gesture is reported, not thrown.** `AuthoringResult` says a broken invariant "throws, or is reported through the non-throwing reporter" (`space-authoring.ts`) without saying which a caller picks; at this seam it is always reported. A pointer release or a key press arrives from the browser's event loop mid-gesture, so throwing there unmounts the tree and costs the author their Space for a defect they did not commit. The gesture instead authors nothing and answers the outcome that owes the author no prose — never a refusal, which would put a wiring defect in front of them as their own mistake. Two modules make the call today, `connection-completion.ts` for a `queued` completion and `embedded-authoring.ts` for a completion kind an embedded Diagram does not support, and each takes its reporter from the composition (ADR 0016) rather than reaching for `console`. Don't re-argue it a third time.
- **React Flow's interaction model is the default.** Start from the pinned release's documented keyboard, focus, selection, pointer and accessibility behavior. Prefer shaping Hyper's feature around those expectations over reshaping React Flow around a locally convenient interaction. Every deviation needs an explicit product requirement and an interrogated, recorded reason; do not customize merely because a different gesture seems preferable.

## Multi-Graph overlay and the fixture

On multi-Graph rendering (`.scratch/multi-route/` retains its historical path): a Diagram overview draws every Graph that Diagram owns, and **activation is emphasis, not filtering** — at all times, not only while presenting. Activating a Graph never changes which Graphs the Diagram owns or draws. There is one Active Graph in the current Diagram, not a selection plus an emphasis (ADR 0040/0041). The dimming surface uses Graph names (`projectGraphEdges`, `GraphHud`'s Graph key and related helpers); do not restore superseded Route-named aliases. `graphThingIds` is right for a view that wants one Graph; the handle filters that stood beside it went with the per-Graph anchors (ADR 0087). **A Diagram's `graphs` is ownership, not a filter** (ADR 0040): it is the full Graph values that Diagram owns, and what a selected Diagram draws is exactly them. The superseded `graphs` array of Graph *ids* — a filter over a Space-level collection — is gone, along with the Space-level collection itself; `space.graphs` is now a derived flatten across Diagrams, and a document declaring a Space-level one is **rejected at intake** — by the private `retiredSpaceGraphs` in `graph/src/space.ts`, composed into `documentRefusal` and reached only through it, which `loadSpace`, `loadSpaceSnapshot` and `readSingleSpace` each ask once, so neither a file, a commit nor an import can carry one. It is deliberately *not* declared in the schema: `spaceFileSchema` is strict, so an undeclared key is already refused rather than stripped, and this check survives that to *name* the one that matters — a Space-level `graphs` carried the whole topology, and a reader told only that some key is unrecognized has to work out why that one mattered. Don't answer it by declaring the key, which puts it in the inferred document type Hono's RPC contract is checked against. Which Things a View chooses from its subject is passed into the strategy (ADR 0005, ADR 0040) — don't let the strategy decide it.
The overlay limit: only an acyclic union of the visible Graph Edges lays out on a clean left-to-right axis, as parallel forward paths. A backward Edge can come from a cycle inside one Graph or from two Graphs disagreeing on the order of shared Things. Nothing routes an Edge: the strategy contract has no routed sections to emit and `RoutedEdge` has no polyline branch left, so the bezier is the only Edge geometry drawn — as it always was, that branch never having executed in the application (ADR 0086) — and a back-edge therefore reads as a self-curling stub. Here “routed” is qualified graph-layout geometry, not the retired Route entity. Read `.scratch/multiple-routes/findings.md` before extending any of this.
The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against purpose-shaped Graphs rather than demo prose. It is **two disconnected collections** sharing no Things, which are its two Diagrams, `Collection 1` and `Collection 2`: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several Graphs over one spine — plus `T`, a sixth member of that Diagram no Edge reaches, whose Title is the fixture's one three-line Title (ADR 0083), so the Title ladder and the Diagram membership Add Thing leaves behind are both drawn by the Space the app and Playwright actually load; (2) `Echo E→F→G→H→E′` — a plain linear collection. Two Diagrams rather than one is deliberate — it is the only place in the tree where the Space-subject flatten crosses a Diagram boundary. Both position maps are **authored**, as placement always is (ADR 0014): a hand-set grid in the space file, so selecting a Diagram draws its Things where the file put them and first paint moves nothing. Nothing recomputes the fixture's positions — don't compute them and write the result back, which is authored placement overwritten by a computed one. Each returns to its start via an Alias (`A′`/`E′`, which the Front says with the kind glyph alone, drawn by every kind in the Thing's own header rail above the title; the Thing front names nothing outside itself — no Target name and no referenced Space name — so an Alias and its Target are told apart by the glyph and the dotted border, and by the Titles the author gave them), never an Edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture Graph is a **line** — one Edge out per Thing — which is the degenerate Graph shape, not a second kind; forks and merges are covered by unit and property tests, not here. The demo stays in `packages/app/example/`, dormant — it is a Space directory nothing loads, kept as narrative content rather than as a pending capability, since the CLI importer now loads real Space directories. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a Space file would be scanned as a Thing). If legible multi-Graph overlay becomes real product work, design it deliberately.
