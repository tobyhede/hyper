# Canvas & Rendering

React Flow, ELK, handle geometry, the camera, and Edge Authoring. Read before touching `packages/react-flow-adapter`, the canvas/camera modules in `packages/app`, or `edge-authoring.ts`.

## Edge Authoring and drafts

- **ADR 0033 — authoring is drag-to-connect through four spatial handles coloured as the Active Graph.** Built: source handles appear on the hovered or selected Card; target handles appear during the drag. They are Graph-independent and the chosen side is not authored. Algorithmic View conversion, initial-Graph minting and Option/Alt empty-drop create-and-connect are also built, and package 7 added the rest of the Edge lifecycle — the keyboard Connect control and its target picker, Active-Graph Edge focusability, the selected Edge's controls and endpoint editor (now `SelectedEdgeControls`, see below), pointer reconnection and selection-based deletion. Detached Card creation now has its controls too — the toolbar's Add Card and the graph-focused `C` — while *structural* deletion, meaning a Card's, is still built **as operations and not as controls**; see the ADR 0040 entry in `docs/agents/editing-and-persistence.md`, which is the one place that list is kept. The per-Graph attachment machinery in `react-flow-adapter` serves overview rendering and is not visible authoring UX.
- **Edge Authoring is one module for the whole Edge lifecycle, and it owns no copy of anything (`.scratch/card-route-editing/edge-authoring-design.md`).** `packages/app/src/edge-authoring.ts` holds the one interaction draft, the refusal that draft ran into and the focus continuation a completed projection owes; `edge-authoring-react.tsx` is its React interface, answering `{ edges, edgeTypes, reactFlowProps, layer, provide }` plus the Edge half of the canvas's delete dispatch. The **render adapter** stays authoritative for the projection, Card movement and the discriminated `none | card | edge` selection; **Space Authoring** stays authoritative for eligibility and every semantic Edit. Three consequences are load-bearing. *Selection is folded additively*: one React Flow selection action produces two callback batches — the new subject selected, then the other kind deselected — so reading the resulting arrays answers `none` for a click that plainly selected something, and the second batch must clear the union only when it still names the subject stored. *The Edge subject is the domain `{ graphId, edge }`, never the React Flow id*, which is `<graphId>::<index>` and re-indexes whenever a Graph loses an Edge. *The commands context wraps `<ReactFlow>` rather than sitting in `layer`* — React Flow renders Edges itself, as a sibling of the children it is given, so a provider inside the layer reaches no Edge at all. Deletion goes through `onBeforeDelete`, which returns `false` for the **whole** payload: a payload carrying nodes is a Card deletion whose incident Edges React Flow gathered for it, not several Edge deletions, and nothing is ever removed locally — the completed Edit supplies the next projection. **Reconnection runs through the connection callbacks as well as its own, and that is the trap.** `EdgeUpdateAnchors` calls `onReconnectStart` and *then* the store's `onConnectStart`; on release it calls the store's `onConnectEnd` before `onReconnectEnd`. So a reconnect drag arrives as a connection starting from the endpoint that stays put — which silently replaced the reconnect draft, leaving `reconnect()` with nothing drafted and the gesture authoring nothing, and let an Alt-held release author a Card *and* delete the Edge. A `reconnecting` ref stands both connection handlers down for the drag's duration; don't remove it, and don't reach for a per-gesture flag in state, since both reads happen inside React Flow's own event. Two more facts in the same seam: `onReconnectStart`'s `handleType` names the endpoint that **stays** (the source anchor reports `'target'`), so the endpoint being moved is its inverse; and a source-endpoint drag looks for a new **source** handle, which is why `CardNode` reads `connection.fromHandle.type` rather than assuming a drag always seeks a target. All of it is invisible to a unit test that calls `beginPointerReconnect` directly — `editing.spec.ts` is what pins it. Hyper never calls `reconnectEdge`; only the *selected* Active-Graph Edge is `reconnectable`, so two transparent endpoint anchors are not permanently live over every Card's authoring handles. An endpoint released on empty canvas deletes the Edge, and that is safe to distinguish from a cancellation because `onReconnectEnd` is the *only* way a drag can end: **React Flow has no Escape path for a drag at all** — the key is consumed by the focusable node and edge wrappers, and a reconnect anchor is a bare `<circle>` that takes no focus — and `XYHandle` removes its document listeners only from its own `onPointerUp`. Those listeners have no React cleanup, so even an Edge that leaves the projection mid-drag still ends through that handler, which is what makes the `reconnecting` guard safe to clear there and nowhere else. `queued` at the React Flow seam is an invariant violation rather than an outcome — a pointer release arrives from the event loop with no Edit on the stack — so `connection-completion.ts` reports it and draws nothing.
- **The selected Edge's controls are `SelectedEdgeControls` in `app`, and the HUD's Graph key is `GraphHud`'s own markup.** Two vertical production modules that share a design language and no state. `AuthorableEdge` stays the React Flow adapter and owns exactly the framework's half: the routed Edge, `EdgeLabelRenderer`, the label coordinates, the selection translation, the portal placement and the `nodrag`/`nopan`/`nokey` containment — plus, now, resolving Edge Authoring's one module-wide refusal to the two channels a selected Edge owns. `SelectedEdgeControls` takes domain facts and callbacks and **no `EdgeProps`, coordinates, `EdgeSubject` or commands context**, which is what lets `packages/app/test/SelectedEdgeControls.test.tsx` and the Ladle catalogue mount every state with no canvas under them. Its endpoint choices are snapshotted when the editor opens, so rows do not move under a pointer already on its way to one; the completion's own re-validation is what keeps the pick safe. Popover open state is controlled from Edge Authoring, which owns the draft. On the HUD side, the published `GraphLegend` component in `@project/ui` is **deleted** — one production caller, so folding its markup into `GraphHud` concentrated rather than spread complexity — while `graphColor` and `FALLBACK_GRAPH_COLOR` stay a shared seam in `packages/ui/src/graph-color.ts` because the Sidebar's Graphs group and the HUD's key are two real consumers that must not disagree. The key is kept deliberately: it is the on-canvas colour reference beside the Edges being read, and the only one of the two still on screen once the Sidebar is collapsed (`overview.spec.ts` holds them to the same titles, colours and emphasis). `GraphHud` uses Tailwind utilities, which is why `packages/app/src/tailwind.css` now `@source`s `packages/react-flow-adapter/src` — without it those classes are purged.
- **Edge Authoring carries a structured refusal across its seam, never prose (ADR 0057).** `EdgeAuthoringState.refusal` is an `EdgeRefusal`: the domain's `AuthoringRefusal` plus the least context a surface needs to recognise its own — `connection` (the keyboard picker's Target field and form), `reconnection` with the attempted `endpoint` (the editor's From/To and form), `deletion` (the selected Edge's controls, no field), and `gesture` (a completed pointer drag whose surface has gone, so the canvas announcement is all that is left). `connection-completion.ts` answers the same structured value. Which channel a refusal lands on is decided where the interaction is known — a pointer reconnect is a `gesture`, a keyboard one a `reconnection` — so no surface has to infer it from an absent draft. The prose and the Field come from the exhaustive adapters in `authoring-refusal.ts`, derived per render and never stored. A retained `deletion` refusal is dropped when the canvas selection moves, because it names the Edge that was selected when it was made.
- **ADR 0042 — interaction drafts stay local, and Space replacement invalidates them. Built.** The **result vocabulary** is described in full in `docs/agents/editing-and-persistence.md`, under "Space Authoring's completed-edit lifecycle". The **invalidation half** landed with package 7, and it is the Edge draft that carries it, because that draft is the only one there is: `edge-authoring.ts` holds the epoch it last saw and cancels the draft when `replacementEpoch` moves, when the selected renderer changes, when the Active Graph changes, or when the draft's own subject leaves the projection — and by nothing else, so an unrelated completed Edit leaves a drag standing. A cancelled draft also asks for focus, since the element it was about may have been holding it. `replacementEpoch` still gates the completion drain (`space-authoring.ts`) and `SpaceCanvas` is still remounted on `key={replacementEpoch}` in `App.tsx`; those are the other two readers, and they answer different questions. See `.scratch/adr-0040-0042/issues/03`.

## The strategy contract and Placement

- **The strategy contract lives in `graph`, not the adapter.** Geometry lands as optional fields on the cards and handles, mirroring how ELK itself models it. `gridStrategy` (pure, places no handles) exists partly to keep the seam honest; if a change only works for `elkStrategy`, the contract has leaked. Which cards get arranged is the view's choice, passed in. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored, and no engine owns it (ADR 0025).** A strategy is *automatic* (computes placement from Cards and Graphs alone — grid, name-sort, ELK) or *positioned* (reads a Layout the author wrote). **ELK is one automatic strategy among several and must never be the focus**; if a change only makes sense for `elkStrategy`, the seam has leaked. Editing an Algorithmic View is legal and **converts** it: the Card positions already on screen are copied into a new Layout and the Edit written there, so nothing moves at the moment of conversion. There is no edit mode; persistence status is the state worth surfacing. **Don't re-suggest seeding or constraining ELK to honour a drop point**: three spike increments — append, then branch, then seeded and interactive ELK — each reshuffled the *existing* Cards and placed the new one by global optimisation, so a drop landed somewhere arbitrary. The failure is structural, not a matter of tuning. Written up in ADR 0025 and `.scratch/graph-editing/`.
- **A `Placement` is built through its module, never by hand; and the omitted-Card fallback band is standing on purpose.** The card→position map is one branded `ReadonlyMap<CardId, LayoutPosition>` in `graph/src/placement.ts`, over `core`'s schema-derived point — `graph`'s duplicate `LayoutPoint` is gone. Reads are ordinary map reads; **construction is closed** — `new Map()` will not typecheck as one — because the map built by hand and installed whole is the specific bug this exists to prevent, and it was fixed twice under two names before the type stopped it. Under ADR 0040 a Layout's position keys **are** its Card membership, so omission means the Card is not in that Layout — but `positionedStrategy` still draws an omitted Space Card in an internal fallback band below everything the map places, and that is **deliberate, not vestigial**: package 5 of `.scratch/card-route-editing/implementation-handoff.md` deletes it and builds its replacement — Cards View, Add to Layout, Remove from Layout — in the same change, and between here and there the band is the only surface that can reach such a Card. **Don't remove it early.** Two guards keep it from becoming authorship: `Placement.next` promotes only the Cards a completed gesture placed, so a Card drawn in the band stays unplaced however often it is redrawn, and the render adapter's `syncProjection` reports rendered geometry rather than installing it. A Card a reprojection catches mid-drag likewise keeps the place the author last left it. Nothing in the module mutates an argument or hands two callers the same map — `SpaceAuthoring.install` retains what it is given rather than copying it, which is why `empty` is a function and the points are copied on the way in. A completed Edit does **not** need a forced identity to re-render: it replaces the working snapshot, and the `LayoutGraph` derived from it re-fires the same effect (pinned in `placement-rendering.test.tsx` and `space-authoring.test.ts`).

## Handle geometry and ELK ports

- **The six handle rules below belong to the overview, not to the domain (ADR 0033).** They hold because that rendering overlays several Graphs over one set of Card positions and needs distinct attachment points to stay legible. The **authoring** interaction uses four Graph-independent spatial handles per Card, coloured as the Active Graph; none of the overview bookkeeping applies there. Don't restate any of it as a rule the model obeys, and don't let it shape the visible authoring controls.
- **ELK port offsets are applied to handles.** ELK's *port* is React Flow's *handle* — same thing, two libraries' words. ELK computes each one's position, and those exact offsets drive where `CardNode` renders the handle, so a Graph's Edges meet its Cards cleanly. Don't hardcode handle positions.
- **Port constraints are `FIXED_SIDE`, not `FIXED_ORDER`.** ELK orders `FIXED_ORDER` ports **clockwise** around the node — EAST top-to-bottom but WEST *bottom-to-top*. Handing both sides the same list order therefore puts a Graph's outbound handle at the top of one Card and its inbound handle at the bottom of the next, crossing every Graph at every shared Card. `FIXED_SIDE` fixes the side and lets ELK order within it. Don't switch back without reading `.scratch/layout-seam/issues/04-elk-fixed-side-ports.md`.
- **ELK port ids are namespaced per card.** A handle id (`<graphId>::out`/`::in`) is the *same* on every Card a Graph passes through, so `elkStrategy` hands ELK `<cardId>##<handleId>` (`elkPortId`) and builds Edge endpoints from the same key, stripping the prefix on read-back, so handles keep their bare ids and `CardNode` is unaffected. Never hand ELK a bare handle id — it then can't tell which Card an Edge attaches to and mislays *even single-Graph* graphs. See `.scratch/layout-seam/issues/01-namespace-elk-port-ids.md`.
- **Handle ids must be distinguishable per card per side — React Flow's rule, not just ELK's.** The entry above covers why ELK needs `<cardId>##<handleId>`; React Flow separately requires that *"multiple handles of the same kind on a node need to have distinguishable IDs"*, or it can't resolve an edge's `sourceHandle`/`targetHandle` and warns (#008). The `<graphId>::out`/`::in` scheme satisfies both libraries, for different reasons. Don't collapse it to a per-side counter.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `CardNode` dims handles via `opacity` and it looks like a styling choice; it isn't. Same for the CSS in `styles.css`.
- **Handle geometry is declared, never re-measured — do not add `useUpdateNodeInternals`.** React Flow measures handles once and caches, which is its named cause of warning #008, and the documented remedy is `useUpdateNodeInternals`. Here that remedy is **wrong**. `projectCardNodes` declares `node.handles` from the strategy (`declaredHandles` in `projection.ts`), and `parseHandles` in `@xyflow/system` builds `handleBounds` from those declarations without consulting the DOM at all — this is the `node.handles` alternative the old spike note proposed, and it is built. Crucially, a card declares `<graphId>::in`/`::out` for **every** Graph, including ones not yet incident to it, so a completed connection resolves in the same render that first makes its target incident. `useUpdateNodeInternals` passes `force: true`, and the forced path *replaces* `handleBounds` via `getHandleBounds`, which reads only the anchors present in the DOM — silently dropping every not-yet-incident declaration and breaking the **next** connection rather than the current one. Verified both ways against the fixture: with the hook, a second connection in one session fails with six #008 warnings; without it, it passes (`editing.spec.ts`, "a second connection drawn in the same session resolves its handles"). Unit tests cannot catch this — the forced path needs truthy `offsetWidth`/`offsetHeight`, which are 0 in jsdom, so it silently no-ops there. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **Neither React Flow's `toNode` nor the DOM alone answers "is this empty canvas".** `getClosestHandle` resolves `toNode` by distance from the pointer to a *handle* within `connectionRadius` — 20 at the pinned 12.11.2 — so it is non-null over blank canvas near a handle and **null over the middle of a Card**, whose centre is some 73px from the nearest handle at 260x146. An Alt/Option empty-drop therefore needs both answers, with a connection target in range outranking the element underneath: drop the DOM half and a release onto a Card's body authors a Card on top of it, drop React Flow's half and a release just outside a Card authors one where the author was aiming at a handle. The pure rule is `newCardDrop` in `packages/app/src/edge-authoring.ts`, which package 7 moved there rather than wrapping. Preview and release ask the same rule but deliberately supply different DOM facts once the pointer leaves the canvas: preview keeps the last container `onMouseMove` classification, while release performs the authoritative `elementFromPoint`. Closing that gap would add a document-level pointer listener and a DOM hit-test on every frame, defeating the narrowed non-positional state write that avoids per-frame flow rerenders. The accepted argument is `.scratch/card-route-editing/edge-authoring-design.md`; don't re-inline the rule into `SpaceCanvas`, and don't make the preview hit-test live without measuring that cost.

## Camera

- **A camera command is issued, never awaited, and never contained (ADR 0043).** `setCenter`, `fitView`, `fitBounds` and `zoomTo` return a Promise that is **not a completion signal**. At the pinned release it resolves only when the animation reaches its end: a *superseded* transition fires d3's `interrupt`, which `getD3Transition` does not listen for, so that Promise stays pending forever — and any second camera command while the first is running produces exactly that. `fitView` before `panZoom` exists hangs too (`resolveFitView` begins `if (!panZoom) return`, abandoning the `withResolvers()` resolver). So **never chain required work on one** — the superseded two-phase presentation move did, with `.then`, and stranded the camera at the overview zoom whenever the author traversed inside the pan's own 400ms. Nothing chains today, because ADR 0044 left the seam with one command and no follow-up work; if any ever appears, it goes on a timer the issuing effect cancels. `fitView` is worse than the rest here — it *reuses* one resolver across calls, so a second call before the first settles cannot be told apart from it. Equally, **never add a blanket `.catch`**: neither bundle calls `reject`, so the only reachable rejection is a synchronous d3 throw inside a Promise executor — a genuine fault, and the one signal worth hearing — while both real failures are hangs a `.catch` cannot observe. Plain `void` is deliberate. Every camera call in the app lives in `packages/app/src/components/cameras.tsx`, which is what makes that checkable by reading one module; coverage is `packages/app/test/cameras.test.tsx`, where every stubbed call never settles.
- **`maxZoom` must cover the presenting zoom — don't drop it back to the default.** A card is 260x146, so filling a 1280x720 viewport with one needs ~3.97 and a 4K one ~12.8, against React Flow's default ceiling of 2. `SpaceCanvas` passes `maxZoom={MAX_ZOOM}` (`packages/app/src/camera.ts`) for that reason and nothing else. Removing it does not fail a test, because d3-zoom is asymmetric: `setCenter` ends in `zoom.transform`, which never consults `scaleExtent`, while the wheel, pinch and `scaleBy` paths all clamp into it — so the camera still reaches the presenting zoom and the *first wheel tick* yanks it down to 2 mid-presentation, recovering only at the next traversal step. Measured against the fixture at 1280x720: 0.55 overview, 3.97 presenting, 2 after one wheel tick before the fix and 4.68 after it. This mirrors React Flow's own presentation tutorial, which raises `minZoom` for the opposite reason.
- **Presenting is this canvas, closer in (ADR 0027).** There is no second surface and nothing a Card is turned into. `PresentingCamera` in `components/cameras.tsx` is the whole mechanism, and it is one `fitView({ nodes: [{ id }], padding, duration })` (ADR 0044). **Don't reinstate the two-phase move** — pan at the wider scale then close in, which ADR 0027 recommends copying from impress.js. impress needs it because it animates with CSS transitions; React Flow animates through d3-zoom, whose default interpolator is already `interpolateZoom` (Van Wijk zoom-out-pan-zoom-in). Both were built behind a toggle and watched on the fixture: indistinguishable. The version it would restore is also the one whose chained second half stranded the camera at the overview zoom (ADR 0043). The chrome (`PresentingChrome`) is screen-fixed and enumerates the active card's outgoing edges, because at a zoom where the card is legible its neighbours are provably off frame. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a store selector** — `Navigation.moves()` is called at render time in `App` for exactly this reason; as a selector it handed the store a new array identity every render and re-rendered until React gave up. It is deliberately **not** `useMemo`'d either: `moves()` takes no arguments and reads the session's current working Space through Navigation, so a memo keyed on the values in scope would go stale when an authored Edge changed the Space and `PresentingChrome` would stop offering the move that had just been drawn — which is exactly what makes an Edge drawn from the presented Card immediately traversable. A render-time call is safe here because nothing subscribes to the array's identity — `moves` feeds no effect, no dependency array and no memoized child, so a fresh array cannot feed a re-render.

## React Flow itself

- **React Flow is pinned to 12.11.2.** The declarative `node.handles` path above intentionally depends on behavior verified against that release. Upgrade both consuming manifests together and run the complete Playwright suite; do not widen the range or accept an automated upgrade without revalidating handle resolution, consecutive connections and warning #008 in a real browser. The camera-Promise facts above are pinned to it too — re-read `setTransform`, `scaleTo`, `scaleBy`, `resolveFitView` and `getD3Transition` when it moves.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. **It is incomplete, though** — a read of it for nesting reported sub flows as absent while `/learn/layouting/sub-flows` exists and is quoted in our own findings, so use it for breadth and fetch the page for a specific mechanism. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`, whose §8 covers multiple canvases and nesting.
- **React Flow's interaction model is the default.** Start from the pinned release's documented keyboard, focus, selection, pointer and accessibility behavior. Prefer shaping Hyper's feature around those expectations over reshaping React Flow around a locally convenient interaction. Every deviation needs an explicit product requirement and an interrogated, recorded reason; do not customize merely because a different gesture seems preferable.

## Multi-Graph overlay and the fixture

On multi-Graph rendering (`.scratch/multi-route/` retains its historical path): a Layout overview draws every Graph that Layout owns, and **activation is emphasis, not filtering** — at all times, not only while presenting. Activating a Graph never changes which Graphs the Layout owns or draws. There is one Active Graph in the current Layout, not a selection plus an emphasis (ADR 0040/0041). The dimming surface uses Graph names (`projectGraphEdges`, `GraphHud`'s Graph key and related helpers); do not restore superseded Route-named aliases. `filterHandlesByGraph` and `graphCardIds` are right for a view that wants one Graph. **A Layout's `graphs` is ownership, not a filter** (ADR 0040): it is the full Graph values that Layout owns, and what a selected Layout draws is exactly them. The superseded `graphs` array of Graph *ids* — a filter over a Space-level collection — is gone, along with the Space-level collection itself; `space.graphs` is now a derived flatten across Layouts, and a document declaring a Space-level one is **rejected at intake** — by the private `retiredSpaceGraphs` in `graph/src/space.ts`, composed into `documentRefusal` and reached only through it, which `loadSpace`, `loadSpaceSnapshot` and `readSingleSpace` each ask once, so neither a file, a commit nor an import can carry one. It is deliberately *not* enforced by the schema: `spaceFileSchema` is a plain object and so strips an undeclared key, which is the right answer for the retired `cards` and `edges` — they carried nothing the document does not already say — but the wrong one here, since a Space-level `graphs` carried the whole topology and stripping it yields a Space that loads looking complete. Don't answer it with `.strict()`, which takes that leniency with it, or by declaring the key, which puts it in the inferred document type Hono's RPC contract is checked against. Which Cards a View chooses from its subject is passed into the strategy (ADR 0005, ADR 0040) — don't let the strategy decide it.
The overlay limit: only an acyclic union of the visible Graph Edges lays out on a clean left-to-right axis, as parallel forward paths. A backward Edge can come from a cycle inside one Graph or from two Graphs disagreeing on the order of shared Cards. `elkStrategy` returns ELK's routed `sections` on each Edge and the adapter draws them (a bezier fallback covers grid/first-paint), so a back-edge reads as a routed channel rather than a self-curling stub. Here “routed” is qualified graph-layout geometry, not the retired Route entity. Read `.scratch/multiple-routes/findings.md` before extending any of this.
The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against purpose-shaped Graphs rather than demo prose. It is **two disconnected collections** sharing no Cards, which ELK lays out as separate bands and which are its two Layouts, `Collection 1` and `Collection 2`: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several Graphs over one spine; (2) `Echo E→F→G→H→E′` — a plain linear collection. Two Layouts rather than one is deliberate — it is the only place in the tree where the Space-subject flatten crosses a Layout boundary. Both position maps are seeded from **one ELK run over the whole fixture**, and `packages/app/test/fixture-placement.test.ts` re-runs that exact seam and compares within half a pixel, so a change to the ELK options that would silently move the fixture fails there rather than being noticed by eye or not at all. Each returns to its start via an Alias (`A′`/`E′`, which the Front says twice — the persistent kind glyph beside the title, and the Target's title drawn plain beneath it as `card__alias-of`; the `↳` that used to prefix that second line is gone, because the kind now says the same thing about the whole Card rather than about one line of it), never an Edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture Graph is a **line** — one Edge out per Card — which is the degenerate Graph shape, not a second kind; forks and merges are covered by unit and property tests, not here. `03`'s back-edge rendering is proven by a unit test (`elk-strategy.test.ts`), not the fixture. The demo stays in `packages/app/example/`, dormant — it is a Space directory nothing loads, kept as narrative content rather than as a pending capability, since the CLI importer now loads real Space directories. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a Space file would be scanned as a Card). The ELK options in `elk/layout.ts` are a minimal baseline: don't tune global layout options against this fixture's screenshot. If legible multi-Graph overlay becomes real product work, design it deliberately.
