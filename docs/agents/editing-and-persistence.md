# Editing & Persistence

`SpaceBackend`/`SpaceSession`, Space Authoring's completed-edit lifecycle, and the Layout/Graph/View aggregate model. Read before touching `packages/persistence`, `packages/graph`, `space-authoring.ts` in `packages/app`, `migrations/**`, or `src/prisma/**`.

## PostgreSQL & the document contract

- **ADR 0030 — PostgreSQL is the live write model; files are imported and exported.** The application and database foundations are **built**: every public id is a UUID, the import schemas allow persistence-owned ids to be omitted, and `SpaceBackend`/`SpaceSession` drive optimistic whole-snapshot commits, ordered coalescing, explicit retry and visible conflicts. Node 24, pinned Prisma Next and PostgreSQL, the document contract, formal migration and typed runtime entry are in place. The Prisma Next/PostgreSQL repository lists, loads and revision-checks completely identified aggregates, commits them transactionally, and imports complete new Spaces without updating or merging existing ones. The `hyper` CLI discovers one Space or a batch of immediate child Spaces, minting every missing Card, Graph and Layout id in process through `newUuid` while a space's id comes from its column default; an existing Space or Card identity rejects and rolls back the complete batch. The built document is the first-public **version 1**, which ADR 0040 put in place of the disposable pre-release shape rather than migrating it: a Graph is a nested owned value of its Layout, a Layout identity is scoped to its Space, and a Graph id is unique across the whole Space because the flattened Space-subject View keys on that id alone (ADR 0045). Import mints a Layout's id and its Graphs' ids in the same pass, before validation and before the first Card is written. A version 2 document is **rejected, never migrated**, and so is a version 1 document carrying the retired space-level `graphs` — through **one composed gate, `documentRefusal` in `@project/graph`**, which `loadSpace`, `loadSpaceSnapshot` and `readSingleSpace` each ask once, before the schema that would otherwise answer. Both checks it composes exist because that schema's own answer misleads: a cascade of moved keys for a version it cannot read, and a *silently stripped* topology for the retired key, since a plain Zod object drops what it does not declare. **They are private on purpose and the gate is offered composed** — a door that could name them individually would take some and miss others, which is exactly what happened (issues `08` and `10`: the importer had the version check alone and imported a Space with its whole `graphs` array dropped, looking complete). A third check added inside `documentRefusal` reaches all three doors with nobody carrying it there. The refusal is the whole of what the importer says: one diagnostic, ahead of the cards it does not parse and ahead of a card it could not even read, because a document refused outright was never going to load and its author should not be sent to fix a file permission first. The one thing that still precedes it is an unreadable **space file** — with no document there is nothing for the gate to decide. The snapshot decoders do not ask the gate, deliberately — they parse `spaceSnapshotSchema` first, so they refuse a version 2 snapshot by cascade rather than by name, which buys nothing when no version 2 documents exist and no human hand-authors a snapshot (issue `09`, wontfix). The `version` literal on those schemas stays as the shape check reading the same `SPACE_FILE_VERSION`, not as a second answer; if that door ever matters, ask the gate earlier there and never decide a version somewhere new. Identities of different entity kinds may still share a UUID. `--dangerous-truncate` deletes all Hyper content and inserts the batch in that same transaction. Server-side startup creates or loads the zero/one/many-space database experience, the CLI applies that policy after import or with no path, and the normal browser runtime now lists, opens and commits through the typed `HttpSpaceBackend` and Fetch-native Hono application. Standard E2E uses the same HTTP interface over isolated memory repositories; an opt-in PostgreSQL browser test proves durability across a fresh Vite host. CI provisions the exact pinned Compose service with generated masked credentials, applies the committed migration history, runs the complete PostgreSQL integration suite and verifies the live contract. The Save action, file write-back, virtual file module and source-byte preservation flow are gone. The CLI-only canonical exporter regenerates deterministic version 1 directories through staged, validated replacement and records the exact projected revision. The existing `space.json` plus card Markdown structure stays. See `docs/superpowers/specs/2026-07-28-postgres-document-persistence-design.md`.
- **A renamed persisted key is a codebase edit and nothing else (ADR 0056, refining ADR 0054).** Rename the field, roll the fixtures, seeds, stories, exporter and tests forward with it, confirm the old spelling appears nowhere the repo generates, and stop. **`documentRefusal` is not where a retired key goes.** Every database and space directory is derived, so the stored documents a compatibility path would protect are regenerated by the reset that follows any format change — there is nothing on the other side of the gate to answer. This is the trap the `defaultView` → `defaultRenderer` rename set twice: review proposed a transitional read, then a pre-parse refusal beside `retiredSpaceGraphs`, and both were refused on the same grounds. The refusals already there stay, and are a different thing — `unsupportedDocumentVersion` answers a version this build cannot read, and `retiredSpaceGraphs` answers a shape a *current* hand or stale producer can still write. Both are consistency inside the codebase; neither is compatibility with a build that is gone.
- **Prisma Next 0.16.0 packaging workaround.** Its emitted `contract.d.ts` imports types directly from `@prisma-next/adapter-postgres`, `@prisma-next/target-postgres`, `@prisma-next/sql-contract`, and `@prisma-next/contract`, but pnpm's strict layout does not expose transitive packages to that project-owned file. Those four packages are therefore exact `0.16.0` root devDependencies only so generated types resolve. Authored config/runtime/application code still imports database capabilities only through the `@prisma-next/postgres` facade. Do not add hoisting or patch emitted artifacts; remove the four direct devDependencies when an upstream release emits facade-resolvable types.
- **Prisma Next 0.16.0 `int8` typing workaround.** Its PostgreSQL codec declares `int8` input and output as JavaScript `number`, although the codec and node-postgres runtime pass bigint-compatible values through unchanged. Repository revisions remain `bigint`; one compatibility cast is isolated in `toDatabaseRevision` and runtime values are checked when read. Do not convert revisions through `Number`, which loses PostgreSQL `bigint` range, and remove the cast when upstream exposes a lossless `int8` type.

## The Layout/Graph/View aggregate

- **ADR 0025 — a Layout is optional, and editing an Algorithmic View creates one.** The placement half is **built**: `positionedStrategy` exists, the composed renderer resolver returns it whenever `defaultRenderer` names a declared Layout, and an Algorithmic View keeps its computed Card positions in runtime state until the first completed placement edit converts it. That conversion copies every Card already on screen, submits the Positioned Layout through `SpaceSession`, and repoints `defaultRenderer` at it. ADR 0045 now makes a View one interface over an open subject: it receives Cards and zero or more Graphs, and on conversion returns those Cards with their positions plus one or more Graphs, each under a fresh identity owned by the new Layout. A tree over the Cards one Graph connects is a subject, not a kind of View, and its product interaction is deferred beyond version 1. After conversion, the current and every later render comes from the authored Layout; obsolete asynchronous strategy results cannot replace it. ELK renders the fixture because the fixture names no `defaultRenderer` — a resolution outcome, not a privileged engine. It *declares* two Layouts, one per disconnected collection, since a Graph is owned by a Layout and the fixture has four; leaving `defaultRenderer` absent is what still opens it in Flow, over the flatten across both. The structural half of 0025's definition of editing — create, delete, connect — begins with ADR 0033's Graph-authoring behavior. Issues `01`–`07`, `12`, and `13` are resolved; `01`–`07` were written against the superseded 0013/0017 model, so don't read them as the design either.
- **ADR 0031 — Views and Layouts are selected; conversion keeps no strategy provenance.** Built: the toolbar has peer icon selectors for application-supplied Algorithmic Views and Space-owned Positioned Layouts. Selection is navigation and never persists by itself. Editing an Algorithmic View creates and selects the next neutrally titled Layout without touching existing Layouts; automatic persistence adds it and makes it `defaultRenderer`. Editing a selected Layout updates it in place. The converted Layout remembers no source strategy, and the prototype Auto-arrange control plus the resolved view's `automatic` flag are gone. See resolved issue `16`.
- **ADR 0040 — Layouts own Card membership and Graphs (terminology refined by ADR 0041).** The aggregate is **built**, in the first-public version 1 document and with no compatibility migration from version 2: a Layout's position keys are its explicit Card membership, its non-empty ordered `graphs` are nested owned values and there is no Space-level Graph collection, and every owned Edge endpoint must name a Card in that Layout — one rule, checked in `validateReferences` — which now tells its two readings apart, since an endpoint naming no Card at all (`graph-edge-missing-card`) and one naming a Space Card outside its Layout (`graph-edge-card-outside-layout`) send an author to different places. `Space.graphs` survives as a **derived flatten** across the Layouts in declared order, never stored, beside the one `space.lookup` that answers a Graph with its owning Layout; that is why colour assignment, handle derivation, render Edge derivation, the canvas projection and Navigation still read one collection. Converting an Algorithmic View creates the Layout's initial empty Active Graph in the same Edit. **What remains is surface, not semantics** (`.scratch/card-route-editing/implementation-handoff.md`): package 3 built **fifteen** completions behind Space Authoring, and **seven of them still have no control that reaches them** — `added-card-to-layout`, `removed-card-from-layout`, `deleted-card`, `added-graph`, `renamed-graph`, `recolored-graph` and `deleted-graph`, the refusal to delete a Layout's last Graph included. Dispatched today: `settled-card-movement` (`render-adapter.ts`), `connected-cards`, `create-and-connect`, `reconnected-edge` and `deleted-edge` (all four in `edge-authoring.ts`, package 7), `edited-card` (`App.tsx`, from the opened-Card editor, the inline title editor, and an Alias rename or retarget — both of those last two through the one `editAlias` helper, since they differ only in which key the change carries), and `created-card` and `created-alias` (`App.tsx`, package 4's controls). The controls are packages 4–8, not 5 and 6 alone: Card and Alias creation is 4 (**built**, its delegated-pane rename and retarget recorded by ADR 0046, which refines ADR 0039's "the delegated pane renames nothing"; the Frame 5 Alias modifier gestures it declined are unowned and triaged in `.scratch/card-route-editing/issues/15`), Cards View with Add/Remove from Layout is 5, Graph management is 6, the Edge lifecycle is 7 (**built**), and the Delete-Card-from-Space cascade is 8. Omitted Cards still render in `positionedStrategy`'s fallback band, which package 5 deletes together with its replacement (see the `Placement` bullet in `docs/agents/rendering.md` — do not delete it early). ADR 0045 replaces the View-subject section outright — there are no View kinds — and a future tree View over the Cards one Graph connects is deferred as a product feature. Tickets and sequencing: `.scratch/first-public-aggregate/`.
- **ADR 0045 — a View takes Cards and Graphs and returns a Layout. Built**, and it refines 0040 rather than reopening it. A View is one interface with two sides: in, its subject — Cards and *zero* or more Graphs, because a new Space has none and still renders; out, on conversion, those Cards with positions and *one* or more Graphs, which may hold no Edges. Two obligations sit at that boundary and nowhere else: every Edge endpoint of every returned Graph is among the returned Cards, and every returned Graph carries a fresh identity owned by the new Layout. The second is what makes 0040's ownership structural — no View can hand two Layouts one Graph — and it is the mechanism 0040 claimed without supplying. **There are no View kinds**: 0040's Space-scoped/Graph-scoped section is replaced, and a tree over one Graph's Cards is a subject. A View whose subject is the Space's Cards draws every Graph in the Space, **flattened across its Layouts** — derived, never stored, and closed for free since every Edge endpoint is a Space Card. That flatten is why **a Graph id is unique across the Space** and not merely within its owning Layout, which is 0040's one identity sentence refined: the lookup intake builds is a `Map` and would silently drop a duplicate, and `<graphId>::out`/`::in` would put one handle id on a Card for two Graphs, which React Flow forbids per Card per side. Ownership is untouched — only the scope the id is unique in moves. Don't answer a duplicate by owner-qualifying Graph references through the render pipeline; that was weighed and costs the handle-id scheme to buy reuse nothing wants. Flow returning a fresh empty Graph on conversion is that View's choice among legal outputs, not a rule: don't lift it into the boundary, and don't let a View return a source Graph's identity however plainly the author meant *that* Graph. **The boundary is `convertSubject` in `packages/app/src/renderer.ts` and is nowhere else**: `RendererSubject` names the exact Cards and Graphs going in, and a conversion answers a non-empty tuple of Graphs coming out — Graphs only, because Space Authoring already holds the completed Placement and a second copy could only disagree with it. Every refusal throws a `RendererInvariantError`, because a View that broke an obligation is wrong and the Edit that called it has nothing to fall back to; Space Authoring must not turn one into `unchanged` or `refused`. **Fresh identity is now unrepresentable rather than checked**: a View policy answers `GraphWithoutId`, and the shared module mints every id — fresh against the whole Space, after the output has been validated whole, so a refused conversion consumes none. `packages/app/test/renderer.property.test.ts` generates deliberately hostile policies (an Edge naming a Card outside the Placement, an Edge repeated, no Graph at all) and is what makes the obligations hold for Views nobody has designed yet — which is why `convertSubject` and `checkSubject` are exported at all, against an implementation handoff that asked for the resolver to be the only way in. Nothing in `app` calls either but that test, and the registry is still private; the trade is written out in `.scratch/architecture-review/issues/01-the-conversion-boundary-is-exported-for-its-property-test.md` rather than argued from this sentence. A repeated Graph id is the matching load error, `duplicate-graph-id`, one per repeated id naming every occurrence with its Layout and index. See resolved issues `02` and `06` in `.scratch/adr-0040-0042/`, and `.scratch/first-public-aggregate/` for the tickets that built it.
- **`Layout` is data and `LayoutStrategy` is behaviour — don't collapse them back (ADR 0014, ADR 0040).** A `Layout` (in `core`) owns an authored card→position map whose keys are explicit Card membership, plus the ordered Graphs over those Cards; a `LayoutStrategy` (in `graph`) is `(graph: LayoutStrategyGraph) => Promise<LayoutStrategyGraph>` in the first-public vocabulary. Every Layout has a strategy that renders it; not every strategy has a Layout behind it. There is no `Arrangement` type and geometry rides as optional fields on the elements (ADR 0005) — don't introduce one. Older comments call the *function* a Layout; that is stale vocabulary, not a second concept. The strategy intermediates are `LayoutStrategyGraph`, `LayoutStrategyCard` and `LayoutStrategyPort`.
- **A card is one file: frontmatter, then body (ADR 0020, refined by ADR 0051).** Shared frontmatter is `id`, `title` and `kind`; Alias adds `target`, while Markdown content follows the fence as the body. There is no shared Description. The space file holds `version`, `id`, `title`, `layouts`, `defaultRenderer` — structure, and no `cards` array; a Layout holds the Graphs it owns, so there is no space-level `graphs` key (ADR 0040). Cards are discovered by scanning two locations, **non-recursively**: `*.md` beside the space file, and `cards/*.md`. Non-recursion is deliberate — ADR 0001's nested spaces will want subdirectories, and a recursive scan would make each one ambiguous with card discovery. A card's identity is its frontmatter `id` and never its filename, so renaming a file is not a data migration; a duplicate id across files is a load error naming both. A body may begin with a heading — the title lives in the same file, so a heading is just a heading. Every `.md` in scope *is* a card, so there is nowhere to leave a draft — and a `README.md` beside a space file would be read as one, which is why the fixture's moved to `packages/app/README.md`. **`body` is the field, `content` is the domain word**, and they are not synonyms to be reconciled: `CONTEXT.md` still lists "body" under _Avoid_ for a card's content in general, because a space-card's content is a graph and has no body. `Card.body` is what a *markdown* card's content is stored as. Don't rename one into the other in either direction.
- **Graphs are a Layout's only connection structure.** There is no authored `edges` array *beside* Graphs; ADR 0007 deleted that along with the `sequence`/`reference` kinds, and it stays deleted — don't reintroduce a structural layer next to Graphs. Under ADR 0040/0041 a Layout owns one or more Graphs over its explicit Card members, and every Graph Edge is closed over that set. A Graph **is** a set of `{from, to}` Edges the author draws (ADR 0032), so “Edge” names both the Graph's stored element and React Flow's drawn line — one word for one thing, and the only place the render layer and the domain share vocabulary. Cycles and self-Edges are legal; an exact duplicate within one Graph is not. The built types are `GraphEdge` (`core`) for the authored value, `GraphRenderEdge` (`graph/graph-rendering.ts`) for the handle-resolved projection, and `LayoutStrategyEdge` (`graph/layout.ts`) once a strategy has routed it. Do not preserve superseded Route-named aliases.
- **`manifest` is retired, in vocabulary and code (ADR 0010).** The top-level domain value is a **Space**, minted only by `loadSpace(input, cardFiles) → { ok, space } | { ok: false, errors }` in `@project/graph` — the one intake that parses (the space file *and* every card file's frontmatter), validates references, and indexes, so a `Space` is consistent and O(1)-resolvable by construction. `space.lookup` reads that index; every `graph`/adapter/app signature takes a `Space`. The on-disk shape is a **space directory**: the **space file** (`space.json`, validated by `core`'s `spaceFileSchema`) plus a markdown file per card (ADR 0020). A value that only passes that schema is *not yet* a Space. `loadSpace` gained the card files as an argument, not a capability — it still does no I/O and is still synchronous, and reading the bytes stays outside it. Don't reintroduce `manifest` anywhere — not as a type, not as the word for the file. There is no shared `Draft`: unfinished gestures and invalid editor input remain local to that editor. An editor installs valid authoritative state and emits a payload-free notification; Edit completion then derives and validates the whole next Space before effects.
- **A Graph may contain cycles and self-Edges (ADR 0032, terminology refined by ADR 0041).** Authoring records the Graph the author draws; Graph navigation and Presenting decide how to traverse it. An Alias is still the way to place and title the same content as a distinct Card, but it is not required merely to return to an existing Card. `loadSpace` rejects only an exact duplicate Edge within one Graph; drawing that duplicate live is an idempotent no-op.

## The SpaceBackend / SpaceSession contract

- **The browser never imports files or names storage.** `SPACE_DIR`, `virtual:space-file` and the Vite file plugin are gone. File discovery and parsing remain server-side CLI/import concerns. Browser resources are fixed to list, load and commit under `/api/spaces`; requests cannot carry database URLs, filesystem paths or arbitrary targets. A completed edit commits a whole `SpaceSnapshot` through `SpaceBackend`. Canonical export belongs to the CLI (ADR 0030) and is built (`src/export/export-space.ts`), never an app Save action.
- **Persistence crosses the app at `SpaceBackend` and `SpaceSession`.** Normal composition is `PostgresSpaceRepository` → Fetch-native Hono application → typed `HttpSpaceBackend` → one opened `SpaceSession`; standard E2E substitutes only an isolated `E2eMemorySpaceRepository` behind the same application. Startup lists over HTTP, opens the sole UUID or renders the UUID-only selector, while server-side policy ensures an empty database receives the normal new Space. Selection does not enlarge `SpaceSession`, which still owns one already-open workspace. Every backend commit validates both public shape and normal domain intake (`loadSpaceSnapshot`), so dangling references, duplicate Edges within one Graph, an Edge endpoint that is not a Card of its own Layout, one Graph id held by two Layouts and invalid aliases/layouts are permanent `invalid-snapshot` failures rather than stored state. Graph cycles and self-edges are valid authored structure (ADR 0032).
- **A session submits complete snapshots after completed edits.** It allows one commit in flight, coalesces waiting edits to the newest snapshot, chains the committed revision into the next optimistic write, and exposes pending, retryable failure, permanent rejection and conflict states. Persistence is totally asynchronous: Edit completion relies only on `submit` installing the local working snapshot synchronously, never waits for backend acknowledgement, and immediately selects the resulting Layout from that local state. Accepting remote replaces the session snapshot through Space Authoring rather than remounting: `acceptStoredSpace` validates the stored snapshot first, then installs the session, placement and a fresh Navigation together and advances `replacementEpoch`, which is what makes the render adapter drop the projection and drag bookkeeping so no store retains stale local positions. Graph activation is not an edit and does not submit.
- **Session notification is non-throwing, and a submit made from an observer is queued rather than re-entered.** An observer that throws cannot interrupt the publisher: `publish` contains each listener's failure, hands it to `SpaceSessionOptions.reportObserverError` (defaulting to `console.error`) and carries on to the remaining observers, so persistence, the working Space and any reentrant Edit completion all continue. The reporter is wrapped too, and unlike `@project/http`'s `invokeLogError` it never rethrows — nothing above a notification could handle the failure. Separately, an observer *may* legally submit the next Edit while the publishing submit is still on the stack, so **`submit` decides from `state.working`, never from its argument** — a reentrant call runs to completion first, and deciding from the argument queues the older snapshot behind the newer one and stores it last, undoing a completed Edit at the next load. Nothing suppresses a nested call to stop it double-committing; identity against the in-flight snapshot answers that at any depth. **Don't replace it with a guard scoped to a call's publication**: `retry` and `resolveConflict` publish `pending` from *inside* an optimistic publication, and a submit answering that notification has a commit to wait behind while the call underneath it is gated on the failure it published under and will decide nothing — the newest Edit then reaches no queue at all and the session reports `settled` without it. All of this is pinned in `session.test.ts`.

## Space Authoring's completed-edit lifecycle

- **Every semantic operation answers `completed`, `unchanged` or `refused`, and the three are not interchangeable (ADR 0042, refined by ADR 0057).** `AuthoringCompletion` is one discriminated union naming the completed authored fact an interaction knows — identities and a settled value, never a plan — and `complete` is the one operation over all of them. **`unchanged` is the value the author already authored** and is a surface's ordinary close. **`refused` carries a stable discriminated identity and typed domain context; application composition owns its wording, field placement and recovery.** This half of ADR 0057 is built; `.scratch/structured-errors/issues/02-use-http-problem-details.md` owns the remaining HTTP roll-forward. A broken invariant is neither and still throws. `edgeEligibility` is the proposal-shaped query behind every Edge gesture and returns the same structured refusal the completion re-asks. Domain tests assert refusal codes and context; presentation tests assert prose and accessibility. `space-authoring.property.test.ts` continues to hold every non-Edit to leaving the working snapshot's identity alone.
- **A Graph-creating gesture stores its palette colour, whichever gesture made it.** `nextGraphColor` rotates by the new Graph's appended position in its **owning Layout**, not by a count across the Space. The palette is six colours, and spending it per Layout gives every Layout a full run of them, so a Layout overview — which draws all of that Layout's Graphs at once, and where colour is what tells one line from another — stays distinct up to six. Rotating by the Space flatten instead would spend the palette globally and wrap at the seventh Graph *anywhere* in the Space, and that wrap can land inside one Layout, drawing two of its Graphs in one colour over shared Cards. Layout-local also keeps a Layout-owned value (ADR 0040) a function of its owning Layout alone, rather than of how many Graphs unrelated Layouts hold. Both creation gestures use it: Add Graph in `space-authoring.ts`, and `freshEmptyGraph` in `renderer.ts` for the Graph a conversion mints — a conversion creates the Layout, so its initial Graph is always the first palette colour. The cost is that a Space-subject View, which draws every Graph flattened across Layouts (ADR 0045), shows each Layout's first Graph in that same colour; the legend names them, and recolouring a Graph is the author's answer. `Graph.color` stays optional in the domain and `graphColorMap` still resolves a fallback for an imported Graph that carries none — by Space-flatten index, since resolution has no owning Layout in hand.
- **Authoring's completion sequence is total, and the runner that used to make it so is still gone.** `space-authoring.ts` splits a completed Edit in two. `deriveCompletedEdit` is the pure core: every read of current state a derivation makes, every refusal and the one `loadSpaceSnapshot` that can throw happen there, before a collaborator has moved, and it answers a `CompletedEdit` with nothing left to decide. **One decision is deliberately outside it**, and it is not a refusal the core could make: the drain's `replacementEpoch` gate reads the current epoch to answer whether a queued entry is derived *at all*, because an entry the epoch has outlived names a Space that is gone and the core would derive it happily against the one that replaced it (the bullet below has the rest of that argument). It is taken in `complete`, before `deriveCompletedEdit` is called and outside every install window, so the guarantee that matters is untouched: nothing inside the window has anything left to decide. `installCompletedEdit` is the shell, and **`session.submit` is deliberately first** — the Navigation call resolves the Graph and the Layout against `currentSpace()`, which reads the snapshot `submit` installs synchronously, so no other order exists. The useful consequence is that the only fallible statement is also the first: nothing later can invalidate something earlier, and a throwing `submit` leaves the placement and Navigation untouched instead of half-applied. One failure shape survives by construction: the session ahead of the placement and Navigation. It is the recoverable one, because the snapshot the session took already carries the completed placement in its Layout, and it is why `b091623` inverted the order. **Navigation is handed the renderer and its Active Graph in one call — `continueInRenderer(selection, activeGraphId)` — and Edit completion never calls `activateGraph`.** Under Layout-owned Graphs (ADR 0040) the two are one answer the Edit produced, and the intermediate state a second call would leave is not merely awkward but *invalid*: adopting the converted Layout while Navigation still holds the previously emphasised Graph names a Layout beside a Graph **another Layout owns**, which is exactly the pair `continueInRenderer` refuses — so a split would throw on every conversion, which is every first edit on an Algorithmic View. **Don't split them back**, and don't answer that by reversing them either: activating first would validate the Graph against the renderer the Edit *began* in rather than the one it produced, which is strictly weaker and is the thing the original two-call rule existed to prevent. The property that rule bought is intact — the Graph is still checked against the renderer this Edit wrote — and it now holds by construction rather than by ordering. **Don't re-check the Graph or the Layout inside the window** — the snapshot passed domain intake a line earlier, so those branches cannot be taken; the guards that do exist live in Navigation, where the invariant is, and this window is a caller that satisfies them. All of this is pinned by fault injection in `space-authoring.test.ts`.
- **The install gate counts depth, publishes in the `finally`, and contains a drained completion's failure.** Both windows (completion and `acceptStoredSpace`) run through `installTogether`, which raises the `installing` gate and **publishes in the `finally`**: the gate means Authoring's publication is the only one a subscriber gets, so a publication skipped by a throw left `getState()` answering the pre-Edit state permanently, until an unrelated notification happened along. That is not a `catch` — the failure still reaches the caller. **The gate counts depth and is not a boolean**, because the windows nest: `acceptStoredSpace` notifies from inside its own, when `session.acceptRemote()` publishes before the placement, Navigation and `replacementEpoch` have moved, and an observer is as entitled to complete an Edit from there as it is to submit from a session notification. A flag is cleared by the inner `finally`, and the rest of the outer sequence then publishes every part-way state the window was raised to hide, including the accepted Space carrying the `replacementEpoch` of the Space it replaced. Only the outermost window publishes. Separately, a completion the drain *reaches* is contained — its failure is reported and draining stops there, because the Edit that drained the queue had already installed and published and must not be charged someone else's failure. Completions still queued behind that failure are discarded, and that too is reported. What is **not** contained is a throw from the Edit the caller made itself: treat that as an unhandled case, and restoring the guarantee means making the sequence total, not adding a `catch`. **The drain also gates on ADR 0042's `replacementEpoch`** — the counter formerly called `opening`, which is one counter and not two: each entry records the epoch current when it was enqueued, and the drain discards, without deriving, any entry whose epoch differs. Refusing would not save it, since the identities usually still exist in the replacement and nothing would reject the completion — it would write an abandoned gesture over the Space the author has just accepted. The discard skips rather than stops, because a completion queued from inside the accept's own publication carries the new epoch and is the one the ADR says must still be honoured, and it reports once per drain through the same `safelyReport`. **This is where that argument is written out** — the drain comment, the ticket and both tests point here rather than restating it, and a fifth copy is a drift risk, not thoroughness. Interaction-draft invalidation, 0042's other half, reads the same epoch and is not built. All of it is pinned in `space-authoring.test.ts`.
- **Renderer resolution answers the subject; the strategy does not (ADR 0040/0041/0045).** A resolved renderer is a **discriminated** value and never a pair of nullable fields: `ResolvedLayoutRenderer` carries the Space's own canonical `ResolvedLayout` and is updated in place, `ResolvedViewRenderer` carries a `convert` and is converted by being edited (ADR 0025). Both carry a `RendererSubject` of **exact Cards and Graphs from the source Space** — a Layout's position keys in `space.cards` order and the Graphs it owns, or every Space Card and the flatten across every Layout. Values rather than ids, because every obligation stated over a subject is about the things themselves; a subject that is not the Space's own values, or repeats one, is refused as `invalid-subject`. Keep that resolution in one composition seam — `createRendererResolver` in `packages/app/src/renderer.ts` is that seam, and Flow and Grid are private definitions behind it (title, subject selector, strategy factory, identity-free Graph policy). **There is no public View registration**, deliberately: persisted View ids and missing-plugin behavior are undecided, and a seam exposed before either question is answered would be a guess. Which Graphs a renderer draws is now `renderer.subject.graphs` and nothing else — Navigation's membership test and the canvas projection both read it, so two places cannot disagree. A Layout's Active Graph is `resolvedLayout.activeGraph`, resolved once at intake; a View's `defaultActiveGraph` is used **only** when Navigation opens or explicitly selects it, and `continueInRenderer` carries the Active Graph the completed Edit produced rather than quietly applying a renderer's default.
- **A completed edit persists automatically (ADR 0030).** The editor first installs its authoritative completed state and synchronously emits a payload-free `EditCompleted` notification. Edit completion derives and validates the complete current `SpaceSnapshot`, submits it to `SpaceSession`, and immediately selects its resulting Layout; intermediate drag frames never reach persistence. The session status (`Persisting…`, `Persisted`, retry, rejection or conflict) is the persistence indicator. There is no Save button, keyboard Save command or browser file write-back. The `beforeunload` guard is registered only while persistence is not settled — an always-attached handler would cost the page its bfcache. It calls `preventDefault()` and nothing else; `event.returnValue = ''` is deprecated and lint rejects it.
- **Activating a Graph is not an Edit (ADR 0028, refined by ADRs 0040 and 0041).** It converts no Algorithmic View and never submits persistence by itself. Edit completion samples the current Layout's Active Graph only when `EditCompleted` is emitted, rather than subscribing Graph activation into an Edit trigger. The submitted Layout names its Active Graph outright because the resolve-to-first fallback is a read and persisted state should not depend on Graph order. `updatePositionedLayout` replaces a Layout's positions **and its owned Graphs** whole, because the editor holds the whole truth of both and a Graph is a nested owned value with nowhere else to be written (ADR 0040); an Edit naming no Active Graph carries the existing one through rather than clearing it. `space.graphs` is never written back — it is the derived flatten, and every Graph reaches the wire inside its Layout.
