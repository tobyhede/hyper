# AGENTS.md

Instructions for AI coding agents working in this repo.

A local, file-first prototype for **graph-native technical presentations**: Markdown cards on a spatial graph, authored in a space file and presented as curated routes. Placement is **authored, not computed** — a **Layout** is the card→position map the author writes, and the thing that arranges cards is a **LayoutStrategy** (ADR 0014) — with elkjs demoted to one automatic strategy among several and to the engine behind Auto-arrange (ADR 0013). *Not built yet: the app still runs `elkStrategy()` on every boot; the spec is `.scratch/positioned-layout/`.* The overview draws every route at once, each as a colored line of React Flow edges, with the selected one emphasised. Cards in the graph show their title; **opening** a card reads it in place, and **presenting** a route is a separate reveal.js deck (ADR 0006, ADR 0008). pnpm + TypeScript (strict) monorepo.

## Commands

- Install: `pnpm install` (Node >= 20, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173). **A dev server is usually already running on :5173, owned by the human in their own terminal — leave it alone.** Do NOT start, stop, restart, or kill it, and do not free the port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). Assume it's up and hot-reloading (Vite HMR + React Fast Refresh); your edits are already live in it. `strictPort: true`, so a second `pnpm dev` will fail rather than pick another port — don't run one. To verify changes, use `pnpm test`/`pnpm e2e` (Playwright starts its own server) — never the human's dev server.
- Verify: `pnpm verify` runs `typecheck` -> `lint` -> `format:check` -> `test` (i.e. `tsc --noEmit`, `eslint .`, `prettier --check .`, `vitest run`).
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- E2E: `pnpm e2e` (Playwright, chromium only). One-time first: `pnpm exec playwright install chromium`. The config auto-starts the dev server.
- Build: `pnpm build` (Vite build of the app).

## Package layout & boundaries

Five `@project/*` workspace packages under `packages/`:

- `core` — domain model. Zod schemas (`schema.ts`, incl. `spaceFileSchema` — the space-file shape) + the `Card`/`Route`/`RouteStep`/`Layout` types derived from them (`types.ts`). No React, no framework deps.
- `graph` — pure graph logic over a `Space`: `loadSpace` (the one intake — parse, validate references, index), the `Space` type, O(1) lookups, route navigation (clamped step indexing), route→handles/edges derivation, reference validation, and the `LayoutStrategy` contract (`LayoutGraph`, `buildLayoutGraph`, `gridStrategy`, `positionedStrategy`). Depends only on `core`.
- `react-flow-adapter` — the ONLY place React-Flow (`@xyflow/react`) and elkjs specifics live: projects a space+route into RF nodes/edges, implements `LayoutStrategy` as `elkStrategy`, renders `CardNode`.
- `ui` — reusable, presentation-agnostic React components + shadcn-style primitives (Tailwind v4, Radix Select, CVA). Depends on `core` only.
- `app` — wiring/composition: Zustand store, TanStack Router, space loading, graph/presentation views, hand-rolled CSS.

Hard rules:
- Domain logic stays out of React (keep it in `core`/`graph`).
- React-Flow / elkjs specifics stay in `react-flow-adapter` — nothing else imports them.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases (declared in `tsconfig.base.json` AND mirrored in `vitest.config.ts` `resolve.alias`; Vite resolves them via the workspace). Keep the two alias lists in sync when adding a package.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **`Layout` is data and `LayoutStrategy` is behaviour — don't collapse them back (ADR 0014).** A `Layout` (in `core`) is the authored card→position map a space carries; a `LayoutStrategy` (in `graph`) is `(graph: LayoutGraph) => Promise<LayoutGraph>`. ADR 0005 called the *function* a Layout, which is the vocabulary you'll find quoted in older comments and in ADR 0005 itself — that decision (no `Arrangement` type, geometry as optional fields on the elements) still stands; only the noun moved. Every Layout has a strategy that renders it; not every strategy has a Layout behind it. `LayoutGraph`/`LayoutCard`/`LayoutPort` belong to the *strategy* despite the name.
- **The strategy contract lives in `graph`, not the adapter.** Geometry lands as optional fields on the cards and handles, mirroring how ELK itself models it. `gridStrategy` (pure, places no handles) exists partly to keep the seam honest; if a change only works for `elkStrategy`, the contract has leaked. Which cards get arranged is the view's choice, passed in. The contract is uniformly async — the earlier `LayoutGraph | Promise<LayoutGraph>` union was collapsed once nothing exercised the sync branch (`gridStrategy` is now `async`); see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored; ELK does not own it (ADR 0013).** A strategy is *automatic* (computes placement from cards and routes alone — ELK, grid) or *positioned* (reads a Layout the author wrote, which lives in the space file). Editing placement requires a Layout, so an automatic view is read-only — whether the view resolved to a Layout is what decides, and there is no edit mode to track. **Don't re-suggest seeding or constraining ELK to honour a drop point**: three spike increments — append, then branch, then seeded and interactive ELK — each reshuffled the *existing* cards and placed the new one by global optimisation, so a drop landed somewhere arbitrary. The failure is structural, not a matter of tuning. The harness itself has been deleted; the finding is ADR 0013 and `.scratch/graph-editing/`, in words. It was only gitignored at first, which was not enough: it went stale against the `elkLayout` → `elkStrategy` rename and then broke `pnpm dev`, because Vite's dependency scanner reads every `.html` in the package root and does not consult `.gitignore` — while tsc and eslint both skip `.scratch/`, so nothing else in the toolchain saw it. Write a harness up and delete it.
- **ELK port offsets are applied to handles.** ELK's *port* is React Flow's *handle* — same thing, two libraries' words. ELK computes each one's position, and those exact offsets drive where `CardNode` renders the handle, so a route's edges meet its cards cleanly. Don't hardcode handle positions.
- **Port constraints are `FIXED_SIDE`, not `FIXED_ORDER`.** ELK orders `FIXED_ORDER` ports **clockwise** around the node — EAST top-to-bottom but WEST *bottom-to-top*. Handing both sides the same list order therefore puts a route's outbound handle at the top of one card and its inbound handle at the bottom of the next, crossing every route at every shared card. `FIXED_SIDE` fixes the side and lets ELK order within it. Don't switch back without reading `.scratch/layout-seam/issues/04-elk-fixed-side-ports.md`.
- **ELK port ids are namespaced per card.** A handle id (`<routeId>::out`/`::in`) is the *same* on every card a route passes through, so `elkStrategy` hands ELK `<cardId>##<handleId>` (`elkPortId`) and builds edge endpoints from the same key, stripping the prefix on read-back, so handles keep their bare ids and `CardNode` is unaffected. Never hand ELK a bare handle id — it then can't tell which card an edge attaches to and mislays *even single-route* graphs. See `.scratch/layout-seam/issues/01-namespace-elk-port-ids.md`.
- **Handle ids must be distinguishable per card per side — React Flow's rule, not just ELK's.** The entry above covers why ELK needs `<cardId>##<handleId>`; React Flow separately requires that *"multiple handles of the same kind on a node need to have distinguishable IDs"*, or it can't resolve an edge's `sourceHandle`/`targetHandle` and warns (#008). The `<routeId>::out`/`::in` scheme satisfies both libraries, for different reasons. Don't collapse it to a per-side counter.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `CardNode` dims handles via `opacity` and it looks like a styling choice; it isn't. Same for the CSS in `styles.css`.
- **Changing a handle's position or count needs `useUpdateNodeInternals`.** React Flow measures handles once and caches; a `data` change re-renders but does not re-measure, which is React Flow's named cause of warning #008 and of edges attaching to stale positions. Handle `offsetY` *does* change here when ELK resolves — the exposure is currently masked because `RoutedEdge` draws ELK's own points and ignores React Flow's measured `sourceX/Y`, so only the bezier fallback (grid strategy, first paint) reads the stale value. It stops being masked the moment routes can be added or removed on a live graph. Decide this before graph editing lands; `node.handles` (declaring port geometry from ELK rather than having React Flow measure it) is the alternative worth a spike. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`.
- **A card is one file: frontmatter, then body (ADR 0020).** `id`, `title`, `description`, `kind` and `target` are the card file's frontmatter; the markdown under it is the content. The space file holds `version`, `id`, `title`, `routes`, `layouts`, `defaultView` — structure, and no `cards` array. Cards are discovered by scanning two locations, **non-recursively**: `*.md` beside the space file, and `cards/*.md`. Non-recursion is deliberate — ADR 0001's nested spaces will want subdirectories, and a recursive scan would make each one ambiguous with card discovery. A card's identity is its frontmatter `id` and never its filename, so renaming a file is not a data migration; a duplicate id across files is a load error naming both. **The old rule that a body must not begin with a heading is gone**, along with the e2e test that policed it: the title now lives in the same file as the body, so a heading is just a heading. Every `.md` in scope *is* a card, so there is nowhere to leave a draft — and a `README.md` beside a space file would be read as one, which is why the fixture's moved to `packages/app/README.md`. **`body` is the field, `content` is the domain word**, and they are not synonyms to be reconciled: `CONTEXT.md` still lists "body" under _Avoid_ for a card's content in general, because a space-card's content is a graph and has no body. `Card.body` is what a *markdown* card's content is stored as. Don't rename one into the other in either direction.
- **Routes are a space's only structure.** There is no authored `edges` array; ADR 0007 deleted it along with the `sequence`/`reference` kinds. `Edge` is React Flow's word for the drawn line, one per route step transition, and `CONTEXT.md` lists it under a render-layer section rather than as a domain term. Don't reintroduce authored edges as a "structural layer".
- **`path` now means a file path only.** The Route rename is done: the manifest key is `routes`, and the code says `Route`/`routeId`/`buildRouteEdges`. Remaining `path` identifiers are filesystem paths, TanStack Router URL paths, or React Flow's own SVG `edge-path` class — don't "fix" those.
- **`manifest` is retired, in vocabulary and code (ADR 0010).** The top-level domain value is a **Space**, minted only by `loadSpace(input, cardFiles) → { ok, space } | { ok: false, errors }` in `@project/graph` — the one intake that parses (the space file *and* every card file's frontmatter), validates references, and indexes, so a `Space` is consistent and O(1)-indexable by construction. `getCard`/`getRoute` read that index; every `graph`/adapter/app signature takes a `Space`. The on-disk shape is a **space directory**: the **space file** (`space.json`, validated by `core`'s `spaceFileSchema`) plus a markdown file per card (ADR 0020). A value that only passes that schema is *not yet* a Space. `loadSpace` gained the card files as an argument, not a capability — it still does no I/O and is still synchronous, and reading the bytes stays outside it. Don't reintroduce `manifest` anywhere — not as a type, not as the word for the file. The future edit buffer (a `Draft`, not built) is where a mutable, possibly-invalid working copy would live; a Space is never that.
- **Styling is split:** `ui` uses Tailwind v4 + shadcn-style primitives; the graph/card CSS stays hand-rolled in `packages/app/src/styles.css`. Tailwind scans `app` + `ui/src` via `@source` in `tailwind.css`.
- **Markdown is excluded from Prettier** (`.prettierignore`) — don't rely on `format` to touch `*.md`.
- **A saved arrangement lives in `space.local.json`, and the seam is a Vite plugin.** `packages/app/vite-space-file-plugin.ts` serves the space file *and* the card files as a `virtual:space-file` module (`spaceFile` prefers `fixture/space.local.json` and falls back to `fixture/space.json`; `cardFiles` is the two-location scan, and the plugin is where read scope is decided — only the space file has a local variant) and takes saves on `PUT /__space`, which validates with `spaceFileSchema` **server-side** and writes a path fixed in the config — the client never sends one, because an endpoint taking a path from the browser is an arbitrary-file-write primitive for any page you have open. `SPACE_BASE_ONLY` pins reads to the base *and* no-ops writes; `playwright.config.ts` sets it so e2e tests a known graph and parallel drag tests don't race on the file. Deleting `space.local.json` throws an arrangement away. Nothing watches the file — it is picked up on the next full page load, deliberately, because HMR-ing the space mid-drag is a feedback loop.
- **Don't import a workspace package by name into `vite.config.ts`.** Vite loads the config in Node and externalizes bare specifiers, so `@project/core` hands *Node* the TypeScript source, whose extensionless relative imports (`export * from './schema'`) Node's ESM resolver rejects — the config then fails to load at all and the dev server will not start. Import by relative path (`../core/src/index`) so esbuild bundles it. This is the one place the repo's extensionless-import convention does not hold.
- **The space-file plugin is not `apply: 'serve'`.** Reading has to work in a build, because `space.ts` imports the virtual module unconditionally; only *saving* is dev-only, and that lives in `configureServer`, a hook Vite calls only for the dev server. A build always reads the authored base — baking one machine's arrangement into a bundle would ship working state as content.
- **Changing the Vite config needs a dev server restart** — plugins load at config time and HMR won't pick them up. That server is the human's; say it needs restarting rather than restarting it.
- **Delete a spike harness when you write it up; ignoring it is not enough.** `packages/app/spike.html` sat gitignored, went stale against the `elkLayout` → `elkStrategy` rename, and broke `pnpm dev` — Vite's dependency scanner treats every root `.html` as an entry and does not read `.gitignore`, while tsc and eslint both skip `.scratch/`, so `pnpm verify` stayed green and only the dev server saw it.

## Scope discipline

Keep to the MVP. Don't over-generalize the domain model and don't add features beyond what's asked.

On multi-route rendering (shipped 2026-07-20, `.scratch/multi-route/`): the overview draws every route, and **selection is emphasis, not filtering** — at all times, not only while presenting. The dimming in `projectRouteEdges`, `CardNode` and `RouteLegend` is now live; it was dead code from the initial commit until then. `filterHandlesByRoute` and `routeCardIds` still exist and are still right for a view that wants one route. Which routes a view shows is a View decision passed into the strategy (ADR 0005) — don't let the strategy or `graph` decide it.

**A route may not revisit a card (ADR 0012).** A revisit is the one backward edge a *single* route could create, and it renders cleanly only as a channel looping around the cards or by unrolling into duplicate nodes — but "return to earlier content" already has a better word: an **alias** (ADR 0009), a distinct forward-stepped card showing the same content. `loadSpace` rejects a route whose steps repeat a card (`route-revisits-card`). So single-route graphs are acyclic by construction.

The overlay limit that remains: only **compatible** routes — their combined step-order (every route's `step[i] → step[i+1]`, unioned) is acyclic — lay out on a clean left-to-right axis, as parallel forward paths. A backward edge can now come only from **two routes disagreeing** on the order of shared cards (ADR 0003 still permits that). **`layout-seam/03` is shipped:** `elkStrategy` returns ELK's routed `sections` on each edge and the adapter's `RoutedEdge` draws them (a bezier fallback covers grid/first-paint), so such a cross-route back-edge reads as a routed channel rather than a self-curling stub. Read `.scratch/multiple-routes/findings.md` before extending any of this.

The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against a purpose-shaped graph rather than demo prose. It is **two disconnected collections** sharing no cards, which ELK lays out as separate bands: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several routes over one spine; (2) `Echo E→F→G→H→E′` — a plain linear collection. Each returns to its start via an alias (`A′`/`E′`, which the `↳` marker names), never a revisit, so the fixture is acyclic and lays out as clean forward paths. `03`'s back-edge rendering is proven by a unit test (`elk-strategy.test.ts`), not the fixture. The demo stays in `packages/app/example/`, dormant, for when real space-loading exists. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a space file would be scanned as a card). And note the ELK options in `elk/layout.ts` are back to a minimal baseline — a round of spacing/alignment tuning against this fixture was reverted as fixture-polish; if legible multi-route overlay becomes real product work, design it deliberately, not by tuning global options against a screenshot.
