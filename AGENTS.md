# AGENTS.md

Instructions for AI coding agents working in this repo.

A local prototype for **graph-native technical presentations**: Markdown Cards on spatial Layouts, connected into curated directed Graphs and presented by traversal. PostgreSQL is the live write model and the browser reaches it over HTTP; memory repositories are confined to isolated development and E2E runs. Placement is **authored, not computed** — a **Layout** owns an explicitly positioned subset of Space Cards and the Graphs authored across them, while the thing that arranges Cards is a **LayoutStrategy** (ADR 0014, ADR 0040, ADR 0041). A Space need not carry a Layout: an automatic strategy the app supplies renders it, and editing converts that into a Layout (ADR 0025). **No strategy is privileged** — elkjs is one member of a growing set (grid, sorts, tree, cluster), never the thing "layout" means. A Layout overview draws every Graph it owns at once, each as a coloured line of React Flow Edges, with the Active Graph emphasised. Cards in the graph show their title; **opening** a Card reads it in place, and **presenting** traverses the Active Graph (ADR 0006, ADR 0011, ADR 0024).

## Decided — read these before the code

Accepted ADRs run ahead of the code, and standing workarounds constrain it. Read them before touching the areas they govern, and do not read the current code as the design. Each entry states what is built and what is not; most of this section is now built, so the build status to trust is the one written in the entry.

- **ADR 0041 — Graph is the first-public name for Route — built.** The vocabulary rename is complete: schemas, code, tests and fixtures use Graph, Graph navigation and Traversal history; Route and Walk survive only in historical records and qualified HTTP or graph-layout routing prose. Unqualified `Graph` and `GraphEdge` name the domain; strategy and render intermediates use `LayoutStrategyGraph` and `GraphRenderEdge`; the canvas is `SpaceCanvas`; and the former Graph-labelled Algorithmic View is Flow. ADR 0040's Layout-owned first-public document was a separate structural change, landed after it by `.scratch/first-public-aggregate/`.

- **ADR 0030 — PostgreSQL is the live write model; files are imported and exported.** The application and database foundations are **built**: every public id is a UUID, the import schemas allow persistence-owned ids to be omitted, and `SpaceBackend`/`SpaceSession` drive optimistic whole-snapshot commits, ordered coalescing, explicit retry and visible conflicts. Node 24, pinned Prisma Next and PostgreSQL, the document contract, formal migration and typed runtime entry are in place. The Prisma Next/PostgreSQL repository lists, loads and revision-checks completely identified aggregates, commits them transactionally, and imports complete new Spaces without updating or merging existing ones. The `hyper` CLI discovers one Space or a batch of immediate child Spaces, minting every missing Card, Graph and Layout id in process through `newUuid` while a space's id comes from its column default; an existing Space or Card identity rejects and rolls back the complete batch. The built document is the first-public **version 1**, which ADR 0040 put in place of the disposable pre-release shape rather than migrating it: a Graph is a nested owned value of its Layout, a Layout identity is scoped to its Space, and a Graph id is unique across the whole Space because the flattened Space-subject View keys on that id alone (ADR 0045). Import mints a Layout's id and its Graphs' ids in the same pass, before validation and before the first Card is written. A version 2 document is **rejected, never migrated** — by name at domain intake (`unsupported-version`, which says which version arrived) and on the `version` literal at the wire and file-import schemas that parse ahead of it. Identities of different entity kinds may still share a UUID. `--dangerous-truncate` deletes all Hyper content and inserts the batch in that same transaction. Server-side startup creates or loads the zero/one/many-space database experience, the CLI applies that policy after import or with no path, and the normal browser runtime now lists, opens and commits through the typed `HttpSpaceBackend` and Fetch-native Hono application. Standard E2E uses the same HTTP interface over isolated memory repositories; an opt-in PostgreSQL browser test proves durability across a fresh Vite host. CI provisions the exact pinned Compose service with generated masked credentials, applies the committed migration history, runs the complete PostgreSQL integration suite and verifies the live contract. The Save action, file write-back, virtual file module and source-byte preservation flow are gone. The CLI-only canonical exporter regenerates deterministic version 1 directories through staged, validated replacement and records the exact projected revision. The existing `space.json` plus card Markdown structure stays. See `docs/superpowers/specs/2026-07-28-postgres-document-persistence-design.md`.
- **Prisma Next 0.16.0 packaging workaround.** Its emitted `contract.d.ts` imports types directly from `@prisma-next/adapter-postgres`, `@prisma-next/target-postgres`, `@prisma-next/sql-contract`, and `@prisma-next/contract`, but pnpm's strict layout does not expose transitive packages to that project-owned file. Those four packages are therefore exact `0.16.0` root devDependencies only so generated types resolve. Authored config/runtime/application code still imports database capabilities only through the `@prisma-next/postgres` facade. Do not add hoisting or patch emitted artifacts; remove the four direct devDependencies when an upstream release emits facade-resolvable types.
- **Prisma Next 0.16.0 `int8` typing workaround.** Its PostgreSQL codec declares `int8` input and output as JavaScript `number`, although the codec and node-postgres runtime pass bigint-compatible values through unchanged. Repository revisions remain `bigint`; one compatibility cast is isolated in `toDatabaseRevision` and runtime values are checked when read. Do not convert revisions through `Number`, which loses PostgreSQL `bigint` range, and remove the cast when upstream exposes a lossless `int8` type.
- **ADR 0025 — a Layout is optional, and editing an Algorithmic View creates one.** The placement half is **built**: `positionedStrategy` exists, the composed renderer resolver returns it whenever `defaultView` names a declared Layout, and an Algorithmic View keeps its computed Card positions in runtime state until the first completed placement edit converts it. That conversion copies every Card already on screen, submits the Positioned Layout through `SpaceSession`, and repoints `defaultView` at it. ADR 0045 now makes a View one interface over an open subject: it receives Cards and zero or more Graphs, and on conversion returns those Cards with their positions plus one or more Graphs, each under a fresh identity owned by the new Layout. A tree over the Cards one Graph connects is a subject, not a kind of View, and its product interaction is deferred beyond version 1. After conversion, the current and every later render comes from the authored Layout; obsolete asynchronous strategy results cannot replace it. ELK renders the fixture because the fixture names no `defaultView` — a resolution outcome, not a privileged engine. It *declares* two Layouts, one per disconnected collection, since a Graph is owned by a Layout and the fixture has four; leaving `defaultView` absent is what still opens it in Flow, over the flatten across both. The structural half of 0025's definition of editing — create, delete, connect — begins with ADR 0033's Graph-authoring behavior. Issues `01`–`07`, `12`, and `13` are resolved; `01`–`07` were written against the superseded 0013/0017 model, so don't read them as the design either.
- **ADR 0031 — Views and Layouts are selected; conversion keeps no strategy provenance.** Built: the toolbar has peer icon selectors for application-supplied Algorithmic Views and Space-owned Positioned Layouts. Selection is navigation and never persists by itself. Editing an Algorithmic View creates and selects the next neutrally titled Layout without touching existing Layouts; automatic persistence adds it and makes it `defaultView`. Editing a selected Layout updates it in place. The converted Layout remembers no source strategy, and the prototype Auto-arrange control plus the resolved view's `automatic` flag are gone. See resolved issue `16`.
- **ADR 0033 — authoring is drag-to-connect through four spatial handles coloured as the Active Graph.** Built: source handles appear on the hovered or selected Card; target handles appear during the drag. They are Graph-independent and the chosen side is not authored. Algorithmic View conversion, initial-Graph minting and Option/Alt empty-drop create-and-connect are also built; detached Card creation and structural deletion are not. The per-Graph attachment machinery in `react-flow-adapter` serves overview rendering and is not visible authoring UX.
- **ADR 0040 — Layouts own Card membership and Graphs (terminology refined by ADR 0041).** The aggregate is **built**, in the first-public version 1 document and with no compatibility migration from version 2: a Layout's position keys are its explicit Card membership, its non-empty ordered `graphs` are nested owned values and there is no Space-level Graph collection, and every owned Edge endpoint must name a Card in that Layout — one rule, checked in `validateReferences` — which now tells its two readings apart, since an endpoint naming no Card at all (`graph-edge-missing-card`) and one naming a Space Card outside its Layout (`graph-edge-card-outside-layout`) send an author to different places. `Space.graphs` survives as a **derived flatten** across the Layouts in declared order, never stored, beside the one `space.lookup` that answers a Graph with its owning Layout; that is why colour assignment, handle derivation, render Edge derivation, the canvas projection and Navigation still read one collection. Converting an Algorithmic View creates the Layout's initial empty Active Graph in the same Edit. **Three parts are not built and belong to package 5 of `.scratch/card-route-editing/implementation-handoff.md`**: omitted Cards still render in `positionedStrategy`'s fallback band (see the `Placement` bullet below — do not delete it early), Remove from Layout and the Delete-Card-from-Space cascade have no surface, and Graph management — including the refusal to delete a Layout's last Graph — does not exist. ADR 0045 replaces the View-subject section outright — there are no View kinds — and a future tree View over the Cards one Graph connects is deferred as a product feature. Tickets and sequencing: `.scratch/first-public-aggregate/`.
- **ADR 0045 — a View takes Cards and Graphs and returns a Layout. Built**, and it refines 0040 rather than reopening it. A View is one interface with two sides: in, its subject — Cards and *zero* or more Graphs, because a new Space has none and still renders; out, on conversion, those Cards with positions and *one* or more Graphs, which may hold no Edges. Two obligations sit at that boundary and nowhere else: every Edge endpoint of every returned Graph is among the returned Cards, and every returned Graph carries a fresh identity owned by the new Layout. The second is what makes 0040's ownership structural — no View can hand two Layouts one Graph — and it is the mechanism 0040 claimed without supplying. **There are no View kinds**: 0040's Space-scoped/Graph-scoped section is replaced, and a tree over one Graph's Cards is a subject. A View whose subject is the Space's Cards draws every Graph in the Space, **flattened across its Layouts** — derived, never stored, and closed for free since every Edge endpoint is a Space Card. That flatten is why **a Graph id is unique across the Space** and not merely within its owning Layout, which is 0040's one identity sentence refined: the lookup intake builds is a `Map` and would silently drop a duplicate, and `<graphId>::out`/`::in` would put one handle id on a Card for two Graphs, which React Flow forbids per Card per side. Ownership is untouched — only the scope the id is unique in moves. Don't answer a duplicate by owner-qualifying Graph references through the render pipeline; that was weighed and costs the handle-id scheme to buy reuse nothing wants. Flow returning a fresh empty Graph on conversion is that View's choice among legal outputs, not a rule: don't lift it into the boundary, and don't let a View return a source Graph's identity however plainly the author meant *that* Graph. **The boundary is `convertSubject` in `packages/app/src/renderer.ts` and is nowhere else**: `RendererSubject` names the exact Cards and Graphs going in, and a conversion answers a non-empty tuple of Graphs coming out — Graphs only, because Space Authoring already holds the completed Placement and a second copy could only disagree with it. Every refusal throws a `RendererInvariantError`, because a View that broke an obligation is wrong and the Edit that called it has nothing to fall back to; Space Authoring must not turn one into `no-edit`. **Fresh identity is now unrepresentable rather than checked**: a View policy answers `GraphWithoutId`, and the shared module mints every id — fresh against the whole Space, after the output has been validated whole, so a refused conversion consumes none. `packages/app/test/renderer.property.test.ts` generates deliberately hostile policies (an Edge naming a Card outside the Placement, an Edge repeated, no Graph at all) and is what makes the obligations hold for Views nobody has designed yet — which is why `convertSubject` and `checkSubject` are exported at all, against an implementation handoff that asked for the resolver to be the only way in. Nothing in `app` calls either but that test, and the registry is still private; the trade is written out in `.scratch/architecture-review/issues/01-the-conversion-boundary-is-exported-for-its-property-test.md` rather than argued from this sentence. A repeated Graph id is the matching load error, `duplicate-graph-id`, one per repeated id naming every occurrence with its Layout and index. See resolved issues `02` and `06` in `.scratch/adr-0040-0042/`, and `.scratch/first-public-aggregate/` for the tickets that built it.
- **ADR 0034 — the HTTP application is Fetch-native.** Built: the browser-safe `@project/http` package owns the complete Hono route tree, request policy, inferred application type and typed browser backend, over the narrow repository seam `@project/persistence` declares. Development, preview and E2E compose that Fetch application over the selected repository, and the Vite host uses Hono's maintained Node adapter while leaving non-API requests to Vite. Runtime validation stays at the wire. Node, Vite, PostgreSQL, asset serving and process lifecycle stay in adapters or deployment composition rather than the portable route module. The superseded raw Node handler and boolean fallthrough interface are deleted. See `.scratch/fetch-native-http/`.

## Commands

- Install: `pnpm install` (Node >= 24, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173) is the normal PostgreSQL-backed HTTP runtime and requires the configured database to be up. `pnpm dev:new` (port 5174) serves an initially empty memory repository; server-side startup creates the normal one-card **new space** once (ADR 0018). `pnpm dev:fixture` (port 5175) serves the tracked fixture through the same HTTP boundary over an isolated memory repository. Edits in either memory runtime survive browser reloads for that server's lifetime. None writes source files. **A dev server is usually already running on :5173, owned by the human in their own terminal — leave it alone.** Do NOT start, stop, restart, or kill it, and do not free the port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). Assume it's up and hot-reloading (Vite HMR + React Fast Refresh); your edits are already live in it. `strictPort: true`, so a second `pnpm dev` will fail rather than pick another port — don't run one. To verify changes, use `pnpm test`/`pnpm e2e` (Playwright starts its own servers) — never the human's dev server.
- Verify: `pnpm verify` runs `typecheck` -> `typecheck:packages` -> `lint` -> `format:check` -> `test:coverage` (i.e. `tsc --noEmit` over the root program, then `pnpm -r typecheck` over each package's own config, `eslint . --max-warnings=0`, `prettier --check .`, `vitest run --coverage`). **Both typechecks are needed**: the root program's `include` has `"*.config.ts"`, and `*` does not cross directory boundaries, so `packages/app/vite.config.ts`, `vite-space-http-plugin.ts` and `http-server-build.config.ts` are covered only by the per-package pass. Warnings fail the lint run; coverage thresholds are per-package and pinned at what already holds (`core`, `graph`, `persistence`), with no global threshold on purpose.
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- E2E: `pnpm e2e` (Playwright, Chromium only) stays database-free and exercises HTTP; `pnpm e2e:fixture` selects only the tracked-fixture project. Every test owns a fresh Vite host, `E2eMemorySpaceRepository` and catalog; reloads and extra pages inside that test share them, while no revision leaks to another test. The `chromium` project imports the tracked fixture and `new-space` starts empty so database startup creates one card. Hosts use worker-scoped ports beginning at 5300, away from the human's 5173–5175. `pnpm e2e:postgres` is the separate opt-in one-test project proving a real PostgreSQL edit survives a fresh Vite host; run it only with PostgreSQL up and always stop PostgreSQL afterward. One-time first: `pnpm exec playwright install chromium`.
- Build: `pnpm build` (Vite build of the app).
- PostgreSQL integration: copy `.env.example` to the ignored `.env`, fill its password and matching `DATABASE_URL`, then run `pnpm postgres:up` followed by `pnpm test:integration:postgres`. Always finish with `pnpm postgres:down`; it keeps the named volume. `docker compose down --volumes` is the destructive reset. Normal `pnpm verify` and `pnpm e2e` do not require PostgreSQL.

## Package layout & boundaries

Seven `@project/*` workspace packages under `packages/`:

- `core` — domain model. Zod schemas (`schema.ts`, incl. `spaceFileSchema` — the space-file shape) + schema-derived `Card`/`Graph`/`GraphEdge`/`Layout` types (`types.ts`). No React, no framework deps.
- `graph` — pure graph logic over a `Space`: `loadSpace` (the one intake — parse, validate references including duplicate Edges within a Graph, index), the `Space` type and the one `SpaceLookup` it carries, Graph→render-handle/Edge derivation, traversal, and the `LayoutStrategy` contract (`LayoutStrategyGraph`, `buildLayoutStrategyGraph`, `gridStrategy`, `positionedStrategy`). Depends only on `core`. **Its index is curated and there is no `export *`**, and the unit of curation is the **module**: it names every function something outside the package calls, and every type exported by a module those calls reach — whether or not a consumer writes that type down today. `frontmatter` and `validate` are absent as whole modules: the first is how `card-file` reads a fence, the second runs inside `loadSpace`, which ADR 0010 makes the one intake. `SpaceReferenceError` is off the surface although `loadSpace`'s `SpaceError` union names it, while `CardFileError` in that same union is offered — reachability is not the test, and neither is depth. Adding a name is a deliberate act — `test/unit/graph-package-surface.test.ts` holds the index's declarations and the module they produce to one list, so a new export fails until it is listed there. A test of an internal helper imports it from its own module rather than through the index.
- `http` — browser-safe Fetch transport: the Hono `/api/spaces` route tree, request and response policy and the inferred `SpaceHttpApp` client contract. It *consumes* the narrow `SpaceResourceRepository` seam rather than declaring it — that lives in `persistence`, beside the `LoadedSpace` and `SpaceSummary` it is written in terms of. Depends only on `core`, `persistence`, Hono and runtime-neutral media parsing; imports no host, database, app or render implementation.
- `persistence` — browser-safe `SpaceBackend` and `SpaceSession` contracts, optimistic revision handling, commit coalescing, retry/conflict states, and the memory adapter. It also declares the **stored** side of the seam once, for both consumers: `SpaceResourceRepository` and `RepositoryCommitResult` (`src/repository.ts`), which `@project/http` takes and which `src/persistence/space-repository.ts` extends into `SpaceRepository` by adding `importSpaces` and `markExported`. The server seam is a superset, never a second declaration — a `Card`/`Graph` change cannot leave the two sides disagreeing, and the browser still cannot name import or export because the seam the Fetch application consumes does not declare them. Depends on `core` and `graph` so every committed snapshot passes the normal domain intake. It also owns **`createObservableState`**, the one observable-state seam behind `SpaceSession`, Navigation and SpaceAuthoring's own `getState`/`subscribe` interfaces: publication installs the next state synchronously, snapshots the subscriber set so a listener added mid-publication begins at the next one rather than part-way through the current, contains synchronous throws and thenable rejections, continues to the observers behind the failure, and reports through a sink `createNonThrowingReporter` has made incapable of interrupting the work it describes. Each collaborator keeps its own state and its own interface — only notification moved. **`app` therefore imports observable state from `persistence` although Navigation has nothing to do with persistence**; `.scratch/authoring-seams/issues/01-one-observable-state-module.md` records why that home was taken and what the alternatives cost.
- `react-flow-adapter` — the ONLY place React-Flow (`@xyflow/react`) and elkjs specifics live: projects a Space and its Layout-owned Graphs into RF nodes/edges, implements `LayoutStrategy` as `elkStrategy`, renders `CardNode`.
- `ui` — reusable, presentation-agnostic React components + shadcn-style primitives (Tailwind v4, Radix Select, CVA). Depends on `core` only.
- `app` — wiring/composition: Navigation and Space Authoring, each keeping its own state behind `createObservableState` and read through one `useSyncExternalStore` (the Active Graph, Traversal history, the opened Card); the Zustand-backed **render adapter**, which owns the published projection, drag bookkeeping and React Flow's own Card selection; TanStack Router, Space loading, the canvas and its cameras, presenting chrome, hand-rolled CSS. Zustand is the render adapter's and nothing else's — Traversal history lives in Navigation. **`canvasProjection` is what the render adapter publishes**: `canvasProjection(space, renderer)` answers a `PendingCanvasProjection` — the `strategyGraph` it builds, the `colors` it derives from the Space, the `visibleGraphs` it reads off `renderer.subject.graphs`, and a `project(laidOut, interaction)` returning the React Flow nodes and edges. **A `ResolvedRenderer` supplies only a subject and a strategy**; none of those three is state it carries, and nothing should look for them on it. It is a pure module and deliberately not a hook — no store, no React, no DOM — so the whole derivation is tested in the node environment (`canvas-projection.test.ts`, and a property test for the handle-resolution invariant React Flow warns about as #008). The `LayoutStrategyGraph` it takes is **not nullable on purpose**: there is nothing worth projecting before a strategy resolves, and requiring one is what stops a caller publishing a projection whose every Card sits at the origin. The word *projection* names this bridging construct in `app` and the adapter and is deliberately absent from `CONTEXT.md`, whose render-layer section forbids inventing a domain term between React Flow's vocabulary and ours.

Hard rules — **all four are now enforced, not just documented**. Two layers, because neither catches what the other does: ESLint `no-restricted-imports` zones catch package specifiers and relative escapes (`../../*`), and each package's narrowed tsconfig `paths` makes an illegal alias unresolvable. `rootDir` is set on `core` alone — anywhere else it rejects the legitimate `@project/*` import too, since the aliased file resolves outside the package, which is why the relative-escape half is a lint rule rather than a compiler setting. Before this, `core` could import `@project/ui`, cycle back into `@project/graph`, and reach `../../app/src/store` with typecheck and lint both green.

- Domain logic stays out of React (keep it in `core`/`graph`).
- React-Flow / elkjs specifics stay in `react-flow-adapter`. Precisely: **`core`, `graph`, `persistence` and `ui` must not import them**, which is what `no-restricted-imports` enforces. `app` does import `@xyflow/react` and legitimately so, being the composition layer — the older "nothing else imports them" was already false.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.
- A module bundled into a Vite config (`vite.config.ts`, `http-server-build.config.ts`) imports `@project/*` by **relative path only** — a bare specifier is externalized and hands Node the workspace TypeScript, and the dev server then will not start at all.

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases: declared in `tsconfig.base.json`, mirrored in `vitest.config.ts` `resolve.alias`, and **narrowed per package** in each `packages/*/tsconfig.json` so a package can only resolve what it may legally depend on. Vite needs no alias at all — it resolves through the workspace `exports`, and the third copy that used to sit in `packages/app/vite.config.ts` is gone (removing it built an identical bundle). Vitest's *is* load-bearing: the root package declares no `@project/*` deps, so there is no symlink to resolve through. Two lists to keep in sync, plus the package's own narrowed one.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **Use a functional core and imperative shell for cross-module coordination.** Compute and validate the complete next state in a private pure core before producing side effects; a thin imperative shell then updates collaborators in an order that preserves valid intermediate states. Expose the coordination as one operation rather than returning a plan for callers to execute. Keep framework and store events outside the seam, depend on existing module interfaces, and do not manufacture single-adapter ports for deterministic private helpers. An edit event is a notification, not state transfer: each editor first installs its authoritative completed state and only then emits the notification; the coordinator derives the next Space from the current state owned by its collaborators rather than from state carried by the event.
- **Inject nondeterminism once when composing a module, not through each domain operation, and never by mocking the ambient generator (ADR 0016).** A module that mints identities, reads time or otherwise depends on a nondeterministic in-process function receives that function at composition so tests can supply a deterministic one; its operational interface then stays in domain language and does not repeat the dependency on every call. There are **two such seams in the authoring path, and that is not a duplication**: `createSpaceAuthoring` takes `newId` exactly as it takes `reportObserverError`, defaulting to `newUuid`, and mints the Card and Layout ids of a completed Edit from it; a converted Graph's identity is minted inside ADR 0045's conversion boundary, which the *resolver* closes over, so `createRendererResolver({ newGraphId })` takes that one. `createApp` composes exactly one resolver and hands the same function to App rendering, Navigation and Space Authoring, so a converted Graph's identity has one source. (The earlier note that a minter must not go on renderer resolution was written when `resolveView` was a free function seven call sites reached; a composed resolver is where the argument said the dependency belongs.) **Don't answer a test's need for a known id with `vi.spyOn(crypto, 'randomUUID')`** — ADR 0016 rejected that when `loadSpace` faced it and the grounds are general: a constant collides across a property test's cases so it needs a counter, at which point a generator exists anyway; `randomUUID` is an unseedable CSPRNG, so controlling it means owning it; and the mock stops working in silence the day the implementation moves to v7 and reads the clock as well as the entropy pool. The seventeen spies this replaced also hid a real defect — one of them named two ids for an Edit that mints three, so a Layout quietly took an id from the real generator. Tests name the ids they assert on through `packages/app/test/minting.ts`, and compose a deterministic resolver for the Graph. Do not hide nondeterminism behind global mocking, and do not manufacture a port or adapter seam when the dependency has one in-process implementation. Deterministic rules stay uninjected — `titles.ts` mints `Card N`, `Layout N` and `Graph N` through three named operations with the `<Prefix> N` arithmetic private, because there is nothing there a test would want to replace.
- **`Layout` is data and `LayoutStrategy` is behaviour — don't collapse them back (ADR 0014, ADR 0040).** A `Layout` (in `core`) owns an authored card→position map whose keys are explicit Card membership, plus the ordered Graphs over those Cards; a `LayoutStrategy` (in `graph`) is `(graph: LayoutStrategyGraph) => Promise<LayoutStrategyGraph>` in the first-public vocabulary. Every Layout has a strategy that renders it; not every strategy has a Layout behind it. There is no `Arrangement` type and geometry rides as optional fields on the elements (ADR 0005) — don't introduce one. Older comments call the *function* a Layout; that is stale vocabulary, not a second concept. The strategy intermediates are `LayoutStrategyGraph`, `LayoutStrategyCard` and `LayoutStrategyPort`.
- **The strategy contract lives in `graph`, not the adapter.** Geometry lands as optional fields on the cards and handles, mirroring how ELK itself models it. `gridStrategy` (pure, places no handles) exists partly to keep the seam honest; if a change only works for `elkStrategy`, the contract has leaked. Which cards get arranged is the view's choice, passed in. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored, and no engine owns it (ADR 0025).** A strategy is *automatic* (computes placement from Cards and Graphs alone — grid, name-sort, ELK) or *positioned* (reads a Layout the author wrote). **ELK is one automatic strategy among several and must never be the focus**; if a change only makes sense for `elkStrategy`, the seam has leaked. Editing an Algorithmic View is legal and **converts** it: the Card positions already on screen are copied into a new Layout and the Edit written there, so nothing moves at the moment of conversion. There is no edit mode; persistence status is the state worth surfacing. **Don't re-suggest seeding or constraining ELK to honour a drop point**: three spike increments — append, then branch, then seeded and interactive ELK — each reshuffled the *existing* Cards and placed the new one by global optimisation, so a drop landed somewhere arbitrary. The failure is structural, not a matter of tuning. Written up in ADR 0025 and `.scratch/graph-editing/`.
- **A `Placement` is built through its module, never by hand; and the omitted-Card fallback band is standing on purpose.** The card→position map is one branded `ReadonlyMap<CardId, LayoutPosition>` in `graph/src/placement.ts`, over `core`'s schema-derived point — `graph`'s duplicate `LayoutPoint` is gone. Reads are ordinary map reads; **construction is closed** — `new Map()` will not typecheck as one — because the map built by hand and installed whole is the specific bug this exists to prevent, and it was fixed twice under two names before the type stopped it. Under ADR 0040 a Layout's position keys **are** its Card membership, so omission means the Card is not in that Layout — but `positionedStrategy` still draws an omitted Space Card in an internal fallback band below everything the map places, and that is **deliberate, not vestigial**: package 5 of `.scratch/card-route-editing/implementation-handoff.md` deletes it and builds its replacement — Cards View, Add to Layout, Remove from Layout — in the same change, and between here and there the band is the only surface that can reach such a Card. **Don't remove it early.** Two guards keep it from becoming authorship: `Placement.next` promotes only the Cards a completed gesture placed, so a Card drawn in the band stays unplaced however often it is redrawn, and the render adapter's `syncProjection` reports rendered geometry rather than installing it. A Card a reprojection catches mid-drag likewise keeps the place the author last left it. Nothing in the module mutates an argument or hands two callers the same map — `SpaceAuthoring.install` retains what it is given rather than copying it, which is why `empty` is a function and the points are copied on the way in. A completed Edit does **not** need a forced identity to re-render: it replaces the working snapshot, and the `LayoutGraph` derived from it re-fires the same effect (pinned in `placement-rendering.test.tsx` and `space-authoring.test.ts`).
- **The six handle rules below belong to the overview, not to the domain (ADR 0033).** They hold because that rendering overlays several Graphs over one set of Card positions and needs distinct attachment points to stay legible. The **authoring** interaction uses four Graph-independent spatial handles per Card, coloured as the Active Graph; none of the overview bookkeeping applies there. Don't restate any of it as a rule the model obeys, and don't let it shape the visible authoring controls.
- **ELK port offsets are applied to handles.** ELK's *port* is React Flow's *handle* — same thing, two libraries' words. ELK computes each one's position, and those exact offsets drive where `CardNode` renders the handle, so a Graph's Edges meet its Cards cleanly. Don't hardcode handle positions.
- **Port constraints are `FIXED_SIDE`, not `FIXED_ORDER`.** ELK orders `FIXED_ORDER` ports **clockwise** around the node — EAST top-to-bottom but WEST *bottom-to-top*. Handing both sides the same list order therefore puts a Graph's outbound handle at the top of one Card and its inbound handle at the bottom of the next, crossing every Graph at every shared Card. `FIXED_SIDE` fixes the side and lets ELK order within it. Don't switch back without reading `.scratch/layout-seam/issues/04-elk-fixed-side-ports.md`.
- **ELK port ids are namespaced per card.** A handle id (`<graphId>::out`/`::in`) is the *same* on every Card a Graph passes through, so `elkStrategy` hands ELK `<cardId>##<handleId>` (`elkPortId`) and builds Edge endpoints from the same key, stripping the prefix on read-back, so handles keep their bare ids and `CardNode` is unaffected. Never hand ELK a bare handle id — it then can't tell which Card an Edge attaches to and mislays *even single-Graph* graphs. See `.scratch/layout-seam/issues/01-namespace-elk-port-ids.md`.
- **Handle ids must be distinguishable per card per side — React Flow's rule, not just ELK's.** The entry above covers why ELK needs `<cardId>##<handleId>`; React Flow separately requires that *"multiple handles of the same kind on a node need to have distinguishable IDs"*, or it can't resolve an edge's `sourceHandle`/`targetHandle` and warns (#008). The `<graphId>::out`/`::in` scheme satisfies both libraries, for different reasons. Don't collapse it to a per-side counter.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `CardNode` dims handles via `opacity` and it looks like a styling choice; it isn't. Same for the CSS in `styles.css`.
- **Handle geometry is declared, never re-measured — do not add `useUpdateNodeInternals`.** React Flow measures handles once and caches, which is its named cause of warning #008, and the documented remedy is `useUpdateNodeInternals`. Here that remedy is **wrong**. `projectCardNodes` declares `node.handles` from the strategy (`declaredHandles` in `projection.ts`), and `parseHandles` in `@xyflow/system` builds `handleBounds` from those declarations without consulting the DOM at all — this is the `node.handles` alternative the old spike note proposed, and it is built. Crucially, a card declares `<graphId>::in`/`::out` for **every** Graph, including ones not yet incident to it, so a completed connection resolves in the same render that first makes its target incident. `useUpdateNodeInternals` passes `force: true`, and the forced path *replaces* `handleBounds` via `getHandleBounds`, which reads only the anchors present in the DOM — silently dropping every not-yet-incident declaration and breaking the **next** connection rather than the current one. Verified both ways against the fixture: with the hook, a second connection in one session fails with six #008 warnings; without it, it passes (`editing.spec.ts`, "a second connection drawn in the same session resolves its handles"). Unit tests cannot catch this — the forced path needs truthy `offsetWidth`/`offsetHeight`, which are 0 in jsdom, so it silently no-ops there. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **Neither React Flow's `toNode` nor the DOM alone answers "is this empty canvas".** `getClosestHandle` resolves `toNode` by distance from the pointer to a *handle* within `connectionRadius` — 20 at the pinned 12.11.2 — so it is non-null over blank canvas near a handle and **null over the middle of a Card**, whose centre is some 73px from the nearest handle at 260x146. An Alt/Option empty-drop therefore needs both answers, with a connection target in range outranking the element underneath: drop the DOM half and a release onto a Card's body authors a Card on top of it, drop React Flow's half and a release just outside a Card authors one where the author was aiming at a handle. The rule is one module — `packages/app/src/connection-gesture.ts` — asked by both the live preview and the release, and **that is where the argument is written out**, including why those two deliberately disagree once the pointer leaves the canvas and what closing that would cost. Don't re-inline it into `SpaceCanvas`, and don't "fix" the preview to hit-test live without first pricing a per-frame `elementFromPoint`.
- **A camera command is issued, never awaited, and never contained (ADR 0043).** `setCenter`, `fitView`, `fitBounds` and `zoomTo` return a Promise that is **not a completion signal**. At the pinned release it resolves only when the animation reaches its end: a *superseded* transition fires d3's `interrupt`, which `getD3Transition` does not listen for, so that Promise stays pending forever — and any second camera command while the first is running produces exactly that. `fitView` before `panZoom` exists hangs too (`resolveFitView` begins `if (!panZoom) return`, abandoning the `withResolvers()` resolver). So **never chain required work on one** — the superseded two-phase presentation move did, with `.then`, and stranded the camera at the overview zoom whenever the author traversed inside the pan's own 400ms. Nothing chains today, because ADR 0044 left the seam with one command and no follow-up work; if any ever appears, it goes on a timer the issuing effect cancels. `fitView` is worse than the rest here — it *reuses* one resolver across calls, so a second call before the first settles cannot be told apart from it. Equally, **never add a blanket `.catch`**: neither bundle calls `reject`, so the only reachable rejection is a synchronous d3 throw inside a Promise executor — a genuine fault, and the one signal worth hearing — while both real failures are hangs a `.catch` cannot observe. Plain `void` is deliberate. Every camera call in the app lives in `packages/app/src/components/cameras.tsx`, which is what makes that checkable by reading one module; coverage is `packages/app/test/cameras.test.tsx`, where every stubbed call never settles.
- **`maxZoom` must cover the presenting zoom — don't drop it back to the default.** A card is 260x146, so filling a 1280x720 viewport with one needs ~3.97 and a 4K one ~12.8, against React Flow's default ceiling of 2. `SpaceCanvas` passes `maxZoom={MAX_ZOOM}` (`packages/app/src/camera.ts`) for that reason and nothing else. Removing it does not fail a test, because d3-zoom is asymmetric: `setCenter` ends in `zoom.transform`, which never consults `scaleExtent`, while the wheel, pinch and `scaleBy` paths all clamp into it — so the camera still reaches the presenting zoom and the *first wheel tick* yanks it down to 2 mid-presentation, recovering only at the next traversal step. Measured against the fixture at 1280x720: 0.55 overview, 3.97 presenting, 2 after one wheel tick before the fix and 4.68 after it. This mirrors React Flow's own presentation tutorial, which raises `minZoom` for the opposite reason.
- **React Flow is pinned to 12.11.2.** The declarative `node.handles` path above intentionally depends on behavior verified against that release. Upgrade both consuming manifests together and run the complete Playwright suite; do not widen the range or accept an automated upgrade without revalidating handle resolution, consecutive connections and warning #008 in a real browser. The camera-Promise facts above are pinned to it too — re-read `setTransform`, `scaleTo`, `scaleBy`, `resolveFitView` and `getD3Transition` when it moves.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. **It is incomplete, though** — a read of it for nesting reported sub flows as absent while `/learn/layouting/sub-flows` exists and is quoted in our own findings, so use it for breadth and fetch the page for a specific mechanism. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`, whose §8 covers multiple canvases and nesting.
- **React Flow's interaction model is the default.** Start from the pinned release's documented keyboard, focus, selection, pointer and accessibility behavior. Prefer shaping Hyper's feature around those expectations over reshaping React Flow around a locally convenient interaction. Every deviation needs an explicit product requirement and an interrogated, recorded reason; do not customize merely because a different gesture seems preferable.
- **shadcn and its underlying primitives supply the default UI interaction model.** Start from the chosen shadcn component's documented keyboard, focus, dismissal and accessibility behavior, including the Radix or Base UI primitive it composes. Prefer shaping Hyper's feature around those sensible defaults over recreating or overriding them. Every deviation needs an explicit product requirement and an interrogated, recorded reason; do not hand-roll behavior the primitive already supplies.
- **Hono's own docs are the reference, and they ship one for agents:** fetch `https://hono.dev/llms-full.txt` when working in `http` — the whole docs site as a single document, regenerated by `scripts/build-llm-docs.ts` as a `prebuild` step in `honojs/website`, so don't vendor a copy. **Take `llms-full.txt`, never `llms-small.txt`**: its `tinyExclude` drops `concepts/`, `helpers/` and `middleware/`, and the `startsWith` predicate catches `guides/middleware.md` by basename too, so the small file holds zero occurrences of `bodyLimit` — most of what this package does. There is no official Hono agent skill or MCP server: `hono-skill` and `@hono/skill` are both 404 on npm, the request to make one official (`honojs/hono#4812`) is still open, and in `honojs/cli#77` the maintainer proposes deleting the CLI's `docs`/`search` commands because "you can use the 'Web Fetch' function in the agent". `@hono/mcp` is middleware for *building* MCP servers with Hono and documents nothing about Hono — don't mistake it for a docs source. The two pages carrying the non-obvious rules are `/docs/guides/rpc` and `/docs/guides/best-practices`. Findings and what they mean for this repo: `.scratch/hono-guidance/findings.md`.
- **Hono hands the host a rejected promise unless the app terminates every path.** Two rules, both load-bearing, both proven by regressions in `space-http-app.test.ts`. **Never call `context.notFound()` inside the handler `app.notFound()` installed** — Hono seeds the Context's not-found handler from the app's, so it re-enters itself until the stack blows, on every path off the declared contract including the trailing slash an address bar produces; return an explicit response instead, which is also what the RPC docs say when a client infers types. **Never rethrow from `onError`** — Hono does not convert that into a 500, it re-invokes the handler and lets the throw escape, so `app.fetch()` rejects and a host without a `.catch` gets an unhandled rejection, which Node 24 answers by killing the process. A non-`Error` throw never reaches `onError` at all. An `onError` that returns a Response is entered once; one that rethrows is entered once per compose frame.
- **One media policy, or Hono's json validator silently hands you `{}`.** Its `jsonRegex` is narrower than RFC 9110 — it rejects space before `;`, spaces around `=`, `_` in a parameter name, and quoted strings containing `;` — and on disagreement it does not parse the body and reports nothing, which surfaced as a 400 about the fields of a body never read. `requireSupportedRequestMedia` therefore rewrites the header it has just validated to canonical `application/json`; don't remove that and don't add a second policy beside it. Relatedly, `content-type@2` validates **nothing** — `parse` has no throw path and answers `parse('garbage')` with `{ type: 'garbage' }` — so the hand-rolled scanner is the whole of this module's media validation, not a duplicate of the dependency.
- **The Node host must keep `@hono/node-server`'s global `Request`/`Response`, and Hono answers HEAD from the GET handler.** Two host-level facts the portable route module quietly depends on. **`getRequestListener` replaces `globalThis.Request`/`Response`** with its own lightweight classes unless `overrideGlobalObjects: false` is passed, and defines them non-writable and non-configurable — a permanent, process-wide swap. Leave it on: `requireSupportedRequestMedia` and `requireBoundedCommitBody` both rebuild the request through the *global* `Request` constructor, so with the override off the constructor is handed an instance it does not recognise and **every commit answers 500** while all the rejection paths stay green. This is `@project/http`'s one host requirement — portable does not mean indifferent to the host. Separately, **Hono routes a HEAD request to the GET handler and strips the body**, so a resource that does not explicitly intercept HEAD answers 200 carrying nothing; `unservedContractPath` is that interception, and it is shared with `app.notFound()` so the two cannot disagree about whether a non-UUID segment is a 400 or a 405. Both are pinned in `vite-hono-host.test.ts` and `space-http-app.test.ts`.
- **Hono types a json validator's input as its output unless you say otherwise, and partial generics make it worse.** `in.json` collapses to the callback's return type when `InputType` is unsupplied, which put the decoded `bigint` revision into the request contract — a value `JSON.stringify` throws on, so no client could satisfy it. TypeScript has no partial type argument inference, so supplying only `InputType` drops every other parameter to its *default*, and `VF` defaulting to `=> any` removes the route from the schema entirely and silently: `$put` stopped existing on the client. That is why `decodeCommitBody` is a named function — so `VF` can be supplied too. Separately, a bare `MiddlewareHandler` (which is how `bodyLimit` was declared, before it was dropped for the reasons below) erases its statuses from the contract while a hand-written one beside it survives; produce every status in our own code. Both are pinned by `space-http-app-types.test.ts` — which `pnpm test` does **not** enforce, since `expectTypeOf` is a runtime no-op without `test.typecheck`; only the root `pnpm typecheck` catches it.
- **`Content-Length` is never trusted, and an oversized body is drained rather than dropped.** `requireBoundedCommitBody` counts the bytes that arrive; the header is deleted and never consulted. Hono's `bodyLimit` is **deliberately not used**, for two independent reasons. It *trusts* the header when present — comparing and returning without reading a byte — so an understated length would smuggle any body through. And on overflow it abandons a **locked** reader without consuming the rest of the body, so nothing downstream can drain the request: Node's `_dump()` cannot resume a stream the web wrapper holds, the socket dies with the 413, and a keep-alive client loses its connection. Draining is what the superseded raw handler did (`request.resume()` after clearing its buffer), and `vite-hono-host.test.ts` pins reuse for both framings at 4× the cap — the older one-times-the-cap case passed by accident, since a body that small is already flushed before the response. The drain is itself bounded at `MAX_DRAINED_BODY_BYTES`: an honest overshoot keeps its connection, a client that never stops sending loses it. A declared-length pre-check used to sit here as a fast path and was **deliberately dropped** — it answered 413 for a body the client had not sent. Don't reintroduce it without first deciding what a dishonest `Content-Length` should mean. The old raw handler's canonical-length strictness died with it at ticket 04; the count subsumes it.
- **A wire codec throws prose, not Zod.** `spaceSnapshotSchema.parse` puts its entire serialized issue array in `Error.message`, and `decodeCommitBody` ships that straight into the `{ message: string }` error contract — a JSON document nested inside a field clients render as a sentence. `decodeSnapshot` in `http-protocol.ts` uses `safeParse` and summarises the first three issues instead, matching `exactRecord` and `decodeRevision` beside it. Don't call `.parse` directly in a decoder whose error reaches a client.
- **A card is one file: frontmatter, then body (ADR 0020).** `id`, `title`, `description`, `kind` and `target` are the card file's frontmatter; the markdown under it is the content. The space file holds `version`, `id`, `title`, `layouts`, `defaultView` — structure, and no `cards` array; a Layout holds the Graphs it owns, so there is no space-level `graphs` key (ADR 0040). Cards are discovered by scanning two locations, **non-recursively**: `*.md` beside the space file, and `cards/*.md`. Non-recursion is deliberate — ADR 0001's nested spaces will want subdirectories, and a recursive scan would make each one ambiguous with card discovery. A card's identity is its frontmatter `id` and never its filename, so renaming a file is not a data migration; a duplicate id across files is a load error naming both. A body may begin with a heading — the title lives in the same file, so a heading is just a heading. Every `.md` in scope *is* a card, so there is nowhere to leave a draft — and a `README.md` beside a space file would be read as one, which is why the fixture's moved to `packages/app/README.md`. **`body` is the field, `content` is the domain word**, and they are not synonyms to be reconciled: `CONTEXT.md` still lists "body" under _Avoid_ for a card's content in general, because a space-card's content is a graph and has no body. `Card.body` is what a *markdown* card's content is stored as. Don't rename one into the other in either direction.
- **Graphs are a Layout's only connection structure.** There is no authored `edges` array *beside* Graphs; ADR 0007 deleted that along with the `sequence`/`reference` kinds, and it stays deleted — don't reintroduce a structural layer next to Graphs. Under ADR 0040/0041 a Layout owns one or more Graphs over its explicit Card members, and every Graph Edge is closed over that set. A Graph **is** a set of `{from, to}` Edges the author draws (ADR 0032), so “Edge” names both the Graph's stored element and React Flow's drawn line — one word for one thing, and the only place the render layer and the domain share vocabulary. Cycles and self-Edges are legal; an exact duplicate within one Graph is not. The built types are `GraphEdge` (`core`) for the authored value, `GraphRenderEdge` (`graph/graph-rendering.ts`) for the handle-resolved projection, and `LayoutStrategyEdge` (`graph/layout.ts`) once a strategy has routed it. Do not preserve superseded Route-named aliases.
- **`path` means a file path only.** The document and the implementation agree on `graphs`/`activeGraph` — the sentence here used to contrast a planned spelling with a built one, and the rename closed that gap. Remaining `path` identifiers are filesystem paths, TanStack Router URL paths, or React Flow's own SVG `edge-path` class — don't “fix” those.
- **`manifest` is retired, in vocabulary and code (ADR 0010).** The top-level domain value is a **Space**, minted only by `loadSpace(input, cardFiles) → { ok, space } | { ok: false, errors }` in `@project/graph` — the one intake that parses (the space file *and* every card file's frontmatter), validates references, and indexes, so a `Space` is consistent and O(1)-resolvable by construction. `space.lookup` reads that index; every `graph`/adapter/app signature takes a `Space`. The on-disk shape is a **space directory**: the **space file** (`space.json`, validated by `core`'s `spaceFileSchema`) plus a markdown file per card (ADR 0020). A value that only passes that schema is *not yet* a Space. `loadSpace` gained the card files as an argument, not a capability — it still does no I/O and is still synchronous, and reading the bytes stays outside it. Don't reintroduce `manifest` anywhere — not as a type, not as the word for the file. There is no shared `Draft`: unfinished gestures and invalid editor input remain local to that editor. An editor installs valid authoritative state and emits a payload-free notification; Edit completion then derives and validates the whole next Space before effects.
- **Styling is split:** `ui` uses Tailwind v4 + shadcn-style primitives; the graph/card CSS stays hand-rolled in `packages/app/src/styles.css`. Tailwind scans `app` + `ui/src` via `@source` in `tailwind.css`.
- **Markdown is excluded from Prettier** (`.prettierignore`) — don't rely on `format` to touch `*.md`.
- **The browser never imports files or names storage.** `SPACE_DIR`, `virtual:space-file` and the Vite file plugin are gone. File discovery and parsing remain server-side CLI/import concerns. Browser resources are fixed to list, load and commit under `/api/spaces`; requests cannot carry database URLs, filesystem paths or arbitrary targets. A completed edit commits a whole `SpaceSnapshot` through `SpaceBackend`. Canonical export belongs to the CLI (ADR 0030) and is built (`src/export/export-space.ts`), never an app Save action.
- **Persistence crosses the app at `SpaceBackend` and `SpaceSession`.** Normal composition is `PostgresSpaceRepository` → Fetch-native Hono application → typed `HttpSpaceBackend` → one opened `SpaceSession`; standard E2E substitutes only an isolated `E2eMemorySpaceRepository` behind the same application. Startup lists over HTTP, opens the sole UUID or renders the UUID-only selector, while server-side policy ensures an empty database receives the normal new Space. Selection does not enlarge `SpaceSession`, which still owns one already-open workspace. Every backend commit validates both public shape and normal domain intake (`loadSpaceSnapshot`), so dangling references, duplicate Edges within one Graph, an Edge endpoint that is not a Card of its own Layout, one Graph id held by two Layouts and invalid aliases/layouts are permanent `invalid-snapshot` failures rather than stored state. Graph cycles and self-edges are valid authored structure (ADR 0032).
- **A session submits complete snapshots after completed edits.** It allows one commit in flight, coalesces waiting edits to the newest snapshot, chains the committed revision into the next optimistic write, and exposes pending, retryable failure, permanent rejection and conflict states. Persistence is totally asynchronous: Edit completion relies only on `submit` installing the local working snapshot synchronously, never waits for backend acknowledgement, and immediately selects the resulting Layout from that local state. Accepting remote replaces the session snapshot through Space Authoring rather than remounting: `acceptStoredSpace` validates the stored snapshot first, then installs the session, placement and a fresh Navigation together and advances `replacementEpoch`, which is what makes the render adapter drop the projection and drag bookkeeping so no store retains stale local positions. Graph activation is not an edit and does not submit.
- **Session notification is non-throwing, and a submit made from an observer is queued rather than re-entered.** An observer that throws cannot interrupt the publisher: `publish` contains each listener's failure, hands it to `SpaceSessionOptions.reportObserverError` (defaulting to `console.error`) and carries on to the remaining observers, so persistence, the working Space and any reentrant Edit completion all continue. The reporter is wrapped too, and unlike `@project/http`'s `invokeLogError` it never rethrows — nothing above a notification could handle the failure. Separately, an observer *may* legally submit the next Edit while the publishing submit is still on the stack, so **`submit` decides from `state.working`, never from its argument** — a reentrant call runs to completion first, and deciding from the argument queues the older snapshot behind the newer one and stores it last, undoing a completed Edit at the next load. Nothing suppresses a nested call to stop it double-committing; identity against the in-flight snapshot answers that at any depth. **Don't replace it with a guard scoped to a call's publication**: `retry` and `resolveConflict` publish `pending` from *inside* an optimistic publication, and a submit answering that notification has a commit to wait behind while the call underneath it is gated on the failure it published under and will decide nothing — the newest Edit then reaches no queue at all and the session reports `settled` without it. All of this is pinned in `session.test.ts`.
- **Authoring's completion sequence is total, and the runner that used to make it so is still gone.** `space-authoring.ts` splits a completed Edit in two. `deriveCompletedEdit` is the pure core: every read of current state a derivation makes, every refusal (`null`) and the one `loadSpaceSnapshot` that can throw happen there, before a collaborator has moved, and it answers a `CompletedEdit` with nothing left to decide. **One decision is deliberately outside it**, and it is not a refusal the core could make: the drain's `replacementEpoch` gate reads the current epoch to answer whether a queued entry is derived *at all*, because an entry the epoch has outlived names a Space that is gone and the core would derive it happily against the one that replaced it (the bullet below has the rest of that argument). It is taken in `complete`, before `deriveCompletedEdit` is called and outside every install window, so the guarantee that matters is untouched: nothing inside the window has anything left to decide. `installCompletedEdit` is the shell, and **`session.submit` is deliberately first** — the Navigation call resolves the Graph and the Layout against `currentSpace()`, which reads the snapshot `submit` installs synchronously, so no other order exists. The useful consequence is that the only fallible statement is also the first: nothing later can invalidate something earlier, and a throwing `submit` leaves the placement and Navigation untouched instead of half-applied. One failure shape survives by construction: the session ahead of the placement and Navigation. It is the recoverable one, because the snapshot the session took already carries the completed placement in its Layout, and it is why `b091623` inverted the order. **Navigation is handed the renderer and its Active Graph in one call — `continueInRenderer(selection, activeGraphId)` — and Edit completion never calls `activateGraph`.** Under Layout-owned Graphs (ADR 0040) the two are one answer the Edit produced, and the intermediate state a second call would leave is not merely awkward but *invalid*: adopting the converted Layout while Navigation still holds the previously emphasised Graph names a Layout beside a Graph **another Layout owns**, which is exactly the pair `continueInRenderer` refuses — so a split would throw on every conversion, which is every first edit on an Algorithmic View. **Don't split them back**, and don't answer that by reversing them either: activating first would validate the Graph against the renderer the Edit *began* in rather than the one it produced, which is strictly weaker and is the thing the original two-call rule existed to prevent. The property that rule bought is intact — the Graph is still checked against the renderer this Edit wrote — and it now holds by construction rather than by ordering. **Don't re-check the Graph or the Layout inside the window** — the snapshot passed domain intake a line earlier, so those branches cannot be taken; the guards that do exist live in Navigation, where the invariant is, and this window is a caller that satisfies them. All of this is pinned by fault injection in `space-authoring.test.ts`.
- **The install gate counts depth, publishes in the `finally`, and contains a drained completion's failure.** Both windows (completion and `acceptStoredSpace`) run through `installTogether`, which raises the `installing` gate and **publishes in the `finally`**: the gate means Authoring's publication is the only one a subscriber gets, so a publication skipped by a throw left `getState()` answering the pre-Edit state permanently, until an unrelated notification happened along. That is not a `catch` — the failure still reaches the caller. **The gate counts depth and is not a boolean**, because the windows nest: `acceptStoredSpace` notifies from inside its own, when `session.acceptRemote()` publishes before the placement, Navigation and `replacementEpoch` have moved, and an observer is as entitled to complete an Edit from there as it is to submit from a session notification. A flag is cleared by the inner `finally`, and the rest of the outer sequence then publishes every part-way state the window was raised to hide, including the accepted Space carrying the `replacementEpoch` of the Space it replaced. Only the outermost window publishes. Separately, a completion the drain *reaches* is contained — its failure is reported and draining stops there, because the Edit that drained the queue had already installed and published and must not be charged someone else's failure. Completions still queued behind that failure are discarded, and that too is reported. What is **not** contained is a throw from the Edit the caller made itself: treat that as an unhandled case, and restoring the guarantee means making the sequence total, not adding a `catch`. **The drain also gates on ADR 0042's `replacementEpoch`** — the counter formerly called `opening`, which is one counter and not two: each entry records the epoch current when it was enqueued, and the drain discards, without deriving, any entry whose epoch differs. Refusing would not save it, since the identities usually still exist in the replacement and nothing would reject the completion — it would write an abandoned gesture over the Space the author has just accepted. The discard skips rather than stops, because a completion queued from inside the accept's own publication carries the new epoch and is the one the ADR says must still be honoured, and it reports once per drain through the same `safelyReport`. **This is where that argument is written out** — the drain comment, the ticket and both tests point here rather than restating it, and a fifth copy is a drift risk, not thoroughness. Interaction-draft invalidation, 0042's other half, reads the same epoch and is not built. All of it is pinned in `space-authoring.test.ts`.
- **Don't import a workspace package by name into `vite.config.ts`.** Vite loads the config in Node and externalizes bare specifiers, so `@project/core` hands *Node* the TypeScript source, whose extensionless relative imports (`export * from './schema'`) Node's ESM resolver rejects — the config then fails to load at all and the dev server will not start. Import by relative path (`../core/src/index`) so esbuild bundles it. This is the one place the repo's extensionless-import convention does not hold.
- **Vite hosts a fixed server runtime, not browser-selected capabilities.** The thin config-time plugin imports no application package. Development loads the chosen runtime with Vite's SSR module runner; preview loads the dedicated bundled Node artifact. The server configuration fixes PostgreSQL versus isolated E2E memory and fixture versus empty catalog before any browser request.
- **Changing the Vite config needs a dev server restart** — plugins load at config time and HMR won't pick them up. That server is the human's; say it needs restarting rather than restarting it.
- **Delete a spike harness when you write it up; ignoring it is not enough.** `packages/app/spike.html` sat gitignored, went stale against the `elkLayout` → `elkStrategy` rename, and broke `pnpm dev` — Vite's dependency scanner treats every root `.html` as an entry and does not read `.gitignore`, while tsc and eslint both skip `.scratch/`, so `pnpm verify` stayed green and only the dev server saw it.
- **Card markdown is sanitised before it is injected.** `CardContent` renders through `dangerouslySetInnerHTML`, and `marked` has had no `sanitize` option since v5, so `DOMPurify.sanitize()` sits between them. Don't remove it on the argument that a card came from a local import: backend implementations and future import sources broaden that premise. `packages/ui/test/CardContent.test.tsx` fails without the sanitiser.

## Before claiming done

- Run `pnpm verify` and report the real output.
- For any UI/graph change, also run `pnpm e2e` and report it.
- Do not assert success without having run the commands.

## Scope discipline

Keep to the MVP. Don't over-generalize the domain model and don't add features beyond what's asked.

On multi-Graph rendering (`.scratch/multi-route/` retains its historical path): a Layout overview draws every Graph that Layout owns, and **activation is emphasis, not filtering** — at all times, not only while presenting. Activating a Graph never changes which Graphs the Layout owns or draws. There is one Active Graph in the current Layout, not a selection plus an emphasis (ADR 0040/0041). The dimming surface uses Graph names (`projectGraphEdges`, `GraphLegend` and related helpers); do not restore superseded Route-named aliases. `filterHandlesByGraph` and `graphCardIds` are right for a view that wants one Graph. **A Layout's `graphs` is ownership, not a filter** (ADR 0040): it is the full Graph values that Layout owns, and what a selected Layout draws is exactly them. The superseded `graphs` array of Graph *ids* — a filter over a Space-level collection — is gone, along with the Space-level collection itself; `space.graphs` is now a derived flatten across Layouts, and a document declaring a Space-level one is **rejected at intake** — `retiredSpaceGraphs` in `graph/src/space.ts`, a pre-parse check beside the version answer and run by both `loadSpace` and `loadSpaceSnapshot`, so neither a file nor a commit can carry one. It is deliberately *not* enforced by the schema: `spaceFileSchema` is a plain object and so strips an undeclared key, which is the right answer for the retired `cards` and `edges` — they carried nothing the document does not already say — but the wrong one here, since a Space-level `graphs` carried the whole topology and stripping it yields a Space that loads looking complete. Don't answer it with `.strict()`, which takes that leniency with it, or by declaring the key, which puts it in the inferred document type Hono's RPC contract is checked against. Which Cards a View chooses from its subject is passed into the strategy (ADR 0005, ADR 0040) — don't let the strategy decide it.

**Renderer resolution answers the subject; the strategy does not (ADR 0040/0041/0045).** A resolved renderer is a **discriminated** value and never a pair of nullable fields: `ResolvedLayoutRenderer` carries the Space's own canonical `ResolvedLayout` and is updated in place, `ResolvedViewRenderer` carries a `convert` and is converted by being edited (ADR 0025). Both carry a `RendererSubject` of **exact Cards and Graphs from the source Space** — a Layout's position keys in `space.cards` order and the Graphs it owns, or every Space Card and the flatten across every Layout. Values rather than ids, because every obligation stated over a subject is about the things themselves; a subject that is not the Space's own values, or repeats one, is refused as `invalid-subject`. Keep that resolution in one composition seam — `createRendererResolver` in `packages/app/src/renderer.ts` is that seam, and Flow and Grid are private definitions behind it (title, subject selector, strategy factory, identity-free Graph policy). **There is no public View registration**, deliberately: persisted View ids and missing-plugin behavior are undecided, and a seam exposed before either question is answered would be a guess. Which Graphs a renderer draws is now `renderer.subject.graphs` and nothing else — Navigation's membership test and the canvas projection both read it, so two places cannot disagree. A Layout's Active Graph is `resolvedLayout.activeGraph`, resolved once at intake; a View's `defaultActiveGraph` is used **only** when Navigation opens or explicitly selects it, and `continueInRenderer` carries the Active Graph the completed Edit produced rather than quietly applying a renderer's default.

**A completed edit persists automatically (ADR 0030).** The editor first installs its authoritative completed state and synchronously emits a payload-free `EditCompleted` notification. Edit completion derives and validates the complete current `SpaceSnapshot`, submits it to `SpaceSession`, and immediately selects its resulting Layout; intermediate drag frames never reach persistence. The session status (`Persisting…`, `Persisted`, retry, rejection or conflict) is the persistence indicator. There is no Save button, keyboard Save command or browser file write-back. The `beforeunload` guard is registered only while persistence is not settled — an always-attached handler would cost the page its bfcache. It calls `preventDefault()` and nothing else; `event.returnValue = ''` is deprecated and lint rejects it.

**Activating a Graph is not an Edit (ADR 0028, refined by ADRs 0040 and 0041).** It converts no Algorithmic View and never submits persistence by itself. Edit completion samples the current Layout's Active Graph only when `EditCompleted` is emitted, rather than subscribing Graph activation into an Edit trigger. The submitted Layout names its Active Graph outright because the resolve-to-first fallback is a read and persisted state should not depend on Graph order. `updatePositionedLayout` replaces a Layout's positions **and its owned Graphs** whole, because the editor holds the whole truth of both and a Graph is a nested owned value with nowhere else to be written (ADR 0040); an Edit naming no Active Graph carries the existing one through rather than clearing it. `space.graphs` is never written back — it is the derived flatten, and every Graph reaches the wire inside its Layout.

**Presenting is this canvas, closer in (ADR 0027).** There is no second surface and nothing a Card is turned into. `PresentingCamera` in `components/cameras.tsx` is the whole mechanism, and it is one `fitView({ nodes: [{ id }], padding, duration })` (ADR 0044). **Don't reinstate the two-phase move** — pan at the wider scale then close in, which ADR 0027 recommends copying from impress.js. impress needs it because it animates with CSS transitions; React Flow animates through d3-zoom, whose default interpolator is already `interpolateZoom` (Van Wijk zoom-out-pan-zoom-in). Both were built behind a toggle and watched on the fixture: indistinguishable. The version it would restore is also the one whose chained second half stranded the camera at the overview zoom (ADR 0043). The chrome (`PresentingChrome`) is screen-fixed and enumerates the active card's outgoing edges, because at a zoom where the card is legible its neighbours are provably off frame. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a store selector** — `Navigation.moves()` is called at render time in `App` for exactly this reason; as a selector it handed the store a new array identity every render and re-rendered until React gave up. It is deliberately **not** `useMemo`'d either: `moves()` takes no arguments and reads the session's current working Space through Navigation, so a memo keyed on the values in scope would go stale when an authored Edge changed the Space and `PresentingChrome` would stop offering the move that had just been drawn — which is exactly what makes an Edge drawn from the presented Card immediately traversable. A render-time call is safe here because nothing subscribes to the array's identity — `moves` feeds no effect, no dependency array and no memoized child, so a fresh array cannot feed a re-render.

**A Graph may contain cycles and self-Edges (ADR 0032, terminology refined by ADR 0041).** Authoring records the Graph the author draws; Graph navigation and Presenting decide how to traverse it. An Alias is still the way to place and title the same content as a distinct Card, but it is not required merely to return to an existing Card. `loadSpace` rejects only an exact duplicate Edge within one Graph; drawing that duplicate live is an idempotent no-op.

The overlay limit: only an acyclic union of the visible Graph Edges lays out on a clean left-to-right axis, as parallel forward paths. A backward Edge can come from a cycle inside one Graph or from two Graphs disagreeing on the order of shared Cards. `elkStrategy` returns ELK's routed `sections` on each Edge and the adapter draws them (a bezier fallback covers grid/first-paint), so a back-edge reads as a routed channel rather than a self-curling stub. Here “routed” is qualified graph-layout geometry, not the retired Route entity. Read `.scratch/multiple-routes/findings.md` before extending any of this.

The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against purpose-shaped Graphs rather than demo prose. It is **two disconnected collections** sharing no Cards, which ELK lays out as separate bands and which are its two Layouts, `Collection 1` and `Collection 2`: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several Graphs over one spine; (2) `Echo E→F→G→H→E′` — a plain linear collection. Two Layouts rather than one is deliberate — it is the only place in the tree where the Space-subject flatten crosses a Layout boundary. Both position maps are seeded from **one ELK run over the whole fixture**, and `packages/app/test/fixture-placement.test.ts` re-runs that exact seam and compares within half a pixel, so a change to the ELK options that would silently move the fixture fails there rather than being noticed by eye or not at all. Each returns to its start via an Alias (`A′`/`E′`, which the `↳` marker names), never an Edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture Graph is a **line** — one Edge out per Card — which is the degenerate Graph shape, not a second kind; forks and merges are covered by unit and property tests, not here. `03`'s back-edge rendering is proven by a unit test (`elk-strategy.test.ts`), not the fixture. The demo stays in `packages/app/example/`, dormant — it is a Space directory nothing loads, kept as narrative content rather than as a pending capability, since the CLI importer now loads real Space directories. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a Space file would be scanned as a Card). The ELK options in `elk/layout.ts` are a minimal baseline: don't tune global layout options against this fixture's screenshot. If legible multi-Graph overlay becomes real product work, design it deliberately.
