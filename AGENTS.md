# AGENTS.md

Instructions for AI coding agents working in this repo.

A local prototype for **graph-native technical presentations**: Markdown cards on a spatial graph, imported from a space directory and presented by traversing curated routes. PostgreSQL is the live write model and the browser reaches it over HTTP; memory repositories are confined to isolated development and E2E runs. Placement is **authored, not computed** — a **Layout** is the card→position map the author writes, and the thing that arranges cards is a **LayoutStrategy** (ADR 0014). A space need not carry a Layout: an automatic strategy the app supplies renders it, and editing converts that into a Layout (ADR 0025). **No strategy is privileged** — elkjs is one member of a growing set (grid, sorts, tree, cluster), never the thing "layout" means. The overview draws every route at once, each as a colored line of React Flow edges, with the active one emphasised. Cards in the graph show their title; **opening** a card reads it in place (ADR 0006, ADR 0011), and **presenting** a route walks its edges (ADR 0024). pnpm + TypeScript (strict) monorepo.

## Decided — read these before the code

Accepted ADRs run ahead of the code, and standing workarounds constrain it. Read them before touching the areas they govern, and do not read the current code as the design. Each entry states what is built and what is not; most of this section is now built, so the build status to trust is the one written in the entry.

- **ADR 0030 — PostgreSQL is the live write model; files are imported and exported.** The application and database foundations are **built**: version 2 public ids are UUIDs, the import schemas allow persistence-owned ids to be omitted, and `SpaceBackend`/`SpaceSession` drive optimistic whole-snapshot commits, ordered coalescing, explicit retry and visible conflicts. Node 24, pinned Prisma Next and PostgreSQL, the document contract, formal migration and typed runtime entry are in place. The Prisma Next/PostgreSQL repository lists, loads and revision-checks completely identified aggregates, commits them transactionally, and imports complete new Spaces without updating or merging existing ones. The `hyper` CLI discovers one Space or a batch of immediate child Spaces, minting every missing card, route and layout id in process through `newUuid` while a space's id comes from its column default; an existing Space or Card identity rejects and rolls back the complete batch. Route and Layout identities are scoped to their owning Space, so they may be reused in another Space; duplicates within one Space are rejected by domain intake. Identities of different entity kinds may also share a UUID. `--dangerous-truncate` deletes all Hyper content and inserts the batch in that same transaction. Server-side startup creates or loads the zero/one/many-space database experience, the CLI applies that policy after import or with no path, and the normal browser runtime now lists, opens and commits through the typed `HttpSpaceBackend` and Fetch-native Hono application. Standard E2E uses the same HTTP interface over isolated memory repositories; an opt-in PostgreSQL browser test proves durability across a fresh Vite host. CI provisions the exact pinned Compose service with generated masked credentials, applies the committed migration history, runs the complete PostgreSQL integration suite and verifies the live contract. The Save action, file write-back, virtual file module and source-byte preservation flow are gone. The CLI-only canonical exporter regenerates deterministic version 2 directories through staged, validated replacement and records the exact projected revision. The existing `space.json` plus card Markdown structure stays. See `docs/superpowers/specs/2026-07-28-postgres-document-persistence-design.md`.
- **Prisma Next 0.16.0 packaging workaround.** Its emitted `contract.d.ts` imports types directly from `@prisma-next/adapter-postgres`, `@prisma-next/target-postgres`, `@prisma-next/sql-contract`, and `@prisma-next/contract`, but pnpm's strict layout does not expose transitive packages to that project-owned file. Those four packages are therefore exact `0.16.0` root devDependencies only so generated types resolve. Authored config/runtime/application code still imports database capabilities only through the `@prisma-next/postgres` facade. Do not add hoisting or patch emitted artifacts; remove the four direct devDependencies when an upstream release emits facade-resolvable types.
- **Prisma Next 0.16.0 `int8` typing workaround.** Its PostgreSQL codec declares `int8` input and output as JavaScript `number`, although the codec and node-postgres runtime pass bigint-compatible values through unchanged. Repository revisions remain `bigint`; one compatibility cast is isolated in `toDatabaseRevision` and runtime values are checked when read. Do not convert revisions through `Number`, which loses PostgreSQL `bigint` range, and remove the cast when upstream exposes a lossless `int8` type.
- **ADR 0025 — a Layout is optional, and editing an Algorithmic View creates one.** The placement half is **built**: `positionedStrategy` exists, `resolveView` returns it whenever `defaultView` names a declared Layout, and an Algorithmic View keeps its computed card positions in runtime state until the first completed placement edit converts it. That conversion copies every card already on screen, submits the Positioned Layout through `SpaceSession`, and repoints `defaultView` at it. After conversion, the current and every later graph render from the authored Layout; obsolete asynchronous strategy results cannot replace it. ELK renders the fixture because the fixture declares no Layout — a resolution outcome, not a privileged engine. The structural half of 0025's definition of editing — create, delete, connect — begins with ADR 0033's Route-authoring work, below. Issues `01`–`07`, `12`, and `13` are resolved; `01`–`07` were written against the superseded 0013/0017 model, so don't read them as the design either.
- **ADR 0031 — Views and Layouts are selected; conversion keeps no strategy provenance.** Built: the toolbar has peer icon selectors for application-supplied Algorithmic Views and Space-owned Positioned Layouts. Selection is navigation and never persists by itself. Editing an Algorithmic View creates and selects the next neutrally titled Layout without touching existing Layouts; automatic persistence adds it and makes it `defaultView`. Editing a selected Layout updates it in place. The converted Layout remembers no source strategy, and the prototype Auto-arrange control plus `ResolvedView.automatic` are gone. See resolved issue `16`.
- **ADR 0033 — authoring is drag-to-connect through four spatial handles coloured as the active Route.** Built: source handles appear on the hovered or selected card; target handles appear during the drag. They are route-independent and the chosen side is not authored. Algorithmic View conversion, first-Route minting and Option/Alt empty-drop create-and-connect are also built; detached Card creation and structural deletion are not. The per-route attachment machinery still in `react-flow-adapter` serves overview rendering and is not visible authoring UX.
- **ADR 0034 — the HTTP application is Fetch-native.** Built: the browser-safe `@project/http` package owns the complete Hono route tree, request policy, inferred application type, typed browser backend and narrow repository seam. Development, preview and E2E compose that Fetch application over the selected repository, and the Vite host uses Hono's maintained Node adapter while leaving non-API requests to Vite. Runtime validation stays at the wire. Node, Vite, PostgreSQL, asset serving and process lifecycle stay in adapters or deployment composition rather than the portable route module. The superseded raw Node handler and boolean fallthrough interface are deleted. See `.scratch/fetch-native-http/`.

## Commands

- Install: `pnpm install` (Node >= 24, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173) is the normal PostgreSQL-backed HTTP runtime and requires the configured database to be up. `pnpm --filter @project/app dev:memory` serves the tracked fixture through the same HTTP boundary over an isolated memory repository. `pnpm dev:new` (port 5174) serves an initially empty memory repository; server-side startup creates the normal one-card **new space** once, and edits survive browser reloads for that server's lifetime (ADR 0018). None writes source files. **A dev server is usually already running on :5173, owned by the human in their own terminal — leave it alone.** Do NOT start, stop, restart, or kill it, and do not free the port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). Assume it's up and hot-reloading (Vite HMR + React Fast Refresh); your edits are already live in it. `strictPort: true`, so a second `pnpm dev` will fail rather than pick another port — don't run one. To verify changes, use `pnpm test`/`pnpm e2e` (Playwright starts its own servers) — never the human's dev server.
- Verify: `pnpm verify` runs `typecheck` -> `typecheck:packages` -> `lint` -> `format:check` -> `test:coverage` (i.e. `tsc --noEmit` over the root program, then `pnpm -r typecheck` over each package's own config, `eslint . --max-warnings=0`, `prettier --check .`, `vitest run --coverage`). **Both typechecks are needed**: the root program's `include` has `"*.config.ts"`, and `*` does not cross directory boundaries, so `packages/app/vite.config.ts`, `vite-space-http-plugin.ts` and `http-server-build.config.ts` are covered only by the per-package pass. Warnings fail the lint run; coverage thresholds are per-package and pinned at what already holds (`core`, `graph`, `persistence`), with no global threshold on purpose.
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- E2E: `pnpm e2e` (Playwright, Chromium only) stays database-free and exercises HTTP. Every test owns a fresh Vite host, `E2eMemorySpaceRepository` and catalog; reloads and extra pages inside that test share them, while no revision leaks to another test. The `chromium` project imports the tracked fixture and `new-space` starts empty so database startup creates one card. Hosts use worker-scoped ports beginning at 5276, away from the human's 5173/5174. `pnpm e2e:postgres` is the separate opt-in one-test project proving a real PostgreSQL edit survives a fresh Vite host; run it only with PostgreSQL up and always stop PostgreSQL afterward. One-time first: `pnpm exec playwright install chromium`.
- Build: `pnpm build` (Vite build of the app).
- PostgreSQL integration: copy `.env.example` to the ignored `.env`, fill its password and matching `DATABASE_URL`, then run `pnpm postgres:up` followed by `pnpm test:integration:postgres`. Always finish with `pnpm postgres:down`; it keeps the named volume. `docker compose down --volumes` is the destructive reset. Normal `pnpm verify` and `pnpm e2e` do not require PostgreSQL.

## Package layout & boundaries

Seven `@project/*` workspace packages under `packages/`:

- `core` — domain model. Zod schemas (`schema.ts`, incl. `spaceFileSchema` — the space-file shape) + the `Card`/`Route`/`RouteEdge`/`Layout` types derived from them (`types.ts`). No React, no framework deps.
- `graph` — pure graph logic over a `Space`: `loadSpace` (the one intake — parse, validate references including duplicate Edges within a Route, index), the `Space` type, O(1) lookups, route→handles/edges derivation, and the `LayoutStrategy` contract (`LayoutGraph`, `buildLayoutGraph`, `gridStrategy`, `positionedStrategy`). Depends only on `core`.
- `http` — browser-safe Fetch transport: the Hono `/api/spaces` route tree, request and response policy, inferred `SpaceHttpApp` client contract and narrow `SpaceResourceRepository` seam. Depends only on `core`, `persistence`, Hono and runtime-neutral media parsing; imports no host, database, app or render implementation.
- `persistence` — browser-safe `SpaceBackend` and `SpaceSession` contracts, optimistic revision handling, commit coalescing, retry/conflict states, and the memory adapter. Depends on `core` and `graph` so every committed snapshot passes the normal domain intake.
- `react-flow-adapter` — the ONLY place React-Flow (`@xyflow/react`) and elkjs specifics live: projects a space+route into RF nodes/edges, implements `LayoutStrategy` as `elkStrategy`, renders `CardNode`.
- `ui` — reusable, presentation-agnostic React components + shadcn-style primitives (Tailwind v4, Radix Select, CVA). Depends on `core` only.
- `app` — wiring/composition: Zustand store (selection + the walk), TanStack Router, space loading, the graph view and its cameras, presenting chrome, hand-rolled CSS.

Hard rules — **all four are now enforced, not just documented**. Two layers, because neither catches what the other does: ESLint `no-restricted-imports` zones catch package specifiers and relative escapes (`../../*`), and each package's narrowed tsconfig `paths` makes an illegal alias unresolvable. `rootDir` is set on `core` alone — anywhere else it rejects the legitimate `@project/*` import too, since the aliased file resolves outside the package, which is why the relative-escape half is a lint rule rather than a compiler setting. Before this, `core` could import `@project/ui`, cycle back into `@project/graph`, and reach `../../app/src/store` with typecheck and lint both green.

- Domain logic stays out of React (keep it in `core`/`graph`).
- React-Flow / elkjs specifics stay in `react-flow-adapter`. Precisely: **`core`, `graph`, `persistence` and `ui` must not import them**, which is what `no-restricted-imports` enforces. `app` does import `@xyflow/react` and legitimately so, being the composition layer — the older "nothing else imports them" was already false.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.
- A module bundled into a Vite config (`vite.config.ts`, `http-server-build.config.ts`) imports `@project/*` by **relative path only** — a bare specifier is externalized and hands Node the workspace TypeScript, and the dev server then will not start at all.

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases: declared in `tsconfig.base.json`, mirrored in `vitest.config.ts` `resolve.alias`, and **narrowed per package** in each `packages/*/tsconfig.json` so a package can only resolve what it may legally depend on. Vite needs no alias at all — it resolves through the workspace `exports`, and the third copy that used to sit in `packages/app/vite.config.ts` is gone (removing it built an identical bundle). Vitest's *is* load-bearing: the root package declares no `@project/*` deps, so there is no symlink to resolve through. Two lists to keep in sync, plus the package's own narrowed one.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **Use a functional core and imperative shell for cross-module coordination.** Compute and validate the complete next state in a private pure core before producing side effects; a thin imperative shell then updates collaborators in an order that preserves valid intermediate states. Expose the coordination as one operation rather than returning a plan for callers to execute. Keep framework and store events outside the seam, depend on existing module interfaces, and do not manufacture single-adapter ports for deterministic private helpers. An edit event is a notification, not state transfer: each editor first installs its authoritative completed state and only then emits the notification; the coordinator derives the next Space from the current state owned by its collaborators rather than from state carried by the event.
- **`Layout` is data and `LayoutStrategy` is behaviour — don't collapse them back (ADR 0014).** A `Layout` (in `core`) is the authored card→position map a space carries; a `LayoutStrategy` (in `graph`) is `(graph: LayoutGraph) => Promise<LayoutGraph>`. Every Layout has a strategy that renders it; not every strategy has a Layout behind it. There is no `Arrangement` type and geometry rides as optional fields on the elements (ADR 0005) — don't introduce one. Older comments call the *function* a Layout; that is stale vocabulary, not a second concept. `LayoutGraph`/`LayoutCard`/`LayoutPort` belong to the *strategy* despite the name.
- **The strategy contract lives in `graph`, not the adapter.** Geometry lands as optional fields on the cards and handles, mirroring how ELK itself models it. `gridStrategy` (pure, places no handles) exists partly to keep the seam honest; if a change only works for `elkStrategy`, the contract has leaked. Which cards get arranged is the view's choice, passed in. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored, and no engine owns it (ADR 0025).** A strategy is *automatic* (computes placement from cards and routes alone — grid, name-sort, ELK) or *positioned* (reads a Layout the author wrote). **ELK is one automatic strategy among several and must never be the focus**; if a change only makes sense for `elkStrategy`, the seam has leaked. Editing an Algorithmic View is legal and **converts** it: the card positions already on screen are copied into a new Layout and the edit written there, so nothing moves at the moment of conversion. There is no edit mode; persistence status is the state worth surfacing. **Don't re-suggest seeding or constraining ELK to honour a drop point**: three spike increments — append, then branch, then seeded and interactive ELK — each reshuffled the *existing* cards and placed the new one by global optimisation, so a drop landed somewhere arbitrary. The failure is structural, not a matter of tuning. Written up in ADR 0025 and `.scratch/graph-editing/`.
- **The six handle rules below belong to the overview, not to the domain (ADR 0033).** They hold because that view overlays several routes over one set of card positions and needs distinct attachment points to stay legible. The **authoring** interaction uses four route-independent spatial handles per card, coloured as the active Route; none of the overview bookkeeping applies there. Don't restate any of it as a rule the model obeys, and don't let it shape the visible authoring controls.
- **ELK port offsets are applied to handles.** ELK's *port* is React Flow's *handle* — same thing, two libraries' words. ELK computes each one's position, and those exact offsets drive where `CardNode` renders the handle, so a route's edges meet its cards cleanly. Don't hardcode handle positions.
- **Port constraints are `FIXED_SIDE`, not `FIXED_ORDER`.** ELK orders `FIXED_ORDER` ports **clockwise** around the node — EAST top-to-bottom but WEST *bottom-to-top*. Handing both sides the same list order therefore puts a route's outbound handle at the top of one card and its inbound handle at the bottom of the next, crossing every route at every shared card. `FIXED_SIDE` fixes the side and lets ELK order within it. Don't switch back without reading `.scratch/layout-seam/issues/04-elk-fixed-side-ports.md`.
- **ELK port ids are namespaced per card.** A handle id (`<routeId>::out`/`::in`) is the *same* on every card a route passes through, so `elkStrategy` hands ELK `<cardId>##<handleId>` (`elkPortId`) and builds edge endpoints from the same key, stripping the prefix on read-back, so handles keep their bare ids and `CardNode` is unaffected. Never hand ELK a bare handle id — it then can't tell which card an edge attaches to and mislays *even single-route* graphs. See `.scratch/layout-seam/issues/01-namespace-elk-port-ids.md`.
- **Handle ids must be distinguishable per card per side — React Flow's rule, not just ELK's.** The entry above covers why ELK needs `<cardId>##<handleId>`; React Flow separately requires that *"multiple handles of the same kind on a node need to have distinguishable IDs"*, or it can't resolve an edge's `sourceHandle`/`targetHandle` and warns (#008). The `<routeId>::out`/`::in` scheme satisfies both libraries, for different reasons. Don't collapse it to a per-side counter.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `CardNode` dims handles via `opacity` and it looks like a styling choice; it isn't. Same for the CSS in `styles.css`.
- **Handle geometry is declared, never re-measured — do not add `useUpdateNodeInternals`.** React Flow measures handles once and caches, which is its named cause of warning #008, and the documented remedy is `useUpdateNodeInternals`. Here that remedy is **wrong**. `projectCardNodes` declares `node.handles` from the strategy (`declaredHandles` in `projection.ts`), and `parseHandles` in `@xyflow/system` builds `handleBounds` from those declarations without consulting the DOM at all — this is the `node.handles` alternative the old spike note proposed, and it is built. Crucially, a card declares `<routeId>::in`/`::out` for **every** Route, including ones not yet incident to it, so a completed connection resolves in the same render that first makes its target incident. `useUpdateNodeInternals` passes `force: true`, and the forced path *replaces* `handleBounds` via `getHandleBounds`, which reads only the anchors present in the DOM — silently dropping every not-yet-incident declaration and breaking the **next** connection rather than the current one. Verified both ways against the fixture: with the hook, a second connection in one session fails with six #008 warnings; without it, it passes (`editing.spec.ts`, "a second connection drawn in the same session resolves its handles"). Unit tests cannot catch this — the forced path needs truthy `offsetWidth`/`offsetHeight`, which are 0 in jsdom, so it silently no-ops there. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **React Flow is pinned to 12.11.2.** The declarative `node.handles` path above intentionally depends on behavior verified against that release. Upgrade both consuming manifests together and run the complete Playwright suite; do not widen the range or accept an automated upgrade without revalidating handle resolution, consecutive connections and warning #008 in a real browser.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`.
- **Hono's own docs are the reference, and they ship one for agents:** fetch `https://hono.dev/llms-full.txt` when working in `http` — the whole docs site as a single document, regenerated by `scripts/build-llm-docs.ts` as a `prebuild` step in `honojs/website`, so don't vendor a copy. **Take `llms-full.txt`, never `llms-small.txt`**: its `tinyExclude` drops `concepts/`, `helpers/` and `middleware/`, and the `startsWith` predicate catches `guides/middleware.md` by basename too, so the small file holds zero occurrences of `bodyLimit` — most of what this package does. There is no official Hono agent skill or MCP server: `hono-skill` and `@hono/skill` are both 404 on npm, the request to make one official (`honojs/hono#4812`) is still open, and in `honojs/cli#77` the maintainer proposes deleting the CLI's `docs`/`search` commands because "you can use the 'Web Fetch' function in the agent". `@hono/mcp` is middleware for *building* MCP servers with Hono and documents nothing about Hono — don't mistake it for a docs source. The two pages carrying the non-obvious rules are `/docs/guides/rpc` and `/docs/guides/best-practices`. Findings and what they mean for this repo: `.scratch/hono-guidance/findings.md`.
- **Hono hands the host a rejected promise unless the app terminates every path.** Two rules, both load-bearing, both proven by regressions in `space-http-app.test.ts`. **Never call `context.notFound()` inside the handler `app.notFound()` installed** — Hono seeds the Context's not-found handler from the app's, so it re-enters itself until the stack blows, on every path off the declared contract including the trailing slash an address bar produces; return an explicit response instead, which is also what the RPC docs say when a client infers types. **Never rethrow from `onError`** — Hono does not convert that into a 500, it re-invokes the handler and lets the throw escape, so `app.fetch()` rejects and a host without a `.catch` gets an unhandled rejection, which Node 24 answers by killing the process. A non-`Error` throw never reaches `onError` at all. An `onError` that returns a Response is entered once; one that rethrows is entered once per compose frame.
- **One media policy, or Hono's json validator silently hands you `{}`.** Its `jsonRegex` is narrower than RFC 9110 — it rejects space before `;`, spaces around `=`, `_` in a parameter name, and quoted strings containing `;` — and on disagreement it does not parse the body and reports nothing, which surfaced as a 400 about the fields of a body never read. `requireSupportedRequestMedia` therefore rewrites the header it has just validated to canonical `application/json`; don't remove that and don't add a second policy beside it. Relatedly, `content-type@2` validates **nothing** — `parse` has no throw path and answers `parse('garbage')` with `{ type: 'garbage' }` — so the hand-rolled scanner is the whole of this module's media validation, not a duplicate of the dependency.
- **The Node host must keep `@hono/node-server`'s global `Request`/`Response`, and Hono answers HEAD from the GET handler.** Two host-level facts the portable route module quietly depends on. **`getRequestListener` replaces `globalThis.Request`/`Response`** with its own lightweight classes unless `overrideGlobalObjects: false` is passed, and defines them non-writable and non-configurable — a permanent, process-wide swap. Leave it on: `requireSupportedRequestMedia` and `requireBoundedCommitBody` both rebuild the request through the *global* `Request` constructor, so with the override off the constructor is handed an instance it does not recognise and **every commit answers 500** while all the rejection paths stay green. This is `@project/http`'s one host requirement — portable does not mean indifferent to the host. Separately, **Hono routes a HEAD request to the GET handler and strips the body**, so a resource that does not explicitly intercept HEAD answers 200 carrying nothing; `unservedContractPath` is that interception, and it is shared with `app.notFound()` so the two cannot disagree about whether a non-UUID segment is a 400 or a 405. Both are pinned in `vite-hono-host.test.ts` and `space-http-app.test.ts`.
- **Hono types a json validator's input as its output unless you say otherwise, and partial generics make it worse.** `in.json` collapses to the callback's return type when `InputType` is unsupplied, which put the decoded `bigint` revision into the request contract — a value `JSON.stringify` throws on, so no client could satisfy it. TypeScript has no partial type argument inference, so supplying only `InputType` drops every other parameter to its *default*, and `VF` defaulting to `=> any` removes the route from the schema entirely and silently: `$put` stopped existing on the client. That is why `decodeCommitBody` is a named function — so `VF` can be supplied too. Separately, a bare `MiddlewareHandler` (which is how `bodyLimit` was declared, before it was dropped for the reasons below) erases its statuses from the contract while a hand-written one beside it survives; produce every status in our own code. Both are pinned by `space-http-app-types.test.ts` — which `pnpm test` does **not** enforce, since `expectTypeOf` is a runtime no-op without `test.typecheck`; only the root `pnpm typecheck` catches it.
- **`Content-Length` is never trusted, and an oversized body is drained rather than dropped.** `requireBoundedCommitBody` counts the bytes that arrive; the header is deleted and never consulted. Hono's `bodyLimit` is **deliberately not used**, for two independent reasons. It *trusts* the header when present — comparing and returning without reading a byte — so an understated length would smuggle any body through. And on overflow it abandons a **locked** reader without consuming the rest of the body, so nothing downstream can drain the request: Node's `_dump()` cannot resume a stream the web wrapper holds, the socket dies with the 413, and a keep-alive client loses its connection. Draining is what the superseded raw handler did (`request.resume()` after clearing its buffer), and `vite-hono-host.test.ts` pins reuse for both framings at 4× the cap — the older one-times-the-cap case passed by accident, since a body that small is already flushed before the response. The drain is itself bounded at `MAX_DRAINED_BODY_BYTES`: an honest overshoot keeps its connection, a client that never stops sending loses it. A declared-length pre-check used to sit here as a fast path and was **deliberately dropped** — it answered 413 for a body the client had not sent. Don't reintroduce it without first deciding what a dishonest `Content-Length` should mean. The old raw handler's canonical-length strictness died with it at ticket 04; the count subsumes it.
- **A wire codec throws prose, not Zod.** `spaceSnapshotSchema.parse` puts its entire serialized issue array in `Error.message`, and `decodeCommitBody` ships that straight into the `{ message: string }` error contract — a JSON document nested inside a field clients render as a sentence. `decodeSnapshot` in `http-protocol.ts` uses `safeParse` and summarises the first three issues instead, matching `exactRecord` and `decodeRevision` beside it. Don't call `.parse` directly in a decoder whose error reaches a client.
- **A card is one file: frontmatter, then body (ADR 0020).** `id`, `title`, `description`, `kind` and `target` are the card file's frontmatter; the markdown under it is the content. The space file holds `version`, `id`, `title`, `routes`, `layouts`, `defaultView` — structure, and no `cards` array. Cards are discovered by scanning two locations, **non-recursively**: `*.md` beside the space file, and `cards/*.md`. Non-recursion is deliberate — ADR 0001's nested spaces will want subdirectories, and a recursive scan would make each one ambiguous with card discovery. A card's identity is its frontmatter `id` and never its filename, so renaming a file is not a data migration; a duplicate id across files is a load error naming both. A body may begin with a heading — the title lives in the same file, so a heading is just a heading. Every `.md` in scope *is* a card, so there is nowhere to leave a draft — and a `README.md` beside a space file would be read as one, which is why the fixture's moved to `packages/app/README.md`. **`body` is the field, `content` is the domain word**, and they are not synonyms to be reconciled: `CONTEXT.md` still lists "body" under _Avoid_ for a card's content in general, because a space-card's content is a graph and has no body. `Card.body` is what a *markdown* card's content is stored as. Don't rename one into the other in either direction.
- **Routes are a space's only structure.** There is no authored `edges` array *beside* routes; ADR 0007 deleted that along with the `sequence`/`reference` kinds, and it stays deleted — don't reintroduce a structural layer next to routes. A route **is** a set of `{from, to}` edges the author draws (ADR 0032), so "edge" names both the route's stored element and React Flow's drawn line — one word for one thing, and the only place the render layer and the domain share vocabulary. Cycles and self-edges are legal; an exact duplicate within one Route is not. Three types carry an Edge, each adding to the last: `RouteEdge` (`core`) is the authored `{from, to}`; `GraphEdge` (`graph/routes.ts`) is that resolved onto the handles it attaches to and tagged with its route; `LayoutEdge` (`graph/layout.ts`) is that again once a strategy has routed it. Don't collapse them and don't add a fourth.
- **`path` means a file path only.** The space file's key is `routes` and the code says `Route`/`routeId`/`buildRouteEdges`. Remaining `path` identifiers are filesystem paths, TanStack Router URL paths, or React Flow's own SVG `edge-path` class — don't "fix" those.
- **`manifest` is retired, in vocabulary and code (ADR 0010).** The top-level domain value is a **Space**, minted only by `loadSpace(input, cardFiles) → { ok, space } | { ok: false, errors }` in `@project/graph` — the one intake that parses (the space file *and* every card file's frontmatter), validates references, and indexes, so a `Space` is consistent and O(1)-indexable by construction. `getCard`/`getRoute` read that index; every `graph`/adapter/app signature takes a `Space`. The on-disk shape is a **space directory**: the **space file** (`space.json`, validated by `core`'s `spaceFileSchema`) plus a markdown file per card (ADR 0020). A value that only passes that schema is *not yet* a Space. `loadSpace` gained the card files as an argument, not a capability — it still does no I/O and is still synchronous, and reading the bytes stays outside it. Don't reintroduce `manifest` anywhere — not as a type, not as the word for the file. There is no shared `Draft`: unfinished gestures and invalid editor input remain local to that editor. An editor installs valid authoritative state and emits a payload-free notification; Edit completion then derives and validates the whole next Space before effects.
- **Styling is split:** `ui` uses Tailwind v4 + shadcn-style primitives; the graph/card CSS stays hand-rolled in `packages/app/src/styles.css`. Tailwind scans `app` + `ui/src` via `@source` in `tailwind.css`.
- **Markdown is excluded from Prettier** (`.prettierignore`) — don't rely on `format` to touch `*.md`.
- **The browser never imports files or names storage.** `SPACE_DIR`, `virtual:space-file` and the Vite file plugin are gone. File discovery and parsing remain server-side CLI/import concerns. Browser resources are fixed to list, load and commit under `/api/spaces`; requests cannot carry database URLs, filesystem paths or arbitrary targets. A completed edit commits a whole `SpaceSnapshot` through `SpaceBackend`. Canonical export belongs to the future CLI (ADR 0030), never an app Save action.
- **Persistence crosses the app at `SpaceBackend` and `SpaceSession`.** Normal composition is `PostgresSpaceRepository` → Fetch-native Hono application → typed `HttpSpaceBackend` → one opened `SpaceSession`; standard E2E substitutes only an isolated `E2eMemorySpaceRepository` behind the same application. Startup lists over HTTP, opens the sole UUID or renders the UUID-only selector, while server-side policy ensures an empty database receives the normal new Space. Selection does not enlarge `SpaceSession`, which still owns one already-open workspace. Every backend commit validates both public shape and normal domain intake (`loadSpaceSnapshot`), so dangling references, duplicate Edges within one Route and invalid aliases/layouts are permanent `invalid-snapshot` failures rather than stored state. Route cycles and self-edges are valid authored structure (ADR 0032).
- **A session submits complete snapshots after completed edits.** It allows one commit in flight, coalesces waiting edits to the newest snapshot, chains the committed revision into the next optimistic write, and exposes pending, retryable failure, permanent rejection and conflict states. Persistence is totally asynchronous: Edit completion relies only on `submit` installing the local working snapshot synchronously, never waits for backend acknowledgement, and immediately selects the resulting Layout from that local state. Accepting remote replaces the session snapshot and remounts the workspace so graph, editor and view stores cannot retain stale local positions. Route activation is not an edit and does not submit.
- **Session notification is non-throwing, and a submit made from an observer is queued rather than re-entered.** An observer that throws cannot interrupt the publisher: `publish` contains each listener's failure, hands it to `SpaceSessionOptions.reportObserverError` (defaulting to `console.error`) and carries on to the remaining observers, so persistence, the working Space and any reentrant Edit completion all continue. The reporter is wrapped too, and unlike `@project/http`'s `invokeLogError` it never rethrows — nothing above a notification could handle the failure. Separately, an observer *may* legally submit the next Edit while the publishing submit is still on the stack; that reentrant call installs its working Space and stops, and the submit already on the stack makes the one commit decision from the newest installed state. Deciding from the snapshot it was handed instead queues the older snapshot behind the newer one and stores it last, undoing a completed Edit at the next load. Both are pinned in `session.test.ts`; `edit-completion.test.ts` pins that a failing completion effect still leaves the later effects their turn.
- **Don't import a workspace package by name into `vite.config.ts`.** Vite loads the config in Node and externalizes bare specifiers, so `@project/core` hands *Node* the TypeScript source, whose extensionless relative imports (`export * from './schema'`) Node's ESM resolver rejects — the config then fails to load at all and the dev server will not start. Import by relative path (`../core/src/index`) so esbuild bundles it. This is the one place the repo's extensionless-import convention does not hold.
- **Vite hosts a fixed server runtime, not browser-selected capabilities.** The thin config-time plugin imports no application package. Development loads the chosen runtime with Vite's SSR module runner; preview loads the dedicated bundled Node artifact. The server configuration fixes PostgreSQL versus isolated E2E memory and fixture versus empty catalog before any browser request.
- **Changing the Vite config needs a dev server restart** — plugins load at config time and HMR won't pick them up. That server is the human's; say it needs restarting rather than restarting it.
- **Delete a spike harness when you write it up; ignoring it is not enough.** `packages/app/spike.html` sat gitignored, went stale against the `elkLayout` → `elkStrategy` rename, and broke `pnpm dev` — Vite's dependency scanner treats every root `.html` as an entry and does not read `.gitignore`, while tsc and eslint both skip `.scratch/`, so `pnpm verify` stayed green and only the dev server saw it.
- **Card markdown is sanitised before it is injected.** `CardContent` renders through `dangerouslySetInnerHTML`, and `marked` has had no `sanitize` option since v5, so `DOMPurify.sanitize()` sits between them. Don't remove it on the argument that a card came from a local import: backend implementations and future import sources broaden that premise. `packages/ui/test/CardContent.test.tsx` fails without the sanitiser.

## Before claiming done

- Run `pnpm verify` and report the real output.
- For any UI/graph change, also run `pnpm e2e` and report it.
- Do not assert success without having run the commands.
- CI (`.github/workflows/ci.yml`) runs both on every push and PR, with `--frozen-lockfile`. It is a backstop, not a substitute — a red CI after the fact is slower than a green run before the commit.

## Scope discipline

Keep to the MVP. Don't over-generalize the domain model and don't add features beyond what's asked.

On multi-route rendering (`.scratch/multi-route/`): the overview draws every route, and **selection is emphasis, not filtering** — at all times, not only while presenting. A Layout carries the filter (`routes`, which routes it shows at all) and the **active** route is the emphasis; activating a route never changes what is visible. There is one active route, not a selection plus an emphasis (ADR 0026). The dimming lives in `projectRouteEdges`, `CardNode` and `RouteLegend`. `filterHandlesByRoute` and `routeCardIds` are right for a view that wants one route. Which routes a view shows is a View decision passed into the strategy (ADR 0005) — don't let the strategy or `graph` decide it, and `resolveView` is where it is made.

**`resolveView` answers which routes show and which is active; nothing else does (ADR 0026).** Both fallbacks live there — absent `routes` means every route, absent `activeRoute` means the first *visible* one, and it is the filter the fallback runs over, or a Layout would open active on a route it does not draw. `createSpaceStore` takes the answer as an argument rather than reaching for `space.routes[0]`; two places answering it would disagree the moment a Layout filters.

**A completed edit persists automatically (ADR 0030).** The editor first installs its authoritative completed state and synchronously emits a payload-free `EditCompleted` notification. Edit completion derives and validates the complete current `SpaceSnapshot`, submits it to `SpaceSession`, and immediately selects its resulting Layout; intermediate drag frames never reach persistence. The session status (`Persisting…`, `Persisted`, retry, rejection or conflict) is the persistence indicator. There is no Save button, keyboard Save command or browser file write-back. The `beforeunload` guard is registered only while persistence is not settled — an always-attached handler would cost the page its bfcache. It calls `preventDefault()` and nothing else; `event.returnValue = ''` is deprecated and lint rejects it.

**Activating a route is not an edit (ADR 0028).** It converts no automatic layout and never submits persistence. Edit completion samples `useSpaceStore.getState().activeRouteId` only when `EditCompleted` is emitted, rather than subscribing route activation into an edit trigger. The submitted Layout names the active route outright because the resolve-to-first fallback is a read and persisted state should not depend on route order. `updatePositionedLayout` carries a Layout's `routes` filter through rather than replacing it — positions are replaced because the editor store holds the whole truth of them, but the filter is authored and the app has no surface for writing one.

**Presenting is this canvas, closer in (ADR 0027).** There is no second surface and nothing a Card is turned into. `PresentingCamera` in `GraphView` is the whole mechanism: `setCenter` to the active card, and a **split** move when the zoom changes by more than a tenth — pan at the wider scale, then close in — because one combined move whips. The chrome (`PresentingChrome`) is screen-fixed and enumerates the active card's outgoing edges, because at a zoom where the card is legible its neighbours are provably off frame. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a Zustand selector** — `movesFrom` takes its three inputs and is called at render time in `App` for exactly this reason; as a selector it handed Zustand a new array identity every render and re-rendered until React gave up. It is deliberately **not** `useMemo`'d: `movesFrom` reads the Zustand-owned `space` installed synchronously by `installSpace`, so a memo keyed only by its three explicit inputs would go stale when an authored Edge changed the Space and `PresentingChrome` would stop offering the move that had just been drawn. A render-time call is safe here because nothing subscribes to the array's identity — `moves` feeds no effect, no dependency array and no memoized child, so a fresh array cannot feed a re-render.

**A Route may contain cycles and self-edges (ADR 0032).** Authoring records the graph the author draws; presenting decides how to traverse it. An Alias is still the way to place and title the same content as a distinct Card, but it is not required merely to return to an existing Card. `loadSpace` rejects only an exact duplicate Edge within one Route; drawing that duplicate live is an idempotent no-op.

The overlay limit: only an acyclic union of the visible route Edges lays out on a clean left-to-right axis, as parallel forward paths. A backward Edge can come from a cycle inside one Route or from two Routes disagreeing on the order of shared Cards. `elkStrategy` returns ELK's routed `sections` on each Edge and the adapter's `RoutedEdge` draws them (a bezier fallback covers grid/first-paint), so a back-edge reads as a routed channel rather than a self-curling stub. Read `.scratch/multiple-routes/findings.md` before extending any of this.

The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against a purpose-shaped graph rather than demo prose. It is **two disconnected collections** sharing no cards, which ELK lays out as separate bands: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several routes over one spine; (2) `Echo E→F→G→H→E′` — a plain linear collection. Each returns to its start via an alias (`A′`/`E′`, which the `↳` marker names), never an edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture route is a **line** — one edge out per card — which is the degenerate graph, not a second kind; forks and merges are covered by unit and property tests, not here. `03`'s back-edge rendering is proven by a unit test (`elk-strategy.test.ts`), not the fixture. The demo stays in `packages/app/example/`, dormant, for when real space-loading exists. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a space file would be scanned as a card). The ELK options in `elk/layout.ts` are a minimal baseline: don't tune global layout options against this fixture's screenshot. If legible multi-route overlay becomes real product work, design it deliberately.
