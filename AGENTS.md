# AGENTS.md

Instructions for AI coding agents working in this repo.

A local prototype for **graph-native technical presentations**: Markdown cards on a spatial graph, imported from a space directory and presented by traversing curated routes. PostgreSQL is the target live write model; the current first increment exercises the same backend/session seam with a memory adapter. Placement is **authored, not computed** — a **Layout** is the card→position map the author writes, and the thing that arranges cards is a **LayoutStrategy** (ADR 0014). A space need not carry a Layout: an automatic strategy the app supplies renders it, and editing converts that into a Layout (ADR 0025). **No strategy is privileged** — elkjs is one member of a growing set (grid, sorts, tree, cluster), never the thing "layout" means. The overview draws every route at once, each as a colored line of React Flow edges, with the active one emphasised. Cards in the graph show their title; **opening** a card reads it in place (ADR 0006, ADR 0011), and **presenting** a route walks its edges (ADR 0024). pnpm + TypeScript (strict) monorepo.

## Decided but not built

Accepted ADRs run ahead of the code. Read them before touching the areas they govern, and do not read the current code as the design.

- **ADR 0030 — PostgreSQL is the live write model; files are imported and exported.** The application and database foundations are **built**: version 2 public ids are UUIDs, the import schemas allow persistence-owned ids to be omitted, `SpaceBackend`/`SpaceSession` define the browser-safe seam, and the memory adapter drives automatic whole-snapshot commits, retry and conflict UI. Node 24, pinned Prisma Next and PostgreSQL, the document contract, formal migration, typed runtime entry and opt-in database test are also in place. The Prisma Next/PostgreSQL repository now lists, loads and revision-checks completely identified aggregates, commits them transactionally, and supports additive identified import. The Vite virtual module is read-only import input; the Save action, write-back endpoint and source-byte preservation flow are gone. Still unbuilt: missing-id allocation and the transactional file importer, HTTP backend, database-backed startup and CLI-only canonical exporter. The existing `space.json` plus card Markdown structure stays, but PostgreSQL allocates every missing space, card, route and layout id. See `docs/superpowers/specs/2026-07-28-postgres-document-persistence-design.md`.
- **Prisma Next 0.16.0 packaging workaround.** Its emitted `contract.d.ts` imports types directly from `@prisma-next/adapter-postgres`, `@prisma-next/target-postgres`, `@prisma-next/sql-contract`, and `@prisma-next/contract`, but pnpm's strict layout does not expose transitive packages to that project-owned file. Those four packages are therefore exact `0.16.0` root devDependencies only so generated types resolve. Authored config/runtime/application code still imports database capabilities only through the `@prisma-next/postgres` facade. Do not add hoisting or patch emitted artifacts; remove the four direct devDependencies when an upstream release emits facade-resolvable types.
- **Prisma Next 0.16.0 `int8` typing workaround.** Its PostgreSQL codec declares `int8` input and output as JavaScript `number`, although the codec and node-postgres runtime pass bigint-compatible values through unchanged. Repository revisions remain `bigint`; one compatibility cast is isolated in `toDatabaseRevision` and runtime values are checked when read. Do not convert revisions through `Number`, which loses PostgreSQL `bigint` range, and remove the cast when upstream exposes a lossless `int8` type.
- **ADR 0025 — a Layout is optional, and editing an Algorithmic View creates one.** The placement half is **built**: `positionedStrategy` exists, `resolveView` returns it whenever `defaultView` names a declared Layout, and an Algorithmic View keeps its computed card positions in runtime state until the first completed placement edit converts it. That conversion copies every card already on screen, submits the Positioned Layout through `SpaceSession`, and repoints `defaultView` at it. After conversion, the current and every later graph render from the authored Layout; obsolete asynchronous strategy results cannot replace it. ELK renders the fixture because the fixture declares no Layout — a resolution outcome, not a privileged engine. The structural half of 0025's definition of editing — create, delete, connect — remains ADR 0021's, below. Issues `01`–`07`, `12`, and `13` are resolved; `01`–`07` were written against the superseded 0013/0017 model, so don't read them as the design either.
- **ADR 0031 — Views and Layouts are selected; conversion keeps no strategy provenance.** Decided, not built: replace the generic Auto-arrange toolbar button with an icon selector grouped into application-supplied Algorithmic Views and Space-owned Positioned Layouts. Selection is navigation and never persists by itself. Editing an Algorithmic View creates a new neutrally titled Layout without touching existing Layouts; automatic persistence adds it and makes it `defaultView`. The converted Layout remembers no source strategy. Remove `ResolvedView.automatic`; it is prototype wiring, not a domain concept. See issue `16`.
- **ADR 0021 — authoring is drag-to-connect with a single neutral handle.** The per-route handle machinery still in `react-flow-adapter` serves the overview; it is not the authoring model.

## Commands

- Install: `pnpm install` (Node >= 24, pnpm 9).
- Dev: `pnpm dev` (app at http://localhost:5173) imports the fixture because the script sets `SPACE_DIR=fixture`. `pnpm dev:new` (port 5174) explicitly clears `SPACE_DIR` and opens a freshly minted **new space** with one card on every full page load (ADR 0018); inherited shell state and gitignored `packages/app/.space` scratch files cannot retarget it. Live edits go only to the page's memory backend; neither command writes a directory. An invalid explicit import renders its complete validation error and never falls back to a new space. **A dev server is usually already running on :5173, owned by the human in their own terminal — leave it alone.** Do NOT start, stop, restart, or kill it, and do not free the port (`kill`/`pkill vite`/`lsof -ti:5173 | xargs kill` etc.). Assume it's up and hot-reloading (Vite HMR + React Fast Refresh); your edits are already live in it. `strictPort: true`, so a second `pnpm dev` will fail rather than pick another port — don't run one. To verify changes, use `pnpm test`/`pnpm e2e` (Playwright starts its own server) — never the human's dev server.
- Verify: `pnpm verify` runs `typecheck` -> `typecheck:packages` -> `lint` -> `format:check` -> `test:coverage` (i.e. `tsc --noEmit` over the root program, then `pnpm -r typecheck` over each package's own config, `eslint . --max-warnings=0`, `prettier --check .`, `vitest run --coverage`). **Both typechecks are needed**: the root program's `include` has `"*.config.ts"`, and `*` does not cross directory boundaries, so `packages/app/vite.config.ts` and `vite-space-file-plugin.ts` are covered only by the per-package pass. Warnings fail the lint run; coverage thresholds are per-package and pinned at what already holds (`core`, `graph`, `persistence`), with no global threshold on purpose.
- Test: `pnpm test` (Vitest, `vitest` for watch). Unit + property tests (fast-check) live in `packages/*/test`.
- E2E: `pnpm e2e` (Playwright, chromium only) — **three servers and projects, on their own ports**: `chromium` drives the fixture on **5273**, `new-space` drives an explicitly cleared `SPACE_DIR` server on **5274**, and `invalid-space` drives a tracked unsupported import on **5275**. All are started by Playwright from the `e2e:server*` scripts with `reuseExistingServer: false`. The new-space server is deliberately given a poisoned inherited `SPACE_DIR`; its script must clear it, which keeps the test and `pnpm dev:new` semantics aligned. Keeping the *ports* off 5173/5174 stops the suite driving the human's dev server or another working tree. Don't point e2e back at a port a human runs. One-time first: `pnpm exec playwright install chromium`.
- Build: `pnpm build` (Vite build of the app).
- PostgreSQL integration: copy `.env.example` to the ignored `.env`, fill its password and matching `DATABASE_URL`, then run `pnpm postgres:up` followed by `pnpm test:integration:postgres`. Always finish with `pnpm postgres:down`; it keeps the named volume. `docker compose down --volumes` is the destructive reset. Normal `pnpm verify` and `pnpm e2e` do not require PostgreSQL.

## Package layout & boundaries

Six `@project/*` workspace packages under `packages/`:

- `core` — domain model. Zod schemas (`schema.ts`, incl. `spaceFileSchema` — the space-file shape) + the `Card`/`Route`/`RouteEdge`/`Layout` types derived from them (`types.ts`). No React, no framework deps.
- `graph` — pure graph logic over a `Space`: `loadSpace` (the one intake — parse, validate references incl. the per-route cycle check, index), the `Space` type, O(1) lookups, route→handles/edges derivation, and the `LayoutStrategy` contract (`LayoutGraph`, `buildLayoutGraph`, `gridStrategy`, `positionedStrategy`). Depends only on `core`.
- `persistence` — browser-safe `SpaceBackend` and `SpaceSession` contracts, optimistic revision handling, commit coalescing, retry/conflict states, and the memory adapter. Depends on `core` and `graph` so every committed snapshot passes the normal domain intake.
- `react-flow-adapter` — the ONLY place React-Flow (`@xyflow/react`) and elkjs specifics live: projects a space+route into RF nodes/edges, implements `LayoutStrategy` as `elkStrategy`, renders `CardNode`.
- `ui` — reusable, presentation-agnostic React components + shadcn-style primitives (Tailwind v4, Radix Select, CVA). Depends on `core` only.
- `app` — wiring/composition: Zustand store (selection + the walk), TanStack Router, space loading, the graph view and its cameras, presenting chrome, hand-rolled CSS.

Hard rules — **all four are now enforced, not just documented**. Two layers, because neither catches what the other does: ESLint `no-restricted-imports` zones catch package specifiers and relative escapes (`../../*`), and each package's narrowed tsconfig `paths` makes an illegal alias unresolvable. `rootDir` is set on `core` alone — anywhere else it rejects the legitimate `@project/*` import too, since the aliased file resolves outside the package, which is why the relative-escape half is a lint rule rather than a compiler setting. Before this, `core` could import `@project/ui`, cycle back into `@project/graph`, and reach `../../app/src/store` with typecheck and lint both green.

- Domain logic stays out of React (keep it in `core`/`graph`).
- React-Flow / elkjs specifics stay in `react-flow-adapter`. Precisely: **`core`, `graph`, `persistence` and `ui` must not import them**, which is what `no-restricted-imports` enforces. `app` does import `@xyflow/react` and legitimately so, being the composition layer — the older "nothing else imports them" was already false.
- Reusable UI goes in `ui`; app-specific glue goes in `app`.
- A module bundled into a Vite config (`vite.config.ts`, `vite-space-file-plugin.ts`) imports `@project/*` by **relative path only** — a bare specifier is externalized and hands Node the workspace TypeScript, and the dev server then will not start at all.

## Conventions & gotchas

- **Strict TypeScript everywhere**, incl. `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters`, `noImplicitOverride`.
- **`verbatimModuleSyntax` + ESLint `consistent-type-imports` are on** — use `import type` for type-only imports or lint/typecheck fails.
- **Cross-package imports** use the `@project/*` path aliases: declared in `tsconfig.base.json`, mirrored in `vitest.config.ts` `resolve.alias`, and **narrowed per package** in each `packages/*/tsconfig.json` so a package can only resolve what it may legally depend on. Vite needs no alias at all — it resolves through the workspace `exports`, and the third copy that used to sit in `packages/app/vite.config.ts` is gone (removing it built an identical bundle). Vitest's *is* load-bearing: the root package declares no `@project/*` deps, so there is no symlink to resolve through. Two lists to keep in sync, plus the package's own narrowed one.
- **Relative imports inside a package are EXTENSIONLESS** (`./foo`, not `./foo.ts`).
- **`Layout` is data and `LayoutStrategy` is behaviour — don't collapse them back (ADR 0014).** A `Layout` (in `core`) is the authored card→position map a space carries; a `LayoutStrategy` (in `graph`) is `(graph: LayoutGraph) => Promise<LayoutGraph>`. Every Layout has a strategy that renders it; not every strategy has a Layout behind it. There is no `Arrangement` type and geometry rides as optional fields on the elements (ADR 0005) — don't introduce one. Older comments call the *function* a Layout; that is stale vocabulary, not a second concept. `LayoutGraph`/`LayoutCard`/`LayoutPort` belong to the *strategy* despite the name.
- **The strategy contract lives in `graph`, not the adapter.** Geometry lands as optional fields on the cards and handles, mirroring how ELK itself models it. `gridStrategy` (pure, places no handles) exists partly to keep the seam honest; if a change only works for `elkStrategy`, the contract has leaked. Which cards get arranged is the view's choice, passed in. The contract is uniformly async, `gridStrategy` included; see `.scratch/layout-seam/issues/06-revisit-async-optionality.md`.
- **Placement is authored, and no engine owns it (ADR 0025).** A strategy is *automatic* (computes placement from cards and routes alone — grid, name-sort, ELK) or *positioned* (reads a Layout the author wrote). **ELK is one automatic strategy among several and must never be the focus**; if a change only makes sense for `elkStrategy`, the seam has leaked. Editing an Algorithmic View is legal and **converts** it: the card positions already on screen are copied into a new Layout and the edit written there, so nothing moves at the moment of conversion. There is no edit mode; persistence status is the state worth surfacing. **Don't re-suggest seeding or constraining ELK to honour a drop point**: three spike increments — append, then branch, then seeded and interactive ELK — each reshuffled the *existing* cards and placed the new one by global optimisation, so a drop landed somewhere arbitrary. The failure is structural, not a matter of tuning. Written up in ADR 0025 and `.scratch/graph-editing/`.
- **The six handle rules below belong to the overview, not to the domain (ADR 0021).** They hold because that view overlays several routes over one set of card positions and needs distinct attachment points to stay legible. The **authoring** view uses React Flow floating edges and one neutral handle per card; none of this applies there. Don't restate any of them as a rule the model obeys, and don't let them shape the authoring surface.
- **ELK port offsets are applied to handles.** ELK's *port* is React Flow's *handle* — same thing, two libraries' words. ELK computes each one's position, and those exact offsets drive where `CardNode` renders the handle, so a route's edges meet its cards cleanly. Don't hardcode handle positions.
- **Port constraints are `FIXED_SIDE`, not `FIXED_ORDER`.** ELK orders `FIXED_ORDER` ports **clockwise** around the node — EAST top-to-bottom but WEST *bottom-to-top*. Handing both sides the same list order therefore puts a route's outbound handle at the top of one card and its inbound handle at the bottom of the next, crossing every route at every shared card. `FIXED_SIDE` fixes the side and lets ELK order within it. Don't switch back without reading `.scratch/layout-seam/issues/04-elk-fixed-side-ports.md`.
- **ELK port ids are namespaced per card.** A handle id (`<routeId>::out`/`::in`) is the *same* on every card a route passes through, so `elkStrategy` hands ELK `<cardId>##<handleId>` (`elkPortId`) and builds edge endpoints from the same key, stripping the prefix on read-back, so handles keep their bare ids and `CardNode` is unaffected. Never hand ELK a bare handle id — it then can't tell which card an edge attaches to and mislays *even single-route* graphs. See `.scratch/layout-seam/issues/01-namespace-elk-port-ids.md`.
- **Handle ids must be distinguishable per card per side — React Flow's rule, not just ELK's.** The entry above covers why ELK needs `<cardId>##<handleId>`; React Flow separately requires that *"multiple handles of the same kind on a node need to have distinguishable IDs"*, or it can't resolve an edge's `sourceHandle`/`targetHandle` and warns (#008). The `<routeId>::out`/`::in` scheme satisfies both libraries, for different reasons. Don't collapse it to a per-side counter.
- **Hide a handle with `opacity: 0` or `visibility: hidden` — never `display: none`.** React Flow measures each handle to place edges, and `display: none` reports 0×0, so edges attach to the wrong point. `CardNode` dims handles via `opacity` and it looks like a styling choice; it isn't. Same for the CSS in `styles.css`.
- **Changing a handle's position or count needs `useUpdateNodeInternals`.** React Flow measures handles once and caches; a `data` change re-renders but does not re-measure, which is React Flow's named cause of warning #008 and of edges attaching to stale positions. Handle `offsetY` *does* change here when ELK resolves — the exposure is currently masked because `RoutedEdge` draws ELK's own points and ignores React Flow's measured `sourceX/Y`, so only the bezier fallback (grid strategy, first paint) reads the stale value. It stops being masked the moment routes can be added or removed on a live graph. Decide this before graph editing lands; `node.handles` (declaring port geometry from ELK rather than having React Flow measure it) is the alternative worth a spike. See `.scratch/react-flow-guidance/findings.md` §3.2, §3.10.
- **React Flow's own docs are the reference, and they ship one for agents:** fetch `https://reactflow.dev/llms-full.txt` when working in `react-flow-adapter` — the whole docs site as a single document, regenerated from the page map, so don't vendor a copy. There is no official React Flow agent skill or MCP server; xyflow built a skill, measured it as making results worse, and shelved it. The two pages carrying the non-obvious rules are `/learn/troubleshooting/common-errors` and `/learn/customization/handles`. Findings and what they mean for this repo: `.scratch/react-flow-guidance/findings.md`.
- **A card is one file: frontmatter, then body (ADR 0020).** `id`, `title`, `description`, `kind` and `target` are the card file's frontmatter; the markdown under it is the content. The space file holds `version`, `id`, `title`, `routes`, `layouts`, `defaultView` — structure, and no `cards` array. Cards are discovered by scanning two locations, **non-recursively**: `*.md` beside the space file, and `cards/*.md`. Non-recursion is deliberate — ADR 0001's nested spaces will want subdirectories, and a recursive scan would make each one ambiguous with card discovery. A card's identity is its frontmatter `id` and never its filename, so renaming a file is not a data migration; a duplicate id across files is a load error naming both. A body may begin with a heading — the title lives in the same file, so a heading is just a heading. Every `.md` in scope *is* a card, so there is nowhere to leave a draft — and a `README.md` beside a space file would be read as one, which is why the fixture's moved to `packages/app/README.md`. **`body` is the field, `content` is the domain word**, and they are not synonyms to be reconciled: `CONTEXT.md` still lists "body" under _Avoid_ for a card's content in general, because a space-card's content is a graph and has no body. `Card.body` is what a *markdown* card's content is stored as. Don't rename one into the other in either direction.
- **Routes are a space's only structure.** There is no authored `edges` array *beside* routes; ADR 0007 deleted that along with the `sequence`/`reference` kinds, and it stays deleted — don't reintroduce a structural layer next to routes. A route **is** a set of `{from, to}` edges the author draws (ADR 0023), so "edge" names both the route's stored element and React Flow's drawn line — one word for one thing, and the only place the render layer and the domain share vocabulary. Three types carry it, each adding to the last: `RouteEdge` (`core`) is the authored `{from, to}`; `GraphEdge` (`graph/routes.ts`) is that resolved onto the handles it attaches to and tagged with its route; `LayoutEdge` (`graph/layout.ts`) is that again once a strategy has routed it. Don't collapse them and don't add a fourth.
- **`path` means a file path only.** The space file's key is `routes` and the code says `Route`/`routeId`/`buildRouteEdges`. Remaining `path` identifiers are filesystem paths, TanStack Router URL paths, or React Flow's own SVG `edge-path` class — don't "fix" those.
- **`manifest` is retired, in vocabulary and code (ADR 0010).** The top-level domain value is a **Space**, minted only by `loadSpace(input, cardFiles) → { ok, space } | { ok: false, errors }` in `@project/graph` — the one intake that parses (the space file *and* every card file's frontmatter), validates references, and indexes, so a `Space` is consistent and O(1)-indexable by construction. `getCard`/`getRoute` read that index; every `graph`/adapter/app signature takes a `Space`. The on-disk shape is a **space directory**: the **space file** (`space.json`, validated by `core`'s `spaceFileSchema`) plus a markdown file per card (ADR 0020). A value that only passes that schema is *not yet* a Space. `loadSpace` gained the card files as an argument, not a capability — it still does no I/O and is still synchronous, and reading the bytes stays outside it. Don't reintroduce `manifest` anywhere — not as a type, not as the word for the file. The future edit buffer (a `Draft`, not built) is where a mutable, possibly-invalid working copy would live; a Space is never that.
- **Styling is split:** `ui` uses Tailwind v4 + shadcn-style primitives; the graph/card CSS stays hand-rolled in `packages/app/src/styles.css`. Tailwind scans `app` + `ui/src` via `@source` in `tailwind.css`.
- **Markdown is excluded from Prettier** (`.prettierignore`) — don't rely on `format` to touch `*.md`.
- **`SPACE_DIR` selects import input, and nothing else does (ADR 0018).** Supplied, the plugin reads `space.json` and the two non-recursive Markdown card locations from that directory. Missing or absent input defers to `newSpace()`. Read once at config load, resolved against the server's cwd, and server-side by construction: the client never names a directory. The no-directory branch emits `import { newSpace } from '@project/graph'` as browser source rather than importing it in Node — a bare `@project/*` specifier here would be externalized and hand Node the workspace TypeScript. `pnpm build` sets no `SPACE_DIR`, so a build ships a new space rather than baking in a fixture nobody authored.
- **Files are import-only in the application.** `vite-space-file-plugin.ts` only exposes `spaceFile` and `cardFiles` through `virtual:space-file`; it has no `configureServer` write middleware, no browser endpoint and no source-byte preservation flow. A completed edit commits a whole `SpaceSnapshot` through `SpaceBackend`. Canonical export belongs to the future CLI (ADR 0030), never an app Save action. `read-only.spec.ts` proves a real drag reaches persistence while leaving the imported fixture byte-identical.
- **Persistence crosses the app at `SpaceBackend` and `SpaceSession`.** Startup imports files, seeds the configured backend, then lists, loads and opens the first workspace. The memory adapter is the current implementation. Every backend commit validates both public shape and normal domain intake (`loadSpaceSnapshot`), so dangling references, route cycles and invalid aliases/layouts are permanent `invalid-snapshot` failures rather than stored state.
- **A session submits complete snapshots after completed edits.** It allows one commit in flight, coalesces waiting edits to the newest snapshot, chains the committed revision into the next optimistic write, and exposes pending, retryable failure, permanent rejection and conflict states. Accepting remote replaces the session snapshot and remounts the workspace so graph, editor and view stores cannot retain stale local positions. Route activation is not an edit and does not submit.
- **Don't import a workspace package by name into `vite.config.ts`.** Vite loads the config in Node and externalizes bare specifiers, so `@project/core` hands *Node* the TypeScript source, whose extensionless relative imports (`export * from './schema'`) Node's ESM resolver rejects — the config then fails to load at all and the dev server will not start. Import by relative path (`../core/src/index`) so esbuild bundles it. This is the one place the repo's extensionless-import convention does not hold.
- **The space-file plugin is not `apply: 'serve'`.** Importing has to work in a build because `space.ts` imports the virtual module unconditionally. There is no dev-only write hook. A build without `SPACE_DIR` mints a new space rather than baking in a fixture nobody authored.
- **Changing the Vite config needs a dev server restart** — plugins load at config time and HMR won't pick them up. That server is the human's; say it needs restarting rather than restarting it.
- **Delete a spike harness when you write it up; ignoring it is not enough.** `packages/app/spike.html` sat gitignored, went stale against the `elkLayout` → `elkStrategy` rename, and broke `pnpm dev` — Vite's dependency scanner treats every root `.html` as an entry and does not read `.gitignore`, while tsc and eslint both skip `.scratch/`, so `pnpm verify` stayed green and only the dev server saw it.
- **Card markdown is sanitised before it is injected.** `CardContent` renders through `dangerouslySetInnerHTML`, and `marked` has had no `sanitize` option since v5, so `DOMPurify.sanitize()` sits between them. Don't remove it on the argument that a card came from a local import: backend implementations and future import sources broaden that premise. `packages/ui/test/CardContent.test.tsx` fails without the sanitiser.

## Scope discipline

Keep to the MVP. Don't over-generalize the domain model and don't add features beyond what's asked.

On multi-route rendering (`.scratch/multi-route/`): the overview draws every route, and **selection is emphasis, not filtering** — at all times, not only while presenting. A Layout carries the filter (`routes`, which routes it shows at all) and the **active** route is the emphasis; activating a route never changes what is visible. There is one active route, not a selection plus an emphasis (ADR 0026). The dimming lives in `projectRouteEdges`, `CardNode` and `RouteLegend`. `filterHandlesByRoute` and `routeCardIds` are right for a view that wants one route. Which routes a view shows is a View decision passed into the strategy (ADR 0005) — don't let the strategy or `graph` decide it, and `resolveView` is where it is made.

**`resolveView` answers which routes show and which is active; nothing else does (ADR 0026).** Both fallbacks live there — absent `routes` means every route, absent `activeRoute` means the first *visible* one, and it is the filter the fallback runs over, or a Layout would open active on a route it does not draw. `createSpaceStore` takes the answer as an argument rather than reaching for `space.routes[0]`; two places answering it would disagree the moment a Layout filters.

**A completed edit persists automatically (ADR 0030).** `App` watches the editor's completed-edit revision, constructs the complete current `SpaceSnapshot`, and submits it to `SpaceSession`; intermediate drag frames never reach persistence. The session status (`Persisting…`, `Persisted`, retry, rejection or conflict) is the persistence indicator. There is no Save button, keyboard Save command or browser file write-back. The `beforeunload` guard is registered only while persistence is not settled — an always-attached handler would cost the page its bfcache. It calls `preventDefault()` and nothing else; `event.returnValue = ''` is deprecated and lint rejects it.

**Activating a route is not an edit (ADR 0028).** It converts no automatic layout and never submits persistence. The completed-edit effect samples `useSpaceStore.getState().activeRouteId` only when constructing the edited Layout, rather than subscribing route activation into an edit trigger. The submitted Layout names the active route outright because the resolve-to-first fallback is a read and persisted state should not depend on route order. `updatePositionedLayout` carries a Layout's `routes` filter through rather than replacing it — positions are replaced because the editor store holds the whole truth of them, but the filter is authored and the app has no surface for writing one.

**Presenting is this canvas, closer in (ADR 0027).** There is no second surface and nothing a Card is turned into. `PresentingCamera` in `GraphView` is the whole mechanism: `setCenter` to the active card, and a **split** move when the zoom changes by more than a tenth — pan at the wider scale, then close in — because one combined move whips. The chrome (`PresentingChrome`) is screen-fixed and enumerates the active card's outgoing edges, because at a zoom where the card is legible its neighbours are provably off frame. **Don't add an `isLinear` branch**: one outgoing edge is a one-member selection and the degenerate case falls out (ADR 0024). **Don't put a derived array in a Zustand selector** — `movesFrom` takes its three inputs and is memoized in `App` for exactly this reason; as a selector it re-rendered until React gave up.

**A route may not close a cycle (ADR 0023).** `loadSpace` rejects one (`route-has-cycle`). Forks and merges are legal and expected; only cycles are not. Don't add cycles to get "return to earlier content" — that has a better word, an **alias** (ADR 0009), a distinct card showing the same content reached by a forward edge. A cycle renders cleanly only as a channel looping around the cards or by unrolling into duplicate nodes.

The overlay limit: only **compatible** routes — the union of every route's edges is acyclic — lay out on a clean left-to-right axis, as parallel forward paths. A backward edge comes only from **two routes disagreeing** on the order of shared cards, which ADR 0003 permits. `elkStrategy` returns ELK's routed `sections` on each edge and the adapter's `RoutedEdge` draws them (a bezier fallback covers grid/first-paint), so such a cross-route back-edge reads as a routed channel rather than a self-curling stub. Read `.scratch/multiple-routes/findings.md` before extending any of this.

The app loads the **abstract layout fixture** (`packages/app/fixture/`), not the narrative demo — this is what `pnpm dev` serves and what Playwright drives, so e2e asserts *behaviour* against a purpose-shaped graph rather than demo prose. It is **two disconnected collections** sharing no cards, which ELK lays out as separate bands: (1) `Long A→B→C→D→A′` / `Mid A→B→C→D` / `Short A→B→C` — several routes over one spine; (2) `Echo E→F→G→H→E′` — a plain linear collection. Each returns to its start via an alias (`A′`/`E′`, which the `↳` marker names), never an edge back, so the fixture is acyclic and lays out as clean forward paths. Every fixture route is a **line** — one edge out per card — which is the degenerate graph, not a second kind; forks and merges are covered by unit and property tests, not here. `03`'s back-edge rendering is proven by a unit test (`elk-strategy.test.ts`), not the fixture. The demo stays in `packages/app/example/`, dormant, for when real space-loading exists. Don't reconflate fixtures with content (`packages/app/README.md` documents the shape — it sits outside `fixture/` because a `README.md` beside a space file would be scanned as a card). The ELK options in `elk/layout.ts` are a minimal baseline: don't tune global layout options against this fixture's screenshot. If legible multi-route overlay becomes real product work, design it deliberately.
